From HTTPS Address to First Byte: What the Browser Does

When you type https://example.com/products into a browser and press Enter, nothing visible happens for a moment. Behind the scenes the browser works through a fixed sequence of steps before the first byte of the response arrives. The time between pressing Enter and receiving that first byte is called Time To First Byte (TTFB). Each step below adds to it.

1. Parsing the URL

The browser first splits the address into parts. The scheme is https, the host is example.com, the port is implied as 443 (the default for HTTPS), and the path is /products. If you typed something that is not a valid URL, the browser treats it as a search query instead.

Before going to the network, the browser checks a few local things. It looks at its HSTS list (HTTP Strict Transport Security), which records sites that must only be reached over HTTPS. It also checks its caches: if it holds a fresh stored copy of the resource, it can skip the network entirely. A service worker, if one is registered for the site, may also intercept the request here and answer it on its own.

2. DNS resolution

Networks route traffic by IP address, not by name, so the browser needs to turn example.com into something like 93.184.216.34. This is DNS (Domain Name System) resolution. The lookup checks several places in order:

- the browser's own DNS cache
- the operating system's cache and the hosts file
- a recursive resolver, usually run by your ISP or a public provider

If the resolver does not already know the answer, it asks the DNS hierarchy: a root server points to the server for the .com top-level domain, which points to the domain's authoritative name server, which returns the IP address. Each answer carries a TTL (time to live) saying how long it may be cached, so most lookups never go this far. A cold lookup can still take tens of milliseconds or more. The result may contain both IPv4 (A) and IPv6 (AAAA) addresses, and the browser may race them and use whichever connects first.

3. Opening a TCP connection

With an IP address, the browser opens a connection to port 443. TCP provides a reliable, ordered byte stream, and it starts with a three-way handshake:

1. The client sends SYN.
2. The server replies SYN-ACK.
3. The client sends ACK.

This costs one full round trip (RTT) before any data can flow. If the server is far away, say 100 ms each way, that is already 100 ms spent on the handshake alone. This is why geography and CDNs matter for performance.

Modern browsers may use HTTP/3 instead, which runs over QUIC on UDP. QUIC folds the transport and encryption handshakes together to save round trips. Browsers usually learn that a site supports HTTP/3 from an earlier HTTP/2 response header (Alt-Svc) or a DNS record, so a first visit often still uses TCP.

4. The TLS handshake

The "S" in HTTPS means the connection is encrypted with TLS (Transport Layer Security). Before any HTTP is sent, the browser and server negotiate security parameters. In TLS 1.3, the common version today, this works roughly as follows:

- ClientHello: the browser sends the TLS versions and cipher suites it supports, a random value, and its key-exchange share. It also sends the hostname in an extension called SNI (Server Name Indication), so a server hosting many sites knows which certificate to present. It may also offer ALPN, a list of application protocols such as h2 and http/1.1.
- ServerHello: the server picks a cipher suite and protocol, sends its own key-exchange share, and then its certificate.
- Both sides now combine their key shares to derive the same session keys, without the keys ever crossing the network. This is an ephemeral Diffie-Hellman exchange, and it gives forward secrecy: a stolen server key later cannot decrypt recorded traffic.
- The server proves it holds the certificate's private key and sends a Finished message. The client verifies and replies with its own Finished message.

TLS 1.3 needs one round trip. Older TLS 1.2 needed two. On a repeat visit, session resumption can shorten this further.

Certificate validation

During the handshake the browser checks the server's certificate. It confirms that:

- the certificate chains up to a certificate authority (CA) the browser trusts, usually through one or more intermediate certificates
- the certificate has not expired
- the hostname you asked for matches a name listed in the certificate
- the certificate has not been revoked (checked through mechanisms like OCSP stapling or browser-maintained lists)

If any check fails, you see a full-page warning and the request stops. This is what makes HTTPS meaningful: encryption alone would not stop an attacker from impersonating the site, but a valid certificate for the right hostname does.

5. Sending the HTTP request

Only now, with an encrypted channel established, does the browser send the request itself. It looks like this (shown here in HTTP/1.1 form, though HTTP/2 and HTTP/3 carry the same information in binary frames):

GET /products HTTP/1.1
Host: example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The browser attaches headers describing what it can accept, any cookies stored for this domain, and caching validators such as If-None-Match if it has a stale cached copy it wants to revalidate. All of this is encrypted in transit, so intermediaries such as your Wi-Fi network can see which server you contacted (through the IP address and, usually, SNI) but not the path, headers, or body.

HTTP/2 and HTTP/3 let the browser reuse this one connection for many requests at once, which is why a connection that is already open skips steps 2 to 4 entirely.

6. The server does its work

The request may first reach a CDN edge server or a load balancer rather than your application. If a CDN holds a cached copy, it answers immediately. If not, the request passes to an origin server, where a web server hands it to application code. That code may run authentication, query a database, call other services, and render a page. All of this happens before the server can send a response, and it is usually the part of TTFB you control as a developer. A slow database query shows up directly as a slow first byte.

7. The first byte arrives

When the server begins writing the response, the status line and headers, such as HTTP/1.1 200 OK and Content-Type: text/html, come first. The first byte of that response reaching the browser is the moment TTFB measures. A redirect (a 301 or 302 status) would restart much of this process for the new URL, which is why unnecessary redirects hurt performance.

Putting the costs together

For a first visit to a new site, the time before the first byte roughly adds up to:

DNS lookup + TCP handshake (1 RTT) + TLS handshake (1 RTT) + request travel and server processing + response travel back

Practical consequences for you as a developer:

- Reduce round trips: use a CDN so the server is physically closer.
- Avoid redirect chains, especially http to https to www.
- Cache aggressively, so many requests never reach the origin.
- Keep server-side work fast, since it counts directly toward TTFB.
- You can inspect each phase yourself in the browser's DevTools Network tab: open a request's Timing view and look for DNS Lookup, Initial connection, SSL, and Waiting for server response (TTFB).

From HTTPS address to first byte

You type https://shop.example.com/cart into the address bar and press Enter. Between that keypress and the first byte of the server's reply, the browser does a surprising amount of work. Most of it is invisible, and most of it is about finding and trusting the other machine before any page content moves at all. This walk-through follows the steps in order.

1. Parsing the address

The browser first splits the URL into parts. The scheme is https, the host is shop.example.com, and the path is /cart. No port is given, so it assumes 443, the default for HTTPS. If you had typed something that is not a valid URL, the browser would treat it as a search query instead.

Before going to the network, it also checks a few local rules. One is HSTS, a list of sites that have told the browser "only ever talk to me over HTTPS". Another is the cache: if a fresh copy of this resource is already stored, the request may never leave your machine. Assume neither applies here.

2. Finding the IP address (DNS)

Networks route traffic by IP address, not by name, so the browser must translate shop.example.com into a number such as 203.0.113.7. This is the job of the Domain Name System, DNS.

The lookup checks several caches first. The browser has one, the operating system has one, and your router may have one. Any hit ends the search immediately. On a miss, the request goes to a recursive resolver, usually run by your ISP or a public provider. If the resolver does not know the answer either, it asks the DNS hierarchy: a root server points to the servers for .com, those point to the servers for example.com, and the last of them gives the address. The resolver caches the result for the record's time to live (TTL) and hands it back.

This can take anywhere from under a millisecond to a few hundred. A cold lookup is often the first slow step, which is why developers sometimes add hints like dns-prefetch for hosts they know they will need.

3. Opening a TCP connection

With an IP address in hand, the browser opens a connection to 203.0.113.7 on port 443. Traditional HTTPS runs on TCP, which guarantees that bytes arrive complete and in order. TCP earns that guarantee with a handshake. The client sends a SYN, the server answers with a SYN-ACK, and the client replies with an ACK. That is one full round trip before anything useful happens.

Round trips matter because they are bounded by distance and the speed of light. A server 100 ms away costs 100 ms for every round trip, however fast your bandwidth is. Keep that in mind, because the next step adds more of them.

A note on HTTP/3. Newer connections use QUIC, which runs over UDP and merges the transport and encryption handshakes. The browser learns it is available from an Alt-Svc header on an earlier visit. The ideas below still apply, but the sequence is shorter.

4. The TLS handshake

The connection is open, but it is not yet secure. The browser now negotiates TLS, the protocol that makes HTTPS "S".

The client sends a ClientHello. It lists the TLS versions and cipher suites it supports, includes a random value, and sends a key share for the key exchange. It also includes the Server Name Indication (SNI) extension, which states the hostname it wants. Many sites share one IP address, so the server needs that name to choose the right certificate.

The server replies with its choice of cipher suite, its own key share, and its certificate. With TLS 1.3, both sides can now derive the same session keys, using a Diffie-Hellman exchange, without the secret ever crossing the wire. Everything after the ServerHello is already encrypted. TLS 1.3 completes this in one round trip. TLS 1.2 needed two.

Meanwhile the browser verifies the certificate. It checks that the certificate names shop.example.com, that it has not expired, and that it chains up to a certificate authority the operating system or browser trusts. It may also check revocation status, often via a stapled OCSP response that the server attaches to save a separate lookup. If anything fails, you see the full-page warning and the request stops. This is the step that proves you are talking to the real site and not an impostor in the middle.

Once both sides send a Finished message confirming the handshake was not tampered with, the secure channel is ready. If you have visited recently, session resumption can skip much of this work using a saved ticket.

5. Sending the HTTP request

Only now does the browser say what it wants. Over the encrypted channel, it sends a request like this:

GET /cart HTTP/1.1
Host: shop.example.com
User-Agent: ...
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The request line holds the method and path. The headers describe the client and its preferences. Cookies scoped to this site are attached automatically. With HTTP/2 or HTTP/3, the same information is sent in a compact binary form instead of plain text, and many requests can share one connection.

6. The server does its work

The request travels to the server's network edge. At a large site that is often a CDN or a load balancer, which may answer from its own cache or forward the request to an application server. The application then does whatever the route requires. It might check the session cookie, query a database, and render a template.

This stretch is called server think time, and it is the part you control as a developer. A slow query here delays everything downstream, and no amount of front-end polish will hide it.

7. The first byte arrives

Finally the server begins writing its response: a status line such as 200 OK, then headers, then the start of the body. The moment the first byte of that response reaches the browser is called Time to First Byte, or TTFB.

Notice what TTFB contains. It is the sum of everything above: DNS lookup, TCP handshake, TLS handshake, request travel time, server processing, and the first leg of the response. It is not just "how fast is my server".

Why this matters to you

You can see all of these phases yourself. Open your browser's developer tools, go to the Network tab, click a request, and read the Timing breakdown. It separates DNS lookup, initial connection, SSL, waiting (the server's think time plus travel), and content download. When a page feels slow, that breakdown tells you which stage to blame before you start guessing.

Reuse is the main lever. Keep-alive connections let later requests skip DNS, TCP, and TLS entirely. Caching can skip the network altogether. A CDN shortens the distance for every round trip. And a fast backend shortens the one stage that is purely yours.

The first request to a new host pays full price. Every request after it should not.

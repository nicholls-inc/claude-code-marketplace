Inside the .git directory, Git is at bottom a content-addressable key-value store in which every piece of data is saved as an object whose key is a hash of its own contents, and everything you think of as a file in history, a commit or a branch is assembled from three kinds of object plus a handful of tiny text files that point at them. Objects live under .git/objects, where each one is prefixed with a header giving its type and byte length, hashed (SHA-1 traditionally, SHA-256 in repositories created with that option), compressed with zlib, and written to a path derived from the hash, with the first two hex characters as a directory name and the rest as the filename, so an object whose hash begins e69de29b is found at .git/objects/e6/9de29b followed by the remaining characters. Because the key is computed from the content, identical content is stored only once however many times or under however many names it appears, and nothing that has been stored can change without its key changing too.

The simplest object is the blob, which holds the bytes of one file and nothing else, not its name, not its permissions and not its timestamp. Two files with identical contents in different directories, or one file that stayed untouched across a hundred commits, all resolve to a single blob, while a one-character edit produces an entirely new blob rather than a stored diff, which sounds wasteful until you learn that Git periodically gathers loose objects into packfiles, where similar objects are delta-compressed against each other and the space cost falls dramatically.

Names and modes live in trees. A tree object is a directory listing with one entry per child, each entry made of a file mode, a name and the hash of the child, where the child is a blob if the entry is a file and another tree if it is a subdirectory. The mode distinguishes a regular file (100644) from an executable (100755), a symbolic link (120000, whose blob holds the target path as text), a subdirectory (040000) and a submodule (160000, whose hash names a commit in some other repository). Since a tree's hash covers the hashes of everything beneath it, the hash of the top-level tree is a fingerprint of the whole project at one moment: if you change a single line in src/util/helpers.c, Git writes a new blob for that file and new trees for src/util, src and the root, because each of their contents now includes a changed hash, while every untouched sibling is referenced by its old hash and shared with the previous snapshot at no cost. This is also what the staging area is for, since .git/index is a binary file listing paths, modes and blob hashes, and running git commit turns that list into the tree objects that capture your snapshot.

A commit object is a short piece of text that begins with a line naming the root tree, followed by one parent line for an ordinary commit, two for a merge and none for the first commit in a repository, then author and committer lines with name, email, Unix timestamp and timezone, then a blank line and your message. It contains no diff at all, and the patch you see in git show is computed on demand by comparing the commit's tree with its parent's tree, which is also how Git notices renames, since no rename is ever recorded and a deleted path and a new path with similar contents are simply matched up at display time. The parent hash is part of the commit's own content, so each commit's hash depends on the entire history behind it, and history therefore forms a chain, or more precisely a directed acyclic graph once merges are involved, in which altering any old commit by amending or rebasing necessarily produces new hashes for it and for every descendant. The original commits are not erased by this but sit in the object store, reachable for a while through the reflog, until garbage collection finds nothing pointing at them and removes them.

Because objects are immutable and addressed by hash, something mutable has to say which commit currently matters, and that job belongs to refs. A branch is nothing more than a file such as .git/refs/heads/main containing the forty-character hash of the commit at its tip, and making a commit means writing the new commit object with the old tip as its parent and then overwriting that one file with the new hash, which is why creating a branch, a matter of writing about forty-one bytes, costs essentially nothing. Tags live under refs/tags and work the same way, except that an annotated tag is also a fourth kind of object, carrying a tagger, a date and a message, that the ref points to instead of pointing directly at a commit, while remote-tracking branches such as origin/main sit under refs/remotes and are updated only when you fetch. The file .git/HEAD says where you currently are, and it normally holds a symbolic reference of the form "ref: refs/heads/main", so that committing advances whichever branch it names, whereas a detached HEAD, which is what you have after checking out a bare commit hash, contains a raw hash directly, and commits made in that state are reachable only through HEAD and the reflog until you give them a branch. In large repositories many refs are consolidated into a single .git/packed-refs file for speed, and a loose ref file, when present, takes precedence over the entry in that file.

You can walk this structure yourself without any special tooling beyond Git: git cat-file -p HEAD prints the current commit and shows its tree hash, git cat-file -p on that hash lists the entries in the root directory, and running it again on a blob hash prints a file exactly as it was committed, with git cat-file -t telling you which of the object types any given hash refers to.

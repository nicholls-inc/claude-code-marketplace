Every commit you have ever made lives inside the .git directory as a small file whose name is derived from its own contents, and the whole of Git's storage model follows from that one idea. Under .git/objects Git keeps a content-addressable store in which each item is located by the SHA-1 hash (or SHA-256 in repositories created with that option) of its bytes, preceded by a short header giving the object's type and size. The first two hex characters of the hash become a subdirectory and the remaining thirty-eight become the filename, and each file is compressed with zlib, which is why opening one in an editor shows noise, although git cat-file -p followed by a hash will decode it for you. Because the name is a function of the content, identical data is only ever stored once, and changing a single byte produces an entirely different name, which gives Git integrity checking essentially for free.

There are four kinds of object, and the first is the blob, which holds the raw bytes of a file and nothing more. A blob has no filename, no permissions and no timestamp, so two files in different directories with identical contents, or the same file at ten different points in history, all resolve to a single blob, and renaming a file costs nothing in storage because the content is untouched and only the name recorded elsewhere changes.

That elsewhere is the tree, which plays the role of a directory. A tree object is a list of entries, each carrying a mode (100644 for a regular file, 100755 for an executable, 120000 for a symlink, 040000 for a subdirectory), a name, and the hash of whatever that name refers to, which is a blob for a file and another tree for a subdirectory. The hash of a tree is computed from this list and therefore depends on every name and every child hash beneath it, so a change to one file deep in the project alters its blob, the tree of its containing folder, that folder's parent, and so on up to the root tree, whose hash becomes a fingerprint of the entire snapshot. Git does not store diffs between versions at this layer: each commit refers to a complete tree, and the economy comes from the fact that unchanged files and unchanged subdirectories keep the same hashes and are simply referenced again by the new trees. Running git ls-tree HEAD prints the root tree in readable form.

A commit object sits on top of this structure and is itself tiny. Its body is plain text containing the hash of the root tree, zero or more parent lines giving the hashes of the commits that came directly before it, an author line and a committer line each with a name, email address, Unix timestamp and timezone offset, then a blank line and the message you wrote. The first commit in a repository has no parent, an ordinary commit has one, and a merge commit has two or more, which is the only thing that makes it a merge. Since the parent hash is part of the data being hashed, a commit's identity depends on the whole history behind it, which explains why rebasing or amending produces new hashes for the rewritten commit and for every descendant, while the old commits linger unreferenced until garbage collection removes them. What git log shows you is a walk along the parent pointers, and the diff printed by git show is computed on demand by comparing the commit's tree with its parent's tree rather than being read from storage.

The fourth object type, the annotated tag, is a similar small text file that points at another object, usually a commit, and adds a tagger, a date and a message, while lightweight tags do not use it at all.

Hashes are unfriendly to humans, so Git layers refs on top, and these are plain files whose contents are a hash. A branch is a file such as .git/refs/heads/main holding the forty-character hash of the commit at the tip of that branch, so committing amounts to writing the new commit object and then overwriting that file with its hash, and creating a branch writes one new forty-one-byte file, which is why it is instantaneous. Tags live under .git/refs/tags and remote-tracking branches under .git/refs/remotes, and large repositories sometimes consolidate these into a single .git/packed-refs file without changing their meaning. HEAD, stored in .git/HEAD, is usually a symbolic ref, a file reading ref: refs/heads/main, so that Git follows it to the current branch and advances that branch on every commit; in a detached HEAD state the file holds a commit hash directly, and commits made there are reachable from nothing but HEAD, which is why they can be lost once you check out something else. The reflog, kept under .git/logs, records where each ref used to point and is the usual way back from such a loss.

Loose objects are not their final form for long, because when their number grows, or when you push and fetch, Git gathers them into pack files under .git/objects/pack in which similar objects are stored as deltas against one another and indexed for fast lookup, so a repository with years of history is far smaller than the sum of its snapshots would suggest. Between your working directory and the next commit stands the staging area, a binary file called .git/index listing the path, mode and blob hash of each tracked file; git add writes blobs and updates that index, and git commit converts the index into trees, wraps the root tree in a commit object and moves the current branch ref to point at it.

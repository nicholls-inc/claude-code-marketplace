When you run git commit, the result is a small web of objects stored as files inside the .git directory, plus a tiny text file that gives one of those objects a human-friendly name. Everything Git stores about your history comes down to four ideas, blobs, trees, commits and refs, and once you see how they fit together, a lot of Git's behavior stops seeming mysterious.

Start with the blob. A blob is the contents of one file and nothing else: it has no filename, no permissions and no timestamp. Git takes the file's bytes, prepends a short header giving the object type and the size in bytes, and runs the result through a hash function, SHA-1 in older repositories and SHA-256 in newer ones. The resulting hash is the object's name, and the header plus content, compressed with zlib, is written to .git/objects. The first two hex characters of the hash become a directory name and the remainder becomes the filename, so an object might live at .git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391. Because the name is derived from the content, this is a content-addressable store, so two files with identical contents share a single blob even if they have different names or sit in different directories, and the same file appearing in a thousand commits is stored once. It also means an object can never be silently altered, because changing one byte changes the hash and makes it a different object.

Since blobs carry no names, something has to record which blob is which file, and that is the job of the tree. A tree object represents one directory. It is a list of entries, and each entry holds a file mode (regular file, executable file, symbolic link or subdirectory), a name, and the hash of the object that name points to. For a regular file the hash refers to a blob, and for a subdirectory it refers to another tree, so a project with nested folders is a tree of trees with blobs at the leaves, and the root tree describes the entire top level of your working directory at one moment. The hash of a tree is computed from its entries, so it depends on every name, mode and child hash beneath it. If you edit one file deep in the hierarchy, that blob gets a new hash, its parent tree gets a new hash because an entry changed, and so on up to the root, while directories whose contents did not change keep their old hashes and are reused as they are. This is why Git can snapshot a large project cheaply: a commit only creates new objects along the paths that actually changed.

The commit object sits on top of this. A commit is a small text record with a few fields: the hash of the root tree, the hash of each parent commit, an author with name, email and timestamp, a committer with the same details, and then the commit message. The tree is the snapshot and the rest is metadata about it. A normal commit has one parent, the commit that was current when you made it, whereas the very first commit has none and a merge commit has two or more, and those parent hashes are what link commits into a history. Git does not store diffs between versions. Each commit points at a complete snapshot, and the diffs you see in git log -p or on a pull request are computed on demand by comparing two trees. Like every other object, a commit is hashed, and because the hash includes the parent hashes, each commit's identity depends on its entire ancestry. This is why rewriting an old commit with a rebase or an amend produces new hashes for it and for every descendant: you have not edited anything, you have created a new chain of objects, and the old ones simply stop being referenced.

The last piece is the ref. Hashes are precise but impossible to remember, so Git keeps named pointers. A branch is nothing more than a file under .git/refs/heads whose entire content is the forty-character hash of a commit, and if you open .git/refs/heads/main you will find exactly that. Tags work the same way under .git/refs/tags, and remote-tracking branches live under .git/refs/remotes. When you make a commit, Git writes the new objects and then updates the current branch file to hold the new commit's hash, which is all a branch moving forward means. Creating a branch is just writing a new forty-character file, which is why it is instantaneous, and deleting a branch only removes the pointer and leaves the commits in place, at least until garbage collection finds that nothing can reach them.

One more file ties this together. HEAD, at .git/HEAD, says where you currently are. Normally it contains a line such as ref: refs/heads/main, a symbolic reference naming the branch you have checked out, so that committing advances whatever branch HEAD points to. If you check out a specific commit instead, HEAD holds a raw hash, which is the detached HEAD state that tends to alarm people and which is really just HEAD pointing straight at a commit and not through a branch.

Two practical details are worth knowing. First, you will not always find loose object files, because Git periodically packs objects into compressed packfiles that store similar objects as deltas against one another, a storage optimization that does not change the model above. Second, the staging area, which Git calls the index, is a single file at .git/index listing the paths and blob hashes that will go into the next tree, so running git add writes blobs and updates the index, and running git commit turns the index into trees, wraps the root tree in a commit object, and moves the branch ref.

If you want to see it for yourself, git cat-file -p followed by a hash, or by HEAD, will print any object in readable form, and git cat-file -t will tell you its type.

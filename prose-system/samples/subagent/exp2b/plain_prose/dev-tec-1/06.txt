When you run git commit, the result is a small set of files in the .git/objects directory, and every one of them is named after a hash of its own contents. Git is at bottom a content-addressable store: you hand it some bytes, it computes a SHA-1 (or SHA-256 in newer repositories) of those bytes plus a short header, and it saves the data under that hash. Everything else, including branches, history and tags, is built from four kinds of object and a handful of pointer files.

The first kind is the blob, which holds the contents of a single file and nothing more. It has no filename, no permissions and no timestamp. If you have two files with identical contents, whether in the same directory or in different commits from three years apart, Git stores one blob and refers to it twice. Editing a file and committing creates a new blob with a new hash, while the old one stays put. Objects are written zlib-compressed, with the first two hex characters of the hash used as a directory name and the remaining characters as the filename, so a blob might live at .git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391. Because the hash covers the content, an object can never silently change. If it did, it would simply have a different name.

Names and permissions live in the second kind of object, the tree, which represents a directory. A tree is a list of entries, and each entry records a file mode (regular file, executable, symlink or subdirectory), a name, and the hash of what that name points to. For a file the hash refers to a blob, and for a subdirectory it refers to another tree. A commit therefore captures your project as a nested structure of trees ending in blobs, much like the directory layout on disk. This is also why renaming a file is cheap: the blob is untouched, and only the tree entry that carries the name changes. Likewise, if you edit one file deep inside src/, Git writes a new blob for that file, a new tree for each directory on the path up to the root, and reuses every other tree and blob in the snapshot by hash. A tree's own hash is computed from its entries, so a change anywhere below produces a new hash all the way up to the top, and two trees with the same hash are guaranteed to hold identical content.

The third kind is the commit object, which is what ties a snapshot to history. A commit is a short text record. It names the root tree for the snapshot, lists zero or more parent commits by hash, gives an author and a committer, each with a name, email address and timestamp, and then contains the message you wrote. An ordinary commit has one parent, the first commit in a repository has none, and a merge commit has two or more. Because each commit includes the hash of its parents, and those hashes depend on their own parents, the whole history forms a chain of hashes. Changing an old commit in any way, even fixing a typo in its message, gives it a new hash, and every descendant must then be rewritten with new hashes too. This is what rebase and amend actually do: they create new commits and leave the originals untouched until garbage collection eventually removes them. Notably, a commit does not store a diff. It stores a pointer to a complete snapshot, and the diffs you see in git show are computed on demand by comparing two trees.

The fourth kind, the annotated tag, is a small object that points at another object, usually a commit, and adds a tagger, a date and a message. It is less central to the picture, so it is enough to know it exists.

None of those objects would be easy to use if you had to remember forty-character hashes, and this is where refs come in. A ref is just a file containing a hash. Your branches are files under .git/refs/heads, so .git/refs/heads/main holds the hash of the commit at the tip of main, and lightweight tags are the same idea under .git/refs/tags. Remote-tracking branches such as origin/main live under .git/refs/remotes. Making a commit on a branch writes the new objects, then rewrites that one file to hold the new commit's hash, which is why creating or moving a branch is nearly instantaneous and costs almost nothing. The file called .git/HEAD says where you currently are. Normally it contains a line such as ref: refs/heads/main, meaning HEAD is a symbolic reference to the branch, and committing advances that branch. If you check out a specific commit, HEAD instead holds a raw hash, which is the detached HEAD state that people find alarming but that is really just a pointer with no branch name attached to it.

Putting it together, a commit proceeds in a fixed order. Git takes the files staged in the index, which is a file at .git/index, writes any new blobs, builds the trees that describe the staged directory layout, creates a commit object pointing at the root tree and at the previous commit as its parent, and finally moves the current branch ref to the new commit's hash. If you want to see this for yourself, git cat-file -p followed by a hash prints any object in readable form, and git cat-file -t tells you its type. Start with cat-file -p HEAD, then follow the tree hash it prints, and you can walk the entire snapshot by hand. Over time Git also packs many loose objects into compressed pack files and stores similar objects as deltas, but the model above is unchanged by that. It is purely a storage optimization.

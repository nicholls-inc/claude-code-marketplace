Everything Git remembers about your project lives in the .git directory at the top of your working tree, and the heart of it is the objects directory, which works as a key-value store in which each value is a compressed chunk of data and each key is the SHA-1 hash (SHA-256 in repositories created with the newer option) of that data plus a short header giving its type and size. Because the key is derived from the content, identical content always lands at the same address and nothing stored can change without its name changing, so the whole history of a project reduces to four kinds of object that refer to one another by hash. On disk an object is a zlib-compressed file whose path is built from the first two hex characters of its hash as a directory name and the remaining characters as the filename, so that an object whose hash begins e69de29 sits at .git/objects/e6/9de29..., a layout that stops any single directory from growing enormous.

The first kind of object is the blob, which holds the bytes of one file and nothing else: no filename, no permissions, no timestamp. Two files with identical contents anywhere in your project, or in any commit across years of history, share a single blob, and renaming a file creates no new blob because the content has not changed. When you run git add, Git hashes the file's contents, writes the blob into the object store, and records in the index, the .git/index file that represents your staging area, that a given path now refers to that blob, which is why a file you staged and then deleted from disk can still be recovered.

Names and modes belong to the second kind, the tree, which represents one directory as a list of entries, each carrying a file mode, a name, and the hash of either a blob for a file or another tree for a subdirectory, with 100644 marking an ordinary file, 100755 an executable, 120000 a symbolic link and 040000 a subdirectory. A project with nested folders is therefore a tree of trees, and the hash of the root tree is a fingerprint of the entire project at one moment, because changing any byte of any file changes that blob's hash, which changes the hash of the tree containing it, which changes the hash of each parent up to the root. When you commit, Git builds these trees from the index, and since unchanged directories produce identical trees with identical hashes, a commit that touches one file writes only new blobs and trees along the path from that file up to the root and reuses everything else by reference.

The commit object is the third kind, and it is smaller than people tend to expect: a short text record containing the hash of the root tree, the hash of each parent commit (none for the first commit in a repository, one for an ordinary commit, two or more for a merge), an author line and a committer line each with a name, email, timestamp and timezone, and then a blank line followed by your message. A commit contains no diff, and the changes you see in git show or git log -p are computed on demand by comparing the tree of a commit with the tree of its parent. Since a commit's hash covers its parents' hashes, every commit vouches for all the history behind it, which is why amending or rebasing produces new hashes for the rewritten commit and for everything descended from it, while the old versions linger in the object store until garbage collection removes them. You can watch all of this by running git cat-file -p HEAD, which prints the commit's text, and then git cat-file -p on the tree hash it names, which lists the entries you would find in your project root.

A hash is a poor thing for a person to remember, so refs supply the names. A ref is a file containing a single commit hash, and a branch is simply a ref stored under .git/refs/heads, so that .git/refs/heads/main holds the forty hex characters of the commit at the tip of main. Creating a branch writes a tiny file, and committing on a branch advances it by writing the new commit's hash into that file, which is the whole of what it means for a branch to move forward. Tags live under refs/tags, and remote-tracking branches such as origin/main live under refs/remotes/origin and record where the remote's branch stood when you last fetched. The file .git/HEAD says where you currently are, and normally it holds a symbolic reference such as ref: refs/heads/main, meaning that HEAD follows whatever main points to; in a detached HEAD state it holds a raw commit hash instead, which is why commits made there are easy to lose once you switch away, although the reflog under .git/logs keeps a record of where HEAD and each branch have been for some time.

Git does not keep every object as a loose file forever, because it periodically gathers them into packfiles under objects/pack, where similar objects are stored as deltas against one another, which is how a repository holding thousands of revisions of a large file stays small, but the logical model is unchanged by this: blobs hold content, trees hold names and structure, commits hold snapshots and ancestry, and refs are the movable labels that let you find your way among them.

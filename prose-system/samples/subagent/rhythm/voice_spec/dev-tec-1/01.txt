Git keeps everything it knows in a directory called .git at the top of your working tree, and the core of that directory is a simple key-value store. Each item in the store is called an object. An object is saved under a name that is the SHA-1 hash of its contents, a 40-character hexadecimal string such as e69de29bb2d1d6434b8b29ae775ad8c2e48c5391. Git writes it to .git/objects, using the first two characters of the hash as a subdirectory and the other 38 as the file name. The file is compressed with zlib, so you cannot read it with cat, but `git cat-file -p` will print it for you. Because the name comes from the content, two objects with identical content are the same object and are stored once. If a single byte changes, the hash changes and a new object is created. Objects are never edited after they are written.

There are four kinds of object, and a commit uses three of them. The first is the blob, which holds the contents of one file and nothing else. It does not record the file name, the directory it sits in or its permissions. If you have the same licence text in ten places in a repository, there is one blob. If you edit one line of a large file and commit, Git stores a whole new blob for the new version. It does not keep a line-level diff at this layer, though packfiles later compress similar objects against each other to save space.

The names and permissions live in the second kind of object, the tree. A tree represents one directory. It is a list of entries, and each entry has a mode, a name and the hash of what it points to. The mode is 100644 for an ordinary file, 100755 for an executable, 120000 for a symbolic link and 040000 for a subdirectory. An entry for a file points to a blob and an entry for a subdirectory points to another tree. A tree for a repository with a README and a src directory would therefore have two entries, one pointing to the blob for the README and one pointing to a second tree that describes src. The tree at the top of the project, called the root tree, can be followed down through the others to reach every file in that snapshot. Since a tree's hash depends on the hashes it lists, a change to one file alters its blob, then the tree that contains it, then each tree above it up to the root. Directories that did not change keep the same hash and are reused as they are.

The third kind is the commit object. It is a short text record with a handful of fields. The first is a tree line that gives the hash of the root tree, which is the complete snapshot of the project at that moment. Next come zero or more parent lines, each giving the hash of an earlier commit. An ordinary commit has one parent, the first commit in a repository has none, and a merge commit has two or more. After those come an author line and a committer line, each with a name, an email address, a Unix timestamp and a time zone offset. A blank line follows, and then the commit message. That is all a commit contains. It holds no list of changed files and no diff. When you run `git show` or `git log -p`, Git works out the changes by comparing the commit's tree with its parent's tree.

Because each commit names its parents by hash, and the hash of a commit covers its parent lines, the commits form a chain in which every link depends on the one before it. You cannot alter an old commit without giving it a new hash, which gives every later commit a new hash too. This is why rewriting history with rebase produces new commits instead of modifying the existing ones. The old commits remain in the object store until Git's garbage collection removes them, which by default happens only after they have been unreachable for a couple of weeks.

Hashes are hard to remember, so Git uses refs, the fourth piece. A ref is a name that points to a commit hash. The refs are stored as small files under .git/refs. A branch called main is the file .git/refs/heads/main, and its entire content is one 40-character hash followed by a newline. A tag lives under .git/refs/tags and a remote-tracking branch under .git/refs/remotes. Making a commit means writing the new objects and then updating the current branch file to hold the new commit's hash. Creating a branch is just creating a 41-byte file, which is why it is so quick. Large repositories may bundle refs into a single .git/packed-refs file, and Git reads both places.

The last thing to know is HEAD. The file .git/HEAD usually contains a line such as `ref: refs/heads/main`, which says that the current branch is main and that the next commit should move that branch forward. If you check out a specific commit instead of a branch, HEAD holds a raw hash, and this is the detached state that Git warns about. New commits made in that state are not on any branch, so nothing keeps them reachable once you switch away, other than the reflog.

Putting this together, a commit is a small text object that points to a root tree and to its parents. The tree points to subtrees and blobs, and a ref gives the newest commit a readable name. Everything else you do with Git day to day, including branching, merging, resetting and cherry-picking, is some combination of creating these objects and moving these pointers.

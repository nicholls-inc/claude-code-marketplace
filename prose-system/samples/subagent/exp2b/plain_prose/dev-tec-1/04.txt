Git stores everything inside the .git directory as a simple key-value database, and the keys are content hashes. Every object you ever commit, whether it is a file, a directory listing or a commit, is stored under the SHA-1 (or in newer repositories SHA-256) hash of its contents, prefixed by a short header giving the object's type and size. The object is compressed with zlib and written to .git/objects, in a file whose path is the first two hex characters of the hash as a directory name and the remaining characters as the file name. Because the name is derived from the content, identical content always has the same name and is stored once, and changing a single byte produces a completely different object. Nothing is ever modified in place; Git only adds new objects. Once you hold that idea, the rest of the model follows from it.

The first kind of object is the blob, which holds the raw contents of a file and nothing else. It has no file name, no permissions and no timestamp. If two files in your project have identical contents, whatever they are called and wherever they sit, they share one blob. If you edit a one-line change into a large file, Git writes a whole new blob for the new version rather than storing a diff. That sounds wasteful, but loose objects are later gathered into packfiles, where Git compresses similar objects against each other using deltas. The delta storage is an optimisation layered underneath, and the logical model remains whole snapshots.

Names and permissions live in the second kind of object, the tree. A tree represents one directory. It is a list of entries, and each entry has a mode (such as 100644 for a regular file, 100755 for an executable, 120000 for a symlink or 040000 for a subdirectory), a name and the hash of the object it points to. For a file the hash points to a blob, and for a subdirectory it points to another tree. The root tree therefore describes the top level of your project, and following its entries down through nested trees reaches every file in a given state of the repository. Since a tree's hash is computed from its entries, and those entries contain the hashes of their children, the hash of the root tree depends on every byte of every file beneath it. This is a Merkle tree. If nothing in a subdirectory changed between two versions, that subdirectory's tree hash is identical and the new root tree simply reuses it. This is why a snapshot of a large repository costs so little when only a few files change: Git writes new blobs for the changed files, new trees for each directory on the path from those files up to the root, and leaves everything else shared.

The third kind of object is the commit, and it is small. A commit contains a pointer to a single root tree, which is the complete snapshot of the project at that moment. It contains zero or more parent commit hashes: none for the first commit, one for an ordinary commit, two or more for a merge. It also records an author and a committer, each with a name, email address and timestamp with time zone, followed by the commit message. That is the whole thing. A commit does not store a diff, and the changes you see in git show are computed on demand by comparing the commit's tree with its parent's tree. Because the parent hashes are part of the content that gets hashed, each commit's identity depends on the entire history behind it. If you alter an old commit, its hash changes, so the hash of every descendant changes as well. This is why rewriting history with rebase or amend produces new commits instead of editing the old ones, and why a commit hash can be trusted as a fingerprint of everything that led to it. You can look at any of these objects yourself with git cat-file -p followed by a hash, and git cat-file -t will tell you its type.

Hashes are unwieldy, so Git uses refs to give them names. A ref is just a file containing a commit hash. Branches live under .git/refs/heads, tags under .git/refs/tags, and remote-tracking branches under .git/refs/remotes. A branch called main is a file at .git/refs/heads/main with forty hex characters in it, and nothing more. This explains why creating a branch is instant and cheap: Git writes one small file. Making a commit means writing the new objects, then updating the current branch's ref to point at the new commit, whose parent is the commit the branch used to point at. Branches therefore move forward as you work, while the objects themselves stay put. Over time Git may pack loose refs into a single .git/packed-refs file for efficiency, but the meaning is the same.

The last piece is HEAD, the file .git/HEAD. Normally it does not contain a hash but a symbolic reference such as ref: refs/heads/main, meaning that you are on the branch main and that new commits should advance it. When you check out a specific commit directly, HEAD contains a raw hash instead, which is the detached HEAD state. Commits made there are reachable only through HEAD, and nothing will keep them alive once you switch away, apart from the reflog, a log of where refs have recently pointed. Objects that are not reachable from any ref or reflog entry are eventually removed by garbage collection.

Put together, the picture is compact. Blobs hold content, trees give that content names and structure, commits wrap a tree with history and authorship, and refs attach human-readable names to commits. The staging area, stored in .git/index, is the one extra piece: it is a sorted list of paths with the blob hashes you have staged, and git commit turns it into trees. Everything else you do with Git is ultimately moving those pointers around.

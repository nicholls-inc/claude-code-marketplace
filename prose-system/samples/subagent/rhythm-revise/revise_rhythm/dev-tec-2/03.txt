When you type an HTTPS address into a browser and press enter, the browser first has to work out what you actually asked for. It parses the string into a scheme (https), a host (for example www.example.com), an optional port (443 by default for HTTPS), a path, a query string and a fragment, which never leaves the browser and is used later to scroll the page. Before touching the network, the browser checks a few local sources: its HSTS list, which records sites that must only be reached over HTTPS, and its cache, to see whether it already holds a fresh copy of the resource. If the cache entry is still valid, the response may be served without any network traffic at all, and the story ends here. Otherwise the browser continues, and it also checks whether a service worker controls this origin, because a service worker can answer the request itself.

The next step is turning the hostname into an IP address, since networks route by address rather than by name. The browser looks in its own DNS cache first, then asks the operating system, which checks its cache and the hosts file. If neither knows, the request goes to a recursive resolver, usually run by your ISP or a public provider. If that resolver has no cached answer, it walks the DNS hierarchy: it asks a root server which servers handle the top-level domain, asks those which servers are authoritative for the domain, and finally asks the authoritative server for the record. The answer carries a time-to-live that tells every cache along the way how long it may be reused. The result is one or more A (IPv4) or AAAA (IPv6) records, and modern browsers often try both families in parallel and use whichever connects first, a technique called Happy Eyeballs. Many sites sit behind a CDN, so the address you receive usually points at a nearby edge server rather than the origin machine.

With an address in hand, the browser opens a TCP connection to port 443. TCP provides a reliable, ordered byte stream, and it starts with a three-way handshake in which the client sends a SYN, the server replies with SYN-ACK, and the client sends an ACK, which costs one full round trip before any application data can flow and is why physical distance to the server matters so much for latency. If the browser is using HTTP/3, it skips TCP and uses QUIC over UDP instead, which folds the transport and encryption handshakes together. Browsers learn about HTTP/3 support from an Alt-Svc header on an earlier response or from DNS records, so a first visit usually still begins with TCP.

Next comes TLS, the layer that makes the connection secure. In TLS 1.3 the client opens with a ClientHello listing the protocol versions and cipher suites it supports, a random value, a key share for key exchange, and the Server Name Indication extension naming the host it wants. SNI matters because one IP address often serves many domains, and the server needs to know which certificate to present. The client also offers ALPN, a list of application protocols it can speak, typically h2 and http/1.1, so that the protocol is agreed during the handshake instead of costing an extra round trip. The server answers with its own key share, its certificate chain and a signature proving it holds the private key. Both sides then derive the same session keys using an ephemeral Diffie-Hellman exchange, and everything after the ServerHello is encrypted. Using ephemeral keys gives forward secrecy: recording the traffic and stealing the server's key later does not let an attacker decrypt it.

The browser must decide whether to trust the certificate. It checks that the chain leads to a certificate authority in its trust store, that each certificate is within its validity dates, that the signatures verify, and that the hostname appears in the certificate's Subject Alternative Name list. It may also check revocation, through stapled OCSP responses or browser-maintained revocation lists, and Certificate Transparency evidence that the certificate was publicly logged. If any check fails, the browser stops and shows a full-page warning instead of continuing. After both sides send their Finished messages the handshake is complete, having taken one round trip in TLS 1.3, down from two in TLS 1.2. On a repeat visit, session resumption can shorten the handshake further, and 0-RTT lets a client send early data on the first flight, though only for requests that are safe to replay.

Only now does the browser send the actual HTTP request, and it does so inside the encrypted channel. With HTTP/2 this is a set of binary frames on a multiplexed stream rather than the plain-text format of HTTP/1.1, but the content is conceptually the same: a method such as GET, the path and query, a Host or :authority header, and headers such as Accept, Accept-Encoding, User-Agent and any relevant cookies. The browser attaches cookies that match the domain, path and security attributes, and it may also add conditional headers such as If-None-Match, carrying the ETag of a stale cached copy, so that the server can reply with a tiny 304 Not Modified instead of resending the whole body. If the request is a cross-origin fetch with unusual headers or methods, a CORS preflight OPTIONS request may precede it, adding another round trip.

The request then crosses the internet. If the address belongs to a CDN or load balancer, the edge server terminates TLS and checks its own cache, responding immediately on a hit and, on a miss, forwarding the request to your origin, possibly over a persistent, already-warm connection. The origin application server then runs your code, perhaps querying a database or calling other services, before producing a response, and this server-side processing time is a large part of what developers measure as time to first byte.

The first byte of the response arrives when the server writes the start of its reply, beginning with the status line or, in HTTP/2, a headers frame containing the status code such as 200 and headers like Content-Type, Content-Encoding and Cache-Control. The browser decrypts it, and at that moment the waiting phase ends and the download phase begins. Adding up the stages shows where the delay hides: DNS lookup, TCP connect, TLS handshake, request transit and server processing. This is exactly the breakdown the Network panel in your browser's developer tools shows for each request, and it is the best place to start when something feels slow.

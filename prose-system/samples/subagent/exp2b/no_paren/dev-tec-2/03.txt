Between typing an HTTPS address and receiving the first byte of the response, the browser works through seven stages. It parses the URL, checks its local caches, resolves the hostname to an IP address, opens a TCP connection, negotiates encryption with TLS, sends an HTTP request, and waits for the server to answer. Each stage can add latency. Knowing the order helps you read the timing breakdown in your browser's network panel.

**1. Parsing and local checks**

The browser splits the address into scheme, host, port, path and query. For https the default port is 443. Before touching the network, it checks several local sources.

- An HSTS list tells it whether the host must only be contacted over HTTPS. If you typed http for such a host, the browser upgrades the request internally without sending anything in plaintext.
- A service worker, if the site registered one, may intercept the request and answer from its own cache.
- The HTTP cache may already hold a fresh copy. If it does, no network traffic happens at all.

If none of these answers the request, the browser needs to find the server.

**2. DNS resolution**

Networks route by IP address, so the hostname must be translated. The browser checks its own DNS cache first, then asks the operating system, which checks its cache and the hosts file. If both miss, the operating system sends a query to a recursive resolver. This is usually run by your internet provider or a public service, and it is often reached over UDP port 53 or over an encrypted channel such as DNS over HTTPS.

The recursive resolver does the heavy lifting if it has no cached answer. It asks a root server which servers handle the top level domain, asks that server which servers are authoritative for the domain, and asks the authoritative server for the record. The answer is an A record holding an IPv4 address, an AAAA record holding an IPv6 address, or a CNAME pointing to another name that must be resolved in turn. Every record carries a time to live that controls how long caches may keep it. A cold lookup can take tens of milliseconds, while a cached one is nearly instant.

**3. The TCP handshake**

With an IP address in hand, the browser opens a TCP connection to port 443. This takes a three step handshake. The client sends a SYN, the server replies with SYN and ACK, and the client sends an ACK. The cost is one full network round trip before any application data can flow. If the browser already has an open connection to this host from an earlier request, it reuses that connection and skips this stage and the next one.

Modern browsers may use HTTP/3 instead. It runs over QUIC on UDP and merges the transport and encryption handshakes into one. The browser typically learns about HTTP/3 support from an Alt-Svc header on an earlier response or from a DNS record.

**4. The TLS handshake**

TCP gives a reliable pipe, but anyone along the path could read it. TLS adds privacy, integrity and proof of identity. In TLS 1.3 the handshake takes one round trip.

1. The client sends a ClientHello. It lists supported cipher suites and includes the hostname through the Server Name Indication extension, so a server hosting many sites knows which certificate to use. It also includes its half of a key exchange.
2. The server replies with a ServerHello that picks a cipher suite and supplies its own half of the key exchange. Both sides can now derive shared session keys, and everything after this point is encrypted.
3. The server sends its certificate chain and a signature proving it holds the matching private key. It then sends a Finished message.

The browser validates the certificate. It checks that the chain leads to a certificate authority in its trust store, that every certificate is within its validity dates, that the hostname matches the certificate's subject alternative names, and that the certificate has not been revoked. If any check fails, the user sees a warning page and the request goes no further. If validation passes, the client sends its own Finished message and is ready to send data.

TLS 1.2 needs two round trips for the same job. A returning visitor can often resume a prior session using a ticket, which shortens the handshake further.

**5. Sending the HTTP request**

The browser now writes the request through the encrypted channel. In HTTP/1.1 it is plain text, like this.

GET /products?page=2 HTTP/1.1
Host: shop.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The method, path and headers matter here. The Host header lets one server answer for many domains. Accept-Encoding says which compression the browser understands. Cookies previously stored for this domain are attached automatically. HTTP/2 and HTTP/3 carry the same information in a compact binary form and allow many requests to share one connection.

**6. What the server does**

The request may first reach a CDN or load balancer. If that edge node holds a cached copy, it replies immediately. Otherwise it forwards the request to an origin server. A web server or application framework matches the path to a route, checks the session cookie, and may query a database, call other services or render a template. Slow work here goes into the waiting time of your page, and the network panel reports it as time to first byte.

**7. The first byte arrives**

The server writes a status line and headers, such as a 200 status, a Content-Type and a Content-Encoding. The first bytes of these travel back through the encrypted connection. The moment the browser receives them is the first byte time. The body usually follows in a stream, and the browser starts parsing HTML while it is still arriving.

**Practical takeaways**

Adding the stages up, a first visit to a new host costs roughly one round trip for DNS, one for TCP, one for TLS 1.3, and one for the request itself, plus server processing time. Several things reduce that cost.

- Serve content from a CDN close to the user, which shortens every round trip.
- Use long DNS time to live values for stable records.
- Enable HTTP/2 or HTTP/3 and keep connections alive.
- Turn on HSTS so redirects from http disappear.
- Keep server work fast with caching and efficient queries.
- Use preconnect hints for third party hosts you know the page will need.

In the browser developer tools, the Timing tab of any request separates these phases as DNS lookup, initial connection, SSL, and waiting. Reading it tells you whether slowness comes from the network setup or from your own server code.

# How Git Stores a Commit

The `.git` directory is a content-addressed object store plus a few small files that name points in it. Every object is named by a hash of its contents, and nothing is modified in place. Commits, branches and history all come down to creating objects and moving named pointers.

## The object store

Objects live under `.git/objects`. Each is named by a SHA-1 hash (SHA-256 in repositories created with that format). The hash covers a header plus the payload: the object type, a space, the byte length, a NUL byte, then the content. The file on disk is zlib-compressed. The first two hex characters become a directory, so a blob hashing to `ce0136...` is stored at `objects/ce/0136...`.

Because the name derives from the content, identical content always maps to the same object, and an object cannot change without changing its name. You can inspect any object:

    git cat-file -t <sha>    # type
    git cat-file -p <sha>    # pretty-printed contents

## Blobs

A blob holds the raw bytes of one file and nothing else. The filename, directory and permissions are not part of it. Two identical files in different directories share one blob. Git does not track a file over time; it stores snapshots of content.

## Trees

A tree represents one directory. Each entry has a mode, a type, an object hash and a name. Mode `100644` is a regular file, `100755` executable, `120000` a symlink, `040000` a subdirectory and `160000` a submodule pointer. A subdirectory entry points to another tree, so the root tree is a nested structure whose leaves are blobs.

Changing one file deep in a project creates one new blob, one new tree per directory on the path to the root, and reuses every other hash unchanged. That is why a commit is cheap even in a large repository. Entries are sorted by name, with directory names compared as if they ended in a slash, which keeps each tree's hash canonical.

`git ls-tree HEAD` lists the entries of the root tree of the current commit.

## Commits

A commit object records a snapshot and its context:

    tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
    parent 9f1c2e7a...
    author Ada Example <ada@example.com> 1731300000 +0000
    committer Ada Example <ada@example.com> 1731300000 +0000

    Fix off-by-one in pager

The `tree` line points to the root tree of the snapshot. The `parent` lines point to previous commits: none for a root commit, one for an ordinary commit, two or more for a merge. `author` is who wrote the change and when; `committer` is who applied it, which differs after rebase, cherry-pick or amend. The message follows a blank line.

History is a graph of commits linked by parent hashes. Each commit's hash depends on its parents, so a hash commits to the entire history behind it. Changing an ancestor changes every descendant.

Annotated tags are a fourth object type: a tag object naming another object with a tagger and message.

## Refs

Humans refer to commits by names, and those names are refs: small files containing a 40-character hash. `refs/heads/main` is the branch `main`. `refs/tags/v1.2.0` is a tag. `refs/remotes/origin/main` records the last-seen state of a remote branch.

A branch is not a container of commits. It is a file holding the hash of its tip. Committing on `main` writes the new commit's hash into `refs/heads/main`. The old commits are untouched and remain reachable through their parents. Refs can also be packed into `.git/packed-refs`, which has the same meaning.

`HEAD` is a symbolic ref, a file containing `ref: refs/heads/main`. Git resolves it to the branch, which resolves to a commit. If `HEAD` holds a raw hash instead, you are in detached HEAD state.

You can walk the chain yourself:

    cat .git/HEAD              # ref: refs/heads/main
    git rev-parse HEAD         # hash of the tip commit
    git rev-parse HEAD^{tree}  # root tree of the current snapshot
    git ls-tree HEAD           # its entries

## The index

Between the working tree and the commits sits `.git/index`, a binary file mapping paths to blob hashes, plus cached file stat data. `git add` writes a blob for each changed file's content and records its hash in the index. `git commit` builds tree objects from the index, creates a commit object pointing at that tree and the current `HEAD`, and then updates the branch ref. Only new objects are written; nothing is copied.

## Consequences

- Objects are immutable, so "editing" history means writing new objects and moving refs. `git commit --amend` and `git rebase` create new commits and leave the originals behind.
- Unreachable objects are not deleted at once. The reflog keeps recent ref positions, and `git gc` prunes objects no ref can reach after a grace period.
- Renames are not recorded. Git stores snapshots and infers renames by similarity when diffing.
- Because names are hashes, corruption or tampering is detectable: an object whose content no longer matches its name is invalid.

When you type an HTTPS address into a browser and press Enter, the browser first works out what the address means. It splits the text into a scheme, a host name, an optional port and a path. For https://example.com/products the scheme is https, the host is example.com, the port defaults to 443 because none is given, and the path is /products. Before it sends anything, the browser checks a few local lists. One is its HSTS list, which records sites that must only be reached over HTTPS. Another is its cache, which may already hold a fresh copy of the page. If the cache holds a copy that is still valid, the browser can show it without touching the network at all, and the rest of this description applies only when it cannot.

The browser needs an IP address for the host name, so it begins a DNS lookup. It asks its own cache first, then the operating system's cache, and then the resolver the computer has been configured to use, which is usually run by the home router, the office network or the internet provider. If the resolver does not know the answer, it queries the DNS hierarchy on the browser's behalf. It asks a root server which servers handle .com, asks one of those which servers handle example.com, and finally asks one of those for the address. The answer comes back as an A record holding an IPv4 address such as 93.184.216.34, an AAAA record holding an IPv6 address, or both. Each record carries a time to live, often between 60 seconds and a day, which tells every cache along the way how long it may reuse the answer. A lookup that is answered from a cache takes under a millisecond, while one that walks the whole hierarchy can take 20 to 100 milliseconds.

With an address in hand, the browser opens a TCP connection to port 443. TCP provides an ordered, reliable stream of bytes between two machines, and it sets up that stream with a three-step exchange. The browser sends a SYN packet, the server replies with SYN-ACK, and the browser sends an ACK. This costs one round trip, which is the time for a message to reach the server and a reply to return. A server in the same city might be 10 milliseconds away, and one on another continent might be 150 milliseconds away. Modern browsers also support HTTP/3, which runs over QUIC on UDP instead of TCP. A browser usually learns that a site offers it from an earlier visit or from a DNS record, and QUIC folds the connection setup and the encryption setup together to save a round trip. The rest of this description follows the older and still very common path of HTTP/2 over TCP.

Once the TCP connection exists, the browser and server set up encryption using TLS, normally version 1.3. The browser sends a ClientHello message listing the TLS versions and cipher suites it supports, a random number, and the server name it wants, written in an extension called SNI. The server name matters because one IP address often serves many sites, and the server needs it to pick the right certificate. The ClientHello also carries the browser's half of a key exchange, typically based on elliptic curves. The server answers with its own half of the key exchange, so both sides can calculate the same shared secret without that secret ever crossing the network. The rest of the server's reply is already encrypted with keys derived from that secret.

The server's reply includes its certificate, which is a document naming the host names it covers and carrying the server's public key, signed by a certificate authority. The browser checks several things. The signature must chain up through one or more intermediate certificates to a root certificate that the browser or operating system already trusts. The dates on the certificate must include the present moment. The host name in the address must match a name on the certificate. The browser may also check whether the certificate has been revoked, although many browsers rely on lists distributed in bulk rather than querying each time. The server proves it holds the private key matching the certificate by signing part of the handshake. If any check fails, the browser stops and shows a warning page instead of continuing. In TLS 1.3 this handshake takes one round trip, so with TCP the total so far is one round trip for TCP plus one for TLS, after the DNS lookup. A returning visitor can sometimes resume a previous session and shorten this further.

During the handshake the browser and server also agree on which application protocol to speak, using a TLS extension called ALPN. The browser offers h2 for HTTP/2 and http/1.1, and the server picks one. Both sides now hold session keys, and everything they send from here on is encrypted and authenticated, so anyone watching the network can see the IP addresses and the amount of data but not the contents.

Now the browser sends its request. For HTTP/2 this is a set of binary frames, but its content is the same as in HTTP/1.1. It names a method, here GET, a path of /products, and headers. The headers include Host or its HTTP/2 equivalent, :authority, which says example.com, along with User-Agent, Accept, Accept-Encoding listing formats such as gzip and br, and any cookies the browser holds for that site. If the browser has a stale cached copy, it may add an If-None-Match header carrying the copy's ETag, which lets the server reply with a short 304 Not Modified instead of the whole page.

The request may pass through several machines before it reaches the application. Many sites sit behind a content delivery network, whose edge server ends the TLS connection, answers from its own cache if it can, and otherwise opens a separate connection to the origin server. A load balancer then picks one of several application servers. The chosen server runs the code for /products, which might query a database, assemble HTML and set headers such as Content-Type and Cache-Control.

The server sends back a status line and headers, followed by the body. The first byte of the response arriving at the browser is the point where this description ends. By then the browser has spent time on the DNS lookup, one round trip for TCP, one for TLS, and one more for the request and the start of the reply, plus whatever the server needed to produce the response. On a connection with a 50 millisecond round trip, those four steps already account for roughly 150 to 200 milliseconds before the server's own processing time is counted. This is why reusing connections, caching DNS answers and serving content from nearby machines are common ways to make pages start faster.

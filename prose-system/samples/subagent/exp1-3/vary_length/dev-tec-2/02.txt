From HTTPS address to first byte

You type https://www.example.com/products into the address bar and press Enter. Half a second later, the page starts to arrive. In between, the browser and the network do a surprising amount of work, and nearly all of it happens before your server sees a single line of your code. Knowing the steps will help you diagnose slow pages, odd certificate errors and mysterious redirects.

1. Parsing the address

The browser first splits the string into parts. The scheme is https, the host is www.example.com, the port is implied (443 for HTTPS), and the path is /products. The scheme matters most here. It tells the browser to wrap the whole conversation in encryption and to verify who it is talking to.

Before any network traffic, the browser checks its own memory. Does it hold a fresh cached copy of this resource? If so, it may skip the network entirely. Has the site been marked HSTS, meaning "only ever use HTTPS"? Browsers also ship with a preload list of such sites. If the address had been typed as http://, a match would make the browser upgrade it to https:// locally, with no insecure request ever leaving the machine.

2. Finding the IP address with DNS

Networks route traffic by IP address, not by names, so the browser must translate www.example.com into a number such as 93.184.216.34. This is DNS, the Domain Name System.

The lookup works through a chain of caches. The browser checks its own cache first, then the operating system's, then asks a recursive resolver. That resolver is usually run by your ISP or a public provider. If the resolver has not seen the name recently, it walks the hierarchy. It asks a root server which servers handle .com, asks those which servers handle example.com, and finally asks the authoritative server for the real answer. Each answer carries a time-to-live (TTL) that says how long it may be cached. This is why DNS changes can take a while to spread, and why a warm lookup costs almost nothing while a cold one can cost tens of milliseconds or more.

Modern browsers may also receive an HTTPS record from DNS. It can advertise that the server supports HTTP/3 or even hand over keys for faster encryption setup.

3. Opening a TCP connection

With an IP address, the browser can connect. Traditional HTTPS runs over TCP, which provides a reliable, ordered stream of bytes. TCP begins with a three-step handshake. The client sends a SYN. The server replies with SYN-ACK. The client answers with ACK. That costs one full round trip, the time for a message to travel to the server and back. Round trips are the currency of web performance. A user in London talking to a server in Sydney pays roughly 250 ms for each one, no matter how fast either machine is.

If the browser already has an open connection to this host from an earlier request, it reuses it and skips this step and the next. This is called connection reuse, or keep-alive.

4. The TLS handshake

TCP gets bytes moving, but they are still readable by anyone along the path. The TLS handshake fixes that. It has two jobs. It proves the server is really www.example.com, and it establishes secret keys that only the two endpoints know.

The browser sends a ClientHello. It lists the TLS versions and cipher suites it supports, includes a random value, and sends a key share for the key exchange. The ClientHello also carries the Server Name Indication, or SNI. This is the hostname in plain text, so that a server hosting many sites on one IP address knows which certificate to present. ALPN, another extension in the same message, lists the application protocols the browser can speak, such as h2 (HTTP/2) and http/1.1.

The server replies with its choices and its certificate. In TLS 1.3, the version you should expect today, the server's key share arrives in that same first reply. Both sides can then compute the shared secret, and everything after that point is encrypted. The handshake finishes in a single round trip. TLS 1.2 needed two.

The certificate deserves a closer look. It binds the hostname to a public key, and it is signed by a certificate authority (CA). The browser checks several things. Does the name on the certificate match www.example.com? Has it expired? Does its signature chain, through any intermediate certificates, up to a root CA already trusted by the operating system or browser? Has it been revoked? The server also signs part of the handshake with its private key, which proves it actually owns the certificate rather than merely having copied it. If any check fails, you get the full-page warning about an untrusted connection. That warning is the system working as intended.

On a repeat visit, TLS session resumption can shorten or skip much of this. With 0-RTT, a returning client can even send its request along with the first handshake message. The trade-off is that such early data can be replayed by an attacker, so it should only carry safe requests.

5. QUIC and HTTP/3

There is an alternative path. HTTP/3 runs over QUIC, which uses UDP and folds the transport handshake and the TLS 1.3 handshake into one. A fresh connection then needs only one round trip in total, instead of two for TCP plus TLS. The browser usually learns that a server supports HTTP/3 from an Alt-Svc header on an earlier response or from DNS, and it may race the two approaches against each other.

6. Sending the request

Now the connection is secure, and the browser finally speaks HTTP. Under HTTP/2 or HTTP/3 the request is binary and compressed, but its content is the same as it was in HTTP/1.1:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

It names the method, the path and the host. It declares which formats and compression schemes the browser accepts. It also includes any cookies stored for this site, plus other headers such as User-Agent and Accept-Language. This is the moment your application code finally gets a say.

7. Waiting for the server

The request crosses the network, again encrypted, and often lands on something other than your application. A CDN edge server or load balancer may terminate the TLS connection first. It can answer from its cache, or it can forward the request on to an origin server. The origin may route to your framework, run middleware, check a session, query a database, render a template and then begin writing a response. Any of those steps can be slow, and this is where most of your own code's time goes.

The first byte of the response, headers included, travels back along the same encrypted connection. The browser measures the interval from the start of the request to that first byte and calls it Time to First Byte, or TTFB.

Putting numbers on it

A cold visit on a distant server looks like this: one round trip for DNS (more if uncached), one for TCP, one for TLS 1.3, and one for the request itself, plus server processing time. That is four round trips before the first byte arrives, and none of them is spent on your actual content. A warm visit with a cached DNS result and a reused connection needs only the last one.

This explains the common advice. Put content close to users with a CDN. Use HTTP/2 or HTTP/3. Keep connections alive. Enable TLS 1.3 and session resumption. Cut redirects, since each one repeats some or all of these steps. In the browser's developer tools, the Network tab's timing breakdown shows each phase separately, so you can see which one is costing you.

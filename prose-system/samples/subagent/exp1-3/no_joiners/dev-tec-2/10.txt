Typing an address that begins with https into a browser sets off a chain of small steps, and every one of them adds delay before the first byte of the response shows up. Developers call that delay time to first byte. Understanding the steps tells you where the time goes and what you can do about it.

Parsing the address

The browser first splits the address into parts. The scheme is https, which means HTTP carried over an encrypted connection. The host is the name of the server, such as www.example.com. There may also be a port, a path and a query string. If no port is given, https defaults to 443. Only the scheme, host and port decide which machine the browser talks to. The path and query come later, inside the request itself.

Before any network work starts, the browser checks whether it already knows something useful. It looks at its HSTS list, which records sites that must only be reached over https. It also checks its HTTP cache. If a fresh copy of the resource is stored, the browser can use it right away and no network trip is needed at all. If the copy is stale, the browser may still send a conditional request later, asking the server whether anything changed.

Finding the IP address with DNS

Computers connect using IP addresses, not names, so the browser must translate the host name. That is the job of the Domain Name System. The browser checks its own DNS cache first, then asks the operating system, which has its own cache and may also consult a local hosts file. If nobody knows the answer, the request goes to a recursive resolver, usually run by your internet provider or a public service. The resolver does the hard work. If it has no cached answer, it asks a root server which servers handle the top level domain, such as com. It then asks those servers which servers are responsible for the domain, and finally asks that domain's own name server for the record. The answer carries a time to live value that tells every cache how long it may be reused.

The result may be an IPv4 address, an IPv6 address or both. Modern browsers try both and favour whichever connects faster. A cold DNS lookup can take tens or even hundreds of milliseconds, while a cached one is nearly instant. Large sites often use a content delivery network, whose DNS answers point you to a nearby edge server rather than the origin.

Opening a TCP connection

With an IP address in hand, the browser opens a TCP connection to port 443. TCP gives reliable, ordered delivery over the unreliable internet, but it must be set up first. This uses a three step handshake. The browser sends a SYN packet, the server answers with SYN and ACK, and the browser replies with an ACK. That costs one full round trip, which is the time for a message to reach the server and a reply to come back. If the server is far away, a round trip may be 100 milliseconds or more, and the speed of light means you cannot cheat that number.

If the browser already holds an open connection to the same host, it reuses it and skips this step and the next. This is one reason connection reuse matters so much.

Negotiating encryption with TLS

Because the address says https, the browser now runs a TLS handshake on top of TCP. The goals are to prove the server is who it claims to be and to agree on keys for encrypting everything that follows.

The browser sends a ClientHello message listing the TLS versions and cipher suites it supports, a random number, and a key share for key exchange. It also includes the host name in an extension called Server Name Indication, so a server hosting many sites knows which certificate to present. The server replies with its choice of settings, its own key share and its certificate. From the two key shares, both sides compute the same secret without ever sending it across the network. TLS 1.3 completes this in one round trip. TLS 1.2 needs two. A resumed session can sometimes shorten it further.

The certificate is the identity proof. The browser checks that it names the requested host, that it has not expired, and that it was signed by an authority the browser trusts, possibly through a chain of intermediate certificates. It may also check whether the certificate has been revoked. If any check fails, the browser shows a warning page instead of continuing. Once both sides send Finished messages, the connection is encrypted and authenticated.

Sending the HTTP request

Now the browser finally sends the actual request. In HTTP/1.1 it is plain text, beginning with a line such as GET /products HTTP/1.1, followed by headers like Host, Accept, User Agent, Accept Encoding and any cookies that belong to that site. Cookies matter here because they travel with every request and can make requests heavier than you expect.

HTTP/2 sends the same information in a compact binary format and lets many requests share one connection. HTTP/3 goes further by running over QUIC, which uses UDP and folds the transport and encryption handshakes together, so a new connection needs only one round trip and a repeat visit may need none. Which version is used is settled during the TLS handshake through a feature called ALPN, or learned from earlier responses.

What the server does

The request crosses the network, possibly passing through a CDN, a load balancer or a reverse proxy. Any of these may answer from cache or forward the request onward. Eventually it reaches an application server. The server decrypts the request, parses it, and routes it to code that handles the path. That code might check a session, query a database, call other services and render a template. Slow database queries and chained service calls are among the most common causes of a long wait here.

When the application has something to say, it writes a status line such as 200 OK, response headers like Content Type and Cache Control, and then the body. The first byte of that response travelling back across the network is the moment the browser measures as the end of the wait.

Why this matters

Add up the pieces and a first visit to a distant server involves roughly one round trip for TCP, one for TLS 1.3, one for the request and response, plus DNS and server processing time. That is why the same page can feel instant on a warm connection and sluggish on a cold one.

You can see all this yourself. The Network panel in browser developer tools breaks each request into stalled, DNS lookup, initial connection, SSL, request sent and waiting phases. The waiting phase is the time to first byte. When it is large, look at server work. When the DNS, connection or SSL phases are large, look at geography, CDNs and connection reuse.

We integrate with the GridX API for demand-response/VPP functionality. GridX supports webhook subscriptions (GET /Subscriptions lists current subscriptions, POST /Subscriptions creates one) notifying us of events via a receiver endpoint we host.

Build a periodic monitoring task ensuring we stay subscribed:
1. In dc/third_party_api_clients/gridx/gridx_api_client.py, add client methods for GET and POST /Subscriptions — listing existing subscriptions and creating one pointing at our receiver callback URL. Add request/response payload models in dc/third_party_api_clients/gridx/payloads.py.
2. In dc/tasks/multi_queue_huey/vpp/demand_response/gridx_subscription_monitor.py, implement a Huey periodic task that queries GridX for current subscriptions, checks whether an active subscription already points at our receiver endpoint, and if not creates one. Register in dc/tasks/multi_queue_huey/__init__.py.
3. In dc/views/rest/external/vpp/gridx.py, add a stub receiver endpoint (DRF view) as the callback URL target — it need not fully process payloads yet, just accept and acknowledge (200). Wire in inventev/urls/__init__.py; add required settings in inventev/settings/base.py.
4. Extend dc/logic/openadr_3/payloads.py if subscription payload/typing utilities belong there per existing OpenADR 3.0 conventions.
5. Tests: dc/tests/tasks/demand_response/test_gridx_subscription_monitor.py (subscribing when not subscribed, not re-subscribing when already subscribed, API errors) and extend dc/tests/third_party_api_clients/gridx/test_gridx_api_client.py.

The check must be idempotent and safe on a schedule — determine "are we already subscribed" by comparing existing subscriptions against our receiver URL rather than blindly creating duplicates.

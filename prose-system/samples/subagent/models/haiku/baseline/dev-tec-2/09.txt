**From URL to First Byte: What Happens in an HTTPS Request**

When you type `https://example.com/pricing` and press Enter, a lot of work happens before the server's first byte reaches the browser. This walkthrough follows that path in order. The first byte is what the Time to First Byte (TTFB) metric measures, and most of the delay before it comes from network round trips and server work.

**1. Parsing the address**

The browser splits the URL into a scheme (`https`), host (`example.com`), port (443 is implied for HTTPS), path (`/pricing`), and query string. The scheme sets the default port and requires encryption. The browser also checks its HSTS list. If the site previously sent a `Strict-Transport-Security` header, the browser upgrades any `http://` request to `https://` before it goes out.

**2. Finding the IP address (DNS)**

Packets are routed to IP addresses, not names, so the browser needs to resolve `example.com`. It checks its own DNS cache first, then asks the operating system's resolver, which checks its cache and the hosts file. If no cached answer exists, the query goes to a recursive resolver, usually run by the user's ISP or a public service. That resolver asks a root server, which points to the `.com` servers, which point to the authoritative name servers for `example.com`. Those return the A (IPv4) and AAAA (IPv6) records. Each answer carries a TTL, and every cache along the way keeps it only that long. Browsers may also query HTTPS-type DNS records in this step, which can advertise HTTP/3 support.

A junior developer should note that DNS is often the slowest part of a cold first visit, and TTLs control how quickly a DNS change reaches users.

**3. Opening a TCP connection**

With an IP address, the browser opens a TCP connection to port 443. This takes one full round trip: the client sends SYN, the server replies SYN-ACK, and the client sends ACK. Application data cannot flow until this finishes. If both IPv6 and IPv4 addresses are returned, browsers race the two connections (Happy Eyeballs) and keep whichever connects first. Every round trip costs the full network latency, so a server 150 ms away costs at least 150 ms here.

**4. The TLS handshake**

Because the scheme is HTTPS, the browser negotiates TLS before sending any HTTP.

- **ClientHello:** The browser sends the TLS versions and cipher suites it supports, a random value, and a key share, which is its half of an ephemeral Diffie-Hellman exchange. It also sends the Server Name Indication (SNI) field containing `example.com`, so a server hosting many sites knows which certificate to present. The ALPN field lists the application protocols it can speak, such as `h2` or `http/1.1`.
- **ServerHello and key share:** The server picks a cipher suite and returns its own key share. Both sides now compute the same shared secret without sending it over the wire.
- **Certificate check:** The server sends its certificate chain. The browser checks that the chain leads to a certificate authority in its trust store, that the certificate's dates are valid, that its names match `example.com`, and that it has not been revoked, using OCSP stapling or browser-maintained revocation lists. A failure here produces the familiar certificate warning.
- **Finished messages:** Each side sends a message authenticating the handshake transcript, which proves both derived the same keys. From this point, all traffic is encrypted with symmetric keys, typically AES-GCM or ChaCha20-Poly1305.

In TLS 1.3, this exchange takes one round trip after TCP. TLS 1.2 needed two. Returning visitors can use session resumption to shorten it further, and TLS 1.3 0-RTT can send early data, though that data is open to replay and must be safe to repeat.

**5. Sending the HTTP request**

The browser writes a plain-text HTTP request into the encrypted connection:

```
GET /pricing HTTP/1.1
Host: example.com
Accept: text/html,...
Accept-Encoding: gzip, br
Cookie: session=...
```

The `Host` header matters because one IP address often serves many websites. The browser attaches any cookies that belong to `example.com`. Over HTTP/2, the same request becomes a binary frame on a multiplexed stream. Over HTTP/3, it runs on QUIC, which combines the transport and TLS 1.3 handshakes over UDP.

**6. Server-side work before the first byte**

When the request arrives, several steps can happen before any response is sent:

- A load balancer or CDN edge terminates TLS, so the handshake above may be with a different machine than the origin. If the edge has a cached copy of `/pricing`, it can respond immediately, which is the fastest possible TTFB.
- On a cache miss, the request is forwarded to an application server.
- The application matches the route, runs middleware (authentication, logging, cookie handling), queries a database or cache, and renders a template.
- The first byte is sent only when the framework starts writing the response.

Often this server-side time, not the network, dominates TTFB. Slow database queries and uncached rendering are common causes.

**7. The first byte arrives**

The response starts with a status line such as `HTTP/1.1 200 OK`, followed by headers like `Content-Type`, `Cache-Control`, and `Content-Encoding`. The browser uses these headers to decide how to handle the body, whether to cache it, and how to decompress it. The arrival of that first byte is the TTFB measurement point. The body then streams in, the browser parses the HTML, and discovers further resources such as scripts, stylesheets, and images. Those requests reuse the existing connection through keep-alive or HTTP/2 multiplexing, so they skip steps 2 to 4.

**Summary**

| Step | Typical cost on a cold visit |
|---|---|
| DNS lookup | One or more round trips to resolvers |
| TCP handshake | One round trip |
| TLS 1.3 handshake | One round trip |
| Request and server processing | Network latency plus app time |

For a developer, the practical takeaways are to keep DNS and TLS round trips low (CDNs, connection reuse, session resumption), and to measure server time separately from network time when TTFB is slow.

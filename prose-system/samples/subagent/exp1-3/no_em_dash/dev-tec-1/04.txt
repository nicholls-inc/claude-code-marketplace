Inside .git, a commit is not stored as a diff. Git is a content-addressable store: a simple key-value database in .git/objects where each key is the SHA hash of a value's contents. Four kinds of object live there (blobs, trees, commits and annotated tags), and a small set of text files called refs gives the hashes human-friendly names. Once you see how these pieces connect, most Git behavior stops being mysterious.

**Objects and hashes**

Every object is stored as a header (its type and size) followed by its content, compressed with zlib. Git hashes that whole sequence with SHA-1 (or SHA-256 in newer repositories) and uses the result as the object's name. The first two hex characters become a directory and the rest the filename, so an object with hash `e69de29bb2d1d6434b8b29ae775ad8c2e48c5391` lives at `.git/objects/e6/9de29b...`. Two consequences follow. Identical content always yields the same hash, so it is stored once. And an object can never change without its name changing, which is why Git history is effectively immutable.

You can inspect any object with `git cat-file -p <hash>` for its content and `git cat-file -t <hash>` for its type.

**Blobs: file contents**

A blob holds the raw bytes of one file and nothing else. It has no filename, no permissions and no timestamp. If you copy a file to three different paths, or the same file appears in a hundred commits, Git keeps a single blob. Editing one character of a large file creates a whole new blob, since the hash is of the complete content. Packfiles later compress such similar blobs by storing deltas, but that is a storage optimization hidden beneath the logical model.

**Trees: directories**

A tree is Git's directory listing. Each entry records a mode (such as `100644` for a regular file, `100755` for an executable, `040000` for a subdirectory), a type, a hash and a name. Entries point at blobs for files and at other trees for subdirectories. Running `git cat-file -p HEAD^{tree}` prints the root tree of your latest commit, and might look like this:

```
100644 blob a1b2c3...  README.md
040000 tree 9f8e7d...  src
100755 blob 4c5d6e...  build.sh
```

Filenames live here, not in blobs, which is why renaming a file creates a new tree but no new blob. A tree's hash depends on the hashes of everything beneath it. Change one file deep in `src/lib/` and its blob, the `lib` tree, the `src` tree and the root tree all get new hashes. Untouched subtrees keep their hashes and are reused as is. This structure makes a snapshot cheap: a new commit reuses nearly everything from the last one.

**Commits: snapshots with context**

A commit object is a small text record. Print one with `git cat-file -p HEAD`:

```
tree 3b18e512dba79e4c8300dd08aeb37f8e728b8dad
parent 8a1c0f4e5d6b7a99c2d3e4f5a6b7c8d9e0f1a2b3
author Ada Lovelace <ada@example.com> 1731312000 +0000
committer Ada Lovelace <ada@example.com> 1731312000 +0000

Fix off-by-one in pagination
```

There are four parts. The `tree` line points to the root tree, which is the complete project snapshot at that moment. The `parent` line names the previous commit (a merge commit has two or more, and the very first commit has none). The author and committer lines carry identity and a timestamp, and they can differ, as after a rebase or when applying someone else's patch. Last comes the message.

When you run `git show`, Git displays a diff, but it computes that on the fly by comparing the commit's tree to its parent's tree. Only snapshots are stored. The parent links form a directed acyclic graph, and because each commit's hash covers its parent's hash, altering any historical commit changes every descendant. That is why rewriting history with rebase or amend produces new commits rather than editing old ones. The old commits remain in the object store until garbage collection removes them.

**Refs: names for hashes**

Hashes are unwieldy, so Git keeps refs, which are plain files containing a hash. Branches live under `.git/refs/heads/`, so `.git/refs/heads/main` is a text file holding the 40-character hash of the branch's tip commit. Tags are in `.git/refs/tags/`, and remote-tracking branches such as `origin/main` are in `.git/refs/remotes/`. Creating a branch just writes a new 41-byte file, which is why it is instant. Committing means writing the new commit object, then updating the current branch's file to point to it. Large repositories may consolidate refs into `.git/packed-refs` for speed, but the meaning is the same.

**HEAD: where you are**

`.git/HEAD` records your current position. Normally it contains a symbolic reference such as `ref: refs/heads/main`, meaning "I am on main." When you commit, Git advances whatever branch HEAD points to. In "detached HEAD" state, the file contains a raw commit hash instead, so new commits advance nothing, and they can become unreachable once you switch away. The reflog (`.git/logs/`) records where refs and HEAD have pointed, which is how you can often recover such commits.

**Putting it together**

Running `git add` hashes your files into blobs and records them in the index (`.git/index`), the staging area. `git commit` turns the index into a tree hierarchy, writes a commit object referencing that tree and the current parent, then moves the branch ref forward. Every `git checkout` or `switch` reads a commit, follows it to a tree, and expands the tree and blobs into your working directory.

To see all of this yourself, make a tiny repository and run `find .git/objects -type f` after each step. You will watch blobs, trees and commits appear, and then read them with `git cat-file -p`.

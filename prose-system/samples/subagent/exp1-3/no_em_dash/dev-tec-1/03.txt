When you run `git commit`, Git does not record a diff. It stores a snapshot of your whole project, built from four kinds of things: blobs, trees, commits and refs. Everything lives in the `.git` directory, and most of it is a simple key-value store.

**The object database**

Inside `.git/objects`, Git keeps content-addressed objects. Each object is hashed (SHA-1 traditionally, SHA-256 in newer repositories), and the hash becomes its name. Hash the same content and you get the same name, so identical content is stored once. Objects are immutable. Change one byte and you have a different object with a different name.

A hash like `3b18e512dba79e4c8300dd08aeb37f8e728b8dad` is stored as `.git/objects/3b/18e512...`, with the first two characters used as a directory name. Each file is zlib-compressed and holds a short header (type, a space, the size in bytes) followed by the content. Over time, Git also packs many objects into `.git/objects/pack` files and stores similar objects as deltas to save space. That is a storage optimisation. The model below stays the same.

**Blobs: file contents**

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no timestamp. If two files in your project have identical contents, they share one blob.

You can see this directly:

```
$ echo "hello" | git hash-object --stdin
ce013625030ba8dba906f756967f9e9ca394464a
$ git cat-file -p ce01362
hello
```

**Trees: directories**

A tree is Git's idea of a directory. It lists entries, and each entry has a mode, a type, a hash and a name:

```
$ git cat-file -p HEAD^{tree}
100644 blob ce013625...  README.md
040000 tree 9f4d96d5...  src
100755 blob 7a1c0e3b...  build.sh
```

Filenames and permissions live here, in the parent, and not in the file itself. The mode tells Git whether an entry is a regular file (100644), an executable (100755), a symlink (120000) or a subdirectory (040000). A subdirectory entry points at another tree, so the structure is recursive. The tree at the top represents your whole working directory. Because a tree's hash depends on the hashes of everything beneath it, changing one file changes its blob, the trees above it and the root tree, all the way up. Anything you did not touch keeps the same hash and is reused.

**Commits: snapshots with history**

A commit object is small. It contains a pointer to a root tree, pointers to zero or more parent commits, author and committer details with timestamps, and your message:

```
$ git cat-file -p HEAD
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent a94a8fe5ccb19ba61c4c0873d391e987982fbbd3
author Ada <ada@example.com> 1731300000 +0000
committer Ada <ada@example.com> 1731300000 +0000

Fix off-by-one in pagination
```

A normal commit has one parent, a merge commit has two or more, and the first commit has none. This chain of parent pointers is your history. Nothing in a commit says what changed. When you run `git show` or `git diff`, Git compares the two trees and computes the differences on the fly.

The commit's own hash covers the tree hash, parent hashes, author and message. Since each commit embeds its parent's hash, altering any past commit changes every commit after it. This is why history rewriting (rebase, amend) produces new commits and leaves the old ones intact until they are garbage collected.

**Refs: human-readable names**

Hashes are hard to remember, so Git uses refs, which are files containing a hash. They live under `.git/refs`:

```
$ cat .git/refs/heads/main
a94a8fe5ccb19ba61c4c0873d391e987982fbbd3
```

A branch is exactly that: a file with a 40-character hash in it. Creating a branch is cheap because it writes one tiny file. Committing moves the current branch forward by writing the new commit's hash into that file. Tags work the same way under `refs/tags`. Remote-tracking branches such as `origin/main` live under `refs/remotes`. For efficiency, Git sometimes consolidates refs into `.git/packed-refs`.

**HEAD: where you are**

`.git/HEAD` records your current position. Normally it is a symbolic reference to a branch:

```
$ cat .git/HEAD
ref: refs/heads/main
```

So HEAD points at `main`, and `main` points at a commit. If you check out a specific commit, HEAD instead contains a raw hash, which is the "detached HEAD" state. New commits made there are not on any branch, so nothing keeps them reachable once you switch away, apart from the reflog.

**The index: the staging area**

One more file matters for the commit workflow: `.git/index`. It is the staging area, a sorted list of paths with the blob hash and mode for each. `git add` writes the file's contents as a blob and updates the index entry. `git commit` then turns the index into a tree (writing tree objects for each directory), creates a commit object pointing at that root tree and at the current HEAD commit as its parent, and finally moves the current branch ref to the new commit.

**Putting it together**

Suppose you edit `src/app.js` and commit. Git creates one new blob for the new file contents, a new tree for `src`, a new root tree (since `src` changed), and a new commit that points to the new root tree with the previous commit as parent. Then it updates `refs/heads/main`. Every other file reuses its existing blob, and every unchanged directory reuses its existing tree.

Seen this way, much of Git's behaviour follows. Branches are cheap because they are pointers. Commits are snapshots, so checking out any of them just means materialising a tree. Corruption is detectable because every object name is a checksum of its content. And "lost" commits are often recoverable, because objects stick around until garbage collection removes anything unreachable from a ref or the reflog.

To explore, try `git cat-file -p <hash>`, `git cat-file -t <hash>` and `git ls-tree HEAD` in any repository.

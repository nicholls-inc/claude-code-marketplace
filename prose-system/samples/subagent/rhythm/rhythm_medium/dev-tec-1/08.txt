When you run git commit, you create a small chain of objects inside the hidden .git directory, and understanding that chain explains most of Git's behavior. Everything Git stores lives in .git/objects, which is a content-addressable database: each piece of data is compressed and saved under a name derived from a hash of its contents. Historically that hash is SHA-1, and newer repositories can use SHA-256, but the idea is identical either way. The first two hex characters of the hash become a directory name and the remainder becomes the filename, so an object whose hash begins with "e69de2" lives at .git/objects/e6/9de2... and so on. Because the name is computed from the content, identical content always maps to the same object, and no object can change without also changing its name.

The simplest kind of object is the blob, which holds the raw contents of a single file and nothing else. A blob has no filename, no permissions and no timestamp, only the bytes. If two files in your project have exactly the same contents, Git stores one blob for both, and if you rename a file without editing it, the blob is untouched. This is why Git can detect renames so cheaply, and why a large repository full of duplicated files does not grow as quickly as you might expect.

Since blobs carry no names, something else must record which blob belongs at which path, and that job belongs to the tree. A tree object is essentially a directory listing, where each entry contains a file mode, a name, and the hash of either a blob or another tree. The mode distinguishes regular files, executable files, symbolic links and subdirectories. A project with nested folders is therefore represented as a tree of trees, with the root tree at the top pointing down to subtrees and eventually to blobs. Editing a single file deep in the hierarchy produces a new blob, and because that blob's hash changes, the tree that lists it must change too, and so must each parent tree all the way up to the root. The unchanged siblings are simply referenced again by the same hashes, which is how Git captures a complete snapshot of your project without copying everything on every commit.

The commit object ties a snapshot to history. It is a short text record containing the hash of the root tree, the hash of each parent commit, the author with a timestamp and time zone, the committer with their own timestamp, and finally your commit message. A normal commit has one parent, the first commit in a repository has none, and a merge commit has two or more. Because the parent's hash is part of the commit's own content, each commit's hash depends on the entire history behind it, which makes the history tamper-evident. If you amend a commit or rebase, you are not editing anything in place. You are creating new commit objects with new hashes, which is also why rewritten history looks like entirely different commits to anyone who has the old ones.

None of those objects would be easy to use on their own, because a forty-character hash is hard to remember and Git needs some way to know where you currently are. That is the role of refs, which are simply files containing a hash. Branches live under .git/refs/heads, so a branch called main is a file at .git/refs/heads/main holding the hash of the latest commit on that branch. Tags live under .git/refs/tags, and remote-tracking branches live under .git/refs/remotes. Creating a branch is therefore nearly free, since Git writes one small file, and making a commit just moves the current branch's file to point at the new commit. The special file .git/HEAD records what you currently have checked out. Usually it contains a line such as "ref: refs/heads/main", meaning it points at a branch, and when you commit, Git follows that pointer and updates the branch. If HEAD instead contains a raw commit hash, you are in the detached HEAD state, and new commits are not attached to any branch, so they can be lost once you move away unless you create a branch for them.

Walking through a single commit shows how these pieces fit together. When you run git add, Git writes a blob for each changed file immediately and records the result in the index, a binary file at .git/index that represents the snapshot you are preparing. When you run git commit, Git builds tree objects from the index, creates a commit object that points at the root tree and at the previous commit, and then moves the current branch ref to the new commit. Nothing about the earlier commits is modified, because objects are immutable, and that is why operations like checking out an old version or resetting a branch are fast and mostly reversible. The old commits stay in the database until garbage collection removes objects that nothing can reach.

You can explore all of this yourself with a few plumbing commands. Running git cat-file -p HEAD prints the latest commit, git cat-file -p HEAD^{tree} prints its root tree, and git cat-file -t followed by any hash tells you whether it is a blob, tree, commit or tag. Once you have done that a few times, branches, merges and rebases stop feeling like magic and start to look like what they are, which is small pointers moving around a graph of immutable snapshots.

Open the .git directory of any repository and you will find a small database rather than a pile of diffs. Git is, at its core, a content addressable store. You hand it some data, it computes a hash of that data, and it files the data under that hash. The hash then becomes the name you use to ask for the data later. Everything you think of as history is built from three kinds of object, plus a layer of named pointers called refs.

**Blobs**

The simplest object is the blob. A blob holds the raw bytes of one file and nothing else. It has no filename, no permissions and no timestamp. Git builds a header from the word blob, a space, the byte length and a null byte, then appends the content. It hashes the whole thing with SHA1, or SHA256 in newer repositories, and compresses it with zlib. The result lands in the .git/objects directory. The first two characters of the hash become a subdirectory and the remaining characters become the filename. A blob whose hash begins 8ab686 therefore lives at .git/objects/8a/b686 followed by the rest of the hash.

Two files with identical content share one blob, even if they have different names or sit in different folders. Rename a file and no new blob is created. Edit a single line and you get a whole new blob, because Git stores complete snapshots of content rather than patches.

**Trees**

Since blobs carry no names, something must say which blob is which file. That job belongs to the tree. A tree object represents one directory. It is a list of entries, and each entry records a file mode, a name and the hash of either a blob or another tree. The mode tells Git whether the entry is a regular file, an executable, a symbolic link or a subdirectory. A subdirectory entry points at another tree, so a project of any depth becomes a nested structure of trees with blobs at the leaves.

The tree at the top is called the root tree, and its hash is a fingerprint of the entire project at one moment. Change a single byte in a deeply nested file and its blob hash changes. That changes the hash of the parent tree, then the grandparent, and so on up to the root. Directories you did not touch keep their hashes and are reused as they are. This is why a new commit in a huge repository costs so little space.

**Commits**

A commit object ties a snapshot to a point in history. It is a short text record containing the hash of a root tree, zero or more parent commit hashes, an author with a timestamp, a committer with a timestamp, and your message. The first commit in a repository has no parent. An ordinary commit has one. A merge commit has two or more.

Because a commit includes its parents' hashes in its own content, each commit hash depends on the entire history behind it. Alter an old commit and every descendant receives a new hash. This is exactly why rewriting history with rebase produces new commits instead of modifying existing ones. The old commits still sit in the database until Git eventually garbage collects them.

Notice that a commit stores a snapshot and not a diff. When you run git show, Git computes the diff on the fly by comparing the commit's tree with its parent's tree. The same applies to git log with patches, git blame and every other view of change.

**Refs**

Nobody wants to type forty hexadecimal characters, so Git adds refs. A ref is a file whose entire content is a commit hash. Branches live under .git/refs/heads, so a branch called main is the file .git/refs/heads/main. Tags live under .git/refs/tags and remote tracking branches under .git/refs/remotes. Creating a branch is therefore nothing more than writing a few dozen bytes to a file, which explains why it feels instant.

HEAD is a special ref stored at .git/HEAD. Normally it holds the word ref followed by a branch path such as refs/heads/main, which means HEAD points at a branch and the branch points at a commit. In a detached HEAD state the file holds a commit hash directly. That is all detached HEAD means, and it explains why commits made there can be lost. No branch file points at them, so nothing keeps them reachable once you switch away.

Over time Git may collect many loose ref files into a single .git/packed-refs file, and it may bundle loose objects into packfiles that use delta compression. These are storage optimizations. The model underneath stays the same.

**Putting it together**

When you run git commit, a sequence of small steps happens. Git writes a blob for every file whose content changed. It builds new trees for each directory on the path from those files up to the root. It creates a commit object that points at the new root tree and names the current tip as its parent. Finally it rewrites the branch file so it contains the new commit's hash.

That last step is the only one that modifies an existing file. Everything before it only adds new, immutable objects. This design is what makes Git safe and fast. Objects never change once written, so they can be shared, cached and verified by their hashes. A branch is a movable label, a commit is a labelled snapshot with a parent, and a snapshot is a tree of blobs. Once you hold that picture in your head, commands like reset, cherry pick and rebase stop being mysterious. They simply move refs and create new objects.

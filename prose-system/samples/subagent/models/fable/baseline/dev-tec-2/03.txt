# From HTTPS address to first byte

When you type `https://shop.example.com/products` and press Enter, the browser has to do four things before any of the response arrives: work out what you asked for, find the server, open a secure connection to it, and send the request. The time all of this takes is what performance tools call time to first byte (TTFB). Each step adds delay, and each can fail in its own way, so knowing the sequence helps you read a network waterfall or diagnose a slow page.

## 1. Parsing the URL and checking local state

The browser splits the address into its parts: the scheme (`https`), the host (`shop.example.com`), the port (443 by default for HTTPS) and the path (`/products`).

It then checks whether it needs the network at all. If a fresh copy of the resource is in the HTTP cache, the browser can use that, and a service worker registered for the site can answer the request itself.

The browser also consults its HSTS list. A site on that list has told browsers to use HTTPS only, so even if you typed `http://`, the browser rewrites the address to `https://` before sending anything.

## 2. DNS: turning the name into an address

Computers on the internet are reached by IP address, not by name, so the browser needs the IP address for `shop.example.com`. It tries the nearest caches first: its own, then the operating system's.

If neither has the answer, the operating system asks a resolver, a DNS server usually run by your ISP or a public provider. The resolver either has the answer cached or finds it by asking a chain of servers:

1. A root server says where the `.com` servers are.
2. A `.com` server says where the name servers for `example.com` are.
3. The `example.com` name server returns the actual record.

The answer comes back with a time to live (TTL), which says how long it may be cached. That is why DNS changes take a while to reach everyone.

An uncached lookup typically costs tens of milliseconds; a cached one costs almost nothing. Modern browsers also ask for an HTTPS record, which can tell them in advance that the server supports HTTP/3.

## 3. Opening a connection

With an IP address in hand, the browser opens a connection, unless it already has an idle one to the same origin, in which case it reuses that and skips this step and the next.

For HTTP/1.1 and HTTP/2, the transport is TCP. TCP gives both sides a reliable, ordered stream of bytes, and it starts with a three-way handshake:

1. The browser sends a SYN packet.
2. The server replies with SYN-ACK.
3. The browser sends an ACK.

This costs one round trip: the time for a packet to reach the server and for the reply to come back. A round trip might take 10 ms to a nearby server and 150 ms or more to one on another continent. That time, more than anything else, sets the cost of every remaining step.

## 4. The TLS handshake

The TCP connection is not encrypted. TLS, the "S" in HTTPS, runs on top of it and does three jobs: it encrypts the traffic, it detects tampering, and it proves that the server is who it claims to be.

In TLS 1.3, the current version, the handshake takes one round trip:

1. **ClientHello.** The browser sends the TLS versions and cipher suites it supports, a key share (its half of a key exchange), the hostname it wants (the SNI field, which lets one IP address serve many sites), and the application protocols it speaks, such as `h2` for HTTP/2 (the ALPN field).
2. **ServerHello.** The server chooses the cipher suite and the protocol and sends its own key share. Both sides can now compute the same secret keys, and nobody watching the exchange can work them out. The server also sends its certificate and a signature that proves it holds the certificate's private key.
3. **Verification.** The browser checks that the certificate covers `shop.example.com`, has not expired, and chains back to a certificate authority that the browser or operating system trusts. If any check fails, you see a certificate warning and the request is not sent.
4. **Finished.** The browser confirms the handshake, and it can send encrypted data straight away.

The older TLS 1.2 handshake needs two round trips. In the other direction, a browser that has visited the site recently can resume the earlier session, and can sometimes send the request with its very first packet (0-RTT).

## 5. HTTP/3 shortens the setup

HTTP/3 replaces TCP with QUIC, a transport built on UDP that has TLS 1.3 built into it. Because the transport handshake and the encryption handshake happen together, a new connection takes one round trip, not two.

The browser learns that a server supports HTTP/3 from the DNS HTTPS record or from an `Alt-Svc` header on an earlier response. Often it tries QUIC and TCP at the same time and uses whichever connects first.

## 6. Sending the request

Now the browser sends the HTTP request over the encrypted connection. It contains the method (`GET`), the path (`/products`), the host, and headers such as `Accept`, `Accept-Encoding`, `User-Agent` and any cookies for the site.

In HTTP/1.1 the request is plain text. In HTTP/2 and HTTP/3 it is sent as compressed binary frames on a numbered stream, so that many requests can share one connection.

## 7. The server does its work

The request often does not go directly to your application. It may arrive first at a CDN edge server or a load balancer, which ends the TLS connection and forwards the request to an application server. From the browser's side, the "server" is whatever answered the handshake.

Your code then runs: it routes the request, checks the session, queries the database and renders a template or builds JSON. This is the only part of TTFB that depends on your application code, and it is often the largest part.

## 8. The first byte arrives

The server sends back the response, which begins with the status line and headers (`200 OK`, `Content-Type` and so on). The moment the first byte of that response reaches the browser is the TTFB mark. The body follows, and the browser can start parsing HTML while the rest is still arriving.

## Adding it up

For a first visit over TCP with TLS 1.3, the network costs are:

| Step | Cost |
|---|---|
| DNS lookup | One lookup, or nothing if cached |
| TCP handshake | 1 round trip |
| TLS 1.3 handshake | 1 round trip |
| Request and response | 1 round trip plus server processing time |

That is about three round trips plus DNS and server time. With a 50 ms round trip, a 20 ms DNS lookup and 100 ms of server work, TTFB is about 270 ms. On a reused connection, the same request costs one round trip plus server time, or about 150 ms.

This arithmetic explains most of the standard advice:

- **Keep connections alive**, so that later requests skip the handshakes.
- **Use a CDN**, so that the round trips are short.
- **Add `preconnect` hints** for other origins the page will need, so that the handshakes happen early.
- **Make the server respond quickly**, because its processing time is added to every request.

You can see the steps for any request in the Timing tab of your browser's network panel, which lists DNS lookup, initial connection, SSL and waiting for server response separately.

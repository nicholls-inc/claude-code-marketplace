## How Git Stores a Commit

Open any repository's `.git` directory and you will find that Git is, at its core, a key-value store. You give it content, and it hands back a key. Everything you do with branches, merges and history is built on four ideas: blobs, trees, commits and refs.

### The object database

Git keeps its data in `.git/objects`. Each object is identified by a SHA-1 hash (newer repositories can use SHA-256) of its type, size and content. The object is compressed with zlib and stored in a file named after its hash. The first two hex characters become a subdirectory and the rest become the filename, so an object with hash `a1b2c3...` lives at `.git/objects/a1/b2c3...`.

Two consequences follow. Objects are immutable, because changing the content changes the hash and so creates a different object. And identical content is stored once, no matter how many files or commits contain it.

You can inspect any object with `git cat-file -p <hash>`, and `git cat-file -t <hash>` tells you its type. Over time Git packs loose objects into `.git/objects/pack` files and stores similar objects as deltas. This is only a space optimisation, and the model below is unchanged.

### Blobs: file contents

A blob holds the bytes of one file and nothing else. It has no filename, no permissions and no timestamp. If two files in your project have identical contents, they share one blob. If you edit one line of a 5,000-line file, Git stores a whole new blob for the new version. It does not store a diff at this level.

`git hash-object -w file.txt` writes a blob manually and prints its hash.

### Trees: directories

A tree is Git's representation of a directory. Each entry in a tree holds a mode, a type, a hash and a name:

```
100644 blob 3b18e51...  README.md
100755 blob 9f2c1a7...  build.sh
040000 tree 7d4e0b2...  src
```

The mode records whether the entry is a regular file (`100644`), an executable (`100755`), a symlink (`120000`) or a subdirectory (`040000`). Filenames live here, in the parent tree. Renaming a file therefore changes the tree but reuses the same blob.

Trees nest. The top-level tree points at blobs and at subtrees, which in turn point at more blobs and subtrees. Because each hash covers the content below it, the root tree's hash is a fingerprint of the entire project snapshot. If one file deep in the hierarchy changes, its blob, every tree on the path up to the root, and the root tree all get new hashes. Untouched subtrees keep their old hashes and are reused, which is why snapshots are cheap.

When you run `git add`, Git writes blobs for the staged files and records them in the index (`.git/index`). The index is a binary file that describes the tree you are about to commit.

### Commits: snapshots with history

A commit object ties a snapshot to its context. Run `git cat-file -p HEAD` and you will see something like:

```
tree 7d4e0b2c...
parent 5a91f3e8...
author Ada Lovelace <ada@example.com> 1731300000 +0000
committer Ada Lovelace <ada@example.com> 1731300000 +0000

Fix off-by-one in pagination
```

There are only a few fields. `tree` is the root tree of the snapshot. `parent` is the hash of the previous commit. A root commit has none, and a merge commit has two or more. `author` and `committer` carry a name, email, timestamp and timezone. The message follows a blank line.

The commit does not store a diff. When Git shows you "what changed", it compares the commit's tree with its parent's tree and computes the difference on demand.

The parent hash is included in the commit's own content, so each commit's hash depends on the entire history behind it. This forms a Merkle chain. You cannot alter an old commit without changing every descendant's hash, which is why rebasing and amending produce new commits rather than editing existing ones.

### Refs: human-readable names

Hashes are hard to remember, so Git uses refs, which are files that contain a hash. They live under `.git/refs`:

- `.git/refs/heads/main` is a branch. The file holds 40 hex characters, the hash of the latest commit on that branch.
- `.git/refs/tags/v1.0` is a tag. Lightweight tags point straight at a commit. Annotated tags point at a separate tag object, which stores a tagger, message and target.
- `.git/refs/remotes/origin/main` records where the remote's branch was at your last fetch.

A branch is therefore just a 41-byte file holding a hash. Creating a branch is nearly free. Committing moves the current branch's pointer forward to the new commit, and the new commit's parent is the old tip. Git also packs refs into `.git/packed-refs` for efficiency, and that file is consulted when no loose file exists.

### HEAD

`.git/HEAD` records what you currently have checked out. Normally it contains a symbolic reference such as `ref: refs/heads/main`. After `git commit`, Git follows that reference and updates the branch file. When you check out a specific commit, HEAD holds a raw hash instead. This is the "detached HEAD" state, and new commits made there are reachable only through HEAD until you create a branch.

### Putting it together

When you run `git commit -m "msg"`, Git does the following:

1. Reads the index and writes a tree object for each directory, from the bottom up, reusing any tree that already exists.
2. Creates a commit object containing the root tree's hash, the current HEAD commit as parent, your identity and the message.
3. Writes the new commit's hash into the branch file that HEAD points to.

That is the whole operation. Three small kinds of object and a text file are enough to give you cheap branching, reliable history and content-addressed integrity.

To explore, make a tiny repository and run `find .git/objects -type f`, then pass each hash to `git cat-file -p`. Following one commit down to its blobs makes the model concrete.

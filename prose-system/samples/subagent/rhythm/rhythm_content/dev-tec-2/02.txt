When you type an address such as https://example.com/docs into the address bar, the browser first parses it into a scheme, a host, an optional port and a path, and because the scheme is https it knows that port 443 is the default and that the connection must be encrypted before any HTTP is spoken. Before touching the network it consults several local sources, including an HSTS list that may force https even when you typed http, a cache of earlier responses that can let it skip the request entirely if a stored copy is still fresh, and sometimes a service worker registered by the site that can intercept the request and answer it from its own logic, so a good deal of what feels like network latency can be settled on your own machine in a few milliseconds.

If the request does have to go out, the browser needs an IP address for example.com, and it looks in its own DNS cache, then asks the operating system, which checks its cache and the hosts file and finally sends a query to a recursive resolver, usually run by your ISP or a public provider or set by your network. That resolver, if it does not already hold the answer, walks the hierarchy on your behalf by asking a root server which servers handle .com, asking those which servers are authoritative for example.com, and asking those for the A record (IPv4) and AAAA record (IPv6), each answer carrying a time to live that tells every cache along the path how long it may be reused. Modern browsers may send this query over an encrypted channel such as DNS over HTTPS, and may also ask for an HTTPS record that advertises, among other things, that the server supports HTTP/3. Because sites often sit behind a CDN, the address that comes back is frequently not the origin server but one of many edge machines chosen by DNS to be near the resolver that asked.

With an address in hand the browser opens a connection. For HTTP/1.1 and HTTP/2 that means TCP, which begins with a three-way handshake in which the client sends a SYN, the server replies with SYN-ACK and the client acknowledges, costing one round trip before either side can send data, while for HTTP/3 it means QUIC over UDP, which folds the transport and cryptographic handshakes together to save time. Assuming TCP, the TLS handshake follows, and in TLS 1.3 the client's first message, the ClientHello, lists the cipher suites it supports, includes a key share for an ephemeral Diffie-Hellman exchange, names the wanted host through the Server Name Indication extension so that a server hosting many sites knows which certificate to present, and offers application protocols through ALPN, such as h2 and http/1.1. The server answers with its own key share, which lets both sides derive the same session keys without ever sending them, then with its certificate chain, a signature proving it holds the private key that matches the certificate, and a Finished message, after which the client verifies, sends its own Finished and may transmit the first encrypted request. Verification is where much of the trust lives, because the browser checks that the certificate covers the requested hostname, that it has not expired, that its signature chains through intermediates to a root authority already trusted by the operating system or browser, and often that it has not been revoked or that it appears in public certificate transparency logs. A failure here produces the full-page warning you have seen, and nothing further is sent. Returning visitors can sometimes skip part of this through session resumption, and with 0-RTT can even send a request alongside the first flight, at the cost of weaker replay protection, which is why servers restrict it to safe requests.

Only now is the request itself written, and it is surprisingly small. In HTTP/1.1 it is plain text beginning with a line such as GET /docs HTTP/1.1 followed by headers like Host, Accept, Accept-Encoding, User-Agent and any cookies the browser holds for that domain, while in HTTP/2 and HTTP/3 the same information is carried as compressed binary header fields inside a stream, so that many requests can share one connection without waiting on each other. All of it travels inside TLS records that are split into TCP segments, wrapped in IP packets, framed for your Wi-Fi or Ethernet link and handed across a series of networks, each router looking only at the destination address and choosing a next hop from its routing table, until the packets reach the edge machine. TCP's slow start limits how much data the server may send in its first flight, which is one reason small initial responses are valuable.

On the server side the request is decrypted and may pass through several layers before application code sees it. A CDN edge checks its cache and answers immediately if it holds a fresh copy, and otherwise forwards the request over a long-lived connection to a load balancer, which picks a backend, which may be a reverse proxy such as nginx passing the request to an application process that routes /docs to a handler, perhaps queries a database, renders HTML and begins writing a response. The first byte the browser sees is the start of the status line or, in HTTP/2, of the HEADERS frame carrying the status code, and the time from starting the navigation to receiving that byte is what performance tools call time to first byte, a figure that bundles redirects, DNS lookup, connection setup, TLS negotiation, network travel and server processing into a single number. In the browser's Network panel you can see the individual contributions in the timing breakdown, and the practical lessons follow from it, for instance that long-lived connections and edge caching remove whole round trips, that a redirect from http to https or from a bare domain to www repeats much of the work above, and that a slow database query is only one of many places where the wait can accumulate.

# From HTTPS address to first byte

When you type https://example.com/articles/42 and press Enter, the browser must complete several network steps before it can show anything. Most of the delay comes from packets travelling between machines. This description follows one cold request, where nothing is cached, and notes where caching would skip work. The round-trip time (RTT) is how long a small packet takes to reach a server and return. On a typical connection it is 20 to 200 ms, and most of this process is measured in RTTs.

## 1. Parse the address and check local rules

The browser splits the URL into its parts: scheme (https), host (example.com), port (443 by default) and path (/articles/42). It then checks its HSTS list, which records sites that have asked to be reached only over HTTPS. If the host is listed and the address were plain http, the browser would switch it to https first. Here the scheme is already https, so the browser moves on.

## 2. Resolve the name with DNS

Computers connect to IP addresses, not names, so the host must be translated. The browser checks its own DNS cache, then the operating system's cache. On a miss, the operating system asks the configured recursive resolver, often run by your ISP or a public service. If that resolver has no cached answer, it walks the hierarchy. It asks a root server where .com is, asks a .com server where example.com is, and asks example.com's authoritative nameserver for the address. The answer is an A record (IPv4), possibly an AAAA record (IPv6), and each carries a TTL, the number of seconds caches may keep it. Modern browsers may also request an HTTPS (SVCB) record, which can advertise newer protocols such as HTTP/3.

A cold lookup can take several round trips to different servers. A warm one takes none.

## 3. Open a TCP connection

The browser sends a TCP SYN to the IP address on port 443. The server replies SYN-ACK, and the browser answers ACK. This three-way handshake costs one RTT, and no data can flow until it completes. If the name has both IPv4 and IPv6 addresses, browsers use "Happy Eyeballs": they start one attempt, give it a short head start, begin the other, and keep whichever connects first.

## 4. Negotiate TLS

TLS (Transport Layer Security) turns the TCP connection into an encrypted channel. With TLS 1.3, which most sites use, this costs one more RTT.

1. **ClientHello.** The client lists the TLS versions and cipher suites it supports, a random value, and a key share, which is its public key for an elliptic-curve Diffie-Hellman exchange. It also sends the Server Name Indication (SNI), the hostname in plain text, so a server hosting many sites knows which certificate to return. It sends ALPN, listing application protocols such as h2 (HTTP/2) and http/1.1.
2. **ServerHello.** The server picks a cipher and returns its own key share. Both sides now compute the same shared secret from the two key shares without sending it over the network. From here on, traffic is encrypted.
3. **Server identity.** The server sends its certificate chain (its certificate plus any intermediates). It then sends CertificateVerify, a signature over the handshake transcript made with the certificate's private key, which proves it controls the certificate. It finishes with a Finished message, a MAC that proves the handshake was not altered.
4. **Client validation.** The browser checks that the chain ends at a root authority in its trust store, that the certificate names example.com, that it is within its validity dates, and that it has not been revoked (via OCSP stapling or a revocation list). If a check fails, the browser shows a warning and stops.
5. **Client Finished.** The client sends its own Finished message. In TLS 1.3 it can place the HTTP request in the same flight, so the request goes out without waiting for another round trip.

TLS 1.2 needs two RTTs for this stage. Returning visitors can use session resumption or 0-RTT early data to shorten it further.

## 5. Send the HTTP request

The browser builds the request: a method, a path and headers. Typical headers include Host (or the :authority pseudo-header in HTTP/2), User-Agent, Accept, Accept-Encoding and Cookie, which carries the cookies stored for example.com. With HTTP/2 the request becomes binary frames on a stream, so many requests can share one connection. The frames are encrypted, split into TLS records and carried in TCP segments.

## 6. Server-side work

The packets usually reach an edge server, a CDN or load balancer, rather than the application itself. The edge often terminates TLS, so the handshake above ends there, and it may answer from its cache. On a miss, it forwards the request to the origin server over a new or pooled connection, which may need its own TCP and TLS setup. The web server hands the request to the application, which may query a database, run business logic and render HTML. The time between receiving the full request and producing the first byte of output is the server's processing time, sometimes called "think time".

## 7. Return the first byte

The server writes the status line (for example, HTTP/2 200) and the headers first. Those bytes travel back, taking half an RTT. The browser decrypts them, parses the status and headers, and decides what to do: render, follow a redirect or fetch sub-resources.

Time to first byte (TTFB) is the time from the start of the navigation until that first byte arrives. DevTools reports it as the "Waiting" phase in the Network panel.

## Putting numbers on it

Suppose the RTT is 100 ms, the DNS lookup misses the cache and costs 50 ms, and the server takes 150 ms to produce output. The rough sequence is:

- DNS: 50 ms
- TCP handshake: 100 ms
- TLS 1.3 handshake: 100 ms
- Request transit: 50 ms
- Server processing: 150 ms
- First byte returns: 50 ms

That is about 500 ms to first byte. Each part can be reduced. Keep connections alive and reuse them, serve content from a CDN close to users, use TLS 1.3 with HTTP/2 or HTTP/3, respect DNS TTLs, and remove unnecessary redirects. For a junior developer, the most useful habit is to read the Network panel's timing breakdown for a request and identify which of these phases dominates.

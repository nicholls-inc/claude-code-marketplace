When you type an HTTPS address into a browser and press enter, the browser first splits the address into its parts. In https://www.example.com/shop?item=4, the scheme is https, the host is www.example.com, and the rest is the path and query. The scheme tells the browser to use TLS-protected HTTP, and since no port is given it will use port 443. Before any network traffic, the browser checks a few local things. It looks in its HSTS list to see whether the site must always be reached over HTTPS, and it looks in its HTTP cache for a stored copy of the page that is still fresh. If it finds a fresh copy, no request is sent and the response comes straight from disk. Otherwise it goes on to the network.

The browser needs an IP address for the host, so it begins with DNS. It checks its own DNS cache first, then asks the operating system, which checks its cache and its hosts file. If neither has an answer, the request goes to a recursive resolver, usually run by the internet provider or a public service such as 1.1.1.1 or 8.8.8.8. The resolver may already have the answer cached for the number of seconds set by the record's time to live. If not, it works down the hierarchy, asking a root server which servers handle .com, then asking those which servers are responsible for example.com, and finally asking that domain's authoritative server for the address. The reply might be an A record with an IPv4 address such as 93.184.216.34, an AAAA record with an IPv6 address, or a CNAME that points to another name and has to be followed. Browsers usually ask for both A and AAAA records and will try the IPv6 address first if it is available. A lookup that hits the cache takes a millisecond or two, while a full walk from the root can take tens or hundreds of milliseconds.

With an address in hand, the browser opens a TCP connection to port 443. This uses a three-step handshake. The browser sends a SYN packet, the server answers with SYN-ACK, and the browser sends an ACK. One round trip passes before the browser can send data. If the server is 40 ms away, that handshake costs about 40 ms. Some modern setups use HTTP/3, which runs over QUIC on UDP instead of TCP, and this combines the transport and encryption set-up into fewer round trips. A browser learns that a site supports HTTP/3 from an Alt-Svc header sent on an earlier visit, so a first visit usually still uses TCP.

Next comes the TLS handshake, which sets up encryption and checks who the browser is talking to. In TLS 1.3 the browser sends a ClientHello that lists the cipher suites it supports, the protocols it can speak, and a key share for the key exchange. It also includes the server name, known as SNI, so that a server hosting many sites can pick the right certificate. The ALPN extension in the same message lists the application protocols it supports, such as h2 and http/1.1. The server replies with its choice of cipher suite, its own key share, and its certificate chain. Both sides can now work out the same session keys from the key shares, and everything after that point is encrypted. The browser checks the certificate before it trusts the connection. It confirms that the certificate covers www.example.com, that it has not expired, and that it chains up to a certificate authority that the browser or operating system already trusts. It may also check revocation status and the certificate transparency records. If any check fails, the browser shows a warning page and stops. TLS 1.3 needs one round trip after the TCP handshake, whereas TLS 1.2 needed two. If the browser has connected to the site before, it may be able to resume the earlier session and skip some of the work.

Now the browser can send the HTTP request itself. It writes a request line with the method, path and protocol, followed by headers. A typical request is GET /shop?item=4, with a Host header naming the site, a User-Agent, an Accept header listing the content types it can handle, an Accept-Encoding header listing compression such as gzip and br, and any cookies stored for that domain. If the connection negotiated h2, the same information is sent as binary frames and the headers are compressed with HPACK, but the content is equivalent. If the browser holds a stale cached copy, it adds an If-None-Match or If-Modified-Since header so the server can reply with a short 304 instead of the whole body.

The request travels across the internet as a series of packets. Each packet passes through a number of routers, often between 10 and 20, and each router forwards it toward the destination based on its IP address. Many sites sit behind a CDN or a load balancer. In that case the connection may have ended at a nearby edge server rather than the origin, and the edge either answers from its own cache or opens a second connection to the origin on the browser's behalf. A reverse proxy such as nginx may also sit in front of the application and pass the request to a process running the site's code.

The application receives the request, reads the path, query and cookies, and does whatever work is needed. This might include checking a session, querying a database, or rendering a template. When it has a result, it sends back a status line such as HTTP/1.1 200 OK, then headers including Content-Type, Content-Length or a chunked transfer encoding, Cache-Control and any Set-Cookie lines, then a blank line, then the body. The server's work to produce this is the largest variable in the whole sequence. A cached page might take a millisecond, and a slow database query can take seconds.

The moment the first byte of that response reaches the browser is called time to first byte, or TTFB. It is the sum of everything above: DNS lookup, TCP connect, TLS handshake, the request's trip to the server, the server's processing time, and the first byte's trip back. For a user on a decent connection reaching a nearby server with warm caches, this is often under 100 ms. For a first visit to a distant server it can be several hundred. The browser's developer tools show each stage separately in the Network panel's timing tab, which is a useful place for a developer to see where the time went.

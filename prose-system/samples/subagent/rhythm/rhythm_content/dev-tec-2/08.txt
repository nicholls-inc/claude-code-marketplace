Before anything goes over the network, the browser parses the address into a scheme, a host, an optional port and a path, and checks whether it already knows enough to skip some of the work. It consults its HSTS list, which records hosts that must only be reached over HTTPS, and it checks any service worker registered for the origin, since a service worker can answer the request itself from a cache. It also checks the HTTP cache, where a stored response that is still fresh according to its Cache-Control headers is used with no network traffic at all. Only when none of these produces an answer does the browser need to find a server, and the first thing it needs for that is an IP address.

Name resolution proceeds through a series of caches, each consulted before the next, beginning with the browser's own, then the operating system's resolver cache and the hosts file, and then the recursive resolver configured for the machine, which is usually run by the ISP, the company or a public provider and may answer from its cache. When it cannot, the recursive resolver works down the hierarchy by asking a root server which servers handle the top-level domain, asking those which servers are authoritative for the domain, and finally asking the authoritative server for the address records, with every answer carrying a time to live that tells each cache how long it may be reused. Modern browsers often ask for A and AAAA records together so they can use IPv6 when it is available, and they may also request an HTTPS record, which can advertise that the site supports HTTP/3 and can supply connection hints before any connection exists. Queries to the resolver travel over plain UDP by default, though many browsers are configured to use DNS over HTTPS, which wraps them in an encrypted connection to a resolver the browser trusts.

With one or more addresses in hand, the browser opens a connection, first checking whether it already holds an idle one to the same origin, because reusing an existing HTTP/2 connection skips everything that follows in this paragraph and the next. For a new connection over TCP, the browser sends a SYN packet, the server answers with a SYN-ACK, and the browser acknowledges, so one full round trip passes before either side can send application data. When both IPv4 and IPv6 addresses are available the browser typically races them, starting the second attempt a few hundred milliseconds after the first (the approach is called Happy Eyeballs), so that a broken path to one family does not stall the page. Routers along the way forward these packets hop by hop using their routing tables, and for popular sites the address often points to an anycast edge location of a CDN, so the physically nearest data center terminates the connection.

TLS begins once the transport is up. In TLS 1.3 the browser sends a ClientHello that lists the cipher suites it supports, includes a key share for a Diffie-Hellman exchange (typically X25519, often combined with a post-quantum component in current browsers), and carries the Server Name Indication extension containing the hostname, which lets a server hosting many sites choose the correct certificate before encryption has started. The ClientHello also lists the application protocols the browser can speak through ALPN, usually h2 and http/1.1. The server replies with its own key share, which gives both sides enough to derive shared secrets, and from that point the rest of its handshake is encrypted, including its certificate chain and a signature proving it holds the private key matching the certificate. The browser validates that chain by checking that each certificate is signed by the one above it up to a root authority in its trust store, that the dates are valid, that the hostname appears in the certificate's subject alternative names, and, depending on the browser, that the certificate has not been revoked or is accompanied by Certificate Transparency proofs. Both sides then exchange Finished messages that authenticate the whole transcript, and the browser can send its request in the same flight as its own Finished message, which means TLS 1.3 costs one round trip where TLS 1.2 cost two. If the browser has connected to this server before, it may hold a session ticket that allows resumption and even early data sent in the very first flight, at the price of weaker replay protection for those early bytes.

If the HTTPS record or an Alt-Svc header from an earlier visit told the browser that the server supports HTTP/3, it may instead use QUIC, which runs over UDP and folds the transport and cryptographic handshakes into a single exchange, so a fresh connection needs one round trip in total, with TLS 1.3 built into the protocol rather than layered on top of it. Browsers commonly race QUIC against TCP and keep whichever completes first, falling back to TCP when middleboxes drop UDP.

The request itself is then sent as a set of headers and, for a simple page load, no body. These include the method (GET), the path, the authority, the user agent, the accept and accept-encoding headers that let the server pick a format and a compression scheme, and any cookies the browser has stored for that domain and path, plus conditional headers such as If-None-Match when it holds a stale cached copy it would like to revalidate. In HTTP/2 and HTTP/3 these are serialized into compressed binary frames on a numbered stream with HPACK or QPACK, so repeated headers cost almost nothing on later requests over the same connection, and in HTTP/1.1 they are plain text lines ending in a blank line.

On the server side the request typically meets a load balancer or reverse proxy first, which terminates TLS if the CDN edge has not already done so, applies routing rules, and either answers from its own cache or forwards the request over a pooled connection to an application server. That server may authenticate the cookie against a session store, query a database, render a template or call other services, and the shape of that work determines how long the browser waits between sending its last request byte and receiving the first byte of the reply. That wait, plus all the network round trips accumulated before it, is what developer tools report as time to first byte. It begins counting at the start of navigation in the Navigation Timing API and in the Network panel's timing breakdown shows up as the gap between the stalled, DNS lookup, initial connection and SSL phases and the waiting phase that precedes content download. The first byte arrives as the beginning of the response headers, starting with the status line or its HTTP/2 equivalent, and at that moment the browser knows the status code, can begin following redirects or reading the content type, and can start parsing the body as it streams in.

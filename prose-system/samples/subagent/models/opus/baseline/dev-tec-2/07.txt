From HTTPS Address to First Byte: What the Browser Actually Does

When you type https://shop.example.com/products into the address bar and press Enter, the page can appear in a fraction of a second. In that time the browser carries out a series of separate steps, and each one can add delay. Knowing these steps helps you read the waterfall in DevTools, debug slow pages, and understand why some performance advice exists. This description covers everything up to the moment the first byte of the server's response reaches the browser, a moment usually called time to first byte (TTFB).

1. Parsing the URL and checking local shortcuts

First, the browser decides whether your input is a URL or a search query. Once it treats it as a URL, it splits it into parts: the scheme (https), the host (shop.example.com), the port (443 by default for HTTPS), the path (/products), plus any query string or fragment. The fragment, the part after #, is never sent to the server.

Before it touches the network, the browser checks a few local sources:

- HSTS. If the site has sent a Strict-Transport-Security header before, or is on the browser's built-in preload list, the browser will only use HTTPS for it. A plain http:// link is upgraded internally, and the insecure request is never sent.
- Service workers. If a service worker is registered for this origin, it can intercept the request and answer it from its own cache. In that case nothing goes over the network.
- HTTP cache. If a fresh copy of the resource is cached (according to its Cache-Control headers), the browser can use it straight away. For a top-level page this is less common, but it does happen.

If none of these supplies a response, the browser has to reach the server.

2. Reusing an existing connection

Opening a new secure connection is expensive, so the browser first checks whether it already has one open to this origin. With HTTP/2 and HTTP/3, a single connection can carry many requests at the same time. If the browser finds a usable connection, it skips steps 3 to 5 entirely. This is a main reason why repeat navigations within a site are faster than the first visit, and why hints like <link rel="preconnect"> help: they open the connection early.

3. DNS resolution: turning a name into an IP address

Computers connect to IP addresses, not names, so the browser has to resolve shop.example.com. It checks its own DNS cache, then asks the operating system, which checks its own cache and the hosts file. If neither has the answer, the query goes to a recursive resolver, usually run by your ISP, your company, or a public service such as 1.1.1.1 or 8.8.8.8. Some browsers send this query encrypted, using DNS over HTTPS.

If the recursive resolver does not have the answer cached, it walks the DNS hierarchy. It asks a root server where .com is handled, asks the .com servers where example.com is handled, and finally asks example.com's authoritative name servers for the record. The result is an A record (IPv4) and/or an AAAA record (IPv6). Each record has a TTL (time to live) that controls how long it may be cached. Modern browsers may also request an HTTPS record, which can advertise that the server supports HTTP/3. This lets the browser choose a protocol before it connects.

A cold DNS lookup can take anywhere from a few milliseconds to several hundred. In DevTools it appears as the "DNS Lookup" segment.

4. Establishing a transport connection

With an IP address, the browser opens a connection to port 443.

For HTTP/1.1 and HTTP/2, the connection uses TCP. TCP starts with a three-way handshake. The client sends SYN, the server replies with SYN-ACK, and the client sends ACK. This takes one full round trip (RTT) between your machine and the server. If the server is 100 ms away, that is 100 ms spent before any useful data moves. This is why CDNs, which place servers close to users, help so much.

For HTTP/3, the browser uses QUIC, which runs over UDP. QUIC combines the transport handshake and the encryption handshake into one exchange, which saves a round trip.

5. The TLS handshake: making the connection secure

The "S" in HTTPS is TLS (Transport Layer Security). Before any HTTP data is sent, client and server must agree on encryption keys, and the client must confirm that it is talking to the real shop.example.com. With TLS 1.3, the current standard, this goes as follows:

1. ClientHello. The browser sends the cipher suites it supports, a key share for the key exchange (usually elliptic-curve Diffie-Hellman), and two important extensions. SNI (Server Name Indication) names the host it wants, so one IP address can serve many sites with different certificates. ALPN (Application-Layer Protocol Negotiation) lists the HTTP versions it supports, such as h2 and http/1.1.
2. ServerHello and the rest of the server's reply. The server picks a cipher suite, sends its own key share, and chooses a protocol from the ALPN list. From this point both sides can compute the shared secret, so everything after it is encrypted. The server then sends its certificate chain, a signature proving it holds the certificate's private key (CertificateVerify), and a Finished message.
3. Certificate validation. The browser checks that the certificate covers shop.example.com, has not expired, and chains up to a root certificate authority the browser or operating system trusts. It may also check revocation status and Certificate Transparency.
4. Client Finished. The browser sends its own Finished message, and the secure channel is ready.

TLS 1.3 needs one round trip for a full handshake. TLS 1.2 needed two. If the browser has connected to this server recently, it can resume the session, and in some cases send request data in its very first flight ("0-RTT"). Certificate problems are the classic cause of browser security warnings; they show up as errors such as NET::ERR_CERT_DATE_INVALID.

6. Sending the HTTP request

Now the browser sends the actual request, encrypted inside TLS. Conceptually it looks like this:

GET /products HTTP/2
Host: shop.example.com
User-Agent: ...
Accept: text/html,...
Accept-Encoding: gzip, br
Cookie: session=...

With HTTP/2 and HTTP/3, these headers are compressed (HPACK or QPACK) and sent as binary frames on a numbered stream rather than as plain text lines, but the meaning is the same. The cookies sent are the ones the browser holds for this domain and path, filtered by attributes such as Secure and SameSite.

7. Server processing and the first byte

The request may pass through several layers before reaching your code: a CDN edge, a load balancer, a reverse proxy such as nginx, and then your application server. Any of them may answer from a cache. Otherwise your application runs: it routes the request, checks the session, queries databases, calls other services, and renders HTML. For a dynamic page, this is usually the largest part of TTFB, and it is the part you control most directly as a developer.

When the server starts writing its response (status line, headers, then body), those bytes travel back over the encrypted connection. The browser decrypts the first chunk, and that moment is the first byte. Servers that stream their output, sending the <head> before the whole page is ready, can make this happen much sooner.

Putting it together

On a first visit over TCP and TLS 1.3, the minimum cost before the server even sees your request is roughly: DNS lookup + 1 RTT (TCP) + 1 RTT (TLS) + half an RTT to deliver the request. Server processing time and another half RTT for the response then follow. Open the Network tab in DevTools, click a request, and look at the Timing panel. You will see these phases as Queueing, DNS Lookup, Initial connection, SSL, Request sent, and "Waiting for server response". With the model above, you can tell which phase is slow and which fix fits: a CDN for distance, preconnect for setup cost, connection reuse for repeat requests, or backend work for slow processing.

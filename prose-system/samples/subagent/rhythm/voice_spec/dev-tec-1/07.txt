Git keeps everything it records in a directory called .git at the top of your working tree. Inside it, the folder named objects holds a simple key-value store. Each entry is a file whose name is the SHA-1 hash of its contents, and the hash is split so that the first two hex characters become a subdirectory and the remaining thirty-eight become the file name. An object with the hash e69de29bb2d1d6434b8b29ae775ad8c2e48c5391 therefore lives at .git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391. Every file is compressed with zlib, and once written it is never changed. If the content changes, the hash changes, and Git writes a new object next to the old one. Recent versions of Git are moving towards SHA-256, but the mechanism is the same.

There are four kinds of object, and a commit is built from three of them. The first is the blob, which holds the bytes of one file and nothing else. A blob has no file name, no permissions and no timestamp. It is stored with a short header giving its type and its size in bytes, so a ten-byte file becomes the header "blob 10", a null byte, and then the ten bytes. Two files with identical contents, wherever they sit in the project, share a single blob. The same applies to a file that does not change between commits, which is why a repository with a long history does not grow by a full copy of the project each time.

Names and permissions live in the second kind of object, the tree. A tree represents one directory. It is a list of entries, and each entry has a file mode, a name and the hash of the object it points to. The mode is 100644 for an ordinary file, 100755 for an executable, 120000 for a symbolic link and 040000 for a subdirectory. An entry for a file points to a blob, and an entry for a subdirectory points to another tree. A project with a src folder therefore has a root tree whose entry named src leads to a second tree, and that tree lists the files inside src. The hash of a tree depends on the hashes of everything beneath it, so a change to one file alters its blob, the tree around it, and every tree above that up to the root. You can see this with git cat-file -p followed by a hash, which prints the entries of a tree in readable form.

The third kind is the commit object, which is small and entirely text. It contains the hash of one root tree, which is the complete snapshot of the project at that moment. It then lists the hashes of its parent commits, with none for the first commit in a repository, one for an ordinary commit and two for a merge. After that come the author and the committer, each with a name, an email address, a Unix timestamp and a timezone offset, followed by a blank line and the commit message. A typical commit is only a few hundred bytes. Git does not store a diff in it. When you run git show or git diff, Git works the difference out by comparing the trees of the commit and its parent. The parent hashes are what form the history, since each commit names the one before it, and because each hash covers the parents' hashes as well, changing an old commit would change the hash of every commit after it. This is why rewriting history, as git rebase does, produces new commits and leaves the old ones in place until they are cleaned up.

The fourth kind is the annotated tag, which wraps a pointer to another object with a name, a message and an optional signature. It plays no part in an ordinary commit, so it needs no more than this mention.

Commit hashes are long and awkward to read, so Git also keeps refs, which are human-readable names for them. A ref is a plain text file holding one hash. Your branches sit in .git/refs/heads, so the branch main is the file .git/refs/heads/main, and its contents are the forty-character hash of the newest commit on that branch. Tags are in .git/refs/tags and remote-tracking branches are in .git/refs/remotes. Making a new branch writes a forty-one byte file, which is the hash plus a newline, and this is why branching in Git is so cheap. When you commit, Git writes the new blob, tree and commit objects, then overwrites the branch file with the hash of the new commit. A long-lived repository may pack many refs into a single file called packed-refs, and it packs many objects into compressed packfiles that store similar objects as deltas, but the model is unchanged.

The remaining piece is HEAD, a file directly inside .git that says where you are. Usually it contains a line such as ref: refs/heads/main, which means the current branch is main and that the next commit should advance that file. If you check out a specific commit, HEAD holds a bare hash instead, which is the detached state Git warns about. Taken together, a commit is a chain. HEAD names a branch, the branch names a commit, the commit names a tree and its parents, and the tree names the blobs and subtrees that hold your files.

Inside every repository is a directory called .git, and most of what it holds is a simple key-value store. Git takes a piece of content, works out a SHA-1 hash of it, and saves it in a file named after that hash. The first two characters of the 40-character hash become a subdirectory of .git/objects and the remaining 38 become the file name, so an object with the hash 3b18e512dba79e4c8300dd08aeb37f8e728b8dad lives at .git/objects/3b/18e512dba79e4c8300dd08aeb37f8e728b8dad. Each file holds the content compressed with zlib, preceded by a short header giving the object's type and its size in bytes. There are four types of object, and a commit uses three of them: blobs, trees and commits. The fourth, the annotated tag, is not needed here.

A blob holds the contents of one file and nothing else. It has no file name, no permissions and no timestamp. Because the hash is computed from the content alone, two files with the same bytes produce the same blob, whatever they are called and wherever they sit in the project. If you copy a 5 MB file into three directories, Git stores one blob. If you change one line in that file, Git stores a second complete blob for the new version and leaves the old one in place.

Names and permissions are kept in trees. A tree represents one directory. Each line in it has a file mode, a name and the hash of what it points to. The mode is 100644 for an ordinary file, 100755 for an executable, 120000 for a symbolic link and 040000 for a subdirectory. An entry for a file points to a blob and an entry for a subdirectory points to another tree, so the root directory of the project becomes a tree of trees with blobs at the leaves. The hash of a tree is computed from its list of entries, which means it depends on the hashes of everything below it. When you change one file in src/lib/, the blob for that file changes, so the tree for src/lib/ changes, so the tree for src/ changes, and so does the root tree. Every other tree and blob is untouched and is reused as it is. This is why a commit in a large repository stays small: only the path from the changed file up to the root needs new objects.

A commit object is a short text record. It names one tree, which is the root directory of the project as it stood at that moment, so it is a complete snapshot and not a set of changes. It then lists the hash of each parent commit, with one parent for an ordinary commit, none for the first commit in a repository and two for a merge. After the parents come the author and the committer, each with a name, an email address, a Unix timestamp and a time zone offset, and then a blank line and the message you wrote. The author and committer lines differ after a rebase, or when someone applies your patch, because one records who wrote the change and the other records who last recorded it. Since the parent hash is part of the commit's content, it is part of the commit's own hash. Changing any earlier commit therefore produces a different hash for it and for every commit after it. This is what a rebase does. It writes new commits, and the old ones remain in the object store until Git removes them during garbage collection. Diffs are worked out when you ask for them, by comparing the trees of two commits.

Commits and trees have no memorable names, and a ref supplies one. A ref is a file whose entire content is a hash. The branch main is the file .git/refs/heads/main, which holds the 40 characters of the commit at the tip of that branch, followed by a newline. Creating a branch writes one new 41-byte file, which is why branches cost almost nothing. Tags sit in .git/refs/tags and remote-tracking branches in .git/refs/remotes. Git sometimes gathers many refs into a single file named .git/packed-refs, and it reads that file when a loose ref file is absent. HEAD is a ref of a different kind. It normally contains the text ref: refs/heads/main, naming the branch you have checked out, and it holds a bare hash only when you are in the detached HEAD state.

With these pieces, the making of a commit is easy to follow. Running git add compresses each changed file into a blob and records its hash and path in .git/index, the staging area. Running git commit turns the index into trees, writes a commit object that names the root tree and the current HEAD commit as its parent, and then updates the branch file that HEAD points to so that it contains the new commit's hash. Updating that one file is the step that moves the branch forward. The earlier commit is still there, and the reflog in .git/logs keeps a record of where each ref has pointed, which is how a commit that seems lost can usually be found again.

Loose objects are convenient but wasteful when there are thousands of them. Periodically, and when you push or fetch, Git packs them into a single file under .git/objects/pack, where similar objects are stored as deltas against one another. That changes how the data is laid out on disk and leaves the model unchanged. You can see it for yourself with git cat-file -p followed by a hash or a ref name, which prints a commit, a tree or a blob in readable form and lets you walk from main down to a single line of a single file.

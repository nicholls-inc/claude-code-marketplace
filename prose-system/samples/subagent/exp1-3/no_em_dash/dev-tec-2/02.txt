From HTTPS Address to First Byte: What the Browser Does

When you type https://www.example.com/products into a browser and press Enter, a lot of work happens before the first byte of the response reaches you. This is usually measured as Time To First Byte (TTFB). Understanding each stage helps you debug slow pages and make sense of the Network tab in your developer tools.

1. Parsing the URL

The browser first splits the address into parts. The scheme is "https", the host is "www.example.com", the path is "/products", and the port is implied. HTTPS defaults to port 443, so you only see a port in the URL when it is something unusual.

Before touching the network, the browser applies a few local rules. It checks whether the host is on an HSTS (HTTP Strict Transport Security) list, which forces HTTPS for that site. It also checks whether it already has a usable cached response. A fresh cache entry can end the whole process right here, with no network traffic at all. Service workers, if the site registered one, get a chance to intercept the request too.

2. DNS Lookup

Networks route traffic using IP addresses, not names, so the browser must translate "www.example.com" into something like 93.184.216.34 (or an IPv6 address). This is DNS resolution.

The browser checks several caches in order: its own, then the operating system's, then it asks a recursive resolver, usually run by your ISP or a public provider. If the resolver has no cached answer, it walks the hierarchy. It asks a root server which servers handle ".com", asks those which servers handle "example.com", and finally asks the authoritative server for the actual record. Each answer comes with a TTL (time to live) that says how long it may be cached.

A cold lookup can take tens or hundreds of milliseconds. A cached one takes almost nothing. Modern browsers may also query for newer HTTPS or SVCB records, which can advertise support for HTTP/3.

3. Opening a TCP Connection

With an IP address, the browser opens a connection to port 443. For HTTP/1.1 and HTTP/2 this uses TCP, which provides reliable, ordered delivery. TCP begins with a three-step handshake:

1. The client sends SYN ("I want to connect").
2. The server replies SYN-ACK ("OK, I'm ready").
3. The client sends ACK ("Great, connected").

This costs one full round trip before any application data can flow. If the server is far away, that round trip time (RTT) is the dominant cost. A server 100 ms away means 100 ms spent just on this step.

HTTP/3 is different. It runs over QUIC, which uses UDP and combines the transport and encryption handshakes, saving round trips. A browser typically learns that a site supports HTTP/3 from a previous visit or from DNS, and otherwise starts with TCP.

4. The TLS Handshake

The "S" in HTTPS means the connection is encrypted using TLS (Transport Layer Security). Before sending your request, the browser and server must agree on how to secure the channel and prove the server is who it claims to be.

In TLS 1.3, which most modern sites use, the flow looks like this:

- ClientHello: The browser sends the TLS versions and cipher suites it supports, a random value, a key share for the key exchange, and the Server Name Indication (SNI), which tells the server which hostname is wanted. SNI matters because one IP address often hosts many sites. The browser also advertises supported application protocols (ALPN), such as h2 and http/1.1.
- ServerHello: The server picks a cipher suite and protocol, and sends its own key share. From here, both sides can compute the same shared secret without ever sending it over the wire. Everything after this point is encrypted.
- Certificate: The server sends its certificate chain, which contains its public key and is signed by a certificate authority (CA). The server also proves it holds the matching private key.
- Finished: Both sides confirm the handshake was not tampered with.

The browser validates the certificate. It checks that the signature chain leads to a CA the operating system or browser trusts, that the certificate has not expired, and that the hostname matches one listed in the certificate. It may also check revocation status. If any check fails, you see the familiar full-page warning instead of the site.

TLS 1.3 needs one round trip for a fresh connection. TLS 1.2 needs two. If you have connected to this server recently, session resumption can shorten this further, and TLS 1.3 even allows sending early data in some cases.

5. Sending the HTTP Request

Now the browser can finally send the actual request, through the encrypted channel. In HTTP/1.1 it is plain text:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

In HTTP/2 and HTTP/3 the same information is sent in a compressed binary format, but the meaning is identical: a method, a path, and headers. Notice that cookies for this domain are attached automatically, along with headers describing what content and compression the browser can handle.

6. Server-Side Work

The request travels to the destination, but it often does not hit your application directly. A typical path goes through a CDN edge node, a load balancer, or a reverse proxy such as Nginx. These may answer from their own cache, or forward the request to an origin server.

If it reaches your application, the server routes the request to the right handler, checks authentication from the cookie, queries databases or other services, and renders HTML or JSON. Slow queries, cold caches, and server-side rendering all add time here. For many dynamic sites, this stage is the largest part of TTFB, and it is the part you control most directly as a developer.

7. The First Byte Arrives

Once the server has something to send, it writes the response status line and headers, followed by the body. For example:

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: br

When the first of these bytes reaches the browser, the clock for TTFB stops. Everything up to this point has been waiting. After this, the browser starts parsing HTML and requesting other resources like CSS, scripts, and images.

Redirects add to the total

If the server responds with a redirect (such as 301 from http:// to https://, or from a bare domain to www), the browser repeats much of this process for the new URL. Each redirect can cost a new DNS lookup, connection, and handshake, though connection reuse softens this when the host is the same.

Putting It Together

Roughly, TTFB is the sum of:

- Redirects and cache checks
- DNS lookup
- TCP connection (one round trip)
- TLS handshake (one or two round trips)
- Request travel time and server processing
- Response travel time for the first byte

You can see these phases in your browser's developer tools. In the Network tab, select a request and open the Timing view. It shows labels such as DNS Lookup, Initial connection, SSL, Waiting for server response (the TTFB portion), and Content Download.

Practical Takeaways

- Reuse connections. HTTP keep-alive and HTTP/2 multiplexing avoid repeating the TCP and TLS setup for every request.
- Use a CDN. Placing content nearer to users shrinks every round trip.
- Cache aggressively. Correct Cache-Control headers can skip the network entirely.
- Keep server work fast. Optimise slow queries and consider caching rendered output.
- Avoid redirect chains. Link directly to the final HTTPS URL.
- Enable HSTS and modern protocols. TLS 1.3 and HTTP/3 reduce handshake cost.

Once you can picture these steps, a slow first byte becomes a diagnosis problem rather than a mystery: ask which of the phases is taking the time, then fix that one.

How Git Stores a Commit

Underneath its commands, Git is a key-value store. You give it some content and it gives back a key: the SHA-1 hash of that content. New repositories can use SHA-256 instead, but the idea is the same. Everything Git keeps lives in `.git/objects` as one of four object types. Three of them make up a commit: blobs, trees and commit objects. The fourth, the annotated tag, comes up at the end. Branches and HEAD are not objects. They are refs, small files that point into the object store.

**How an object is stored**

Each object is written in the same format. Git takes a header made of the type, a space, the content length in bytes and a null byte, for example `blob 12\0`. It appends the content and hashes the result. The hash is the object's ID. Git then compresses the header and content with zlib and writes them to `.git/objects/`. The first two hex characters of the hash name a subdirectory and the remaining 38 name the file. An object with hash `e69de29b...` is stored at `.git/objects/e6/9de29b...`.

The key comes from the content, so identical content always gets the same ID and is stored only once. It also means no object can change: alter one byte and you have a different object with a different name. Git calls this content-addressable storage, and the rest of the design depends on it.

You can inspect any object with `git cat-file -t <hash>` to see its type and `git cat-file -p <hash>` to print its contents.

**Blobs**

A blob holds the contents of a file and nothing else. It has no filename, no permissions and no timestamp. If two files in different directories have the same bytes, they share one blob. If you rename a file without editing it, Git writes no new blob. The existing one is just referenced under a new name.

**Trees**

A tree stands for one directory. It is a sorted list of entries, and each entry has three parts:

- a mode: `100644` for a normal file, `100755` for an executable, `120000` for a symlink, `040000` for a subdirectory and `160000` for a submodule commit
- a name
- the hash of the object the entry points to: a blob for a file, another tree for a subdirectory

Running `git cat-file -p` on a tree prints something like this:

```
100644 blob a1b2c3...    README.md
040000 tree d4e5f6...    src
```

This is where filenames and permissions are stored. A tree's hash covers the hashes of everything below it, so one root tree hash identifies an entire snapshot of the project. If one file deep in `src/` changes, Git writes a new blob for it, a new tree for each directory on the path up to the root, and a new root tree. Every other subtree keeps its old hash and is reused. That reuse is why committing a large repository stays cheap even though every commit records a full snapshot rather than a diff.

**Commit objects**

A commit object is a short block of text. Running `git cat-file -p HEAD` shows something like:

```
tree 9f8e7d...
parent 1a2b3c...
author Ada Lovelace <ada@example.com> 1731340800 +0000
committer Ada Lovelace <ada@example.com> 1731340800 +0000

Fix off-by-one in pagination
```

- **tree** is the root tree, meaning the full snapshot of the project at this commit.
- **parent** is the hash of the previous commit. The first commit in a repository has no parent line. A merge commit has two or more.
- **author** and **committer** each carry a name, an email, a Unix timestamp and a timezone offset. The author wrote the change and the committer recorded it. The two differ after a rebase or a cherry-pick, or when someone applies another person's patch.
- A blank line separates these headers from the commit message. Signed commits also include a `gpgsig` header.

The parent hash is part of the content being hashed, so each commit's ID depends on its parent's ID, which depends on that commit's parent, and so on back to the first commit. Changing anything in the past changes every commit after it. This is why rebasing produces new commits with new IDs instead of editing the old ones, and why a single commit hash vouches for the whole history leading up to it.

**Refs**

A 40-character hash is hard to remember, so Git uses refs. A branch is a file such as `.git/refs/heads/main` that holds one commit hash and a newline. When you commit on `main`, Git writes the new commit object and then overwrites that file with the new hash. Creating a branch means writing a 41-byte file, which is why it is instant.

`HEAD`, stored at `.git/HEAD`, usually holds a symbolic reference rather than a hash:

```
ref: refs/heads/main
```

That line tells Git which branch you are on. When you check out a specific commit, HEAD holds that raw hash instead. Git calls this "detached HEAD": new commits will not move any branch forward.

Tags live under `refs/tags/`. A lightweight tag is just a ref that points at a commit. An annotated tag points at a tag object, the fourth object type, which records the tagger, a date, a message and optionally a signature.

**What `git commit` does**

When you run `git commit`, Git:

1. Writes a blob for every staged file whose content it does not already have. Usually `git add` has already done this.
2. Builds tree objects from the index, from the deepest directories up to the root.
3. Writes a commit object that points to the root tree and to the commit HEAD currently resolves to.
4. Updates the current branch ref to the new commit's hash.

**Packfiles**

Over time Git compresses loose objects into packfiles in `.git/objects/pack/`, and it stores similar objects as deltas against each other there. Branch refs can also be gathered into a single `.git/packed-refs` file. These are storage optimisations only. Git still treats every object as a complete snapshot with a fixed hash, and treats every ref as a name that points at one of those hashes.

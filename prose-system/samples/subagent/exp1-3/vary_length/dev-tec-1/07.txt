Git stores everything in a directory called .git, and at its heart that directory is a key-value database. You hand it content, it hands back a key, and later you use the key to get the content back. Commits, branches and tags are all built from this one idea.

**Objects and hashes**

The keys are SHA-1 hashes (newer repositories can use SHA-256). Git computes the hash from the content itself, prefixed with a short header giving the object's type and size. Identical content always produces the same hash, so Git never stores the same thing twice. Change one byte and you get a different object entirely.

Each object is compressed with zlib and written to .git/objects. The first two hex characters of the hash become a subdirectory name, and the remaining thirty-eight become the filename. An object with hash `a94a8fe5...` lives at `.git/objects/a9/4a8fe5...`. Over time, Git packs many loose objects into compact packfiles, but the model stays the same.

There are four object types. Three matter here.

**Blobs**

A blob holds the contents of one file. Nothing else. It has no filename, no permissions, no timestamp. If you have two files with identical contents in different directories, they share a single blob.

You can see this directly. Run `echo "hello" | git hash-object -w --stdin` and Git writes a blob and prints its hash. Then `git cat-file -p <hash>` prints the content back.

This surprises many people. Git doesn't track files as named things. It tracks content, and names live elsewhere.

**Trees**

Names live in trees. A tree object represents one directory. It is a list of entries, and each entry has a mode, a type, a hash and a name. The mode records whether the entry is a regular file, an executable, a symlink or a subdirectory. The hash points either to a blob (for a file) or to another tree (for a subdirectory).

Run `git cat-file -p HEAD^{tree}` in any repository and you'll see something like this:

```
100644 blob 3b18e51...  README.md
040000 tree 9c2f7d0...  src
100755 blob f1a02bc...  build.sh
```

Follow the `src` hash and you get another tree, listing the contents of that directory. The root tree thus describes your entire project at one moment, recursively. Because a tree's hash depends on the hashes of everything beneath it, changing one deeply nested file changes every tree on the path up to the root. Unchanged siblings keep their old hashes and are reused as-is. That is why a commit in a huge repository costs almost nothing in storage.

**Commits**

A commit object is small and plain. It contains a pointer to a root tree, zero or more parent commits, an author, a committer, and a message. Try `git cat-file -p HEAD`:

```
tree 9c2f7d0e...
parent 4be81a3c...
author Ada <ada@example.com> 1731300000 +0000
committer Ada <ada@example.com> 1731300000 +0000

Fix off-by-one in pager
```

Note what is absent: no diff. Git doesn't store changes. A commit is a full snapshot, referenced through its tree. When you run `git show` or `git diff`, Git works out the differences on demand by comparing two trees. Storage stays efficient because unchanged blobs and trees are shared between snapshots, and packfiles additionally delta-compress similar objects.

The parent line is what makes history. Each commit names the commit that came before it, and a merge commit names two or more. Since the parent's hash is part of this commit's content, and therefore part of its own hash, history is tamper-evident. You cannot alter an old commit without changing the hash of every commit after it. This is also why rebasing creates new commits rather than editing old ones: different parents mean different hashes.

**Refs**

Hashes are unfriendly to humans. Refs give them names.

A ref is just a file containing a hash. Look in `.git/refs/heads/` and you'll find one file per local branch. Open `.git/refs/heads/main` and you'll see forty hex characters, the hash of the newest commit on that branch. That's all a branch is. Creating one is writing 41 bytes to a file, which is why it's instantaneous. Making a commit moves the current branch's file forward to the new commit's hash.

Tags live under `.git/refs/tags/`, and remote-tracking branches such as `origin/main` live under `.git/refs/remotes/`. Occasionally Git consolidates these into a single `.git/packed-refs` file, but the meaning is unchanged.

**HEAD**

One more file completes the picture: `.git/HEAD`. Normally it holds a symbolic reference, something like `ref: refs/heads/main`. It says which branch you currently have checked out. When you commit, Git reads HEAD, finds the branch, and updates that branch's file. If you check out a specific commit instead of a branch, HEAD contains a raw hash directly. That is the "detached HEAD" state, and it is less mysterious than it sounds.

**Putting it together**

When you run `git commit`, Git takes the staged snapshot recorded in the index file, writes any new blobs, builds trees from the bottom up, creates a commit object pointing at the root tree and the previous commit, then advances the branch ref. Four steps, a handful of small files.

Everything else in Git, including branching, merging, rebasing and cherry-picking, is manipulation of this graph of immutable objects and a few mutable pointers. Once you see that, the commands stop feeling like incantations. Explore with `git cat-file -p` and `git ls-tree`, and the structure is all there to read.

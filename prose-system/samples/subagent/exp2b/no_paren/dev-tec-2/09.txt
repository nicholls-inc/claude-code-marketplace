When you type an HTTPS address into a browser and press Enter, a surprising amount of work happens before the first byte of the response shows up. This description walks through that sequence in order, from the typed address to the moment the server starts answering.

1. Parsing the address

The browser first splits the address into parts. In https://www.example.com:443/shop?item=7, the scheme is https, the host is www.example.com, the port is 443 by default, the path is /shop and the query is item=7. The scheme tells the browser to use encrypted HTTP. If you typed only a word or phrase, the browser may treat it as a search instead of an address.

Before leaving the machine, the browser also checks a few local shortcuts. It looks at its own cache to see whether it already holds a fresh copy of the resource. It also checks an HSTS list, which records sites that must only be reached over HTTPS. If a fresh cached copy exists, no network request is needed at all, and the process ends here.

2. DNS resolution

Networks route traffic by IP address, not by name, so the browser must turn www.example.com into an address such as 93.184.216.34. This is the job of the Domain Name System.

The lookup checks several caches in order: the browser cache, the operating system cache, and the hosts file. If none has an answer, the operating system asks a recursive resolver, usually run by your internet provider or a public service. If the resolver has no cached answer either, it works down the hierarchy. It asks a root server which servers handle the top-level domain, such as .com. It then asks those servers which name servers are responsible for example.com. Finally it asks those authoritative servers for the address of www.example.com. The answer comes back with a time to live value that says how long it may be cached.

Most lookups are answered from a cache and finish in a few milliseconds. A cold lookup can take tens or hundreds of milliseconds. The answer may include both IPv4 and IPv6 addresses, and the browser can try both.

3. Opening a TCP connection

With an IP address in hand, the browser opens a connection to port 443. Classic HTTP over HTTPS runs on TCP, which provides an ordered and reliable byte stream. TCP sets up a connection with a three step handshake. The client sends a SYN packet, the server replies with SYN and ACK, and the client sends an ACK. Only then can data flow.

This costs one full round trip between you and the server. If the server is far away, that round trip is a noticeable delay, because it is bounded by the speed of light in cables.

Newer HTTP versions can skip this step. HTTP/3 runs over QUIC, which uses UDP and combines connection setup with encryption, saving round trips. The browser learns about HTTP/3 support from a response header or a DNS record, so a first visit usually still starts with TCP.

4. The TLS handshake

Next comes the step that makes HTTPS secure. TLS is a protocol layered on top of the connection. It gives you three guarantees: the server is who it claims to be, nobody can read the traffic, and nobody can alter it unnoticed.

In TLS 1.3, the handshake works like this. The browser sends a ClientHello message. It lists the cipher suites it supports, a random value, and a key share for key agreement. It also includes the server name, a field called SNI, so a server hosting many sites knows which certificate to present. It may also list the application protocols it speaks, such as h2 for HTTP/2, using an extension called ALPN.

The server replies with a ServerHello, choosing a cipher suite and sending its own key share. At this point both sides can compute the same shared secret without ever sending it. The server then sends its certificate, along with proof that it holds the matching private key. The remaining handshake messages are already encrypted.

The browser validates the certificate. It checks that the certificate chains up to a certificate authority it trusts, that it has not expired, that it has not been revoked, and that the name on it matches the host in the address. If any check fails, the browser shows a warning page instead of continuing.

Once both sides finish, they hold session keys and switch to encrypted communication. TLS 1.3 needs one round trip for this. TLS 1.2 needed two. Returning visitors can sometimes resume a previous session and send data even sooner.

5. Sending the HTTP request

Now the browser sends the actual request, inside the encrypted channel. A simple one looks like this:

GET /shop?item=7 HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The method says what to do, the path says which resource, and the headers carry extra information. The browser attaches any cookies that belong to this site and path. With HTTP/2 or HTTP/3 the content is the same, but it is packed into a compact binary format, and many requests can share one connection.

6. The server does its work

The request travels to the server, often passing first through a load balancer, a reverse proxy, or a content delivery network. A CDN edge server near you may answer directly from its cache. If not, the request is forwarded to the origin.

At the origin, the web server hands the request to your application. The application might check authentication, query a database, call other services, and render a template. This time is called server think time, and it is often the largest part of the wait on dynamic pages.

7. The first byte

As soon as the server writes the start of its reply, the status line and headers begin traveling back, for example HTTP/1.1 200 OK followed by headers such as Content-Type and Cache-Control. The moment the first byte of that reply reaches the browser is called Time to First Byte, or TTFB.

TTFB is therefore the sum of everything above: DNS lookup, TCP connection, TLS handshake, request travel time, server processing, and the return trip of the first byte. Browser developer tools show these phases separately in the Network panel, which makes it easy to see where time is going.

Why this matters to you

Each stage suggests a practical optimization. Use a CDN to shorten distance. Keep DNS records sensible with reasonable TTLs. Enable HTTP/2 or HTTP/3 and TLS 1.3. Reuse connections with keep-alive, so later requests skip the DNS, TCP, and TLS steps entirely. Cache responses where you safely can. Keep server code and database queries fast. When a page feels slow before anything appears, this sequence is where to start looking.

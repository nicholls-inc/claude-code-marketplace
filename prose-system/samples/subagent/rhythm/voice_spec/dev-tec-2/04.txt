When you type an address such as https://www.example.com/products into a browser and press Enter, the browser first splits it into parts. The scheme is https, the host is www.example.com, the port is 443 because that is the default for https, and the path is /products. The scheme tells the browser that the connection must be encrypted. Before it uses the network, the browser checks a few local things. It looks in its HTTP cache for a stored copy of the page that is still fresh, and if it finds one the request ends there with no network traffic. It checks whether a service worker registered for the site wants to handle the request. It also checks its HSTS list, which records sites that have told the browser to use only https. That list is the reason a typed http address for such a site is rewritten before any request leaves the machine.

If the request has to go out, the browser needs an IP address for the host name. It looks in its own DNS cache, then asks the operating system, which keeps a cache of its own and may read the hosts file. If neither has an answer, the operating system sends a query to a recursive resolver, which is usually run by the internet provider or by a public service such as 1.1.1.1 or 8.8.8.8. The resolver keeps a cache too, and for a popular site it will often have the answer already. When it does not, it works down the hierarchy. It asks a root server which servers handle .com, asks one of those which servers are responsible for example.com, and asks one of those for the address of www.example.com. The final answer may be a CNAME that points to another name, such as one belonging to a content delivery network, and then the lookup continues for that name. Each record carries a time to live in seconds, which tells every cache how long it may keep the answer. Values between 60 and 3600 are common. A cached lookup takes under a millisecond on the local machine, while a full lookup from cold can take 50 to 200 milliseconds. Many browsers ask for both an IPv4 and an IPv6 address and prefer IPv6 when it works.

With an address in hand, the browser looks for an open connection to the same host that it can reuse. Browsers keep connections open for a while, so a second page from the same site can skip the next two steps. Without one, the browser opens a TCP connection. The client sends a SYN packet, the server replies with SYN-ACK, and the client sends an ACK. This exchange costs one round trip, which is the time for a packet to reach the server and for a reply to come back. Round trip times depend on distance. Around 10 milliseconds is typical within a country, 80 milliseconds across the Atlantic, and 250 milliseconds or more between Europe and Australia. These figures matter because most of what follows is counted in round trips.

TLS comes next. In TLS 1.3, which most sites now use, the browser sends a ClientHello message. It lists the cipher suites it supports, includes a key share for the key exchange, and names the host it wants in a field called Server Name Indication. That field lets one IP address serve many sites, because the server can pick the matching certificate. The message also lists the application protocols the browser can speak, usually h2 for HTTP/2 and http/1.1, in an extension called ALPN. The server replies with its own key share and the cipher suite it chose. From that point both sides can compute the same session keys, and the rest of the handshake is encrypted. The server sends its certificate chain, a signature that proves it holds the matching private key, and a Finished message. This takes one more round trip.

The browser then validates the certificate. It checks that the host name appears in the certificate's subject alternative names, that the current date falls inside the validity period, and that the chain leads through one or more intermediate certificates to a root authority that the operating system or browser already trusts. It verifies the signature on each link in that chain. Revocation is checked, if at all, against lists that the browser vendor distributes in advance and not by a live query to the authority. If any check fails, the browser shows a full-page warning and does not send the request. If all pass, the browser sends its own Finished message and the connection is ready. A browser that has spoken to the server before may hold a session ticket, which lets it resume with a shorter handshake.

Some sites offer HTTP/3, which runs over QUIC on UDP. QUIC combines the transport and encryption handshakes, so a new connection needs one round trip instead of two. A browser learns that a site supports HTTP/3 from an Alt-Svc header on an earlier response or from a DNS record, so a first visit normally goes over TCP.

Now the browser sends the request. With HTTP/2 this is a set of binary frames, but the content matches HTTP/1.1. It holds the method GET, the path /products, the host, and headers such as Accept, Accept-Encoding and User-Agent, along with any cookies stored for the domain. The request travels through the encrypted connection and may reach a CDN edge server or a load balancer first. These often end the TLS connection themselves. They either answer from their own cache or forward the request to an origin server, which can add another connection and another round trip behind the scenes.

The origin server then does its work. The web server hands the request to application code, which may check a session, query a database, fill a template and build the response. This is the part a developer controls most directly, and it ranges from a few milliseconds for a cached page to several hundred for a heavy one. The server writes the status line and headers and begins to send the body. The first byte of that response, arriving through the same encrypted connection, is what the browser records as time to first byte.

Consider a cold visit over TCP to a server with an 80 millisecond round trip. DNS might cost 100 milliseconds, TCP 80, TLS 80, and the request and first byte of response another 80 plus the server's own processing time. That comes to about 340 milliseconds before the application's share. In my view this arithmetic is the most useful thing to hold on to, because it explains why connection reuse, caching, CDNs and short DNS paths each make pages start sooner.

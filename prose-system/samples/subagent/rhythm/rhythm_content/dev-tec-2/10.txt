When you type an address such as https://example.com/products?id=7 into a browser, it first takes the string apart into a scheme (https), a host (example.com), an optional port, a path and a query. The scheme tells it both that the connection must be encrypted and that the default port is 443 unless the URL says otherwise. Before any network traffic, the browser consults local state that can short-circuit parts of what follows. That state includes an HSTS list that would have upgraded an http address to https, and a cache entry that is still fresh and can be served without contacting the server at all. It also includes a service worker registered for the origin, which may intercept the request and answer from its own storage, and an existing pooled connection to the same origin, which can be reused so that most of the steps below are skipped entirely. If none of these apply, the browser has to find a machine to talk to, and since the network routes by IP address rather than by name, it starts with DNS resolution.

The browser checks its own DNS cache, then asks the operating system's resolver, which checks its cache and the hosts file, and finally sends a query to a recursive resolver provided by your ISP, your router or a public service. That query usually goes over UDP to port 53, or increasingly over an encrypted transport such as DNS over HTTPS. If the resolver has no cached answer, it walks the hierarchy by asking a root server which servers handle .com, asking those which servers are authoritative for example.com, and finally asking one of those for the A record (IPv4) and AAAA record (IPv6) of the host. Each answer carries a time-to-live that controls how long it may be cached, which is why DNS is often fast on a second visit and slow on the first, and why a CNAME chain, in which the name points to another name such as a CDN hostname, adds further lookups. Modern browsers may also query the HTTPS record type to learn in advance that the server supports HTTP/3 and which ports to use.

With an address in hand, the browser opens a TCP connection, which begins with the three-way handshake: the client sends a SYN, the server answers with SYN-ACK, and the client's ACK completes it, so one full round trip passes before any application data can be sent. If both IPv4 and IPv6 addresses came back, browsers typically race them with a small head start for IPv6 (the approach called Happy Eyeballs) so that a broken path does not stall the page. When the server supports HTTP/3, the transport is QUIC over UDP instead, which folds the transport and cryptographic handshakes together and saves a round trip, but the browser usually learns about this only from a previous visit's Alt-Svc header or the DNS record mentioned earlier, so a first visit commonly uses TCP.

Because the scheme is https, the connection then needs a TLS handshake before anything readable is sent. The client opens with a ClientHello listing the TLS versions and cipher suites it supports, a random value, a key share for an ephemeral Diffie-Hellman exchange, the Server Name Indication extension containing the hostname, which lets a server hosting many sites on one IP address choose the right certificate, and the ALPN extension offering h2 and http/1.1 so that the HTTP version is negotiated in the same exchange. In TLS 1.3 the server replies in a single flight with its own key share, which allows both sides to derive session keys immediately, followed by its certificate chain and a signature proving that it holds the private key matching the certificate. The browser verifies that the chain leads to a root authority it trusts, that each certificate is within its validity period, that the hostname appears in the certificate's subject alternative names, and that the certificate has not been revoked, although revocation is handled differently across browsers, often through stapled OCSP responses or compiled lists rather than a live query. If any check fails, the user sees a certificate warning and the request stops there. Once the client sends its Finished message, the handshake is complete after one round trip in TLS 1.3, compared with two in TLS 1.2, and a client that has visited before may use a session ticket to resume with fewer messages or, with 0-RTT, to send the request along with its first flight, at the price that this early data can be replayed and is therefore limited to safe requests.

Only now does the browser send the HTTP request itself, encrypted inside the TLS session. Under HTTP/1.1 it is plain text framed as a request line like GET /products?id=7 HTTP/1.1 followed by headers such as Host, User-Agent, Accept, Accept-Encoding and any cookies stored for that domain, while under HTTP/2 the same information is sent as compressed binary header frames on a numbered stream, which lets many requests share the single connection, and under HTTP/3 the equivalent runs over QUIC streams. Cookies matter here because the browser attaches every cookie whose domain, path, Secure and SameSite attributes match, so an authenticated session identifier rides along on this first request and lets the server identify the user without any extra exchange.

The request travels through your router, your ISP and a series of intermediate networks, and often arrives not at the origin server but at a CDN edge or a load balancer, which terminates TLS, may answer from its own cache, and otherwise forwards the request to an application server, perhaps through a reverse proxy such as nginx, where it is routed to your application code, which may query a database before building a response. The server begins its reply with a status line and headers (for example HTTP/2 200 with Content-Type, Content-Encoding and Cache-Control) followed by the body, and the moment the first byte of that response reaches the browser is what performance tools measure as time to first byte. That figure therefore bundles together DNS lookup, connection setup, TLS negotiation, the request's travel time and the server's own processing time, and the timing tab in the browser's Network panel breaks them out separately, so that a slow first byte can be attributed to the correct stage rather than blamed wholesale on the backend. Redirects add to the total, because a 301 from http to https or from a bare domain to www sends the browser back through at least part of this sequence again, which is why linking directly to the canonical https address, keeping certificate chains short, and relying on connection reuse and caching are the usual first steps in reducing it.

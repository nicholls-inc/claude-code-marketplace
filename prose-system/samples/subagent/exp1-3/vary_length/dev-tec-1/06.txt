Git stores everything in a content-addressed database that lives in the .git/objects directory. Once you see how that database works, most of Git's behavior stops being mysterious. A commit is not a diff, a branch is not a copy of your files, and nothing in the system is ever edited in place.

**The object store**

Every piece of data Git tracks is an object. Each object is identified by a hash of its own content, computed with SHA-1 by default or SHA-256 in newer repositories. Git prepends a short header giving the object's type and size, hashes the result, and compresses it with zlib. The hash becomes the object's name. The first two hex characters name a subdirectory, and the rest name the file inside it. An object with the ID `3b18e512dba79e4c8300dd08aeb37f8e728b8dad` therefore lives at `.git/objects/3b/18e512...`.

Because the name is derived from the content, two identical pieces of content always share one object. Change a single byte and you get a different object with a different name. Objects are immutable by construction. You can inspect any of them with `git cat-file -p <id>`, and `git cat-file -t <id>` tells you its type.

There are four object types. Three of them matter for a commit.

**Blobs**

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no timestamp. If you copy `README.md` to `README-copy.md`, Git stores a single blob, because the bytes are identical. Rename a file without editing it and no new blob appears at all.

This is also why Git is not storing deltas between versions at the logical level. Each version of a file is a complete blob. (Later, `git gc` packs objects into packfiles and delta-compresses similar ones for disk efficiency, but that is an optimization layered underneath. The model above is what you reason with.)

**Trees**

If blobs hold content, trees hold structure. A tree object represents one directory. It is a list of entries, and each entry carries a mode, a type, an object ID and a name. Run `git cat-file -p HEAD^{tree}` in any repository and you will see something like this:

```
100644 blob a1b2c3...  README.md
040000 tree d4e5f6...  src
100755 blob 9a8b7c...  build.sh
```

The mode records whether a file is regular, executable or a symlink. Entries of type blob point at file contents. Entries of type tree point at subdirectories, which are themselves tree objects with the same shape. Following the pointers downward reconstructs your whole working directory.

Filenames live here, in the parent tree, rather than in the blob. That is the reason renames are cheap, and also the reason Git has no concept of an explicit "rename" operation. It detects renames after the fact by comparing trees.

There is a useful consequence in how hashes propagate. A tree's ID depends on the IDs of everything beneath it. If you edit one file deep in `src/lib/util/`, the blob changes, so the tree for `util/` changes, so the tree for `lib/` changes, and so on up to the root. Every untouched sibling keeps its existing ID and is reused as is. A commit that changes one line therefore adds only a handful of small objects, not a copy of the project.

**Commits**

A commit object is surprisingly small. It is a plain-text record with a few fields:

```
tree 4c9d1e...
parent 7f3a2b...
author Ada Lovelace <ada@example.com> 1731326400 +0000
committer Ada Lovelace <ada@example.com> 1731326400 +0000

Fix off-by-one in pagination
```

The `tree` line points at the root tree, which is a complete snapshot of the project at that moment. The `parent` line points at the previous commit. A merge commit has two or more parent lines, and the very first commit in a repository has none. Then come the author and committer identities with timestamps, a blank line, and your message.

Notice what is absent. There is no list of changed files and no diff. When you run `git show`, Git computes the diff on demand by comparing the commit's tree with its parent's tree. The commit stores a snapshot, and the history you see is derived from it.

The commit's own ID is the hash of all those lines, including the parent's ID. That makes history a chain of hashes, in the same spirit as a blockchain. Altering any old commit changes its ID, which changes every descendant's ID. This is why `git commit --amend` and `git rebase` do not modify anything. They create new commits and move a pointer, leaving the originals orphaned until garbage collection eventually removes them.

**Refs**

So far everything has been a 40-character hash, which nobody wants to type. Refs solve that. A ref is a human-readable name that points at an object ID, and it is the only mutable part of the system.

Look inside `.git/refs/heads/`. Each file there is a branch. Open `.git/refs/heads/main` and you will find nothing but a commit hash and a newline. That's the whole branch. Creating one means writing 41 bytes, which is why it is instant, and making a commit means moving it forward to the new commit's ID. Tags work the same way under `.git/refs/tags/`, and remote-tracking branches such as `origin/main` live under `.git/refs/remotes/`. (Git may consolidate loose refs into a single `.git/packed-refs` file, but the meaning is identical.)

Then there is `HEAD`, a file at `.git/HEAD`. Normally it holds a symbolic reference such as `ref: refs/heads/main`, meaning "the current branch is main." When you commit, Git follows HEAD to the branch, creates the new commit with the old tip as its parent, and updates the branch file. In a detached HEAD state the file contains a raw commit hash instead, and no branch advances when you commit. That is why such commits are easy to lose.

**Putting it together**

When you run `git commit`, Git takes the index (the staging area at `.git/index`), writes a tree object for each directory it describes, reusing any that already exist, and writes a blob for any new file content. It then writes a commit object pointing at the new root tree and the current tip, and finally moves the branch ref to that commit.

Four object types, one pointer file, and that is the entire storage model behind every Git operation you run each day.

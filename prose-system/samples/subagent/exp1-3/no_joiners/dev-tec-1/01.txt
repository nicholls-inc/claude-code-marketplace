Every day you run git add, git commit and git log, yet the .git directory at the root of your repository probably remains a black box. Inside it, Git is a surprisingly small system. It is a content addressed key and value store, and everything it knows about your project is kept as four kinds of things, namely blobs, trees, commits and refs. Understanding them explains most of Git's behavior.

Content addressing

Git stores its objects under .git/objects. Each object is named by a hash of its contents, computed over a short header giving the type and size followed by the raw bytes. Historically the hash is SHA1, which gives a forty character hexadecimal name, and newer repositories can opt into SHA256. The first two characters of the name become a directory and the remainder becomes the filename, so an object named 8a3f and so on lives at .git/objects/8a/3f and so on. The file is compressed with zlib, which is why you cannot simply open it in an editor. You can read any object with the git cat file plumbing command and its pretty print option, passing it a hash.

Because the name derives from the content, identical content always receives the same name. Storing the same file twice costs nothing, and an object can never change without its name changing. This property is what makes history tamper evident.

Blobs

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no timestamps. When you run git add on a file, Git immediately writes a blob for it into the object database. If two files in different directories have identical bytes, they share a single blob. If you edit one line of a large file, Git writes a whole new blob for the new version. It stores snapshots rather than diffs. Later, packfiles compress similar objects against each other using deltas, but that is a storage optimization hidden beneath the model.

Trees

Names and permissions live in trees. A tree represents one directory and is a list of entries. Each entry has a mode, a name and the hash of whatever it points to. The mode says whether the entry is a regular file, an executable, a symbolic link or a subdirectory. Entries for files point to blobs and entries for subdirectories point to other trees. The root of your repository is therefore a tree, and its subdirectories are nested trees, forming what is known as a Merkle tree.

Renaming a file changes only the tree that contains it and the trees above it, while the blob stays the same. If a directory is unchanged between two commits, it has the same tree hash in both and Git reuses it. The hash of the root tree summarizes the entire project state. Change any byte anywhere and the hash of its blob changes, then the hash of its parent tree, and so on all the way up to the root.

Commits

A commit object is small and plain text before compression. It contains a line naming the root tree, one line for each parent commit, an author line with name, email and timestamp, a committer line in the same form, a blank line and then the message. A first commit has no parent, an ordinary commit has one, and a merge commit has two or more.

Notice what a commit does not contain. It stores no diff. When git show displays a change, it computes the change by comparing the commit's tree with its parent's tree. A commit is a snapshot of the whole project plus metadata about where that snapshot came from.

Because a commit's hash covers its parent hashes, history forms a chain in which each link vouches for everything before it. Amending a commit, rebasing it or editing its message produces a new commit with a new hash, and every descendant must be rewritten too. That is why rewriting shared history is disruptive for collaborators. The old commits are not modified. They are simply no longer reachable from your branch.

Refs

Hashes are hard to remember, so Git uses refs, which are human readable names that point at commits. A ref is just a small file whose entire contents are a hash. A branch called main is the file .git/refs/heads/main. Tags live under .git/refs/tags and remote tracking branches live under .git/refs/remotes. Creating a branch means writing forty characters into a new file, which is why it is instant. Large repositories sometimes gather their refs into a single packed file for speed, but the idea is the same.

A branch is therefore not a container of commits. It is a movable pointer to one commit, and the rest of the history is found by following parent links backwards from that commit.

HEAD

The file .git/HEAD records where you are right now. Usually it names a branch, which is why committing moves that branch forward. If it holds a raw commit hash instead, you are in the detached HEAD state, and new commits are not recorded under any branch name. They remain reachable only until you move away, which is why Git warns you about it.

Putting it together

Suppose you edit one file and run git commit. Git writes a new blob for the changed file. It writes new tree objects for the file's directory and each directory above it, reusing every unchanged subtree by hash. It then writes a commit object that names the new root tree and the previous commit as its parent. Finally it updates the file for the current branch so that it holds the new commit's hash. Four small writes and one file update make up the whole operation.

Reachability and cleanup

An object is alive if some ref, or the reflog, can reach it by following links. Objects nobody can reach linger for a while, which is why you can often recover a lost commit through git reflog. Eventually git gc prunes them and packs the rest.

Once you see the repository as a graph of immutable, hash named objects with a handful of mutable pointers on top, commands such as reset, rebase, cherry pick and checkout stop being mysterious. Each one is just a different way of creating objects or moving a ref.

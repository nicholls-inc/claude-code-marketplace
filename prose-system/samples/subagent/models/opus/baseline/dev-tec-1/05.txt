How Git Stores a Commit

Most developers think of a commit as "a diff plus a message". Inside the .git directory Git stores something different: a full snapshot of the project, built from a small number of object types that refer to each other by hash. This piece covers four of them: blobs, trees, commit objects and refs.

The object database

Everything Git knows about your history is kept in .git/objects. Each object is stored under the hash of its own content. Git takes the object's type and size, joins them to the raw content as "blob 13\0hello, world\n", hashes the result with SHA-1, and compresses it with zlib. The 40-character hex hash becomes the object's address. The first two characters name a subdirectory and the other 38 name the file, so an object with hash e965047ad7c57865823c7d992b1d046ea66edf78 is stored at .git/objects/e9/65047ad7c57865823c7d992b1d046ea66edf78. Newer repositories can use SHA-256 instead, but the design is the same.

This scheme is called content addressing, and two things follow from it. Identical content is stored only once, however many files or commits contain it. Objects also never change, because changing an object's content would change its hash and therefore its address. Git's history can't be altered without anyone noticing because of this.

You can inspect any object with two plumbing commands. `git cat-file -t <hash>` prints the object's type, and `git cat-file -p <hash>` prints its content in readable form.

Blobs: file contents

A blob holds the bytes of one file and nothing else. It has no filename, no permissions and no timestamp. If README.md and docs/intro.md contain exactly the same text, they share one blob. Run `git hash-object README.md` to see the hash Git would give that file. Run `git cat-file -p` on that hash after committing and you get the file back.

So a blob tells you what a file contains but not what it is called or where it lives. Trees supply that.

Trees: directories

A tree object represents one directory. It is a sorted list of entries, and each entry has a mode, a type, a hash and a name:

    100644 blob a906cb2a4a904a152e80877d4088654daad0c859    README.md
    100755 blob 8f94139338f9404f26296befa88755fc2598c289    build.sh
    040000 tree 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0    src

The mode records what kind of entry it is: 100644 is a normal file, 100755 an executable, 120000 a symbolic link, and 040000 a subdirectory. A subdirectory points to another tree, so the whole project forms a tree of trees with blobs as the leaves. (The listing above is how `git cat-file -p` displays a tree. On disk the hashes are stored as raw 20-byte binary.)

Trees are content-addressed like everything else, so a directory that didn't change between two commits keeps the same tree hash, and both commits point at the same object. A commit that changes one file in a large repository creates only a new blob for that file, new trees for each directory on the path from it up to the root, and one new commit. Everything else is reused. That is why storing a full snapshot for every commit costs so little.

Commit objects: snapshots with history

A commit object is short plain text. `git cat-file -p HEAD` shows something like this:

    tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
    parent 3f1c2a9e0b7d4c5e8a6f2b1d0c9e8f7a6b5c4d3e
    author Ada Lovelace <ada@example.com> 1731340800 +0000
    committer Ada Lovelace <ada@example.com> 1731340800 +0000

    Fix off-by-one in pagination

The tree line points to the root tree, which is the complete snapshot of the project at that moment. Each parent line points to a previous commit. The first commit in a repository has no parent line, an ordinary commit has one, and a merge commit has two or more. The author and committer lines record who made the change and when, as a Unix timestamp plus a timezone offset. A blank line separates these headers from the message. A signed commit carries an extra gpgsig header.

Because the parent hashes are part of the commit's content, a commit's hash covers its whole ancestry. If you change anything in an earlier commit, every hash after it changes too. This is why rebasing or amending creates new commits instead of editing the old ones.

The diff that `git show` displays isn't stored anywhere. Git works it out on the fly by comparing the commit's tree with its parent's tree.

Refs: names for hashes

Nobody wants to type 40-character hashes, so Git keeps refs: small files that map a name to a hash. A branch is just a file. .git/refs/heads/main contains one line, the hash of the latest commit on main. Tags are kept under .git/refs/tags and remote-tracking branches under .git/refs/remotes/origin.

When you commit on main, Git writes the new commit object and then overwrites refs/heads/main with the new hash. Creating a branch only writes a new 41-byte file, which is why branching is instant.

HEAD is a special ref at .git/HEAD. It normally holds a symbolic reference such as "ref: refs/heads/main", meaning "the current branch is main". If you check out a commit directly, HEAD holds a raw hash instead, and that state is called "detached HEAD". `git rev-parse main` resolves any ref to its hash.

Two practical notes. Over time Git may move loose refs into a single .git/packed-refs file, so a branch can exist without its own file under refs/heads. In the same way, `git gc` packs loose objects into .git/objects/pack, where similar objects are stored as compressed deltas. The deltas are only a storage optimisation and don't change the model above.

Putting it together

When you run `git commit`, Git turns the staged files into blobs, builds trees for the directories, writes a commit object that points at the root tree and the previous commit, and moves the current branch ref to the new commit. The rest of Git (log, diff, merge, checkout) works by following those hash pointers.

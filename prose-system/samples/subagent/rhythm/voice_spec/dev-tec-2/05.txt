When you type an HTTPS address into a browser, the first thing it does is split the address into its parts. In https://www.example.com/shop?id=7 the scheme is https, the host is www.example.com, the port is the default 443 because none is written, and the path and query are /shop and id=7. Before going to the network the browser checks whether it already holds a usable answer. It looks at its HTTP cache for a fresh copy of the page, and it checks its HSTS list, which records sites that must only be reached over HTTPS. If a fresh cached copy exists, the browser can use it and no request is sent at all.

If a request is needed, the browser must turn the host name into an IP address. It looks in its own DNS cache first, then asks the operating system, which checks its own cache and the hosts file. If neither knows the name, the request goes to a recursive resolver, usually run by the internet provider or a public service such as 1.1.1.1 or 8.8.8.8. The resolver may already have the answer cached. If it does not, it works down the hierarchy: it asks a root server which servers handle .com, asks one of those which servers handle example.com, and asks the last of these for the address of www.example.com. The reply contains an A record with an IPv4 address, an AAAA record with an IPv6 address, or both, along with a time to live in seconds that tells every cache how long it may keep the answer. A cold lookup commonly takes a few tens of milliseconds, and a cached one takes close to none.

With an address in hand, the browser opens a connection to port 443. For HTTP/1.1 and HTTP/2 this is TCP, which begins with a three-step exchange. The browser sends a SYN packet, the server answers with SYN-ACK, and the browser replies with ACK. This costs one round trip, which is the time for a packet to travel to the server and back. On a connection with a 50 millisecond round trip, the handshake therefore takes about 50 milliseconds. If the browser received both IPv4 and IPv6 addresses, it usually tries them in quick succession and keeps whichever connects first. A third option is HTTP/3, which runs over QUIC on UDP and combines the transport and encryption steps. The browser learns that a site supports it from an earlier response header or a DNS record, and otherwise starts with TCP.

Next comes the TLS handshake, which sets up encryption. In TLS 1.3, the version most sites now use, the browser sends a ClientHello message. It lists the cipher suites it supports, names the host in the Server Name Indication field so that a server hosting many sites knows which certificate to use, offers the protocols it can speak through ALPN, and includes a key share, which is its half of a Diffie-Hellman key exchange. The server replies with its own key share and chooses a cipher suite and a protocol. From these two key shares both sides calculate the same secret without ever sending it, and every message after that point is encrypted. The server then sends its certificate chain and a signature that proves it holds the private key matching the certificate. The whole exchange takes one round trip in TLS 1.3. TLS 1.2 needs two, and that is one reason the newer version feels faster.

The browser then checks the certificate. It confirms that the chain leads to a certificate authority listed in the trust store of the browser or operating system, that every certificate in the chain is within its validity dates, and that the host name appears in the certificate's Subject Alternative Name list. It may also check whether the certificate has been revoked, using stapled OCSP data from the server or its own revocation lists. If any check fails, the browser stops and shows a warning page instead of continuing. This is why an expired certificate or a name mismatch blocks users completely, rather than degrading the page.

Once the connection is encrypted, the browser sends the request itself. With HTTP/2 this is a set of binary frames, but the content corresponds to what HTTP/1.1 writes as text: a GET method, the path /shop?id=7, a Host header, and headers such as Accept, Accept-Encoding, User-Agent and any cookies stored for that site. The Accept-Encoding header lists compression formats such as gzip and br, so the server knows what it may use. If the browser holds a stale cached copy, it adds an If-None-Match header with the stored ETag, which lets the server answer with a short 304 status instead of resending the body.

The request travels through the network to the server, but often it does not reach the machine that built the page. Many sites put a content delivery network or a load balancer in front of their application. The edge server that receives the request may terminate the TLS connection itself and either answer from its cache or forward the request over another connection to an origin server. If the answer must come from the origin, the application there reads the path and cookies, may query a database, builds the response, and hands it back.

The first byte of the response arrives as the start of the status line in HTTP/1.1, or the first frame in HTTP/2, usually containing a status such as 200 and the response headers. The time from sending the request to receiving this byte is called time to first byte. Browser developer tools report it under the Network panel as waiting time. Adding up the stages above for a first visit over a 50 millisecond connection gives a rough picture: DNS may take 20 to 100 milliseconds, TCP 50, TLS 50, and the request and server processing at least another 50 plus whatever the application needs. On repeat visits, a kept-alive connection, cached DNS and TLS session resumption remove most of the earlier steps, which is why the second request to a site is typically much quicker than the first. These are the parts of page speed a developer can influence through caching headers, server location, certificate setup and the speed of the application code.

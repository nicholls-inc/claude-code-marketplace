When you run git commit, Git does not record a diff or a list of changed files, as many developers assume. It stores a complete snapshot of your project, built from four kinds of things that all live in the .git directory. Three of them are objects in a content-addressed database, and the fourth is a small text file that gives a human-friendly name to one of those objects.

The object database is a simple key-value store. Every object is hashed with SHA-1 (or SHA-256 in newer repositories) over a short header and its contents, and the resulting hash is both its name and its address. The first two characters of the hash become a subdirectory under .git/objects, and the remaining characters become the filename inside it. The contents are compressed with zlib, which is why you cannot simply open these files and read them, although git cat-file -p will decode any object for you. Because the name is derived from the content, two objects with identical content share a single entry, and changing even one byte produces an entirely different name.

The simplest kind of object is the blob, which holds the raw bytes of a single file. A blob contains no filename, no permissions and no timestamp, only the content. If you have two files in different directories with identical contents, Git stores one blob and points to it twice. If you edit a large file and change one line, Git stores a brand-new blob for the whole new version, rather than a patch, and leaves the old blob untouched. This sounds wasteful, but Git later packs similar objects together and stores them as deltas in packfiles, so the on-disk size stays modest.

Since blobs carry no names, something else must say which blob is which file, and that job belongs to the tree object. A tree represents one directory and is essentially a list of entries. Each entry has a file mode, a name, and the hash of what it refers to. The mode distinguishes a regular file from an executable, a symbolic link, or a subdirectory. When the entry is a file, the hash points to a blob, and when it is a subdirectory, the hash points to another tree. A project with nested folders therefore becomes a tree of trees, with a single root tree at the top that describes the whole working directory at one moment. Because each tree's hash depends on the hashes of everything beneath it, the root tree's hash effectively fingerprints the entire project. If any file anywhere changes, the hashes of its blob, of every tree above it, and of the root all change, while untouched subdirectories keep their old hashes and are shared with the previous snapshot.

The commit object is what turns a snapshot into history. It is a small text object that records the hash of the root tree, the hashes of its parent commits, an author line, a committer line, and your commit message. Each of the author and committer lines carries a name, an email address, a timestamp and a timezone offset. A normal commit has one parent, the first commit in a repository has none, and a merge commit has two or more. These parent links form the chain, or more precisely the directed graph, that you see when you run git log. Because the parent hash is part of the commit's own content, and therefore part of its own hash, you cannot alter an old commit without changing the identity of every commit that follows it. This is why rewriting history, as rebase does, really creates new commits instead of modifying the old ones, and why the old ones linger in the database until garbage collection removes them.

Everything so far is immutable, and that raises the question of how Git knows where you currently are. The answer is refs, which are the only mutable part of the picture. A ref is just a file containing a commit hash, and branches are refs stored under .git/refs/heads. If you open .git/refs/heads/main, you will find forty hexadecimal characters and a newline, and that is the entire branch. Creating a branch means writing a new forty-character file, which is why it is so cheap. Tags live under .git/refs/tags and work the same way, though annotated tags add their own object type that carries a message and points at a commit. When you make a new commit, Git writes the new objects and then moves the current branch's ref forward to the new commit's hash. Remote-tracking branches such as origin/main are likewise refs, stored under .git/refs/remotes, and they update when you fetch. In large repositories, many refs may be gathered into a single packed-refs file for efficiency, but the meaning is unchanged.

One more file ties the picture together. HEAD, at the top of the .git directory, usually contains not a hash but the name of a branch ref, such as ref: refs/heads/main, and that indirection is how Git knows which branch to advance when you commit. When HEAD instead holds a bare commit hash, you are in the detached HEAD state, and new commits are not attached to any branch.

Putting it all together, a commit is a chain of pointers. A ref names a commit, the commit names its root tree and its parents, trees name subtrees and blobs, and blobs hold the bytes. Every link is a hash of the thing it points to, which makes the whole structure tamper-evident and lets Git share unchanged content freely between commits.

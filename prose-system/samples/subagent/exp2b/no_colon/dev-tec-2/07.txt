When you type an HTTPS address into a browser and press Enter, a long chain of steps runs before the first byte of the response arrives. Most of it takes a few hundred milliseconds. Knowing the stages helps you reason about slow pages, certificate errors and caching.

1. Parsing the address

The browser first splits the address into parts. In https://www.example.com/shop?id=7, the scheme is https, the host is www.example.com, the port is implied as 443, the path is /shop and the query is id=7. The scheme tells the browser to use TLS encryption. The browser also checks a built-in list of sites that must only be reached over HTTPS (HSTS). If you typed a plain http address for such a site, the browser upgrades it internally before sending anything.

2. Checking local caches

Before touching the network, the browser asks whether it already has what it needs. It may have a fresh cached copy of the resource, in which case no request is made at all. It may have a service worker registered for the site, which can answer the request from its own logic. If neither applies, the browser moves on to the network.

3. DNS resolution

Networks route by IP address, not by name, so the browser must turn www.example.com into an IP address. It checks its own DNS cache first, then asks the operating system, which checks its cache and its hosts file. If both miss, the OS sends a query to a recursive resolver, usually run by your ISP or a public provider. The resolver may already have the answer cached. If not, it walks the hierarchy. It asks a root server which servers handle .com, asks those which servers handle example.com, and finally asks the authoritative server for example.com, which returns the address. Each record carries a time to live (TTL) that says how long it may be cached. Modern browsers can also use DNS over HTTPS and may receive extra hints about which protocols the server supports. A cold lookup can take tens of milliseconds, while a cached one is nearly instant.

4. Opening a TCP connection

With an IP address in hand, the browser opens a connection to port 443. Classic HTTP over TLS runs on TCP, which begins with a three-step handshake. The client sends a SYN, the server replies with SYN-ACK, and the client sends an ACK. This costs one full round trip before any application data can flow. Round trip time is set largely by physical distance, which is why servers close to users, such as those behind a CDN, feel faster. Browsers often reuse an existing connection to the same host, which skips this step entirely.

HTTP/3 is different. It runs over QUIC, which uses UDP and combines the transport and encryption handshakes into one. If the browser knows the server supports HTTP/3, it may try that route and avoid the separate TCP step.

5. The TLS handshake

Now the browser and server set up encryption and prove who the server is. In TLS 1.3, the common version today, this takes one round trip.

The client sends a ClientHello. It lists the TLS versions and cipher suites it supports, includes a key share for key agreement, and includes the server name via the SNI extension. SNI matters because one IP address may host many sites, and the server needs to know which certificate to present.

The server replies with a ServerHello, its own key share and its certificate. At this point both sides can compute the same session keys without the keys ever crossing the wire. This is done with an ephemeral Diffie-Hellman exchange. Everything after the ServerHello is encrypted. The server also sends a signature proving it holds the private key matching the certificate, and a Finished message.

The browser then validates the certificate. It checks that the certificate chains up to a certificate authority the operating system or browser trusts, that it has not expired, that the hostname you requested matches a name in the certificate, and that it has not been revoked. A failure at any of these points produces the full-page warning you have seen. The browser sends its own Finished message and is ready to send data.

If you have visited the site recently, the browser may use session resumption to shorten the handshake. With 0-RTT it can even send the request alongside the first message, though this has replay risks, so servers restrict what they accept that way.

6. Sending the HTTP request

Over the now encrypted channel, the browser sends the request. In HTTP/1.1 it is plain text. A request line such as GET /shop?id=7 HTTP/1.1 is followed by headers like Host, User-Agent, Accept, Accept-Encoding and Accept-Language. HTTP/2 and HTTP/3 carry the same information in a compact binary form and can multiplex many requests on one connection. The browser also attaches any cookies it holds for that site, which is how the server recognises a logged-in user. If a cached copy exists but is stale, the browser adds conditional headers such as If-None-Match so the server can answer with a short 304 Not Modified response instead of the full body.

7. Server-side processing

The request crosses the internet and reaches the server's network edge. Often the first machine is not your application at all. It may be a CDN node, a load balancer or a reverse proxy that terminates TLS. A CDN can answer straight from its cache. Otherwise the request is forwarded to an application server. That server routes the URL to a handler, may check authentication, query a database, call other services and render HTML or JSON. This phase is entirely under the site owner's control and is often the largest slice of waiting time. It is what developers measure as server response time.

8. The first byte arrives

The server writes the status line and headers, for example HTTP/1.1 200 OK followed by Content-Type and Cache-Control, and then begins sending the body. The moment the first byte of that response reaches the browser is called Time To First Byte (TTFB). Note that TTFB includes everything above, namely DNS, TCP, TLS, the request travelling to the server, the server's work and the first byte travelling back.

What this means in practice

Three things are worth remembering. First, every stage that needs a round trip is limited by distance, so fewer round trips and closer servers help directly. Second, connection reuse, HTTP/2 or HTTP/3, TLS 1.3 and CDNs all exist mainly to cut these early costs. Third, you can see most of these stages yourself. The Network panel in your browser's developer tools breaks a request into DNS lookup, initial connection, SSL, waiting (the TTFB) and content download. When a page feels slow, that breakdown tells you whether to blame the network, the certificate setup or your own server code.

When you run git commit, Git writes a small number of files into the .git directory and then moves a pointer. Everything it stores is kept in an object database under .git/objects, and every object in that database is one of four kinds. Three of them matter for an ordinary commit: the blob, the tree and the commit. The fourth, the annotated tag, appears only when you create one. All objects are named in the same way. Git takes the content, puts a short header in front of it giving the type and the size in bytes, and computes a SHA-1 hash of the result. Newer repositories can use SHA-256 instead. The hash is the object's name. Git compresses the content with zlib and writes it to a file whose path is built from that name, with the first two hex characters as a directory and the remaining thirty-eight as the file name. The empty blob, for example, has the name e69de29bb2d1d6434b8b29ae775ad8c2e48c5391 and lives at .git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391.

A blob holds the contents of one file and nothing else. It has no file name, no permissions and no timestamp. Because the name is derived from the content, two files with identical contents share a single blob, whether they sit in different directories or belong to different points in history. If you change one byte of a file, the hash changes and Git stores a complete new blob. Git does not keep a diff at this level. Later, when it packs the repository, it stores similar objects as deltas against one another to save space, but that is an optimisation underneath the model and not part of it.

The file name and mode live in the tree. A tree object represents one directory. It is a list of entries, and each entry records a mode, a name and the hash of the object it points to. A mode of 100644 marks an ordinary file, 100755 an executable file, 120000 a symbolic link and 040000 a subdirectory. An entry for a file points to a blob, and an entry for a subdirectory points to another tree. The tree for the top of your project therefore points to blobs for the files at the root and to trees for each folder, which in turn point further down. The hash of a tree depends on the hashes of everything beneath it, so a change to one file deep in the project changes the hash of every tree on the path back up to the root. Trees for directories you did not touch keep their old hashes and are reused as they are. This is why a commit in a large repository adds only a handful of new objects.

A commit object ties a tree to its history. It is a short text record. The first line gives the hash of the root tree. After that come one parent line for each parent commit, an author line and a committer line, each with a name, an email address and a timestamp with a time zone. A blank line follows, and then the message. A first commit has no parent line, an ordinary commit has one, and a merge commit has two or more. The commit does not contain the changes you made. When Git shows you a diff, it works the diff out by comparing the tree of the commit with the tree of its parent. The parent's hash is part of the commit's own content, so each commit's name depends on the whole chain before it, and altering an old commit changes the name of every commit after it. This is why rebase and commit --amend do not edit commits. They write new ones and move a pointer to them.

Objects never change once written, so something else has to record where you are. That is the job of refs. A ref is a file containing a 40-character hash. Branches are refs under .git/refs/heads, so the file .git/refs/heads/main holds the hash of the latest commit on main. Tags made with git tag are files under .git/refs/tags, and remote-tracking branches sit under .git/refs/remotes. A branch is nothing more than one of these files, which is why creating one is instant and costs about forty bytes. When you commit, Git writes the new commit object with the current branch tip as its parent, then overwrites the branch file with the new hash. A repository with many refs may gather them into a single file called .git/packed-refs, but the idea is the same.

HEAD is the ref that says what you have checked out. Usually .git/HEAD holds text such as ref: refs/heads/main, which names a branch, and committing moves that branch. If you check out a commit directly, HEAD holds a bare hash instead. This is the detached state that Git warns about, and new commits made in it are not reachable from any branch until you give them one.

Putting this together, take a commit that edits src/app.py in a project with three folders. When you run git add, Git compresses the new file contents into a blob and records its hash against the path in the index, the file at .git/index that lists the paths and blob hashes for the next commit. When you run git commit, Git turns the index into a set of tree objects, one for each directory that changed, and writes a commit object that points to the new root tree and to the previous commit. It then updates the branch ref to the new commit's hash. You can inspect any of this yourself. The command git cat-file -p followed by a hash prints an object's contents, and git cat-file -t prints its type.

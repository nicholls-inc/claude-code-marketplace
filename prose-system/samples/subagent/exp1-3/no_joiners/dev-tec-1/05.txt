Every Git repository keeps its history in a hidden directory called .git. Open it and you find a surprisingly small design. Git is a content addressable store, which means it is a key value database where the key is derived from the value. Everything you commit ends up as one of four kinds of object, and a handful of text files called refs give those objects human names.

Objects live in .git/objects. Each one is hashed with SHA1 over a short header plus its content, though newer repositories can use SHA256 instead. The header holds the object type, a space, the content length and a null byte. The resulting hash is the object's name, written as 40 hex characters. Git compresses the content with zlib and writes it to a file whose directory is the first two characters of the hash and whose filename is the remainder. So an object named 3b18e512 and so on sits at .git/objects/3b/18e512 and so on. Because the name comes from the content, identical content always produces the same object, and changing a single byte produces a different name entirely.

Blobs

A blob stores the contents of one file and nothing else. It holds no filename, no permissions and no timestamps. If you have two files with identical text in different folders, Git stores one blob and points to it twice. If you rename a file without changing it, no new blob is needed. You can inspect one with git cat-file -p followed by a hash, and you can create one yourself with git hash-object -w.

Trees

Names and structure belong to trees. A tree is a list of entries, and each entry holds a file mode, a name and the hash of what it points to. The mode says whether the entry is a regular file, an executable, a symlink or a subdirectory. An entry for a file points to a blob. An entry for a directory points to another tree. A tree therefore describes one directory, and the root tree describes your whole project at one moment.

This produces a useful property. A tree's hash depends on the hashes of everything beneath it. If you edit one file deep inside src, its blob gets a new hash, so every tree on the path up to the root gets a new hash too. Folders you did not touch keep their old trees, and the new root tree simply points at them. That sharing is why snapshots are cheap. Git does not copy your project on each commit. It reuses every unchanged object.

Commits

A commit object ties a snapshot to history. It contains a pointer to a root tree, zero or more parent commits, an author with a timestamp and timezone, a committer with its own timestamp, and the message. The first commit in a repository has no parent, an ordinary commit has one, and a merge commit has two or more. Run git cat-file -p HEAD and you will see these fields as plain text.

Two consequences follow. First, a commit does not store a diff. It stores a complete snapshot by reference, and the diffs you see in git log -p are computed on demand by comparing two trees. Second, because a commit includes its parents' hashes, the hash of a commit covers the entire history behind it. Rewrite an old commit and every descendant gets a new hash. That is exactly what happens during a rebase, and it explains why rebased branches look like brand new commits to your teammates.

Refs

Hashes are poor names for humans, so Git adds refs. A ref is just a file containing a commit hash. Branches live under .git/refs/heads, tags under .git/refs/tags, and remote tracking branches under .git/refs/remotes. Open .git/refs/heads/main and you will find 41 bytes, which is a hash and a newline. That is all a branch is. Creating a branch writes one tiny file, which is why it feels instant.

When you commit, Git builds the new blobs and trees, writes a commit object whose parent is your current commit, and then updates the branch file to hold the new hash. The branch moves forward and the old commits stay exactly where they were.

HEAD is a special ref found at .git/HEAD. Normally it is a symbolic ref, meaning it contains the word ref and the path of a branch rather than a hash. This is how Git knows which branch is checked out. If HEAD holds a raw hash instead, you are in the detached HEAD state, and new commits will not move any branch. Over time Git may also gather refs into .git/packed-refs and gather loose objects into compact packfiles, but these are storage optimizations and do not change the model.

Putting it together

When you run git commit, the index in .git/index supplies the list of staged files. Git turns each one into a blob, builds trees from the directory layout, creates a commit that points at the root tree and your previous commit, and advances the current branch. Four ideas explain all of it. Blobs hold content, trees hold names, commits hold history and refs hold moving labels. Once you see that, commands like reset, cherry pick and reflog stop being magic and become small edits to pointers in a graph of immutable objects.

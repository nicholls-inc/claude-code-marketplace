Inside the .git Directory: How Git Stores a Commit

If you use Git daily, you know add, commit, branch and merge. Underneath those commands sits a surprisingly small design: a key-value store of immutable objects, plus a handful of text files that point into it. Open .git/objects and .git/refs and the whole model becomes visible.

The object database

Git is a content-addressable store. Every piece of data is hashed (SHA-1 traditionally, SHA-256 in newer repositories), and the hash becomes the key. The value is the content, compressed with zlib. Objects live under .git/objects/, split by the first two hex characters of the hash. An object with the id e69de29bb2d1d6434b8b29ae775ad8c2e48c5391 sits at .git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391.

Three kinds of object matter for a commit: blobs, trees and commit objects. A fourth, the annotated tag, is covered briefly below.

Blobs: file contents

A blob stores the contents of one file and nothing else. It has no filename, no permissions, no timestamp. Before hashing, Git prepends a header, "blob", a space, the byte length and a null byte, then hashes header plus content. You can reproduce this yourself:

    echo 'hello' | git hash-object --stdin

Two consequences follow. First, identical content always produces the same blob, so ten copies of a file across a repository, or across a thousand commits, cost one object. Second, renaming a file creates no new blob, because the name was never part of it.

Trees: directories

A tree object represents one directory. It is a list of entries, and each entry holds a mode (regular file, executable, symlink or subdirectory), a name, and the hash of what it points to. Entries that point to files reference blobs. Entries that point to subdirectories reference other trees. So a whole project snapshot is a tree of trees, with blobs at the leaves.

You can inspect one with git ls-tree HEAD, which prints lines like:

    100644 blob a1b2c3...    README.md
    040000 tree d4e5f6...    src

Because a tree's hash is computed from its entries, changing one file changes that blob's hash, which changes its parent tree's hash, and so on up to the root tree. Directories that were not touched keep their hashes and are shared between snapshots. This is why Git can store a full snapshot per commit without copying your whole project each time.

Commit objects: snapshots plus history

A commit is a small text object. Run git cat-file -p HEAD and you will see something like:

    tree 9f3c1e...
    parent 4b7a02...
    author Ada Lovelace <ada@example.com> 1731300000 +0000
    committer Ada Lovelace <ada@example.com> 1731300000 +0000

    Fix rounding error in invoice totals

It contains exactly four things: the hash of the root tree (the snapshot), zero or more parent commit hashes, author and committer identity with timestamps, and the message. A first commit has no parent, an ordinary commit has one, and a merge commit has two or more.

Note what is absent: no diff. Git stores snapshots, not changes. When you run git show or git diff, Git computes the difference between two trees on demand. (Packfiles, which Git creates during gc or when pushing, do delta-compress objects for disk space, but that is a storage optimization hidden behind the same object model.)

Because the commit hash covers the tree hash and the parent hash, history is a Merkle chain. Alter any old file, message or timestamp and that commit's hash changes, which changes every descendant's hash. This is why "rewriting history" with rebase or amend actually creates new commits rather than editing old ones. The originals remain in the database until garbage collection removes them.

Refs: names for hashes

Hashes are unwieldy, so Git uses refs, which are human-readable names that point to a commit. They are plain files. A branch named main is the file .git/refs/heads/main, and its entire content is one commit hash:

    $ cat .git/refs/heads/main
    4b7a02c9...

Creating a branch writes a 41-byte file. Committing on that branch writes the new commit object, then updates the file to the new hash. That is all a branch is: a movable pointer. Tags live in .git/refs/tags/, and remote-tracking branches such as origin/main live under .git/refs/remotes/. A lightweight tag is just a ref that never moves. An annotated tag is a fourth object type that stores a tagger, a message and a target, and the ref points at that object.

In large repositories Git may consolidate refs into a single .git/packed-refs file for speed, but the meaning is identical.

HEAD: where you are

The file .git/HEAD records your current position. Normally it holds a symbolic reference:

    ref: refs/heads/main

Git follows that to the branch file, then to the commit. When you check out a specific commit instead of a branch, HEAD contains a raw hash, which is the "detached HEAD" state. Commits made then have no branch file to advance, which is why they are easy to lose.

The full picture of a commit

When you run git commit, Git does roughly this. It takes the staging area (.git/index), which lists every tracked path with its blob hash, and writes tree objects for each directory. It writes a commit object pointing at the root tree, with the current HEAD commit as parent. Finally it updates the branch file named by HEAD to the new commit hash.

Edit one file in a large project and the new commit adds a handful of objects: one blob, a tree for each directory on the path to that file, and the commit. Everything else is reused by hash.

Try it

Make an empty repository, commit one file, and walk the chain by hand: cat .git/HEAD, then cat the branch file, then git cat-file -p on the commit, then on its tree, then on the blob. Five commands reproduce the entire model. Once you have seen it, branching, resetting, cherry-picking and reflog recovery all reduce to the same operation: moving small text files that point at immutable objects.

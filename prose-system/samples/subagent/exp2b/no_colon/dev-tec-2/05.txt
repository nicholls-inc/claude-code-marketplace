When you type an HTTPS address into a browser and press Enter, a surprising amount of work happens before the first byte of the response comes back. This description walks through those steps in order, using the address https://www.example.com/products as the running example.

**1. Parsing the address**

The browser first splits the address into parts. The scheme is https, the host is www.example.com, the port is implied (443 for HTTPS), and the path is /products. The scheme tells the browser to use an encrypted connection. Before going further, the browser checks a built-in list called the HSTS preload list and its own stored HSTS data. If the site is on that list, the browser will never attempt plain HTTP, even if you typed http://.

**2. Checking caches**

Before touching the network, the browser asks whether it already has what it needs. The HTTP cache might hold a fresh copy of /products, in which case the request may end here with no network traffic at all. A service worker, if the site registered one, can also intercept the request and answer it from its own storage. Only if these fail does the browser carry on.

**3. DNS resolution**

Computers connect to IP addresses, not names, so the browser must turn www.example.com into an address such as 93.184.216.34 (IPv4) or a longer IPv6 value. It checks several layers in turn. First its own DNS cache, then the operating system cache, then the hosts file. If none of these know the answer, the OS asks a recursive resolver, usually run by your ISP or a public provider.

The resolver may also have the answer cached. If not, it works down the DNS hierarchy. It asks a root server which servers handle .com, asks those which servers handle example.com, and finally asks the authoritative server for example.com for the address of www. Each answer carries a time to live (TTL) that says how long it may be cached. Newer browsers can also use DNS over HTTPS, which wraps these lookups in encryption, and may fetch HTTPS or SVCB records that advertise HTTP/3 support. DNS often costs from a few milliseconds to over a hundred, so caching matters.

**4. Opening a TCP connection**

With an IP address in hand, the browser opens a TCP connection to port 443. TCP needs a three-step handshake. The client sends a SYN packet, the server replies with SYN-ACK, and the client sends ACK. This costs one full round trip, meaning the time for a message to travel to the server and back. If the browser picked HTTP/3, it uses QUIC over UDP instead, which combines the transport and encryption handshakes and saves round trips. Browsers often learn about HTTP/3 support from an earlier visit (via the Alt-Svc header) or from DNS records.

Many browsers also try IPv6 and IPv4 in parallel, a technique called Happy Eyeballs, and use whichever connects first. If the browser already has an open connection to this host from earlier, it reuses it and skips steps 3 to 5.

**5. The TLS handshake**

Now the browser and server set up encryption using TLS. In TLS 1.3, which most modern sites use, this takes one round trip.

The client sends a ClientHello. It lists the TLS versions and cipher suites it supports, includes a random value, and includes a key share, which is its half of a key exchange. It also sends the server name (SNI) so that a server hosting many sites knows which certificate to present, and it lists the application protocols it speaks (ALPN), such as h2 and http/1.1.

The server replies with a ServerHello that picks a cipher suite and sends its own key share. At this point both sides can compute the same shared secret, and everything after it is encrypted. The server then sends its certificate chain and a signature proving it holds the matching private key.

The browser now validates the certificate. It checks that the certificate was issued by an authority the operating system or browser trusts, that the chain of signatures is intact, that the dates are valid, that the certificate covers www.example.com, and that it has not been revoked. If any check fails, you see a full-page security warning instead of the site. This step is what stops someone on the network from impersonating the server.

Once both sides send a Finished message, the secure channel is ready. If the browser has connected recently, TLS session resumption lets it skip some of this work, and TLS 1.3 can even send the request in the first flight (called 0-RTT), with some replay-attack caveats.

**6. Sending the HTTP request**

Now the browser sends the actual request, encrypted inside the TLS channel. With HTTP/1.1 it looks like plain text:

GET /products HTTP/1.1
Host: www.example.com
User-Agent: ...
Accept: text/html,...
Accept-Encoding: gzip, br
Cookie: session=abc123

The method is GET, the path is /products, and the headers carry useful details. Host names the site. Accept-Encoding says which compression formats the browser understands. Cookie includes any cookies previously set for this site. Cached copies add headers like If-None-Match so the server can answer with a short 304 Not Modified. With HTTP/2 and HTTP/3 the same information travels in a compact binary format, but the meaning is the same.

**7. What happens at the server side**

The request often does not go straight to the application. It may hit a CDN edge server near you, which answers immediately if it has a cached copy. Otherwise it passes through a load balancer, which picks a healthy backend server. A reverse proxy such as nginx may terminate TLS and forward the request. Finally the application receives it, runs routing logic, perhaps checks your cookie, queries a database, and renders a response. All of this is server think time, and it is often the largest part of the wait.

**8. The first byte arrives**

The server begins sending the response, starting with a status line and headers such as 200 OK and Content-Type: text/html, followed by the body. The moment the first byte of that response reaches the browser is called Time to First Byte (TTFB). It is a widely used performance measurement, and it covers everything described above. That means redirect time, DNS lookup, TCP connect, TLS negotiation, the request travelling to the server, the server processing it, and the first byte travelling back.

**Why this matters to you**

Knowing these stages tells you where to look when a page feels slow. You can see each phase in the Network panel of your browser's developer tools by selecting a request and opening its Timing tab, which labels DNS Lookup, Initial Connection, SSL, Waiting (TTFB), and Content Download.

Some practical lessons follow. Use a CDN so the connection is short and cached content is close to users. Enable HTTP/2 or HTTP/3 and keep connections alive so they are reused. Avoid redirect chains, because each redirect repeats much of this process, sometimes including a new DNS lookup and handshakes. Use sensible cache headers so repeat visits skip the network entirely. Keep your server work fast, since backend delay shows up directly as TTFB. Finally, resource hints like preconnect and dns-prefetch let the browser do steps 3 to 5 early for domains it knows it will need.

In short, the journey is parse, check caches, resolve the name, connect, secure the connection, send the request, wait for the server, and receive the first byte. Each step has its own cost and its own optimizations, and every one of them happens in a few hundred milliseconds on a good connection.

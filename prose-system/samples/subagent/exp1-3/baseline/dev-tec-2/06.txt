# From HTTPS Address to First Byte: What the Browser Does

When you type `https://example.com/products` and press Enter, nothing is sent to the server immediately. The browser does a good deal of work first, and most of it happens before any part of your request leaves your machine. The wait between pressing Enter and seeing the first byte of the response is made up of these steps, and knowing them helps you diagnose slow pages.

## 1. Parsing the URL

The browser splits the address into parts:

- **Scheme**: `https`, meaning HTTP over an encrypted TLS connection.
- **Host**: `example.com`.
- **Port**: not given, so the default for HTTPS, 443, is used.
- **Path**: `/products`, plus any query string or fragment. The fragment (`#...`) is never sent to the server.

If you typed something that is not a valid URL, the browser treats it as a search instead. Before going to the network, it also checks a built-in HSTS preload list and its own HSTS cache. If the site is known to require HTTPS, an `http://` address is upgraded without any insecure request being made.

## 2. Checking caches and service workers

The browser looks for a stored copy before using the network. If a service worker controls the page, it gets the first chance to answer the request. Next comes the HTTP cache. A cached response that is still fresh, based on `Cache-Control: max-age` or `Expires`, is used directly and no network request is made. A stale response may be revalidated with the server using `If-None-Match` or `If-Modified-Since`. A `304 Not Modified` answer lets the browser reuse the stored body, though you still pay for the round trip.

## 3. DNS resolution

Browsers connect to IP addresses, so `example.com` has to be translated into one. The lookup passes through several layers, each of which can answer from its cache:

1. The browser's own DNS cache.
2. The operating system's resolver cache and the hosts file.
3. The configured recursive resolver, usually run by your ISP or a public provider. It answers from its cache if it can. Otherwise it queries the root servers, then the `.com` servers, then the domain's authoritative name server.

The result is one or more A (IPv4) or AAAA (IPv6) records, each with a TTL that says how long it may be cached. A cold lookup can take tens to hundreds of milliseconds. A cached one is close to instant. Modern browsers may also use DNS over HTTPS and may query the HTTPS record type, which can advertise HTTP/3 support. If the DNS lookup fails, you get an error like `DNS_PROBE_FINISHED_NXDOMAIN` and the process stops here.

## 4. Choosing a connection

If the browser already has an open connection to this origin, for example from a previous page, it reuses it and skips the next three steps. Otherwise it needs a new one. HTTP/2 and HTTP/3 multiplex many requests over one connection, so reuse matters a great deal.

## 5. TCP handshake

For HTTP/1.1 and HTTP/2, the browser opens a TCP connection to the server's IP on port 443 with a three-way handshake:

1. Client sends `SYN`.
2. Server replies `SYN-ACK`.
3. Client sends `ACK`.

This costs one full round trip (RTT) before any data can flow. If the network is slow or the server is far away, this step is visibly expensive. HTTP/3 does not use TCP. It runs over QUIC on UDP, which merges the transport and encryption handshakes into one. Browsers usually learn about HTTP/3 from an earlier visit (the `Alt-Svc` header) or from a DNS HTTPS record, and they may race it against TCP.

## 6. TLS handshake

Now the encrypted channel is set up. In TLS 1.3, the common case today:

1. **ClientHello**: the client sends its supported cipher suites, a key share, and the **SNI** (Server Name Indication) extension containing `example.com`. SNI lets one IP address host many sites, as the server needs to know which certificate to present. It also carries ALPN, the list of protocols the client speaks (`h2`, `http/1.1`).
2. **ServerHello and certificate**: the server picks a cipher suite and ALPN protocol, completes the key exchange, and sends its certificate chain.
3. **Certificate validation**: the browser checks that the certificate chains up to a trusted root authority, has not expired, has not been revoked, and covers the requested hostname. If any check fails you see a full-page warning, such as `NET::ERR_CERT_DATE_INVALID`. Developers often meet this with expired or self-signed certificates.
4. **Finished**: both sides derive the same session keys, and everything after this is encrypted.

TLS 1.3 needs one extra round trip. TLS 1.2 needs two. On a return visit, session resumption can shorten this, and 0-RTT can let a client send data with its first flight, though with replay caveats. In total, a brand-new HTTPS connection costs roughly two to three round trips (DNS aside) before the browser can even ask for the page.

## 7. Sending the HTTP request

Over the encrypted channel, the browser sends the request. In HTTP/1.1 form it looks like this:

```
GET /products HTTP/1.1
Host: example.com
Accept: text/html,...
Accept-Encoding: gzip, br
Accept-Language: en-GB
Cookie: session=abc123
User-Agent: ...
```

HTTP/2 and HTTP/3 send the same information as compressed binary frames, using pseudo-headers like `:method` and `:path` in place of the request line. The browser attaches cookies that match the host and path, along with any cached validators from step 2. A `GET` has no body, so the whole request is typically small enough to fit in one packet.

## 8. Server-side processing

The request crosses the network, often arriving at a CDN or load balancer first. The CDN may answer from its edge cache. If not, it forwards the request to the origin. The origin's web server or reverse proxy (nginx, for example) passes it to your application. The app then routes `/products`, checks the session cookie, queries a database, renders HTML or JSON, and builds a response. This is usually the largest controllable piece of the wait. Slow queries, cold starts on serverless platforms, and heavy server rendering all show up here.

## 9. The first byte

The server writes the response status line and headers (`HTTP/1.1 200 OK`, `Content-Type`, `Set-Cookie`, and so on), followed by the start of the body. The moment the first byte reaches the browser is what performance tools call **Time to First Byte (TTFB)**. Note that TTFB as measured by Chrome DevTools and the Navigation Timing API includes redirects, DNS, connection setup, TLS, the request, and server think time. Its "Waiting for server response" phase covers only steps 7 to 9.

## Putting it together

On a cold visit, the sequence is: parse, cache check, DNS, TCP, TLS, request, server work, first byte. Redirects, such as `http` to `https` or the non-`www` host to the `www` one, restart most of this sequence for each hop, which is why redirect chains are costly. For a developer, the practical levers follow directly from the steps: keep DNS TTLs reasonable, serve over HTTP/2 or 3, enable TLS 1.3, avoid redirect chains, use a CDN, cache aggressively, and keep server response time low. Open the Network panel in DevTools and look at a request's Timing breakdown to see each of these phases measured on a real page.

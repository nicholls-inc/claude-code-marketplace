When a person types https://example.com/products?page=2 into the address bar, or clicks a link with that address, the browser first splits it into parts. The scheme is https, the host is example.com, the path is /products and the query is page=2. No port is given, so the browser uses 443, the default for HTTPS. If the host contains non-ASCII characters, they are converted to an ASCII form called punycode, because DNS only handles ASCII labels.

Before it uses the network, the browser checks what it already knows. It looks at its HSTS list, which records hosts that must only be reached over HTTPS, and at a preload list built into the browser for some large sites. If a service worker controls the page, it can answer the request itself. The HTTP cache is consulted next. A stored response that is still fresh under its Cache-Control max-age is used and no traffic is sent. A stale response may be revalidated with a conditional request, which needs the connection steps below. If the browser already has an open connection to the same host, it sends the request on that connection and skips DNS, TCP and TLS. A first visit usually has no such connection.

The browser needs an IP address for example.com. It checks its own DNS cache, then asks the operating system, which checks its cache and the hosts file. If neither has an answer, the operating system sends a UDP query to a recursive resolver, usually on port 53. The resolver is run by the internet provider, the employer or a public service such as 1.1.1.1 or 8.8.8.8. Some browsers use DNS over HTTPS instead, which sends the same question to a chosen resolver inside an encrypted connection. The recursive resolver answers from its own cache when it can. When it cannot, it starts at one of the root servers, which refer it to the servers for the .com top-level domain. Those servers refer it to the authoritative name servers for example.com. The authoritative servers return the records. An A record holds an IPv4 address and an AAAA record holds an IPv6 address. Each answer carries a time to live in seconds, which tells every cache how long it may keep the record. A lookup answered from a cache takes a millisecond or two. A full lookup from a cold cache commonly takes between 20 and 120 milliseconds. If the browser receives both IPv4 and IPv6 addresses, it tries IPv6 first, starts the other family after a delay of a few hundred milliseconds at most, and keeps whichever connects first. This is called Happy Eyeballs.

With an address, the browser opens a TCP connection to port 443. The client sends a SYN segment, the server replies with SYN-ACK, and the client sends an ACK. This costs one round trip. If the round trip time between the two machines is 50 milliseconds, the handshake takes about 50 milliseconds before any data can be sent. The server's congestion window starts small, commonly 10 segments of about 1,460 bytes each, which limits how much it can send before it hears back from the client. If the server advertises HTTP/3 through an Alt-Svc header or an HTTPS DNS record, the browser may use QUIC over UDP instead. QUIC combines the transport and encryption handshakes into one round trip.

TLS then runs on top of the connection. In TLS 1.3 the browser sends a ClientHello. It lists the protocol versions and cipher suites the browser supports, a random value, and a key share for the key exchange, usually using the X25519 curve. It also carries the Server Name Indication extension, which holds the host name so that a server hosting many sites knows which certificate to present. The ALPN extension lists h2 and http/1.1 as the protocols the browser can speak. The server answers with a ServerHello that picks a cipher suite and supplies its own key share. From the two key shares, both sides compute the same secret and derive session keys, and everything the server sends after the ServerHello is encrypted. The server then sends its certificate chain, a signature showing that it holds the matching private key, and a Finished message. The client checks these and sends its own Finished message. This takes one round trip in TLS 1.3. TLS 1.2 needed two.

The browser validates the certificate during this exchange. The host name must match a name in the certificate's Subject Alternative Name field. The current date must fall inside the validity period, and public certificates are limited by the CA/Browser Forum to a period that has been shortening over the years. The chain must lead from the server's certificate through one or more intermediate certificates to a root certificate in the trust store of the browser or operating system, and each signature in the chain is verified. Browsers also expect proof that the certificate was recorded in Certificate Transparency logs, and they generally check revocation against lists they already hold rather than contacting the issuer on each visit. If any check fails, the browser shows a full-page warning and does not send the request.

With the encrypted channel in place, the browser sends the request. Under HTTP/2 this is a HEADERS frame. It carries pseudo-headers for the method, which is GET, the scheme, the authority, which is example.com, and the path, which is /products?page=2. It also carries ordinary headers such as User-Agent, Accept, Accept-Encoding and Accept-Language, and a Cookie header holding any cookies stored for that host. The headers are compressed with a scheme called HPACK. Under HTTP/1.1 the same information is sent as lines of text, beginning with GET /products?page=2 HTTP/1.1 and a Host header. TLS encrypts every byte before it enters TCP.

The request arrives at the server's address, which is often a CDN or a load balancer and not the machine that builds the page. That front end ends the TLS session. It either answers from its own cache or forwards the request to an origin server over a second connection. The origin's web server passes the request to the application, which may read from a database, call other services and render HTML. This is usually the largest and most variable part of the wait. It can be a few milliseconds for cached content and several hundred for a page that needs many queries.

When the server has the start of its answer, it sends the status line and headers, for example a 200 status and a Content-Type of text/html. These travel back through the same encrypted connection. The browser decrypts the first record, and the first byte of the response has arrived. The time from the start of navigation to this point is called time to first byte, and it includes every step described above. For a first visit with a 50 millisecond round trip, DNS might take 40 milliseconds, TCP 50, TLS 50, and the request and response together another 50, plus 30 milliseconds of server work. That gives about 220 milliseconds. Later requests to the same site skip most of these steps because the DNS answer is cached and the connection is still open, which is why the second page of a site tends to start loading sooner than the first. The Network panel in a browser's developer tools shows these stages under the names DNS Lookup, Initial connection, SSL and Waiting for server response, so you can see for yourself where the time goes on any request.

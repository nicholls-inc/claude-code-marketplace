## How Git Stores a Commit

Run `git init` and look inside `.git`. The directory you find is a small database plus a few pointers. Git is a content-addressed store: every piece of data is saved under a key computed from its own content. Everything else you do in Git sits on top of this.

### The object database

Objects live in `.git/objects`. Each one is identified by a SHA-1 hash (newer repositories can use SHA-256), and the hash is computed over a short header (type, space, byte length, NUL) followed by the content. The first two hex characters of the hash name a subdirectory, and the remaining characters name the file. The file holds the zlib-compressed object. Because the key comes from the content, identical content always gets the same key and is stored once. Objects are never modified. A change means a new object with a new hash.

There are four object types. Three of them describe a commit.

### Blobs: file contents

A blob holds the bytes of one file and nothing else. It has no filename, no permissions and no timestamp. If you have two files with identical contents in different directories, they share one blob. You can see this directly:

```
$ echo "hello" | git hash-object -w --stdin
ce013625030ba8dba906f756967f9e9ca394464a
$ git cat-file -p ce01362
hello
```

`git add` does the first half of this. It hashes the file, writes a blob, and records the result in the index (`.git/index`), the staging area. The index is a sorted list of paths, each with a mode and a blob hash. It is the proposed next snapshot.

### Trees: directories

A tree object is a directory listing. Each entry holds a mode, a type, a hash and a name:

```
$ git cat-file -p main^{tree}
100644 blob a5c1966...  README.md
040000 tree 9f3b2e1...  src
100755 blob 7d2c8aa...  build.sh
```

The names and permissions live here, not in the blobs. A subdirectory is another tree, referenced by its hash, so a whole project is a tree of trees with blobs at the leaves. The hash of the top-level tree depends on every entry below it. Change one byte in one file and its blob hash changes. That changes the hash of the tree containing it, then that tree's parent, and so on up to the root. This is a Merkle tree. It also means an unchanged directory keeps its hash, and new snapshots reuse the old subtrees and blobs without copying them.

`git commit` turns the index into trees (the porcelain wraps `git write-tree`). Only the entries that changed produce new objects.

### Commit objects: snapshots with history

A commit is a small text object:

```
$ git cat-file -p HEAD
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 1f7a3c9e0d5b8a2c6e4f1b7d9a3c5e8f0b2d4a6c
author Ada <ada@example.com> 1731300000 +0000
committer Ada <ada@example.com> 1731300000 +0000

Fix off-by-one in pagination
```

It has four kinds of content. The `tree` line points to the root tree of the complete snapshot. Zero or more `parent` lines point to previous commits: none for the first commit, one for a normal commit, two or more for a merge. The author and committer lines carry identity and time. The message follows.

A commit does not store a diff. It stores a complete snapshot, by reference. When you run `git show` or `git diff`, Git computes the differences by comparing the trees of two commits. The parent hash is part of the commit's own content, so a commit's hash covers its entire ancestry. Rewriting an old commit (amend, rebase) cannot be done in place. It creates new commits with new hashes and leaves the old ones to be garbage collected later. This is why history rewrites are visible to anyone who has the old hashes.

The fourth object type, the annotated tag, wraps a reference to another object with a name, a tagger and a message. It is less important here.

### Refs: names for hashes

Nobody wants to type forty hex characters, and the object database has no concept of "the latest commit". That job belongs to refs, which are plain files containing a hash.

```
$ cat .git/refs/heads/main
1f7a3c9e0d5b8a2c6e4f1b7d9a3c5e8f0b2d4a6c
```

A branch is exactly that: a file under `.git/refs/heads/` holding the hash of its tip commit. Tags live under `refs/tags/`, and remote-tracking branches under `refs/remotes/`. Creating a branch writes 41 bytes. Committing moves the current branch file to the new commit hash. Nothing else changes. This is why branching in Git is cheap. (Repositories with many refs also use `.git/packed-refs`, a single file that holds many refs compactly.)

`HEAD` is a special ref, `.git/HEAD`. Usually it is a symbolic ref, a file containing `ref: refs/heads/main`, meaning "the current branch is main". When you check out a commit directly, HEAD contains a raw hash instead. That is the detached HEAD state: new commits move HEAD alone, with no branch to carry them, so nothing keeps them reachable once you switch away. The reflog (`.git/logs`) records where HEAD and each branch have pointed, which is what lets you recover them.

### Putting it together

When you run `git commit -m "msg"`:

1. Git writes a tree object for each directory whose contents changed, from the index, reusing unchanged subtrees. Blobs were already written at `git add`.
2. It writes a commit object that names the root tree, the current HEAD commit as parent, your identity, and your message.
3. It updates the branch ref that HEAD points to, so the branch now holds the new commit's hash.

Three or four small files are created and one is overwritten. Everything you do day to day, such as log, checkout, merge and rebase, is walking this graph of commits, trees and blobs, or moving refs around inside it.

### Further notes

Over time Git also packs loose objects into packfiles (`.git/objects/pack`), storing similar objects as deltas against each other. This is purely a storage optimization. The logical model above is unchanged. To explore, `git cat-file -t <hash>` shows an object's type, `git cat-file -p <hash>` prints it, and `git ls-tree` and `git rev-parse` help you navigate.

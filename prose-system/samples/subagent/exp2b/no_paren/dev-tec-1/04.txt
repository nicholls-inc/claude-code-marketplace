Every Git repository keeps its history in a hidden directory called .git. Inside it, the part that matters most is the object database, a folder named objects. Git is, at its core, a content-addressable key-value store. You give it some content, it computes a SHA-1 hash of that content, and it saves the content under that hash. Everything you think of as a commit, a file or a directory is stored this way. Four kinds of object exist: blobs, trees, commits and annotated tags. Branches and tags are not objects at all. They are refs, which are simple pointers into this store.

Blobs

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no timestamp. Git hashes a short header, the word blob followed by the content size, together with the file bytes. The resulting 40 character hex digest becomes the object's ID.

On disk, the first two characters of the ID name a subdirectory of .git/objects and the remaining 38 name the file inside it. The file contents are compressed with zlib. You can read one with git cat-file -p followed by the ID, and you can create one yourself with git hash-object -w.

Because the ID depends only on content, two identical files anywhere in your project, or anywhere in your history, share a single blob. Renaming a file creates no new blob. Changing one byte creates an entirely new one. Git does not store diffs between versions at this level. Each version of a file is stored whole, and a later step called packing compresses similar blobs against each other to save space.

Trees

Since blobs carry no names, something must map names to content. That is the job of a tree. A tree object represents one directory. It is a list of entries, and each entry records a file mode, a name and the ID of another object.

An entry pointing to a blob represents a file. The mode says whether it is a regular file, an executable or a symbolic link. An entry pointing to another tree represents a subdirectory. A project with nested folders is therefore a tree of trees, with blobs as the leaves.

The ID of a tree is the hash of its entries. This has a useful consequence. If you edit one file deep in your project, its blob changes, so the tree containing it changes, so that tree's parent changes, and so on up to the root tree. Directories you did not touch keep the same IDs and are reused as they are. This is why a snapshot of a huge repository is cheap. You can inspect the root tree with git cat-file -p HEAD^{tree}.

Commit objects

A commit object is a small text record. It contains the ID of one root tree, which is the complete snapshot of the project at that moment. It contains zero or more parent commit IDs. It also holds an author line and a committer line, each with a name, an email address and a timestamp, followed by a blank line and the commit message.

Try git cat-file -p HEAD in any repository and you will see exactly this. The first commit in a repository has no parent. An ordinary commit has one. A merge commit has two or more.

Notice what a commit does not contain. It holds no diff and no list of changed files. When Git shows you a diff, it computes it on demand by comparing the root trees of two commits. A commit is a snapshot plus a link to its history.

Because the parent IDs are part of the data being hashed, each commit ID depends on the entire history behind it. Change an old commit and its ID changes, which changes every descendant. This is why rewriting history with rebase produces new commits rather than altering existing ones, and why the old ones still exist for a while afterwards.

Refs

Hashes are hard to remember, so Git uses refs, which are human readable names that point to commit IDs. A ref is nothing more than a file containing a 40 character hash. A branch named main is the file .git/refs/heads/main. A lightweight tag is a file under .git/refs/tags. Remote tracking branches live under .git/refs/remotes. Large repositories may bundle many refs into a single file called .git/packed-refs for speed, but the idea is the same.

Making a commit moves a branch forward. Git writes the new commit object, then updates the current branch file to contain the new ID. Creating a branch is just writing a new 41 byte file. That is why branching in Git is nearly instant.

HEAD

The file .git/HEAD records where you are. Usually it holds text like ref: refs/heads/main, meaning HEAD points at a branch, which in turn points at a commit. This is called a symbolic ref. When you check out a specific commit rather than a branch, HEAD contains a raw commit ID instead. That is the detached HEAD state.

Putting it together

Suppose you edit one file and run git add and git commit. Git first compresses each changed file into a blob. The index, a file at .git/index that holds your staging area, records the file names with their blob IDs. On commit, Git turns the index into a set of tree objects, writes a commit object that points at the new root tree and at the previous commit as its parent, and finally moves the current branch ref to the new commit.

That is the whole mechanism. Immutable, hash-named objects hold content, structure and history, while tiny mutable files hold names. Once you see that, commands that seemed magical, such as reset, cherry-pick and reflog, become simple operations on pointers and objects.

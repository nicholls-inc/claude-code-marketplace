How Git Stores a Commit

If you use Git daily, you know add, commit, branch and merge. Underneath, Git is a simple key-value store with a few object types and some small text files. Everything lives in the .git directory at the root of your repository, and once you see the pieces, much of Git's behavior stops being mysterious.

The object database

Inside .git/objects, Git stores content addressed by hash. Every object is hashed (SHA-1 traditionally, SHA-256 in newer repositories) over a short header plus its content, and that hash is the object's name. The object is compressed with zlib and written to a file whose path comes from the hash: the first two hex characters become a directory, the rest the filename. Because the name derives from the content, identical content always has the same name, and changing a single byte yields a completely different one. Objects are immutable. Git never edits an object; it only adds new ones.

There are four object types. Three matter for a commit: blobs, trees and commits. (The fourth, the annotated tag, comes up later.)

Blobs

A blob holds the raw contents of one file and nothing else. No filename, no permissions, no timestamps. If you have ten files with identical contents, Git stores one blob. Renaming a file creates no new blob at all, since the content has not changed. You can inspect one with git cat-file -p followed by a hash, which prints the file as it was.

Trees

A tree represents a directory. It is a list of entries, and each entry has a mode (for example 100644 for a regular file, 100755 for an executable, 040000 for a subdirectory), a type, a hash and a name. File entries point to blobs; directory entries point to other trees. This is where filenames live, which is why a rename changes a tree but not a blob.

A tree is a snapshot of one directory, and the root tree is a snapshot of your whole project. Because hashes cover content, any change to a file changes its blob hash, which changes its parent tree's hash, and so on up to the root. Unchanged subdirectories keep the same hash, so a new commit reuses all the trees and blobs that did not change. This is how Git keeps snapshots cheap: each commit is conceptually a full copy, but physically it shares almost everything with its predecessor.

Commit objects

A commit is a small text object with a few fields. It names a tree (the root tree for the project at that moment), zero or more parent commits, an author with timestamp, a committer with timestamp, and the message. You can see it with git cat-file -p HEAD:

tree 9f3c...
parent 4be1...
author Ada <ada@example.com> 1731300000 +0000
committer Ada <ada@example.com> 1731300000 +0000

Note what a commit is not. It is not a diff. Diffs are computed on demand by comparing two trees. A commit is a pointer to a full snapshot plus metadata about where it came from. The parent line creates the history: each commit points backward to its parent, forming a directed graph. The first commit has no parent, and a merge commit has two or more. Since the parent's hash is part of the commit's own content, changing any old commit changes its hash and every descendant's. That is why rewriting history, via rebase or amend, produces new commits rather than modifying existing ones.

Refs

Hashes are poor for humans, so Git adds refs: named pointers to commits. A branch is just a file under .git/refs/heads containing a 40-character hash. Open .git/refs/heads/main and you will see exactly that and a newline. Tags live under .git/refs/tags, and remote-tracking branches under .git/refs/remotes. Creating a branch writes a tiny file; it copies no code, which is why branching is instant.

When you commit, Git writes the new blobs and trees, writes the commit object with the current commit as its parent, and then updates the current branch file to hold the new commit's hash. That last step is what "advancing a branch" means. Nothing else moves.

Packed refs exist too. In a repository with many refs, Git consolidates them into a single .git/packed-refs file for efficiency, and loose files override it. Likewise, objects begin life as loose files but are periodically collected into compact packfiles under .git/objects/pack, where similar objects are stored as deltas. This is a storage optimization only; the logical model stays the same.

HEAD

The file .git/HEAD says where you currently are. Usually it contains a symbolic reference such as ref: refs/heads/main, meaning "the current branch is main." When you check out a specific commit directly, HEAD instead holds a raw hash. That is the detached HEAD state, and the only difference is that new commits are not tracked by any branch name, so they are easy to lose.

Annotated tags are the fourth object type: a tag object points to a commit and adds a tagger, date and message. A lightweight tag is merely a ref.

The index

One more file completes the picture: .git/index, the staging area. It lists the paths and blob hashes you intend to commit next. Running git add writes blobs into the object database and records them in the index; git commit builds trees from the index, so what you staged, not what is in your working directory, is what gets committed.

Seeing it yourself

Try this in a scratch repository. Make a commit, run git cat-file -p HEAD to get the tree hash, then git cat-file -p on that hash to list its entries, then on a blob hash to see the file. You will have walked from ref to commit to tree to blob, which is the entire storage model.

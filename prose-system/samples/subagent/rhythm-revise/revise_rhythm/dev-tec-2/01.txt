When you type an HTTPS address such as https://www.example.com/shop?item=7 into a browser and press Enter, the browser first works out what you meant: it checks whether the text is a full URL or a search phrase, splits a URL into its scheme (https), host (www.example.com), port (443 by default for HTTPS), path and query string, and consults its own state before touching the network. If the host is on the browser's HSTS preload list, or the site has previously sent a Strict-Transport-Security header, the browser will refuse to use plain HTTP even if you had typed it. It also checks the HTTP cache, and if it holds a fresh, unexpired copy of the resource, it can serve it immediately and the network never gets involved, which is why the first byte of a repeat visit can arrive in effectively zero time.

Assuming nothing usable is cached, the browser needs an IP address, because networks route packets to addresses, not names, so it asks the DNS system to resolve the host. First it looks in its own DNS cache, then asks the operating system's resolver, which has its own cache, and then queries a recursive resolver, usually run by your ISP or a public provider. If that resolver does not know the answer, it walks the hierarchy on your behalf: it asks a root server which servers handle the .com top-level domain, asks those which servers are authoritative for example.com, and asks the authoritative server for the address of www. The answer carries a time-to-live telling every cache along the way how long it may be reused. Often the name is an alias that points to a CDN, and the final address you receive may depend on where you are, so that you reach a nearby data centre. Modern browsers may also ask for HTTPS or SVCB records in the same lookup, which can advertise that the server supports HTTP/3. Resolution can take anywhere from a millisecond to a few hundred, and it is a common source of avoidable latency.

With an address in hand, the browser opens a connection, traditionally over TCP, which provides an ordered, reliable byte stream. TCP begins with a three-way handshake: the client sends a SYN, the server replies with a SYN-ACK, and the client sends an ACK. That costs one full round trip, meaning the time for a packet to travel to the server and back, before any application data can flow. Along the way your packets are wrapped in IP packets and handed from your device to your router, across your ISP, and over many routers, each deciding the next hop. If the browser already has an idle, kept-alive connection to this host, it reuses it and skips this step, as well as the TLS step below. HTTP/3 is different: it runs over QUIC, which uses UDP and folds the transport and encryption handshakes together, saving round trips. The browser typically learns about HTTP/3 from earlier visits or from DNS and may race it against TCP.

Because the address is HTTPS, the connection must be encrypted and the server authenticated before anything private is sent, which is the job of TLS. In TLS 1.3, the client sends a ClientHello listing the protocol versions and cipher suites it supports, a random value, and a key share, which is the client's half of a Diffie-Hellman exchange. It also includes the Server Name Indication extension, the hostname in plain form, so that a server hosting many sites on one IP address knows which certificate to present. It may also offer ALPN, a list of application protocols such as h2 and http/1.1, so the two sides agree on the HTTP version in the same exchange. The server answers with its chosen cipher suite, its own key share, and its certificate chain. Both sides can now derive the same shared secret without ever sending it, and the rest of the handshake is encrypted. The server proves it holds the private key matching the certificate by signing the handshake transcript, and both sides send a Finished message. TLS 1.3 needs one round trip; the older TLS 1.2 needed two. If you have visited recently, session resumption can shorten this further, and with 0-RTT some requests can even ride along with the first flight, though with caveats about replay.

The certificate check happens in the middle of this. The browser verifies that the certificate covers the hostname you asked for, that it is within its validity dates, and that it chains up through intermediate certificates to a root authority the operating system or browser already trusts. It may check revocation status through stapled OCSP responses or compressed revocation lists. If any of this fails, you see a full-page warning rather than the site, which is the whole point: the padlock means you are talking to the holder of that name's certificate, not to someone in the middle.

Only now does the browser send the HTTP request, encrypted inside the TLS session: a method and path, such as GET /shop?item=7, plus headers including Host (or the :authority pseudo-header in HTTP/2 and 3), a User-Agent, Accept and Accept-Encoding to say which formats and compressions it understands, Accept-Language, and any cookies stored for that domain. In HTTP/2 and HTTP/3 these headers are compressed with HPACK or QPACK and sent as binary frames on a stream, which allows many requests to share one connection without blocking each other at the HTTP level. Cookies and cached validators matter here too: if the browser holds a stale copy with an ETag, it adds If-None-Match so the server can answer with a tiny 304 Not Modified instead of resending everything.

The request then travels to the server, often not your own origin application but a CDN edge or load balancer that terminates TLS. That machine may serve the page from its own cache, or forward the request to an origin server, perhaps through a reverse proxy, an application framework, a database query, and template rendering. All of that server-side thinking time sits between your request and the answer, and it is usually the largest single piece of what developers call time to first byte.

The moment the first byte of the response, beginning with the status line or the HTTP/2 headers frame, arrives back at the browser, the wait is over. Time to first byte is therefore the sum of everything above: DNS, connection setup, TLS, one request trip, server processing and one response trip. Understanding that sum is how you decide what to optimise, whether that means fewer redirects, a faster DNS provider, connection reuse, a CDN, or a quicker backend.

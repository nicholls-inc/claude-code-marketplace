When you run git commit, the first thing to know is that Git is, at its core, a content-addressable key-value store. Everything inside the .git directory is an object, and every object is stored under a name derived from the SHA-1 hash (or SHA-256 in newer repositories) of its contents. Hash the contents, and you get the key; ask for the key, and you get exactly those contents back. Because the name is computed from the data, two identical files anywhere in your history are stored once, and any corruption or tampering changes the name and is therefore detectable. Objects live in .git/objects, fanned out into subdirectories named after the first two hex characters of the hash, with the remaining thirty-eight characters as the filename. Each object is a zlib-compressed file that begins with a short header giving its type, a space, its size in bytes and a null byte, followed by the payload. Periodically Git also packs many objects into a single pack file with delta compression, but conceptually the loose-object model is the whole story.

There are four object types, and three of them make up a commit. The simplest is the blob, which holds the raw bytes of one file and nothing else, with no filename, no permissions and no timestamp. If you have two files with the same contents in different directories, or the same file at a hundred different points in history, they all point to one blob. When you run git add, Git hashes each file you stage, writes a blob into the object database straight away, and records the result in the index, the staging area kept in .git/index. This is why a staged file survives even if you then delete it from your working tree: its contents are already stored.

The next type is the tree, which gives blobs their names and their structure by acting as a directory listing. Each entry holds a file mode (such as 100644 for a regular file, 100755 for an executable, 120000 for a symlink or 040000 for a subdirectory), a name, and the hash of the object that entry refers to. For a file, that hash points to a blob; for a subdirectory, it points to another tree. So a project with nested folders becomes a tree of trees, and the single hash of the top-level tree acts as a fingerprint for the entire state of your project at one moment. Change one character in one deeply nested file and its blob gets a new hash, so its parent tree gets a new hash, and so on all the way up to the root, while every tree and blob that did not change keeps its old hash and is reused. This is how Git can snapshot a large repository cheaply: a commit does not copy your files, it just creates new tree objects along the path to whatever changed and reuses everything else, and when you run git commit, Git builds these trees from the index.

The commit object is what ties a snapshot to history, and it is a small text object of a handful of lines: it names the hash of the root tree, one parent line for the previous commit (none for the first commit in a repository, and two or more for a merge), an author line with a name, email, timestamp and timezone, a committer line with the same details, then a blank line and your commit message, and nothing more. A commit does not store a diff, and it does not store the files themselves; the diffs you see in git show or git log -p are computed on the fly by comparing the trees of a commit and its parent. Because a commit's hash is computed from its contents, which include the parent's hash, each commit effectively vouches for the entire history behind it. This is why rewriting an old commit, with a rebase or an amend, produces a new hash for that commit and every descendant of it: they are genuinely different objects, and the old ones simply stop being reachable until garbage collection eventually removes them.

Hashes are accurate but unfriendly, and this is where refs come in. A ref is a human-readable name that points at a commit, and unlike objects, refs are mutable. They live as tiny files under .git/refs. A branch called main is nothing more than the file .git/refs/heads/main containing a forty-character commit hash. Tags are similar files under .git/refs/tags, though annotated tags are also stored as a fourth object type that carries a tagger and message, and remote-tracking branches such as origin/main live under .git/refs/remotes. When you make a new commit on a branch, Git writes the new commit object, with the current commit as its parent, and then simply overwrites that branch file with the new hash. That single small write is what moving a branch means, and it is why creating a branch is instant and costs only forty-one bytes. Git may also consolidate many refs into a single .git/packed-refs file, but the meaning is the same.

Finally, there is HEAD, the file .git/HEAD, which tells Git where you currently are. Normally it holds a symbolic reference, a line such as ref: refs/heads/main, meaning that your checked-out branch is main and that new commits should advance it. When you check out a specific commit instead, HEAD holds a raw hash directly, which is what Git means by a detached HEAD: new commits advance nothing but HEAD itself, so no branch name keeps them reachable if you move away.

Put together, the picture is simple: HEAD points to a branch, the branch points to a commit, the commit points to a root tree and to its parent commits, and trees point to blobs and subtrees. You can explore all of it yourself with git cat-file -p followed by any hash, and by browsing .git/objects and .git/refs.

When you type an HTTPS address into a browser and press Enter, a surprising amount of work happens before the first byte of the response shows up. This description follows that journey in order, using https://www.example.com/products as the running example.

**1. Parsing the address**

The browser first splits the address into parts. The scheme is https, the host is www.example.com, the port is implied as 443 (the default for HTTPS), and the path is /products. The scheme matters because it tells the browser that the connection must be encrypted. The browser also checks whether the host is on its HSTS list. HSTS (HTTP Strict Transport Security) is a header that sites send to say "only ever talk to me over HTTPS". If the host is on that list, the browser will refuse to fall back to plain HTTP.

**2. Checking caches and service workers**

Before touching the network, the browser looks locally. A service worker registered for the site may intercept the request and answer from its own cache. The browser's HTTP cache may also hold a fresh copy of /products, in which case no network request is needed at all. Only if both come up empty does the browser go to the network.

**3. DNS lookup**

Computers connect to IP addresses, not names, so the browser must translate www.example.com into an address such as 93.184.216.34. This is DNS, the Domain Name System. The lookup checks several caches in turn. These are the browser's own cache, the operating system's cache, and then a recursive resolver, which is usually run by your ISP or a public provider. If the resolver does not know the answer, it asks the root servers, then the servers for the .com top-level domain, then the site's own authoritative name server. The answer comes back with a TTL (time to live) that says how long it can be cached. Modern browsers may also ask for HTTPS records, which can advertise support for HTTP/3 and other connection hints. DNS often takes tens of milliseconds on a cold lookup and almost nothing when cached.

**4. Opening a TCP connection**

With an IP address, the browser opens a TCP connection to port 443. TCP gives a reliable, ordered stream of bytes, and it starts with a three-step handshake. The client sends SYN, the server replies SYN-ACK, and the client answers with ACK. This costs one full round trip before any real data can flow. If the site uses HTTP/3, the browser instead uses QUIC over UDP, which merges the transport and encryption handshakes to save time. The TCP path is still the most common to explain, so we continue with it.

**5. The TLS handshake**

HTTPS is HTTP carried inside TLS (Transport Layer Security). TLS gives three guarantees. Nobody can read the traffic (confidentiality), nobody can alter it unnoticed (integrity), and you are talking to the real server (authentication).

In TLS 1.3, the handshake works roughly like this.

- The client sends a ClientHello. It lists the TLS versions and cipher suites it supports and includes a key share, which is its half of a key exchange. It also includes the SNI (Server Name Indication) extension containing www.example.com, so a server hosting many sites knows which certificate to present. It also lists protocols it can speak, such as h2 and http/1.1, using ALPN.
- The server replies with a ServerHello containing its own key share. At this point both sides can compute the same shared secret without ever sending it. Everything after this is encrypted.
- The server sends its certificate chain and a signature proving it holds the matching private key.
- Both sides send a Finished message, and application data can begin.

TLS 1.3 needs just one round trip. Older TLS 1.2 needed two. On a repeat visit, session resumption can shorten this further.

**6. Validating the certificate**

The certificate is how the browser knows it has reached the real www.example.com and not an impostor. The browser checks that the certificate covers the requested hostname, that it has not expired, and that it chains up to a certificate authority (CA) the operating system or browser already trusts. Each certificate in the chain is signed by the next one, ending at a root certificate stored locally. The browser may also check revocation status, to see whether the certificate has been cancelled. If any check fails, you see the full-page warning that says the connection is not private. As a developer, this is why a misconfigured or expired certificate takes your site down for users even though the server itself is running.

**7. Sending the HTTP request**

Now the browser can finally send the actual request, inside the encrypted channel. With HTTP/2 it is sent as binary frames, but conceptually it looks like this.

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The browser adds headers on its own. It includes any cookies it holds for that domain, says which compression formats it understands, and identifies itself with a User-Agent. If it has a stale cached copy, it may add conditional headers such as If-None-Match, so the server can reply with a tiny 304 Not Modified instead of resending everything.

**8. What the server does**

The request may not reach your application directly. It often passes through a CDN or load balancer first. A CDN is a network of edge servers that cache content close to users. If the edge has a cached copy, it replies immediately. If not, it forwards the request to the origin server, where a web server such as nginx hands it to your application. The application routes the path, may check authentication, may query a database, and builds a response. This is usually the largest variable in the wait. A slow query or cold cache here directly delays the response.

**9. The first byte arrives**

The server sends back the status line (for example 200 OK), the response headers, and then the start of the body. The moment the first byte of that response reaches the browser is called Time to First Byte, or TTFB. It is a useful performance metric because it includes everything above, namely DNS, TCP, TLS, and server processing time, plus the network delay on the way back.

**Why this matters in practice**

Each stage adds latency, and many of them are round trips whose cost depends on physical distance. This is why developers do the following.

- Use a CDN so servers are close to users.
- Enable HTTP/2 or HTTP/3 so one connection carries many requests.
- Keep connections alive so repeat requests skip the DNS, TCP, and TLS steps.
- Set sensible cache headers so some requests never leave the machine.
- Keep server-side work fast, since it is the stage you control most directly.

You can see these stages yourself. Open your browser's developer tools, go to the Network tab, click a request, and look at the Timing breakdown. It splits the wait into DNS lookup, initial connection, SSL, waiting for the server (TTFB), and content download. The same breakdown is available from the command line with curl -w and its timing variables.

Once you can name each step, slow page loads become much easier to diagnose, because you can ask which stage is actually slow instead of guessing.

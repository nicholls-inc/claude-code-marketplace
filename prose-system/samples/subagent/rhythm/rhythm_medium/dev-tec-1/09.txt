When you commit in Git, nothing is stored as a diff or a changeset. Instead, Git keeps a database of immutable objects inside the .git/objects directory, and every object is named by the SHA hash of its own contents. Each object lives in a file whose path is derived from that hash, with the first two hex characters forming a subdirectory and the remainder forming the filename. The objects are compressed with zlib, and each begins with a short header giving its type and size, followed by a null byte and then the payload. Because the name is computed from the content, two objects with identical content are always the same object, and any change to the content produces a different name. This is why Git can detect corruption so easily and why it can share storage between commits that have a lot in common.

The simplest kind of object is the blob, which holds the raw bytes of a single file and nothing else. A blob has no filename, no permissions and no timestamp, because it records only what the file contained. If you have the same README in ten directories, or the same file unchanged across a thousand commits, Git stores exactly one blob for it. When you run git add, Git reads the file, hashes it, writes the blob into the object database if it is not already there, and records that fact in the index. You can see this directly by running git hash-object -w on a file and then git cat-file -p on the resulting hash to print the contents back.

Since blobs carry no names, something else must say which blob belongs at which path, and that is the job of the tree object. A tree represents a single directory and is essentially a list of entries, each with a file mode, a type, a hash and a name. An entry points either to a blob, for a file, or to another tree, for a subdirectory, so that a whole project becomes a nested structure of trees ending in blobs. The mode records whether a file is regular, executable or a symbolic link, and it is the only place where that information lives. Because a tree's hash is computed from its entries, changing one deeply nested file changes that blob's hash, which changes the hash of every tree above it, all the way up to the root tree. The hash of the root tree therefore acts as a fingerprint of the entire snapshot of your working directory at one moment. Directories whose contents did not change keep the same hash and are simply reused, which is how Git makes snapshots cheap.

A commit object is what ties a snapshot to history. It is a small text object containing a handful of fields: the hash of the root tree, the hashes of zero or more parent commits, an author with a name, email and timestamp, a committer with the same details, and finally the commit message. The first commit in a repository has no parent, an ordinary commit has one, and a merge commit has two or more. Those parent pointers form a graph in which each commit refers back to the commits it was built on, and because every commit's hash includes its parents' hashes, rewriting any old commit necessarily changes every commit after it. This is why operations like rebase produce new commits rather than editing existing ones. When people say a commit is a diff, they are describing how Git presents it, because Git computes the difference on demand by comparing the commit's tree with its parent's tree.

All of the objects described so far are addressed by long hashes, which are inconvenient for humans, so Git adds refs, which are simply human-readable names that point at hashes. A branch is the most familiar example. If you look in .git/refs/heads, you will find a file for each local branch, and each file contains nothing more than the forty-character hash of the commit at the tip of that branch. Creating a branch is therefore almost free, since it just writes one small file, and making a new commit simply updates the current branch's file to the new commit's hash. Tags work the same way under .git/refs/tags, and remote-tracking branches live under .git/refs/remotes. In large repositories Git may pack many refs into a single .git/packed-refs file, but the idea is unchanged.

The remaining piece is HEAD, a file at .git/HEAD that says where you currently are. Normally it contains a symbolic reference such as ref: refs/heads/main, meaning that you are on the main branch and that the next commit should advance it. If you check out a specific commit directly, HEAD instead holds a raw hash, which is the detached state that Git warns about, because new commits would not be recorded under any branch name.

Putting this together, a commit follows a clear path. Git writes blobs for the file contents, builds trees from the index to describe the directory layout, creates a commit object pointing at the root tree and at the previous commit, and then moves the current branch ref to the new commit. Everything else you do in Git is a way of reading or rearranging that graph of objects and the small files that name its entry points.

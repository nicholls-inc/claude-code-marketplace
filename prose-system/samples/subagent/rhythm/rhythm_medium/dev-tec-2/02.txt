When you type an HTTPS address into a browser and press enter, the browser first has to decide what you actually asked for. It parses the URL into a scheme, a host name, an optional port, a path, and a query string, and it normalises the host name so that internationalised characters become the ASCII form that DNS understands. Before touching the network, it checks whether it already knows enough to skip some work. It may find that the host is on an HSTS list, which means the site has previously promised to be reached only over HTTPS, and it may find a cached copy of the resource that is still fresh enough to use without asking the server at all. If neither shortcut applies, the browser has to go and find the server.

The host name is only a label, so the next job is to turn it into an IP address. The browser looks in its own DNS cache first, then asks the operating system, which keeps a cache of its own and may consult a local hosts file. If nothing is cached, the request goes to a recursive resolver, usually run by your internet provider or a public service, and that resolver does the legwork. It asks a root server which servers handle the top-level domain, asks those servers which name servers are responsible for the domain, and finally asks one of those authoritative servers for the address records. Each answer carries a time-to-live value that tells every cache along the way how long it may remember the result, which is why a DNS change can take a while to be seen everywhere. Modern browsers may also use encrypted DNS and may ask for IPv4 and IPv6 addresses at the same time, preferring whichever connection succeeds first.

With an IP address in hand, the browser opens a connection. Classic HTTPS runs over TCP, which begins with a three-step handshake: the client sends a SYN packet, the server replies with a SYN-ACK, and the client answers with an ACK. This costs one full round trip, and the time it takes depends mostly on the physical distance between you and the server, since signals cannot travel faster than light in fibre. Along the way your packets pass through your router, your provider's network, and several other networks, each of which forwards them toward the destination using routing tables. Newer versions of HTTP can instead use QUIC, which runs over UDP and folds the transport and encryption setup into a single exchange, but the underlying goal is the same, which is to get a reliable, ordered channel between the two machines.

Once the connection exists, the browser and server negotiate encryption using TLS. The browser sends a ClientHello that lists the TLS versions and cipher suites it supports, includes a random value and a key share for key exchange, and includes the server name it wants through an extension called SNI. SNI matters because one IP address often hosts many sites, and the server needs to know which certificate to present. In TLS 1.3 the server replies with its own key share, which lets both sides compute the same shared secret without ever sending it, and then sends its certificate chain, all already encrypted. The browser checks that the certificate is valid for the requested host name, that it has not expired, and that it chains up to a certificate authority the operating system or browser already trusts. It may also check revocation status. A signature made with the server's private key proves that the server really holds the certificate, so an attacker in the middle cannot simply pretend to be the site. Both sides then confirm the handshake with Finished messages, and from that moment everything they exchange is encrypted and integrity protected. TLS 1.3 needs one round trip for this, while older TLS 1.2 needed two, and a returning client can sometimes resume a previous session to save even more time.

Now the browser can finally say what it wants. It sends an HTTP request through the encrypted channel, which consists of a method such as GET, the path, the Host header, and a number of other headers describing what the browser accepts, which language and compression it prefers, and any cookies it holds for that site. If a cookie or cached validator is present, the request may be conditional, so the server can answer that nothing has changed. With HTTP/2 and HTTP/3 this is not sent as plain text lines but as compressed binary frames on a stream, which allows many requests to share one connection without blocking each other as badly as in HTTP/1.1.

The request crosses the network again and reaches the server's side, though not necessarily the machine that runs your application. It often arrives first at a CDN edge node or a load balancer, which may terminate TLS itself, answer from its own cache, or forward the request to an origin server. The origin's web server then routes the request to application code, which may check a session, query a database, render a template, or call other services before it has anything to return. All of that is server think time, and it is frequently the largest single contributor to delay after the network itself.

Finally the server writes the response, beginning with a status line or status code, followed by headers such as the content type and cache rules, and then the body. The moment the first byte of that response travels back across the connection and reaches the browser is called time to first byte, and it is the sum of everything described above: DNS lookup, connection setup, the TLS handshake, the request's trip to the server, the server's processing, and the response's trip back. Knowing where each of those costs comes from tells you what you can actually improve, whether through caching, a nearby CDN, connection reuse, or faster server code.

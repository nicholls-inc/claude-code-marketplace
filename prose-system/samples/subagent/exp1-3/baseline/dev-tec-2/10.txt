From HTTPS Address to First Byte

When you type https://www.example.com/products into a browser and press Enter, a lot happens before the first byte of the response arrives. The time this takes is often called Time to First Byte (TTFB). Understanding each step helps you diagnose slow pages and make sensible choices about hosting, caching and CDNs.

1. Parsing the URL

The browser first splits the address into parts: the scheme (https), the host (www.example.com), an optional port (443 by default for HTTPS), the path (/products) and any query string or fragment. The fragment (#section) never leaves the browser. Because the scheme is https, the browser knows it must set up an encrypted connection.

Before touching the network, the browser checks a few local shortcuts. It consults its HSTS list (HTTP Strict Transport Security), which tells it that certain hosts must only be reached over HTTPS. It also checks its HTTP cache. If it holds a fresh copy of the resource, it can answer immediately with no network traffic at all. Service workers, if the site has registered one, can also intercept the request here.

2. DNS resolution

Network hardware talks in IP addresses, not names, so the browser must turn www.example.com into an address such as 93.184.216.34. It checks, in order: its own DNS cache, the operating system's cache and hosts file, and then asks a recursive resolver, usually run by your ISP or a public provider. If the resolver does not already have the answer cached, it walks the hierarchy: a root server points to the .com servers, which point to example.com's authoritative name servers, which return the record. Each record carries a time-to-live (TTL) that controls how long it may be cached.

A cold lookup can take tens to hundreds of milliseconds; a cached one is nearly free. Modern browsers may also request HTTPS or SVCB records, which can advertise support for HTTP/3. Some sites use DNS-based load balancing, so different users receive different IPs, ideally ones close to them.

3. Opening a TCP connection

With an IP address, the browser opens a TCP connection to port 443 using the three-way handshake: the client sends SYN, the server replies SYN-ACK, and the client sends ACK. This costs one full round trip. If you are 100 ms from the server, expect roughly 100 ms spent here. Distance matters, which is why CDNs place servers near users.

HTTP/3 changes this step. It runs over QUIC, which uses UDP and combines the transport and encryption handshakes, saving round trips. Browsers usually learn a site supports HTTP/3 from a previous visit or from DNS, and otherwise fall back to TCP.

4. The TLS handshake

Now the connection must be secured. With TLS 1.3, the handshake takes one additional round trip:

- The client sends a ClientHello listing supported cipher suites, a random value, a key share for key exchange, and the server name via SNI (Server Name Indication). SNI lets one IP address host many sites.
- The server replies with a ServerHello choosing the parameters, its own key share, and its certificate.
- Both sides now derive the same session keys from the key exchange. Everything after the ServerHello is encrypted.

The browser validates the certificate. It checks that the certificate chains up to a root authority the operating system or browser trusts, that it has not expired, that it has not been revoked, and that the hostname matches one of the certificate's names. If any check fails, you see the familiar security warning. A missing intermediate certificate on the server is a common cause of failures that appear on some devices but not others.

Older TLS 1.2 needs two round trips. If the browser has connected to this server recently, session resumption can shorten the handshake, and TLS 1.3 can even send early data with the first request (0-RTT), though that has replay-attack caveats and is used carefully.

Also during this step, the browser negotiates the application protocol using ALPN, agreeing on HTTP/2 or HTTP/1.1 (HTTP/3 is negotiated differently, as noted above).

5. Sending the HTTP request

Once the secure channel exists, the browser sends the request. In HTTP/1.1 form it looks like this:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

Real requests include many more headers, such as User-Agent and Accept-Language. The browser attaches any cookies that match the domain and path, which is one reason large cookies slow every request. HTTP/2 and HTTP/3 send the same information in a compact binary form, with header compression.

If the request needs a CORS preflight (typical for cross-origin API calls with custom headers), an extra OPTIONS request and response happen first, adding another round trip.

6. What the server does

The request travels through the internet, often reaching a CDN or load balancer first. The CDN may have a cached copy and reply straight away. If not, it forwards the request to the origin. The origin's web server (nginx, for example) may pass it to your application. The application might authenticate the user, query a database, call other services and render HTML. This server think time is often the largest and most variable part of TTFB, and it is the portion you control most directly as a developer. Slow queries, cold starts on serverless platforms and missing caches all show up here.

7. The first byte arrives

The server writes the status line and headers, such as HTTP/1.1 200 OK and Content-Type: text/html, followed by the start of the body. When the first byte of that response reaches the browser, TTFB is complete. Notably, the clock is not waiting for the whole page: a server that streams HTML early can have a low TTFB even if the full response takes longer.

Redirects can restart much of this process. A request to http://example.com redirecting to https://www.example.com repeats DNS, connection and TLS work for the new host, so avoid redirect chains.

Putting it together

A rough cold-start cost on a 50 ms round-trip connection: DNS about 50 ms or more, TCP 50 ms, TLS 1.3 50 ms, request and response transit 50 ms, plus the server's processing time. That is around 200 ms before your application code even matters. Warm connections skip DNS, TCP and TLS entirely, which is why reusing connections (keep-alive, HTTP/2 multiplexing) matters so much.

You can see these phases yourself in your browser's developer tools. In the Network panel, select a request and open the Timing tab, which breaks it into DNS lookup, initial connection, SSL, request sent and waiting for server response. The "Waiting" segment is essentially TTFB.

Practical takeaways

- Serve from a CDN or a region near your users to cut round-trip time.
- Use HTTP/2 or HTTP/3 and keep connections alive.
- Enable TLS 1.3 and make sure the full certificate chain is served.
- Cache aggressively, at the CDN, in the application and in the database layer.
- Avoid unnecessary redirects and keep cookies small.
- Measure TTFB with real user data, not only a fast office connection.

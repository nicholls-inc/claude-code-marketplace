From HTTPS address to first byte

You type https://www.example.com/shop into the address bar and press Enter. Nothing visible happens for a moment, yet the browser is busy. Before a single byte of the page arrives, it must work out where the server is, open a connection, prove the server's identity, and agree on encryption keys. Here is that sequence, step by step.

1. Parsing the URL

The browser first splits the address into parts. The scheme is https, the host is www.example.com, and the path is /shop. No port appears, so the browser uses the default for HTTPS, which is 443. If you had typed something that is not a valid URL, the browser would treat it as a search query instead. That is why typing "cats" sends you to a search engine.

Next, the browser checks a few local rules. One is HSTS, a list of sites that must only be reached over HTTPS. Another is its own caches. If it already holds a fresh copy of the page, it may skip the network entirely. Assume it does not.

2. Finding the IP address with DNS

Networks route traffic by IP address, not by name. So the browser must translate www.example.com into something like 93.184.216.34. This is the job of the Domain Name System, DNS.

The lookup checks several caches in order: the browser's own, the operating system's, and then the router's. If all of them miss, the request goes to a recursive resolver, usually run by your ISP or a public provider. The resolver may already know the answer. If not, it asks the root servers, then the servers for .com, then the servers responsible for example.com, and finally gets the address back.

Each answer carries a time-to-live, or TTL. The TTL says how long caches may keep it. This matters in practice. When you change a DNS record and the old address lingers for hours, a long TTL is the reason.

A lookup can take anywhere from under a millisecond (cached) to a few hundred milliseconds (cold). Modern browsers may also ask for an HTTPS record, which can advertise that the server supports HTTP/3. Keep that in mind for later.

3. Opening a TCP connection

Now the browser has an address. It needs a reliable channel to the server. Classic HTTPS uses TCP, which starts with a three-step exchange called the handshake. The browser sends a SYN packet. The server replies with SYN-ACK. The browser answers with ACK. Only then can data flow.

This costs one full round trip. If the server is 80 ms away, you have just spent 80 ms doing nothing but saying hello. Distance is the cost here, which is why content delivery networks (CDNs) put servers close to users.

HTTP/3 works differently. It runs over QUIC, which uses UDP and folds the transport and encryption handshakes together. That saves round trips. But a browser usually learns about it from a previous visit or from that DNS record, so a first visit often still uses TCP.

4. The TLS handshake

A TCP connection is open, but anyone along the route could read it. TLS fixes that. It does two jobs: it proves the server is who it claims to be, and it sets up keys for encrypting everything that follows.

Here is how it goes in TLS 1.3, the current version.

The browser sends a ClientHello. It lists the cipher suites it supports. It also includes a key share, which is its half of a key exchange. It sends the hostname too, in a field called Server Name Indication (SNI). The SNI lets one IP address host many sites, because the server knows which certificate to present.

The server replies with a ServerHello. It picks a cipher suite and sends its own key share. At this moment both sides can compute the same secret key, without ever sending that key across the wire. The method is a Diffie-Hellman exchange. From here on, the server's messages are encrypted.

The server then sends its certificate. This is a signed document that ties the hostname to a public key. The server also signs part of the handshake with its private key, proving it really holds that key. Finally, it sends a Finished message, and the browser does the same.

TLS 1.3 needs just one round trip. TLS 1.2 needed two. If the browser has talked to this server before, it can sometimes use a resumption ticket to shorten things further, and in some cases send data immediately (0-RTT, with caveats about replay attacks).

5. Checking the certificate

The browser does not simply trust the certificate. It checks several things.

- Does the hostname match one listed in the certificate?
- Is the certificate within its validity dates?
- Was it signed by a certificate authority (CA) the browser trusts? Usually there is a chain: the site's certificate is signed by an intermediate, which is signed by a root already stored in your operating system or browser.
- Has it been revoked? Browsers check this in limited ways, such as stapled OCSP responses or compressed revocation lists.

If any check fails, you see a full-page warning. This is the error that catches expired certificates, which is a very common production mistake. For a developer, the lesson is simple: automate renewal.

6. Sending the HTTP request

Only now, after DNS, TCP and TLS, does the browser speak HTTP. The request is small, and it is encrypted before it leaves. In HTTP/1.1 it looks like this:

GET /shop HTTP/1.1
Host: www.example.com
User-Agent: ...
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The browser attaches any cookies that belong to this domain and path. It also states which compressions it understands. In HTTP/2 and HTTP/3 the same information is sent in a compact binary form rather than plain text, but the meaning is identical.

7. Waiting for the server

The request travels to the server, often first reaching a CDN or load balancer. These may answer from cache. Otherwise they forward the request to an application server. The application runs your code: it might check a session, query a database, render a template. Then it builds a response.

The moment the first byte of that response reaches the browser is called Time To First Byte (TTFB). It is the sum of everything above: DNS, TCP, TLS, the request's travel time, and the server's processing time.

Why this matters to you

A slow TTFB is easy to measure and hard to guess at. Open the Network tab in your browser's developer tools, click a request, and look at the Timing breakdown. It splits the wait into DNS lookup, initial connection, SSL, request sent, and waiting for the server. Each segment points to a different fix.

- Slow DNS: use fewer distinct hostnames, or raise TTLs.
- Slow connection or TLS: use a CDN, enable HTTP/2 or HTTP/3, and keep TLS 1.3 on.
- Slow waiting: profile your backend, add caching, or fix that slow query.

Browsers also reuse connections. Once the connection exists, further requests to the same host skip the DNS, TCP and TLS steps. That is why the first request is the expensive one, and why hints such as preconnect and dns-prefetch exist. They let the browser do the setup early, while it is still parsing your page.

Summary

Parse the URL, resolve the name, open TCP (or QUIC), complete the TLS handshake, verify the certificate, send the request, wait for the server. Each stage costs at least a network round trip. Knowing the order tells you where to look when a page feels slow.

When you type an HTTPS address into a browser and press enter, the browser first has to work out what you actually asked for. It parses the string into a scheme (https), a host (for example www.example.com), an optional port (443 by default for HTTPS), a path, and any query string or fragment. Before touching the network it checks a few local things. It may consult its HSTS list, which records sites that must only be reached over HTTPS, and it checks whether it already holds a fresh cached copy of the resource, in which case the request might never leave your machine. If it does need the network, the browser also looks for an existing open connection to the same origin that it can reuse, because reuse skips most of the work described below.

The next step is finding out where the host lives. Browsers and operating systems use the Domain Name System, which maps names to IP addresses. The lookup checks several caches in turn: the browser's own, the operating system's, and often your router's. If none has the answer, the request goes to a recursive resolver, usually run by your internet provider or a public service. That resolver, if it also lacks a cached answer, walks the hierarchy. It asks a root server which servers handle the top-level domain such as .com, asks those which servers are authoritative for example.com, and finally asks an authoritative server for the address records. Each answer carries a time-to-live, which is how long it may be cached, so most lookups for popular sites are answered in a millisecond or two from a cache. The result is one or more IPv4 or IPv6 addresses. Modern browsers often try IPv6 and IPv4 nearly in parallel and use whichever connects first, a technique called Happy Eyeballs. Some browsers can also ask for HTTPS or SVCB DNS records, which can advertise HTTP/3 support or alternate endpoints.

With an address in hand, the browser opens a connection. For classic HTTP/1.1 and HTTP/2 this is a TCP connection, which begins with a three-way handshake. The client sends a SYN packet, the server replies with SYN-ACK, and the client answers with ACK. That costs one round trip, meaning the time for a message to travel to the server and back. Distance matters here: a server 100 milliseconds away adds 100 milliseconds for every round trip you require, which is why the number of round trips is the main thing performance engineers count. If the site supports HTTP/3, the transport is QUIC running over UDP instead, which folds the transport and encryption handshakes together and saves a round trip. A browser usually learns about HTTP/3 from an earlier response header called Alt-Svc or from DNS records, and may race it against TCP.

Once the transport is up, the browser negotiates encryption using TLS, which is what makes the address HTTPS rather than HTTP. In TLS 1.3, the current version, the client opens with a ClientHello message. It lists the cipher suites it supports, includes the server name it wants (the Server Name Indication, so a server hosting many sites knows which certificate to present), lists the application protocols it speaks via ALPN (such as h2 or http/1.1), and includes its half of a key exchange, typically an elliptic-curve Diffie-Hellman share. The server answers with its own key share, and from that point the two sides can derive shared secret keys without ever sending those keys over the wire. The server then sends its certificate chain and a signature proving it holds the private key matching the certificate. This takes one round trip in TLS 1.3, compared with two in older TLS 1.2. If the browser has connected to this server before, session resumption can let it skip some of this, and with 0-RTT it can even send request data in the very first flight, at the cost of weaker replay protection.

The certificate check is what stops someone in the middle from impersonating the site. The browser verifies that the certificate chain leads to a certificate authority it trusts (a root stored in your operating system or browser), that each signature in the chain is valid, that the certificate has not expired, that the name in the certificate matches the host you asked for, and that the certificate has not been revoked. Revocation is checked in various ways, including stapled OCSP responses delivered by the server and compressed revocation lists maintained by the browser vendor. Many browsers also look for Certificate Transparency proof that the certificate was publicly logged. If any check fails you see a full-page warning and the connection does not proceed. If they pass, the client and server both send a Finished message that authenticates the whole handshake, and from then on everything is encrypted and integrity-protected.

Only now does the browser send the actual HTTP request. With HTTP/1.1 this is plain text inside the encrypted channel: a request line such as GET /products HTTP/1.1, followed by headers like Host, User-Agent, Accept, Accept-Encoding, and any cookies the browser holds for this site. HTTP/2 and HTTP/3 carry the same semantics but as compressed binary frames, which let many requests share one connection at once. The browser may also attach conditional headers like If-None-Match if it has a stale cached copy, so the server can answer with a tiny 304 response instead of resending the whole body.

The request then crosses the network to the server. It often does not reach your application directly. It may first hit a CDN edge node, a load balancer, or a reverse proxy that terminates TLS, applies security rules, and either answers from its cache or forwards the request inward to an origin application server. That server routes the path to some code, which might query a database, call other services, and render HTML or JSON. Eventually the server writes a status line and headers, such as HTTP/2 200 with a Content-Type and Cache-Control, followed by the body. The moment the first byte of that response reaches the browser is called Time To First Byte, and it is the sum of everything above: DNS lookup, TCP or QUIC setup, the TLS handshake, the request's trip to the server, the server's processing time, and the first byte's trip back.

For a junior developer, the practical lesson is that most of that time is round trips and distance rather than raw bandwidth, which is why connection reuse, CDNs, HTTP/2 or 3, TLS 1.3, and caching all help. You can see each phase yourself in the browser developer tools Network tab, where the timing breakdown for any request shows DNS, connection, TLS, waiting (the server's think time), and download as separate segments.

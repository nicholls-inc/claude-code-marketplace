When you type an HTTPS address such as https://example.com/docs into a browser and press enter, the browser first parses it. It splits the address into a scheme (https), a host (example.com), a port (443 by default for HTTPS) and a path (/docs). Before any network traffic, it checks a few local things. It looks at its HSTS list, which records sites that must only be reached over HTTPS, and it checks whether it already holds a usable connection to that host. If a connection is already open, most of what follows is skipped.

The browser then needs an IP address for example.com. It looks in its own DNS cache, and then asks the operating system, which keeps a cache of its own and may consult the hosts file. If neither has an answer, the operating system sends a query to a configured resolver, usually one run by the internet provider or a public service. The resolver answers from its cache if it can. Otherwise it works down the hierarchy: it asks a root server which servers handle .com, asks one of those which servers handle example.com, and asks one of those for the address. Each answer carries a time to live, in seconds, which says how long it may be cached. The query is normally a single UDP packet and the reply a single packet back, and a cached answer takes a few milliseconds while an uncached one can take tens or hundreds. The reply may hold an IPv4 address, an IPv6 address, or both, and the browser may try both and use whichever connects first.

With an address in hand, the browser opens a TCP connection to port 443. TCP begins with a three-step handshake. The client sends a SYN packet, the server replies with SYN-ACK, and the client sends an ACK. This costs one round trip, which is the time a packet takes to reach the server and for the reply to return. On a connection between London and a server in Virginia that is about 75 milliseconds. Browsers that support HTTP/3 may instead use QUIC, which runs over UDP and combines the transport and encryption setup into fewer round trips. A browser usually learns that a site offers HTTP/3 from an earlier visit, through an Alt-Svc header, or from a DNS record.

Next comes the TLS handshake, which sets up encryption and checks who the server is. In TLS 1.3, the version most sites now use, the client opens with a ClientHello. It lists the cipher suites it supports, names the host it wants through the Server Name Indication field, lists the application protocols it can speak, such as h2 and http/1.1, and includes a key share, which is its half of a Diffie-Hellman exchange. The server answers with a ServerHello containing its own key share. From the two shares, both sides can compute the same secret without ever sending it. Everything the server sends after the ServerHello is encrypted. That includes its certificate chain, a signature that proves it holds the private key matching the certificate, and a Finished message that covers the whole handshake. TLS 1.3 needs one round trip before the client can send application data. TLS 1.2 needed two. If the browser has connected to the site recently, it can resume the session with a stored ticket and may be able to send data even earlier, though that early data has limits on what it can safely contain.

The browser validates the certificate during this step. It checks that the certificate names the host, here example.com, in its Subject Alternative Name field. It checks that the current date falls between the certificate's start and end dates. It checks that the chain of signatures leads to a certificate authority that the operating system or browser trusts. The browser may also check whether the certificate has been revoked, and it may compare it against Certificate Transparency logs. If any check fails, the browser stops and shows a warning page, and no request is sent.

Once the handshake is complete, the browser can send its HTTP request. With HTTP/2, which the application protocol negotiation will have selected for most sites, the request is encoded as binary frames. The request line and headers are compressed with HPACK and sent on a numbered stream, so many requests can share one connection. The request carries a method, GET here, the path /docs, and an authority value of example.com. It carries headers such as Accept, Accept-Encoding, which lists compression formats like gzip and br, and User-Agent. It also carries any cookies the browser has stored for that site, and it may carry a cached validator, such as an ETag, if the browser holds an older copy of the page. In HTTP/1.1 the same information goes as plain text, a line such as GET /docs HTTP/1.1 followed by headers, one connection handling one request at a time.

The request now travels to the server's address, but that address is often not the machine that produces the page. Commonly it belongs to a CDN edge server or a load balancer, which terminates the TLS connection. It may answer from its own cache, or it may forward the request to an origin server over a separate connection. An application behind it might run the routing code, query a database, and build the response, which can take anywhere from a few milliseconds to several seconds. If the request carried a validator and the content has not changed, the server can answer with a 304 status and no body, and the browser then uses its stored copy.

The server sends back a status line or status frame, such as 200, followed by response headers like Content-Type, Content-Length or Content-Encoding, Cache-Control and Set-Cookie. The body follows. The moment the first byte of this response reaches the browser is what the web performance field calls time to first byte. Measured from the moment navigation started, it includes the DNS lookup, the TCP connection, the TLS handshake, the request's trip to the server, the server's processing time, and the first byte's trip back. For a first visit to a distant site, a total of 200 to 600 milliseconds is typical, and most of it is round trips rather than server work. This is why reuse of connections, caching of DNS answers, CDNs placed near users and TLS session resumption each save a measurable amount of time. After the first byte arrives, the browser reads the headers, decompresses the body if needed, and starts parsing the HTML.

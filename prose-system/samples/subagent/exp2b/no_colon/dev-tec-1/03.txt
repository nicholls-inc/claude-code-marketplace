Git stores everything in a small database inside the .git directory. That database is a content-addressed object store, meaning every piece of data is saved under a name derived from the data itself. Once you see this, commits, branches and tags stop being mysterious. There are four ideas to learn, which are blobs, trees, commit objects and refs.

**The object store**

Open .git/objects and you will find directories with two-character names, each holding files with long hexadecimal names. Each file is one object. The full name of an object is a SHA hash computed from its type, its size and its content. Git compresses the content with zlib and writes it to a path built from the hash. The first two characters become the directory name and the remainder becomes the file name. Because the name comes from the content, identical content always produces the same object, and storing it twice costs nothing. Git also never modifies an object in place. A change produces a new object with a new name.

You can inspect any object with git cat-file. The -t flag prints its type and -p pretty-prints its content. Everything below can be verified this way.

**Blobs**

A blob holds the contents of one file and nothing else. It has no file name, no permissions and no timestamp. If two files in your repository have identical contents, they share one blob. If you rename a file without editing it, the blob is unchanged. This is also why Git can seem to track renames without ever recording them, since it only has to notice that the same blob now appears under a different name.

When you run git add, Git hashes the file, writes the blob into the object store and records it in the index. The index is the staging area. It is a single binary file at .git/index that lists paths, modes and blob hashes for your next commit.

**Trees**

A tree represents a directory. It is a list of entries, and each entry has a mode, a type, a hash and a name. An entry can point to a blob, which is a file, or to another tree, which is a subdirectory. The mode records whether a file is ordinary, executable or a symbolic link.

A tree for a small project might look like this when printed with git cat-file -p.

```
100644 blob 8f2b1c4...  README.md
040000 tree 3a9d7e0...  src
100755 blob c41e6b2...  build.sh
```

The src entry points to another tree, which lists the files inside src. Following these pointers from the top, which is called the root tree, reconstructs the whole directory structure. This is where file names live. Names belong to trees, not blobs.

Trees give Git a useful property. A tree's hash depends on the hashes of everything beneath it. If you change one line in one file deep in the project, that blob gets a new hash. Every tree on the path from that file up to the root also gets a new hash. Trees that were not touched keep their hashes and are reused. So a new snapshot of a large project only writes the few objects that actually changed.

When you run git commit, Git turns the index into a set of tree objects and writes them out. Together they form one complete snapshot of your project.

**Commit objects**

A commit is a small text object with a few fields. Here is what git cat-file -p prints for one.

```
tree 5d3f0a9...
parent 91ce24b...
author Ada Lovelace <ada@example.com> 1731300000 +0000
committer Ada Lovelace <ada@example.com> 1731300000 +0000

Fix off-by-one error in pagination
```

The tree line points to the root tree of the snapshot. The parent line points to the previous commit. The author and committer lines record who did the work and when. After a blank line comes the message.

A merge commit has two or more parent lines. The first commit in a repository has none. Following the parent pointers backwards produces the history you see in git log. The history is a chain of commits, and each one points at a complete snapshot.

Git does not store diffs. Every commit points to a full tree. The commands that show changes, such as git diff and git show, compute the differences on demand by comparing two trees. Git does save space, though. Because unchanged files and directories are shared between snapshots, and because Git periodically packs objects into compressed pack files that store similar objects as deltas, repositories stay small.

The commit's hash covers all of its content, including the tree hash and the parent hash. This means the hash of a commit identifies the whole history behind it. Changing an old commit alters its hash, which alters the hash of every commit after it. This is why rewriting history with rebase produces new commits instead of editing existing ones.

**Refs**

Hashes are hard to remember, so Git uses refs, which are human-readable names for commits. A ref is a file containing a single commit hash. Branches live in .git/refs/heads, and a branch called main is just the file .git/refs/heads/main. Tags live in .git/refs/tags, and remote-tracking branches live in .git/refs/remotes. Open one with cat and you will see forty hexadecimal characters.

Creating a branch writes a 41-byte file. Making a commit creates the new commit object, whose parent is the current commit, and then updates the branch file to contain the new hash. That update is what it means for a branch to advance. This is why branches are cheap and why deleting a branch does not delete commits. It removes only a pointer.

The file .git/HEAD tells Git where you are. Normally it holds a line like ref: refs/heads/main, which means you are on the main branch. When you check out a specific commit instead, HEAD contains a raw hash. That is the detached HEAD state, where new commits are not recorded under any branch name and are easy to lose.

**Putting it together**

When you commit, Git writes blobs for changed files, builds trees from the index, creates a commit pointing at the root tree and its parent, and moves the current branch ref forward. Four kinds of thing, all stored in the same simple way. Try git cat-file -p HEAD in a repository you know, then follow the tree hash downward. The whole model is only a few hops deep.

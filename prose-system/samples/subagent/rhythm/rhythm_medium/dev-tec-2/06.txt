When you type an HTTPS address into a browser and press enter, the browser first has to work out exactly what you are asking for. It parses the address into its parts: the scheme, which here is https, the hostname, an optional port, the path, and any query string or fragment. Because the scheme is https, the browser knows to use port 443 unless told otherwise, and it also checks whether the host appears on its built-in HSTS preload list or has previously told the browser to use secure connections only. If the address was typed without a scheme, the browser may upgrade it to HTTPS automatically before going any further.

Before touching the network, the browser looks for ways to skip work. It checks its HTTP cache for a fresh copy of the resource, and if it finds one that is still valid, it can serve the response immediately without any network traffic at all. It may also consult a service worker, which is a script registered by the site that can intercept requests and answer them from its own storage. Only when none of these produce an answer does the browser go out to the network.

The first network step is DNS resolution, which turns the hostname into an IP address. The browser checks its own DNS cache, then asks the operating system, which checks its cache and its hosts file. If neither knows the answer, the request goes to a recursive resolver, usually run by your internet provider or a public service. That resolver walks the DNS hierarchy if it has no cached answer, asking a root server which servers handle the top-level domain, asking those which servers are authoritative for the domain, and finally asking the authoritative server for the address record. Results are cached according to a time-to-live value set by the domain owner, so repeat lookups are usually fast. Modern browsers may also request HTTPS records in DNS, which can advertise supported protocols and save a later negotiation step.

With an IP address in hand, the browser opens a connection. For traditional HTTPS over HTTP/1.1 or HTTP/2, this means a TCP connection, which begins with a three-step handshake. The client sends a SYN packet, the server replies with SYN-ACK, and the client acknowledges, after which both sides can send data reliably and in order. This costs one full round trip, so distance between you and the server directly affects how long it takes. If the browser already has an open connection to the same host from an earlier request, it can reuse it and skip this step and the next ones entirely.

Once TCP is established, the TLS handshake begins, and this is what makes the connection secure. In TLS 1.3, the client sends a hello message listing the protocol versions and cipher suites it supports, along with a key share for key exchange and the hostname it wants through the Server Name Indication extension. That extension matters because many sites share one IP address, and the server needs to know which certificate to present. It also carries the Application-Layer Protocol Negotiation extension, through which the client and server agree on whether to speak HTTP/1.1 or HTTP/2.

The server answers with its own key share, which lets both sides compute the same shared secret without ever sending it across the wire, and with its certificate chain. From this point the rest of the handshake is encrypted. The browser then validates the certificate. It checks that the certificate chains up to a certificate authority the operating system or browser trusts, that it has not expired, that the hostname you requested matches one of the names listed in the certificate, and that it has not been revoked. It also usually looks for evidence that the certificate was logged in public Certificate Transparency logs. The server proves it owns the certificate's private key by signing the handshake transcript, and both sides confirm the handshake with finished messages. TLS 1.3 completes all this in a single round trip, whereas the older TLS 1.2 needed two. If the browser has connected to this server before, it may use a session ticket to resume the session and, in some cases, send application data in the very first flight.

There is a significant variation worth knowing about. If the server supports HTTP/3, the browser may use QUIC instead of TCP. QUIC runs over UDP and integrates the TLS 1.3 handshake into its own connection setup, so transport and encryption are established together in one round trip rather than two sequential ones. The browser typically learns that a server supports HTTP/3 from an Alt-Svc header on an earlier response or from DNS, and it may race the new and old approaches so a failure of one does not slow the page down.

Now the browser can finally send the actual request. It builds an HTTP request with a method, usually GET, the path, and a set of headers. These include the Host or authority, the user agent, the languages and encodings it accepts, and any cookies stored for that domain, along with cache validators such as an ETag if it holds a stale copy. Under HTTP/2 and HTTP/3 the headers are compressed and the request is carried as a stream on the existing connection, while HTTP/1.1 sends them as plain text. All of this is encrypted by TLS before leaving your machine.

The request then travels across the network to the server, often reaching a CDN edge node or load balancer first. That front layer may terminate TLS, apply security rules, return a cached copy, or forward the request to an origin application server. The application may query a database, render a template, or call other services before it has anything to say. Finally, the server writes the status line and response headers, and the first byte of that response travels back to the browser. The time from sending the request to receiving that first byte is called Time to First Byte, and it is the sum of everything above, which is why DNS speed, connection reuse, caching, and server processing time all matter so much to how fast a page feels.

When you type an HTTPS address into a browser and press Enter, the browser first has to decide what you meant. It parses the text into a scheme, a host, an optional port and a path, and it checks whether the address is on its list of sites that must always use HTTPS, which is called HSTS. If the host is on that list, or the scheme is already https, the browser will refuse to fall back to plain HTTP. Before it touches the network, it also looks in its own caches, because a fresh cached copy of the page could be served without any request at all. Only when nothing usable is found does the real work begin.

The browser knows the name of the server but not where to find it, so it must turn the hostname into an IP address. This is done through DNS, the Domain Name System. The browser checks its own DNS cache first, then asks the operating system, which may have its own cache or a hosts file entry. If neither has an answer, the request goes to a recursive resolver, usually run by your internet provider or a public service. The resolver may already know the answer from an earlier lookup. If it does not, it walks down the hierarchy by asking a root server about the top-level domain, then the server for that domain, and finally the authoritative server for the site itself. Each answer carries a time-to-live value that says how long it may be cached. The result is one or more IP addresses, and a modern browser will often ask for both IPv4 and IPv6 records and try whichever connects first.

With an address in hand, the browser must open a connection, and for HTTPS that connection is built on TCP. TCP gives the two machines a reliable, ordered stream of bytes, and it starts with a three-step handshake. The browser sends a SYN packet, the server replies with a SYN-ACK, and the browser answers with an ACK. This costs one full round trip, which is the time for a message to travel to the server and back, so a distant server makes it noticeably slower. Browsers that speak HTTP/3 take a different path. They use QUIC, which runs over UDP and merges the connection and encryption setup into fewer round trips. A browser usually learns that a site supports it from an earlier visit or from a DNS hint, and otherwise it begins with TCP.

Once the transport exists, the browser and server set up encryption using TLS, the protocol that makes HTTPS secure. The browser opens by sending a ClientHello message, which lists the TLS versions and cipher suites it supports, includes a random value, and sends the hostname it wants through an extension called SNI. SNI matters because one IP address often hosts many sites, and the server needs to know which certificate to present. The browser also sends its half of a key exchange in that first message. The server replies with its choice of cipher suite, its own key share and its certificate. In TLS 1.3 the rest of the handshake is already encrypted, and the whole exchange takes one round trip. Older TLS 1.2 needs two.

The certificate is how the browser decides whether to trust the server. It names the domains it covers and carries the server's public key, and it is signed by a certificate authority. The browser follows the chain of signatures from the server's certificate through any intermediates up to a root certificate that is already installed in the operating system or browser. It checks that the dates are valid, that the hostname matches, and that the certificate has not been revoked. The server also proves it holds the matching private key by signing part of the handshake. If any check fails, the browser shows the full-page warning that many developers will have met on a misconfigured site, and the request goes no further.

When both sides have finished the key exchange, they each derive the same session keys without ever sending those keys across the network. From then on, everything is encrypted and authenticated, so anyone watching the connection sees only scrambled bytes and cannot alter them undetected. If the browser has connected to this server recently, it may be able to resume the session using a saved ticket and skip some of this work. TLS 1.3 can even let the browser send its HTTP request alongside the resumption, which is known as early data, although that carries some replay risks and is used carefully.

Only now does the browser send the HTTP request itself. Through ALPN, a negotiation inside the TLS handshake, the two sides will already have agreed on a protocol version, which is typically HTTP/2 or HTTP/1.1 over TCP. The request consists of a method such as GET, the path, and a set of headers. These headers include the Host, the Accept and User-Agent values, and any cookies the browser holds for that site. In HTTP/2 the request is compressed and framed in binary, but the information it carries is the same. If the browser already has a stale cached copy, it may add a conditional header such as If-None-Match so the server can answer with a short 304 response instead of resending everything.

The request then travels to the server, which is often not the machine that holds your application. It may reach a CDN edge node or a load balancer first, which terminates TLS, applies security rules, and either answers from its own cache or forwards the request on to an origin server. That origin runs your application code, which may query a database, render a template and build a response. The first byte the browser receives is the start of the response, normally the status line or its HTTP/2 equivalent followed by headers. The time from sending the request to that moment is called time to first byte, and it includes the network trip and the server's own processing time.

Seen as a whole, the delay before any content arrives is made of several separate costs that add up. Each of DNS, TCP, TLS and the server's thinking time can be slow on its own. Browser developer tools show them as separate segments in the network timeline, which is the best place for a junior developer to see them for themselves. Knowing where the time goes explains why connection reuse, caching, CDNs and modern protocols help so much, because each of them removes one of these steps or shortens it.

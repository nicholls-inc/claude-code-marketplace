From HTTPS Address to First Byte: What the Browser Does

When you type https://www.example.com/products into a browser and press Enter, a lot happens before the first byte of the response arrives. This is a walkthrough of those steps in order, with the time each one can cost. Knowing them helps you diagnose slow pages, because a delay in any step looks the same from the outside: a blank tab.

1. Parsing the URL

The browser first splits the address into parts. The scheme (https) says which protocol to use. The host (www.example.com) says which server to contact. The port defaults to 443 for HTTPS, and the path (/products) says which resource to ask for. If you typed something that is not a valid URL, the browser treats it as a search query instead.

Before going to the network, the browser also checks a few local things. It may consult its HSTS list, a record of sites that must only be reached over HTTPS, and it checks whether it already has a cached response for this URL that is still fresh. A fresh cache hit can skip the network entirely, so no later steps occur.

2. DNS lookup: turning a name into an address

Computers connect to IP addresses, not names, so the browser must resolve www.example.com to an address such as 93.184.216.34 (IPv4) or an IPv6 equivalent. It checks several caches in turn: its own, the operating system's, and then the configured DNS resolver, usually run by your ISP or a public provider. If the resolver does not know the answer, it queries the DNS hierarchy: root servers point to the .com servers, which point to example.com's authoritative name server, which returns the address. The answer carries a TTL (time to live) saying how long it may be cached.

A cold lookup can take tens of milliseconds or more. A cached one is nearly instant. This is why the first visit to a site is often slower than later ones.

3. TCP connection: the handshake

With an IP address, the browser opens a TCP connection to port 443. TCP provides a reliable, ordered stream of bytes, and it begins with a three-way handshake. The client sends SYN, the server replies SYN-ACK, and the client sends ACK. This costs one full round trip between you and the server. If the server is far away, say 100 ms each way, that round trip is 200 ms spent before any real data moves.

Modern browsers may instead use HTTP/3, which runs over QUIC on UDP and combines the transport and encryption handshakes. The browser learns about this from earlier responses (an Alt-Svc header) or from DNS records, so on a first visit it usually starts with TCP.

4. TLS handshake: making the connection secure

The "S" in HTTPS means the connection is encrypted using TLS. After TCP is established, the browser and server perform a TLS handshake. In TLS 1.3, the current version, this takes one round trip:

- The browser sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, a key share for key exchange, and the server name via SNI (Server Name Indication). SNI matters because one IP address can host many sites, and the server needs to know which certificate to present.
- The server replies with its chosen cipher suite, its own key share, and its certificate chain.
- Both sides combine the key shares to derive the same session keys, without ever sending those keys over the wire. Everything after this is encrypted.

The browser then validates the certificate. It checks that the certificate is signed by a certificate authority (CA) it trusts, directly or through intermediate certificates, that it has not expired, that the hostname matches one listed in the certificate, and, depending on the browser, that it has not been revoked. If any check fails, you see a certificate warning and the request does not proceed.

TLS 1.2 needs two round trips instead of one. When the browser has connected to the server before, TLS 1.3 session resumption can shorten this further, and in some cases allows "0-RTT" data, with a security trade-off around replayed requests.

5. Connection reuse and other shortcuts

DNS, TCP and TLS together are pure setup cost. Browsers reduce it by keeping connections open and reusing them for later requests to the same host (keep-alive, and multiplexing in HTTP/2 and HTTP/3). If you have already loaded a page from this host, the browser may skip steps 2 to 4 completely. Developers can also help with hints such as preconnect, which tells the browser to open a connection early, and dns-prefetch.

6. Sending the HTTP request

Now the browser sends the actual request through the encrypted channel. In HTTP/1.1 it is readable text, though here it travels encrypted:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

In HTTP/2 and HTTP/3 the same information is sent in a compact binary form, but the content is the same: a method, a path, and headers. The browser attaches relevant cookies for that domain, a User-Agent, language preferences, and any cached validators (such as an If-None-Match header holding an ETag) so the server can answer "not modified" instead of resending the page.

7. The server's work

The request reaches the server, but it often does not go straight to your application. It may pass through a CDN edge node, a load balancer, or a reverse proxy such as Nginx. A CDN may answer from its own cache, which is fast and close to the user. Otherwise the request is forwarded to the origin application, which might route it, check authentication, query a database, and render HTML. This stage is called server processing time, and it is the part developers control most directly.

8. The first byte arrives

When the server begins sending the response, the first bytes are the status line and headers, for example 200 OK, a Content-Type, and cache directives. The time from sending the request to receiving this first byte is TTFB, time to first byte. Note that people sometimes use TTFB to mean the whole period from navigation start, which includes redirects, DNS, TCP and TLS. Browser developer tools break these out separately, so check which definition a tool uses.

Where the time goes: a rough budget

- Redirects (for example http to https, or a missing trailing slash): one full extra trip through everything above for each hop.
- DNS: 0 to 100+ ms, depending on caching.
- TCP: one round trip.
- TLS 1.3: one round trip (two for TLS 1.2).
- Request and server processing: one round trip plus however long the server takes.

On a far-away server, the network round trips alone can reach several hundred milliseconds before your code runs at all.

Practical takeaways

- Use a CDN to shorten the distance for round trips.
- Avoid unnecessary redirects.
- Enable HTTP/2 or HTTP/3 and TLS 1.3.
- Use preconnect for third-party origins you know you will need.
- Cache responses with sensible Cache-Control headers, so repeat visits skip the network.
- Keep server processing fast: slow queries and uncached rendering show up directly in TTFB.

Use the Network tab in your browser's developer tools to see this breakdown for any request. The Timing view labels the stages (DNS lookup, initial connection, SSL, waiting for server response) so you can see which step is costing you the most.

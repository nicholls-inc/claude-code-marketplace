When you run git commit, you are asking Git to write a small number of immutable records into a key-value store that lives in the .git/objects directory. Everything Git remembers about your project is built from four kinds of thing: three objects stored by content, namely blobs, trees, and commits, and a fourth, the ref, which is a lightweight pointer that gives those objects human-friendly names.

Start with the blob, the simplest object. When Git stores a file, it takes the file's bytes, prepends a short header containing the word "blob" and the byte length, and runs the whole thing through a SHA-1 hash (newer repositories can use SHA-256, but the idea is identical). The resulting 40-character hexadecimal digest becomes the object's name. The content is then compressed with zlib and written to a file whose path is derived from the name: the first two characters become a subdirectory and the remaining thirty-eight become the filename, so an object named e69de29b... lives at .git/objects/e6/9de29b.... A blob holds only contents, so it does not know its filename, its permissions, or which directory it sits in. Two files with identical contents, in different places or in different commits, share a single blob, which is why Git is economical when you copy files around or revert a change.

Filenames and directory structure live in the second kind of object, the tree. A tree is a list of entries, each with a mode (regular file, executable file, symbolic link, or subdirectory), a name, and the hash of the object that entry refers to. An entry for a file points to a blob, while an entry for a subdirectory points to another tree, so a project with nested folders becomes a tree of trees, rooted at a single top-level tree that represents the repository's root directory. Because a tree's name is the hash of its serialized contents, changing one file changes that file's blob hash, which changes the hash of the tree containing it, which changes the hash of that tree's parent, and so on up to the root. Unchanged subdirectories keep their old hashes and are reused as they are. This is the trick that makes snapshots cheap: a commit that touches one file creates only a new blob and a new chain of trees along the path to it, and everything else is shared with the previous commit.

The commit object ties a snapshot to history. It is a short text record with a handful of fields: the hash of the root tree, the hash of each parent commit, an author line with name, email, and timestamp, a committer line in the same format, and then a blank line followed by your commit message. An ordinary commit has one parent, the first commit in a repository has none, and a merge commit has two or more. The root tree hash is what makes a commit a complete snapshot rather than a diff, because Git does not store "what changed" in the commit and instead computes differences on demand, when you run git show or git diff, by comparing the trees of two commits. Because the parent hash is part of what gets hashed to produce the commit's own name, history is a chain in which every link vouches for the one before it. You cannot alter an old commit, even by changing a single character of its message, without producing a different hash, and therefore different hashes for every descendant. This is why rewriting history with rebase or amend really creates new commits and abandons the old ones.

That leaves the problem of finding things, since commit hashes are not memorable and nothing in the object database says which commit is the latest, and this is the job of refs. A ref is simply a file containing a commit hash. Branches live under .git/refs/heads, so the file .git/refs/heads/main contains the 40 characters naming the commit at the tip of main. Tags live under .git/refs/tags, and remote-tracking branches such as origin/main live under .git/refs/remotes. Creating a branch is nothing more than writing a new forty-one-byte file, which explains why it is instant, and committing on a branch just updates that file to point at the new commit. The new commit records the old tip as its parent, so the chain extends. Over time Git may pack many refs into a single .git/packed-refs file, but the meaning is the same.

One more pointer completes the picture: the file .git/HEAD, which says where you are now. Usually it contains a line like "ref: refs/heads/main", a symbolic reference to a branch, so that committing moves that branch forward. If you check out a specific commit directly, HEAD instead holds a raw commit hash, which is the detached HEAD state that Git warns you about.

Putting it together, a commit proceeds like this. Git takes the files you staged in the index, writes a blob for any content it has not seen before, builds the tree objects that describe the directory layout, creates a commit object naming the root tree and the current HEAD commit as its parent, and finally moves the current branch ref to the new commit's hash. Four kinds of record, all but the last permanent and content-addressed, are enough to represent your entire history. If you want to see this for yourself, git cat-file -p followed by a hash prints any object in readable form, and starting from the hash in .git/refs/heads/main you can walk from a commit to its tree to a blob in three commands.

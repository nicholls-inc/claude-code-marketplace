From HTTPS Address to First Byte: What the Browser Does

When you type https://www.example.com/products into a browser and press Enter, a lot happens before the first byte of the response arrives. The time between the request and that first byte is called Time To First Byte (TTFB). Knowing the steps behind it helps you diagnose slow pages and understand what the browser's network tab is showing you.

1. Parsing the URL

The browser first splits the address into parts. The scheme is https, the host is www.example.com, the port is implied (443 for HTTPS), and the path is /products. The scheme matters because it tells the browser to encrypt the connection. Browsers also consult a built-in HSTS (HTTP Strict Transport Security) list, and a site on that list is only ever contacted over HTTPS, even if you typed http://.

2. Checking caches and service workers

Before touching the network, the browser checks whether it can answer locally. If a service worker controls the page, it may intercept the request and respond itself. Otherwise the HTTP cache is checked. A fresh cached copy, based on headers such as Cache-Control, is used immediately and no network request is made. A stale copy may still be used after the browser asks the server whether it has changed (a conditional request). Only on a miss does the full journey below begin.

3. DNS resolution

Networks route traffic by IP address, not name, so the browser must translate www.example.com into an IP address such as 93.184.216.34. It looks in several places in order: the browser's own DNS cache, the operating system's cache and hosts file, then a recursive resolver, usually run by your ISP or a provider like Cloudflare or Google. If the resolver does not know the answer, it queries the DNS hierarchy: a root server points to the .com servers, which point to example.com's authoritative name server, which returns the address. Results are cached according to the record's TTL, so repeat visits are fast. A cold lookup typically costs 20 to 120 ms. The response may include both IPv4 (A) and IPv6 (AAAA) records, and the browser may race them.

4. Opening a TCP connection

With an IP address, the browser opens a connection to port 443. TCP uses a three-step handshake: the client sends SYN, the server replies SYN-ACK, and the client sends ACK. This costs one round trip. If the server is 50 ms away, the handshake costs roughly 50 ms before any data flows. This is why geographic distance, and CDNs that place servers closer to users, matter so much.

Modern browsers may use HTTP/3 instead, which runs over QUIC on UDP. QUIC merges the transport and encryption handshakes to save round trips. A browser typically learns a site supports HTTP/3 from an Alt-Svc header on an earlier response, or from DNS records, and then tries it.

5. The TLS handshake

HTTPS is HTTP carried inside TLS (Transport Layer Security), which provides encryption, authentication and integrity. Over TCP, TLS 1.3 adds one more round trip:

- The browser sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, a key share for key agreement, and the Server Name Indication (SNI), which is the hostname. SNI lets one IP address host many sites.
- It also sends ALPN, a list of application protocols it speaks (h2, http/1.1). The server picks one, which is how HTTP/2 gets negotiated without an extra trip.
- The server replies with its ServerHello and key share. Both sides now derive the same session keys using an ephemeral Diffie-Hellman exchange, so nobody watching the wire can decrypt the traffic.
- The server sends its certificate chain, encrypted, plus proof that it holds the private key.

Certificate validation is the step that makes the lock icon trustworthy. The browser checks that the certificate chains up to a certificate authority (CA) in its trust store, that it has not expired, that its names (Subject Alternative Names) include www.example.com, and that it has not been revoked. Revocation checking is often done via stapled OCSP responses or browser-maintained lists rather than live lookups, to avoid extra delay. If any check fails, the browser shows a full-page warning and stops.

Older TLS 1.2 needs two round trips instead of one. When a browser has connected before, TLS 1.3 session resumption can shorten this further, and 0-RTT mode can even send data with the first flight, with some replay-attack caveats.

6. Connection reuse

Many of these steps can be skipped. Browsers keep connections open and reuse them for later requests to the same origin. HTTP/2 and HTTP/3 multiplex many requests over one connection, and a browser may coalesce requests for different hostnames onto one connection if the certificate covers both. Developers can also help with hints such as preconnect, which opens DNS, TCP and TLS ahead of time, and dns-prefetch.

7. Sending the HTTP request

Now the browser sends the actual request, encrypted inside the TLS session. In HTTP/1.1 it looks like text:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

HTTP/2 and HTTP/3 carry the same information, but in a compressed binary format with pseudo-headers such as :method and :path. The browser attaches relevant cookies for that domain, and headers describing language, accepted compression and its own identity. If the site was reached through a redirect, such as http to https or non-www to www, the whole process repeats for the new URL, which is a common hidden source of delay.

8. Travel and server-side work

The request crosses the internet through many routers, possibly reaching a CDN edge server first. The CDN may answer from its own cache. If not, it forwards the request to your origin. Along the way a load balancer or reverse proxy such as nginx may pick a backend instance.

The application then does its work: routing the request, checking authentication, querying a database, calling other services, and rendering HTML. This is often the largest and most variable part of TTFB, and it is the part you control most directly. Slow queries, cold starts on serverless platforms, and uncached rendering all show up here.

9. The first byte arrives

As soon as the server writes the start of its response, the status line and headers, such as HTTP/1.1 200 OK, travel back through the same path. The first byte reaching the browser marks the end of TTFB. Everything after that, downloading the body, parsing HTML, fetching CSS and JavaScript, and painting, is a separate phase.

Putting numbers on it

TTFB is roughly: redirects + DNS + TCP + TLS + request travel + server processing + response travel. On a good connection, DNS may be 30 ms, TCP 30 ms, TLS 30 ms and the server 100 ms, so TTFB is around 200 ms. Under about 800 ms is generally considered good.

Seeing it yourself

Open DevTools, go to the Network tab, click a request, and open Timing. You will see the phases labelled Queueing, DNS Lookup, Initial connection, SSL, Waiting for server response (that is TTFB), and Content Download. Comparing a first visit with a repeat visit shows how much caching and connection reuse save.

Practical takeaways

- Serve content from a CDN to cut round-trip distance.
- Enable HTTP/2 or HTTP/3 and TLS 1.3.
- Avoid redirect chains.
- Cache aggressively with correct Cache-Control headers.
- Use preconnect for third-party origins you know you need.
- Profile server-side work, since it is often the real bottleneck.

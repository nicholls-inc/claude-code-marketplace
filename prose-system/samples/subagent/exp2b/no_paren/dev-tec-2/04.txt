From HTTPS Address to First Byte

When you type https://www.example.com/products into a browser and press Enter, a surprising amount of work happens before a single byte of the page comes back. Most of it is invisible, and most of it is measured in milliseconds. Understanding the sequence helps you reason about performance, debug failures, and read the network panel in your developer tools with confidence.

1. Parsing the address

The browser first splits the address into parts. The scheme is https, the host is www.example.com, and the path is /products. No port is given, so the browser assumes 443, the default for HTTPS. Before going to the network, it checks whether the host is on its HSTS list, a record of sites that must only be reached over HTTPS. It also checks its own caches, because the fastest request is the one never sent. If a fresh copy of the resource is stored locally, the browser can skip nearly everything below.

2. Finding the IP address with DNS

Networks route traffic by IP address, not by name, so the browser must translate www.example.com into a number. This is the job of the Domain Name System. The browser looks in its own DNS cache, then asks the operating system, which has a cache of its own. If neither knows the answer, the request goes to a recursive resolver, usually run by your internet provider or a public service.

The resolver also caches answers. On a miss, it works down the hierarchy. It asks a root server which servers handle .com, asks those which servers handle example.com, and finally asks the authoritative name server for the address of www.example.com. The answer comes with a time to live, which says how long it may be cached. Along the way the answer may be a CNAME, an alias pointing to another name, which triggers another lookup. A cold lookup can take tens of milliseconds, while a warm one is nearly instant.

3. Opening a TCP connection

With an IP address in hand, the browser opens a connection to port 443. Traditional HTTPS runs over TCP, which provides reliable, ordered delivery. TCP begins with a three step handshake. The client sends a SYN packet, the server replies with SYN and ACK, and the client answers with an ACK. This costs one full round trip, the time for a message to travel to the server and back. If the server is far away, that round trip may be over a hundred milliseconds, which is why distance matters so much.

Newer versions of HTTP can use QUIC instead, which runs over UDP and folds connection setup and encryption into fewer round trips. The browser learns about this from earlier visits or from DNS records, and falls back to TCP when needed.

4. Negotiating encryption with TLS

Now the connection is open, but nothing on it is private. The browser starts a TLS handshake. In TLS 1.3, the client sends a hello message that lists the encryption methods it supports, a random value, and a key share used for key exchange. It also includes the Server Name Indication, the hostname it wants. This matters because one IP address often hosts many sites, and the server needs to know which certificate to present.

The server answers with its own key share, its certificate, and a signature proving it holds the matching private key. Both sides then derive the same session keys from the exchanged values, without ever sending the keys themselves. TLS 1.3 needs one round trip for this. TLS 1.2 needed two, which is one reason to prefer the newer version. If you have visited the site recently, session resumption can shorten the process further.

5. Verifying the certificate

While this happens, the browser checks that the certificate can be trusted. It confirms that the certificate covers www.example.com, that it has not expired, and that it chains up to a certificate authority the browser already trusts. Each certificate in the chain is signed by the next one, ending at a root certificate stored in the operating system or browser. The browser may also check whether the certificate has been revoked, often using stapled responses delivered by the server. If any check fails, you see a full page warning and the request does not continue. This verification is what stops an attacker on the network from impersonating the site.

6. Sending the HTTP request

Only now does the browser send the request itself, and it is encrypted by the session keys. A simple request looks like this in HTTP/1.1 form.

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The method says what to do, the path says which resource, and the headers carry context. The Host header names the site. Accept-Encoding lists the compression formats the browser can decode. Cookies that belong to this domain are attached automatically. With HTTP/2 and HTTP/3, the same information is sent in a compact binary form, and many requests can share one connection.

7. Server work and the first byte

The request arrives at the server, but often not at the machine you imagine. It may first hit a content delivery network edge, a nearby server that can answer from its cache or forward the request onward. A load balancer then picks one of several application servers. That server routes the request to your code, which may query a database, call other services, and render a response. Each of these steps adds to the waiting time.

The moment the first byte of the response comes back is called time to first byte, or TTFB. It is the sum of everything above. That sum covers DNS lookup, the TCP handshake, the TLS handshake, the request travelling to the server, the server's processing time, and the first piece of the reply travelling back. Developer tools show these as separate segments in the timing breakdown of a request, which makes it easy to see where time is going.

What this means for you

Several practical habits follow. Reuse connections, since the handshakes are the costly part, and keep alive settings and HTTP/2 do this for you. Serve static content from a CDN so the distance is short. Keep server processing fast with caching and efficient queries. Use modern TLS versions, and consider preconnect hints for origins you know the page will need. Finally, when a page feels slow, check the waterfall before guessing. The delay is often in the network setup, not in your code.

When you type an HTTPS address into a browser, the first thing it does is parse the URL into its parts: the scheme (https), the host (for example www.example.com), an optional port (443 by default for HTTPS), the path, and any query string or fragment. The fragment, the part after the hash, never leaves the browser, so it plays no role in what follows. Before touching the network, the browser checks whether it already knows the answer. It looks at its HTTP cache for a fresh copy of the resource, at any service worker registered for the origin that might intercept the request, and at its HSTS list, which records sites that must only ever be reached over HTTPS. If the cache holds a valid response, the process can end here and the "first byte" arrives from local storage almost instantly. Otherwise the browser has to go and find the server.

The first network step is DNS resolution, because the network routes by IP address, not by name. The browser checks its own DNS cache, then asks the operating system, which checks its cache and the hosts file. If neither knows the name, the OS sends a query to a recursive resolver, usually run by your ISP or a public provider, over UDP port 53, or increasingly over an encrypted channel such as DNS over HTTPS or DNS over TLS. The resolver may already have the answer cached. If not, it works through the hierarchy: it asks a root server which servers handle the top-level domain, asks those which servers are authoritative for the domain, and finally asks the authoritative server for the record. The answer is an A record (IPv4) or an AAAA record (IPv6), sometimes reached by following a CNAME alias. Each record carries a time-to-live that tells every cache along the way how long it may be reused. A cold lookup can take tens of milliseconds, while a warm one takes almost none. Modern browsers often ask for IPv4 and IPv6 addresses together and may try both, preferring whichever connects first, a technique called Happy Eyeballs.

With an IP address in hand, the browser opens a TCP connection to port 443. TCP provides a reliable, ordered byte stream on top of the unreliable packet network, and it begins with a three-step handshake. The client sends a SYN packet, the server replies with SYN-ACK, and the client answers with ACK. That costs one full round trip before any data can flow, so the distance between you and the server directly sets a floor on how fast this step can be. Packets travel through your router, your ISP and several other networks, each hop forwarding them by IP routing tables. If a packet is lost, TCP notices and retransmits, which is reliable but slow when it happens during setup. Some sites use HTTP/3 instead, which runs over QUIC on UDP and merges the transport and encryption setup into fewer round trips; the browser learns about this through an Alt-Svc header from an earlier visit or through a DNS HTTPS record, and otherwise falls back to the TCP path described here.

Once TCP is established, the browser and server perform a TLS handshake to secure the connection. In TLS 1.3, the client sends a ClientHello listing the protocol versions and cipher suites it supports, a random value, a key share for key agreement, and the Server Name Indication, which tells the server which hostname the client wants. This is necessary because one IP address often hosts many sites. It also includes the ALPN extension, which advertises the application protocols the client speaks, typically h2 and http/1.1. The server answers with its chosen cipher suite, its own key share, and its certificate chain. Both sides now combine the key shares using an elliptic-curve Diffie-Hellman exchange to derive the same session keys without ever sending those keys over the wire. The rest of the handshake is already encrypted. The server proves it owns the certificate's private key by signing the handshake transcript, and both sides send Finished messages that confirm nothing was tampered with.

The certificate check is what makes HTTPS trustworthy, so it deserves attention. The browser verifies that the certificate is valid for the requested hostname, that it falls within its validity dates, and that it chains up through intermediate certificates to a root certificate authority already trusted by the browser or operating system. It may also check revocation status, using mechanisms such as OCSP stapling, where the server attaches a recent signed statement that the certificate has not been revoked, or the browser's own revocation lists. If any check fails, you see a full-page warning and the request does not continue. TLS 1.3 needs one round trip for this exchange, and TLS 1.2 needs two, so upgrading the protocol version is a simple way to cut latency. If you have connected to this server recently, session resumption can reuse earlier secrets and skip much of the work, and TLS 1.3 even permits sending early data on a resumed connection, though with some replay-related caveats.

Now the encrypted channel is ready, and the browser finally sends the actual HTTP request. If ALPN selected HTTP/2, the request is encoded as binary frames with compressed headers, and several requests can share the one connection. If it selected HTTP/1.1, the request is plain text: a request line such as GET /path HTTP/1.1, followed by headers like Host, User-Agent, Accept, Accept-Encoding and any cookies the browser holds for that site. All of this is encrypted by TLS before leaving your machine, so anyone watching the network sees only the destination IP address, the server name in the ClientHello (unless Encrypted Client Hello is in use), and the amount of traffic.

The request then travels to the server's side. In practice it rarely reaches the application directly. It commonly hits a CDN edge node or a load balancer first, which terminates TLS, may answer from its own cache, and otherwise forwards the request to an origin server, sometimes through a reverse proxy such as nginx. The origin application routes the request, perhaps queries a database, renders HTML or JSON, and begins writing the response. The server sends back a status line and headers, and the very first byte of that response, which is the moment measured as time to first byte, finally reaches the browser after traveling back through the same encrypted connection.

For a junior developer, the practical lesson is that time to first byte is the sum of several separate costs: DNS lookup, TCP handshake, TLS handshake, the request's trip across the network, and the server's own processing time. Each can be measured individually in the browser's network panel, and each has its own remedies: faster DNS and longer TTLs, keeping connections alive and reused, TLS 1.3 and resumption, serving from a CDN near the user, caching responses, and making the backend itself quicker.

How Git Stores a Commit

You run `git commit` many times a day. Each time, Git writes a few small files into `.git/objects` and changes one line of text in `.git/refs`. This piece covers what those files are and how they fit together.

The object database

Git is a content-addressed store at its core. Every piece of data is saved as an object, and the object's name is a hash of its contents. To build an object, Git takes a header made of the object type, a space, the content length in bytes and a NUL byte (for example `blob 12\0`), puts it in front of the content, and hashes the whole thing with SHA-1. Repositories created with `--object-format=sha256` use SHA-256 instead. The result is a 40-character hex ID such as `e69de29bb2d1d6434b8b29ae775ad8c2e48c5391`.

The object is compressed with zlib and written to `.git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391`. The first two hex characters name a subdirectory, which keeps any single directory from holding too many files. A file stored like this is called a loose object.

Content addressing has two consequences. First, identical content is stored once: if a hundred commits contain the same `LICENSE` file, there is one blob for it. Second, objects can never change. Editing the content would change the hash, which would make it a different object. Everything below relies on this.

You can try it yourself. `git cat-file -t <id>` prints an object's type, and `git cat-file -p <id>` prints its contents in readable form.

Blobs

A blob holds the contents of a file and nothing more. It has no filename, no permissions and no timestamp. `echo 'hello' | git hash-object --stdin` returns the same ID on every machine in the world, because the ID depends only on those six bytes.

When you `git add` a file, Git writes the blob straight away and records its ID in the index (`.git/index`). That is why staged content survives even if you later change the file in your working tree.

Trees

Names and directory structure live in tree objects. A tree is a list of entries. Each entry has a mode, a name and the ID of another object:

```
$ git cat-file -p HEAD^{tree}
100644 blob 8ab686eafeb1f44702738c8b0f24f2567c36da6d    README.md
100755 blob 3b18e512dba79e4c8300dd08aeb37f8e728b8dad    build.sh
040000 tree 9f2c1a7e4b0d3c6f5a8e2d1b7c4f0a9e3d6b5c2a    src
```

The mode records the entry's type. `100644` is a normal file, `100755` an executable, `120000` a symlink, `040000` a subdirectory (another tree) and `160000` a submodule (a commit ID in another repository). On disk the hashes are stored as raw bytes, not hex. `cat-file -p` formats them for display.

Because a subdirectory is referenced by its hash, a tree is a Merkle tree. The root tree's ID depends on every file and directory below it. If you change one file deep in `src/`, Git writes a new blob, a new tree for each directory on the path up to the root, and a new root tree. Every untouched subtree is reused by its existing ID. That reuse is why a commit that touches one file in a large repository adds only a handful of objects.

Commit objects

A commit is a short text object:

```
$ git cat-file -p HEAD
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 7d1e2c3b9a0f4e5d6c7b8a9f0e1d2c3b4a5f6e7d
author Ada Lovelace <ada@example.com> 1762851600 +0000
committer Ada Lovelace <ada@example.com> 1762851600 +0000

Fix off-by-one in pagination
```

The `tree` line points at the root tree, which is a complete snapshot of the project. A commit does not store a diff. When `git show` displays changes, it computes them by comparing this commit's tree with its parent's tree.

The `parent` lines link the commit to its history. A root commit has none, an ordinary commit has one, and a merge commit has two or more. Author and committer are recorded separately because they can differ, for example after a rebase or a cherry-pick. Each carries a Unix timestamp and a timezone offset. A signed commit adds a `gpgsig` header. After a blank line comes the message.

The parent IDs are part of the hashed content, so a commit's ID covers its whole ancestry. Changing anything in an old commit changes its ID, and therefore the IDs of every descendant. This is why rewriting history with rebase or amend produces new commits instead of editing the old ones.

Refs

Nobody wants to type 40-character hashes, so Git gives them names. A branch is a file such as `.git/refs/heads/main` that contains one commit ID and a newline. Creating a branch writes a 41-byte file. Committing on a branch writes the new objects and then overwrites that file with the new commit's ID. Nothing else about the branch is stored anywhere.

`HEAD` is usually a symbolic ref. `.git/HEAD` contains `ref: refs/heads/main`, meaning "the current branch is main". When you check out a commit directly, `HEAD` holds a raw ID instead, which is the "detached HEAD" state.

Tags live in `refs/tags/`. A lightweight tag is just a ref to a commit. An annotated tag points to a fourth object type, the tag object, which records a target ID, a tagger, a message and optionally a signature. Remote-tracking branches such as `origin/main` live in `refs/remotes/`.

To save space, Git may move many refs into a single `.git/packed-refs` file, so a missing file under `refs/` does not mean the branch is gone. `git rev-parse main` always resolves a name correctly.

Packfiles

Loose objects are only part of the picture. `git gc`, `git fetch` and `git push` bundle objects into packfiles in `.git/objects/pack/`, where similar objects are stored as deltas against each other. This is a storage optimisation only. Objects keep the same IDs and the same logical contents, so everything above still applies.

Putting it together

A commit does four things. It writes blobs for new file contents, writes trees for every changed directory, writes one commit object that points at the root tree and its parent, and moves a branch ref to point at that commit.

From HTTPS Address to First Byte: What the Browser Does

When you type https://www.example.com/products into a browser and press Enter, a surprising amount of work happens before a single byte of the page arrives. Knowing these stages helps you diagnose slow pages, read the Network tab in DevTools, and understand why things like CDNs, caching and HSTS exist. The stages are: parsing the URL, checking local caches, DNS lookup, TCP connection, TLS handshake, sending the request, and waiting for the server. The first byte of the response is what DevTools calls Time to First Byte (TTFB).

1. Parsing the URL

The browser first splits the address into parts. The scheme is https, the host is www.example.com, the port is implied (443 for HTTPS), and the path is /products. Anything after a ? is the query string and anything after # is the fragment; the fragment never leaves the browser.

If what you typed is not a valid URL, the browser treats it as a search query instead. If the host is on the browser's HSTS list (HTTP Strict Transport Security), the browser will also upgrade any http:// address to https:// itself, without making an insecure request first.

2. Checking local caches

Before touching the network, the browser asks whether it already has what it needs. The HTTP cache may hold a fresh copy of /products, in which case the request can finish without any network traffic. A service worker, if the site registered one, may intercept the request and answer it from its own cache. Only if neither can answer does the browser continue. Even then, it may reuse an already-open connection to the same origin (more on this below), skipping several of the following steps.

3. DNS resolution

Networks route by IP address, not by name, so the browser must turn www.example.com into an address such as 93.184.216.34. It checks, in order:

- The browser's own DNS cache.
- The operating system's cache and its hosts file.
- A recursive resolver, usually run by your ISP, your company, or a public provider.

If the resolver does not know the answer, it queries the DNS hierarchy on your behalf: a root server points it to the .com servers, which point it to the authoritative servers for example.com, which return the final record. Every record carries a TTL (time to live) that says how long it may be cached, which is why most lookups are fast and why DNS changes take time to propagate. A cold lookup can cost tens to hundreds of milliseconds. Modern browsers may also use DNS over HTTPS and may fetch HTTPS/SVCB records that advertise supported protocols.

4. Opening a TCP connection

With an IP address in hand, the browser opens a TCP connection to port 443. TCP gives reliable, ordered delivery, and it begins with a three-way handshake: the client sends SYN, the server replies SYN-ACK, and the client sends ACK. That costs one round trip, so the distance between you and the server matters directly. This is a large part of why CDNs place servers geographically close to users.

(HTTP/3 is the exception. It runs over QUIC, which uses UDP and combines the transport and encryption handshakes into one. A browser typically learns a site supports HTTP/3 from an earlier visit via the Alt-Svc header, or from DNS, and may race it against a TCP connection.)

5. The TLS handshake

The "S" in HTTPS is TLS, which provides three things: encryption, so eavesdroppers cannot read the traffic; integrity, so it cannot be silently altered; and authentication, so you know you are talking to the real example.com. In TLS 1.3, the common case today, the handshake works roughly like this:

1. The client sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, a key share for key exchange, and the Server Name Indication (SNI), which tells the server which hostname is wanted. SNI matters because one IP address often hosts many sites.
2. The server replies with a ServerHello choosing the parameters and completing the key exchange. Both sides can now derive shared session keys, and everything after this point is encrypted.
3. The server sends its certificate and proof that it holds the matching private key.
4. The client verifies the certificate. It checks that the certificate chains up to a certificate authority the browser trusts, that it has not expired, that it has not been revoked, and that it is valid for the requested hostname. If any check fails, you see the full-page certificate warning.
5. Both sides send Finished messages, and application data can flow.

TLS 1.3 needs one round trip for this. TLS 1.2 needed two. Returning visitors can sometimes use session resumption to shorten the handshake further, and in some setups send data immediately (0-RTT), though that has replay-attack caveats.

During this step the client and server also agree on the application protocol using ALPN: HTTP/1.1 or HTTP/2 (HTTP/3 negotiates differently, as noted above).

6. Sending the HTTP request

Now the browser can finally send the request, encrypted inside the TLS session. In HTTP/1.1 it looks like text:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123
User-Agent: ...

The browser attaches headers describing what it accepts, which compression it understands, and any cookies previously set by this site. HTTP/2 and HTTP/3 carry the same information in a compressed binary format and can multiplex many requests over one connection, but the meaning of the request is unchanged. If the browser already has an open, idle connection to this origin, it sends the request on that connection and skips DNS, TCP and TLS entirely. This is connection reuse (keep-alive), and it is why the first request to a site is usually slower than later ones.

7. Waiting for the server

The request travels to the server's IP address, but often not to the machine that holds your application code. It typically passes through a CDN edge node or a load balancer, possibly a reverse proxy, and a web server before reaching the application. Any of them can answer directly from its own cache. If not, the application may check authentication, query a database, call other services, and render HTML. All of that happens inside the TTFB window. A slow database query or an overloaded server shows up here, which is why TTFB is a useful signal for backend health.

Eventually the server begins sending the response: a status line (such as 200 OK), headers, and then the body. The arrival of the first byte of that response marks the end of TTFB. It is also the point where the browser can finally start parsing HTML and discovering the CSS, scripts and images it must fetch next. Many servers send headers and the start of the body early and stream the rest, which lets the browser start working sooner.

Putting it together

For a first visit to a cold site, the sequence adds up roughly as: DNS (0 to a few round trips) + TCP (1 round trip) + TLS 1.3 (1 round trip) + request and server processing (1 round trip plus server time). Each network round trip is limited by distance and the speed of light, so reducing the number of round trips and shortening the distance are the main levers.

Practical takeaways for a junior developer:

- Open DevTools, go to the Network tab, click a request, and look at the Timing breakdown. You will see DNS Lookup, Initial Connection, SSL, Waiting for server response (TTFB) and Content Download, which map to the steps above.
- Slow TTFB with fast DNS/TCP/TLS usually means a slow backend. Slow connection phases usually mean network distance or a missing CDN.
- Cache headers, HTTP/2 or HTTP/3, connection reuse, preconnect hints (rel="preconnect"), and a nearby CDN all remove or shorten steps in this chain.
- Certificate errors are TLS authentication failing: wrong hostname, expired certificate, or an incomplete chain.

Every page load you have ever seen began with this sequence, completing in a fraction of a second.

From HTTPS address to first byte

You type https://shop.example.com/cart into the address bar and press Enter. Nothing visible happens for a moment. Underneath, the browser is doing a long chain of work, and almost all of it happens before the server sends a single byte of its answer. Knowing the chain helps you debug slow pages.

1. Parsing the address

The browser first splits the string into parts. The scheme is https, the host is shop.example.com, and the path is /cart. A port is implied by the scheme: 443 for HTTPS. If you typed something that is not a valid URL, the browser treats it as a search query instead.

Before touching the network, it checks a few local things. Is the site on the HSTS preload list, which forces HTTPS? Is there a cached copy that is still fresh? If the cache says yes, the whole process can end here, and no request leaves your machine.

2. Finding the IP address (DNS)

Networks route traffic by IP address, not by name, so the browser must translate shop.example.com into a number such as 203.0.113.10. This is DNS, the Domain Name System.

The lookup checks several caches in order: the browser's own, then the operating system's, then the router's. If none has an answer, the query goes to a recursive resolver, usually run by your ISP or a public provider. That resolver may already know the answer. If not, it walks the hierarchy. It asks a root server where to find .com, asks the .com servers where example.com lives, and finally asks the authoritative name server for example.com, which returns the address.

Each answer carries a TTL, a time-to-live that says how long it may be cached. This is why DNS changes take time to spread. A cold lookup might take 20 to 120 milliseconds. A cached one takes almost nothing.

The browser may also receive several addresses, both IPv4 and IPv6. It will try them in a sensible order, often racing them so a broken one does not stall the page.

3. Opening a connection (TCP)

With an IP address in hand, the browser needs a reliable channel to the server. Traditionally that is TCP, set up with the three-way handshake. The browser sends a SYN packet. The server replies with SYN-ACK. The browser answers with ACK. One full round trip passes before either side can send real data.

Round trips matter because of physics. A signal from London to a server in Virginia takes roughly 70 milliseconds there and back, however fast your connection is. Every extra round trip adds that cost. Much of web performance work is about removing round trips.

A note on HTTP/3: it runs over QUIC, which uses UDP instead of TCP and merges the transport and encryption setup into fewer round trips. The browser learns that a server supports it from a previous visit or from DNS records, and otherwise falls back to the TCP path described here.

4. Securing the connection (TLS)

The S in HTTPS means the connection is encrypted and the server is authenticated. This happens in the TLS handshake, which runs on top of the new connection.

In TLS 1.3, the browser sends a ClientHello. It lists the encryption methods it supports, a random value, and a key share, which is half of a key agreement. It also includes the server name (SNI), so a server hosting many sites knows which certificate to present.

The server replies with its own key share and its certificate. Both sides can now compute the same secret key without ever sending it. This is the Diffie-Hellman idea. An eavesdropper sees the exchanged values but cannot derive the key from them.

The certificate is the proof of identity. The browser checks that it names shop.example.com, has not expired, and was signed by a certificate authority the browser trusts. Usually the chain runs through an intermediate certificate up to a root already stored on your device. It may also check revocation status. If any check fails, you see the full-page warning, and the request stops.

TLS 1.3 needs one round trip for this. Older TLS 1.2 needed two. If you have visited recently, session resumption can shorten the handshake further.

5. Sending the HTTP request

At last the browser can say what it wants. Over the encrypted channel it sends something like this:

GET /cart HTTP/1.1
Host: shop.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The request line holds the method, the path and the protocol version. The headers add context. Host names the site. Accept-Encoding offers compression formats. Cookie carries any cookies the browser stored for this domain, which is how the server recognises you. HTTP/2 and HTTP/3 send the same information in a compact binary form rather than plain text, but the meaning is identical.

6. Waiting for the server

Now the request travels to the server, often through a CDN or load balancer first. A CDN edge node near you may answer from its cache. If not, it forwards the request to the origin server. The application there runs: it checks your session, queries a database, renders HTML, and begins writing the response.

The delay between sending the last byte of the request and receiving the first byte of the response is called Time to First Byte, or TTFB. Notice that TTFB as measured in browser tools usually includes the time spent on DNS, connection and TLS, plus this server think time. Slow TTFB can therefore come from any stage above, not just a slow backend.

7. The first byte arrives

The server sends back a status line, such as HTTP/1.1 200 OK, followed by headers and then the body. The first byte of that status line is the moment the journey described here ends. The browser then starts parsing the HTML, discovering CSS, scripts and images, and the rendering phase begins. That is a separate story.

Why this matters to you

Each stage can be measured, and each can be improved. In your browser's developer tools, the Network tab breaks a request into DNS lookup, initial connection, SSL, waiting (TTFB) and content download. Use it.

Practical habits follow from the sequence. Keep DNS TTLs sensible. Use a CDN to shorten distances. Enable HTTP/2 or HTTP/3 and TLS 1.3. Reuse connections instead of opening new ones, since a warm connection skips steps 2 to 4 completely. Cache aggressively with correct headers. And keep server work fast, because after all the clever networking, a slow database query still makes the user wait.

When a page feels slow, do not guess. Open the waterfall, find the stage that is long, and start there.

When you type an HTTPS address into a browser or follow a link to one, the browser first parses it into a scheme, a host, an optional port and a path, and then decides whether it needs to go to the network at all. It checks whether the host is on its built-in HSTS preload list or has been seen with a Strict-Transport-Security header before, in which case a plain http address would be silently upgraded, and it looks in its HTTP cache for a stored response that is still fresh, because a fresh cached copy means no request leaves the machine and the "first byte" arrives from local storage. If the cache cannot satisfy the request, the browser also checks whether a service worker registered for that origin wants to intercept it, since a service worker can answer from its own cache or rewrite the request before any network activity happens, and only when none of these shortcuts applies does the real work of reaching the server begin.

The first network step is turning the hostname into an IP address. The browser consults its own DNS cache, then asks the operating system's resolver, which has its own cache and the hosts file, and finally the configured recursive resolver, usually run by your ISP, your company or a public provider. If that resolver does not already have the answer cached, it walks the hierarchy on your behalf: it asks a root server which servers handle the top-level domain, asks those which servers are authoritative for the domain, and asks the authoritative server for the actual address records. Each answer carries a time-to-live that tells every cache along the way how long it may be reused, which is why a DNS change you make can take a while to be seen by everyone. Modern browsers typically ask for both A records (IPv4) and AAAA records (IPv6), and many will also query the newer HTTPS record type, which can announce that the server supports HTTP/3 or provide other connection hints. Where the answer lists several addresses, the browser may race connections to them, preferring IPv6 but falling back quickly to IPv4 if the first attempt stalls, an approach known as Happy Eyeballs.

With an address in hand, the browser has to establish a transport connection. For HTTP/1.1 and HTTP/2 that means TCP, which begins with a three-way handshake: the client sends a SYN, the server answers with a SYN-ACK, and the client acknowledges, so one full round trip passes before either side may send application data. If the browser knows from an earlier visit, or from the HTTPS DNS record, that the server speaks HTTP/3, it may instead use QUIC over UDP, which folds the transport and encryption handshakes together and saves a round trip, and which is also why you may see UDP traffic to port 443. If a proxy is configured, the browser first connects to the proxy and, for HTTPS, asks it with a CONNECT request to open an opaque tunnel to the destination, so the proxy relays bytes without being able to read them.

Over that connection the browser then negotiates TLS, which is what makes the address HTTPS rather than HTTP. It sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, a key share for key agreement, and the Server Name Indication extension containing the hostname, which lets a server that hosts many sites on one IP address choose the right certificate. It also lists the application protocols it can speak, through ALPN, so that HTTP/2 can be agreed on without an extra round trip. In TLS 1.3, which most sites now use, the server responds with its own key share, its certificate chain and a signature over the handshake, and both sides derive the session keys from the key exchange, so the handshake costs one round trip before encrypted application data can flow. In older TLS 1.2 it costs two. The browser verifies the certificate by checking that the chain leads to a root authority in its trust store, that every certificate in the chain is within its validity period, that the name in the certificate matches the hostname you asked for, and that the certificate has not been revoked, which it may check using stapled OCSP responses or compact revocation lists maintained by the browser vendor. A failure at any of these checks produces the full-page certificate warning rather than a connection. If the browser has connected to this server recently, it may resume the earlier session using a ticket and skip much of this, and if the server and client support it, the browser can even send the request in the first flight as 0-RTT early data, accepting that such data can be replayed and is therefore only safe for idempotent requests like a GET.

Only now, with an encrypted channel established, does the browser send the HTTP request itself. In HTTP/1.1 it is plain text, a request line such as GET /path HTTP/1.1 followed by headers like Host, User-Agent, Accept, Accept-Encoding, and any cookies stored for that domain, while in HTTP/2 and HTTP/3 the same information is carried as compressed binary frames on a numbered stream, so that many requests can share one connection without blocking each other at the HTTP layer. The browser adds conditional headers such as If-None-Match if it holds a stale cached copy it would like to revalidate, and the server may answer with a tiny 304 Not Modified response that tells it to reuse what it has.

On the server side the request often passes through several layers before application code sees it: a CDN edge node or load balancer that terminates TLS, possibly answers from its own cache, and otherwise forwards the request to an origin server, where a web server or reverse proxy hands it to your application framework, which routes it, may query a database, and builds a response. The first byte of the response the browser sees is typically the start of the status line or, in HTTP/2 and HTTP/3, the first frame of headers, and the time from sending the request to receiving that byte is what performance tools call time to first byte. It is the sum of everything described above, the DNS lookup, the transport handshake, the TLS handshake, the network latency each way and the time the server spends producing the response, which is why slow DNS, a distant server or a slow backend can each hold up the moment at which the browser can begin to render anything at all.

Inside .git, Git is a content-addressed key-value store with a thin layer of naming on top. Everything you do in Git day to day (commits, branches, tags) is built from four ideas: blobs, trees, commits and refs.

**The object database**

When you run `git add` or `git commit`, Git writes objects into `.git/objects`. Each object is identified by the SHA hash of its contents (plus a short header with its type and size). The first two hex characters of the hash become a directory name and the rest become the filename, so an object with hash `3b18e512dba7...` lives at `.git/objects/3b/18e512dba7...`. The file is compressed with zlib. Because the name is derived from the content, identical content is stored exactly once, and any change to the content produces a different name. Objects are never modified, only added.

There are four object types: blob, tree, commit and annotated tag. The first three make up every commit.

**Blobs: file contents**

A blob stores the raw bytes of one file and nothing else. It has no filename, no permissions and no timestamp. If two files in your repository have the same contents, whether in the same commit or across the whole history, they share one blob. If you change one line of a file, the new version is a new blob with a new hash. (Git later packs similar blobs together into delta-compressed packfiles to save space, but conceptually each version is a complete, separate object.)

You can look at any object with `git cat-file -p <hash>`, and its type with `git cat-file -t <hash>`.

**Trees: directories**

Names and permissions live in trees. A tree object is a list of entries, and each entry holds a mode, a type, a hash and a name. For example:

```
100644 blob a8f3c1e...  README.md
100755 blob 5d2b9c0...  build.sh
040000 tree 91e07ab...  src
```

The mode records whether an entry is a regular file (`100644`), an executable (`100755`), a symlink (`120000`) or a subdirectory (`040000`). Entries that point to blobs are files, and entries that point to other trees are subdirectories. A tree therefore describes one directory, and nested trees describe the whole project. The tree at the top is called the root tree, and its hash is a fingerprint of your entire working directory at one moment.

This has a useful consequence. If you change one file deep in `src/utils/`, Git creates a new blob for the file, a new tree for `src/utils/`, a new tree for `src/`, and a new root tree. Every other tree and blob is reused unchanged. That is why a commit is cheap even in a large repository.

**Commits: snapshots with history**

A commit object is small. You can print one with `git cat-file -p HEAD`:

```
tree 4c2a9e8f...
parent 7be01d93...
author Ada Lovelace <ada@example.com> 1731300000 +0000
committer Ada Lovelace <ada@example.com> 1731300000 +0000

Fix off-by-one in pagination
```

It contains a pointer to a root tree (the snapshot), zero or more parent commits, author and committer details with timestamps, and the message. A first commit has no parent, an ordinary commit has one, and a merge commit has two or more.

Notice that a commit stores a complete snapshot, not a diff. When Git shows you a diff, it computes it on demand by comparing the trees of two commits. Also notice that the parent hash is part of the commit's content, so it is part of the commit's own hash. Change anything about an old commit (even its message) and its hash changes, which changes the hash of every descendant. This is why "rewriting history" with rebase or amend actually creates new commits rather than editing old ones, and why the history is tamper-evident.

**Refs: human-readable names**

Hashes are not something you want to type, so Git keeps refs, which are named pointers to commits. They are plain text files under `.git/refs`:

- `.git/refs/heads/main` holds the hash of the tip commit of the `main` branch.
- `.git/refs/tags/v1.0` holds the hash for a tag (lightweight tags point straight at a commit, while annotated tags point at a tag object, which in turn points at a commit).
- `.git/refs/remotes/origin/main` records where Git last saw `main` on the remote.

Open one with `cat .git/refs/heads/main` and you will see a single 40-character hash. A branch is nothing more than that: a file with a hash in it. Creating a branch costs one tiny file write, which is why branching in Git is instant. Making a commit on a branch moves the file's contents to the new commit's hash, and the new commit's parent is the old value. (Large repositories may pack refs into `.git/packed-refs`, but the idea is the same.)

**HEAD: where you are**

The file `.git/HEAD` says what is currently checked out. Normally it contains a symbolic reference such as `ref: refs/heads/main`, meaning "I am on the main branch". When you commit, Git follows HEAD to the branch file and updates that file. In the "detached HEAD" state, the file contains a raw commit hash instead, so new commits are not recorded by any branch and are easy to lose.

**Putting it together**

When you run `git commit`, Git takes the staged snapshot in the index (`.git/index`), writes any new blobs, builds the tree objects from the bottom up, creates a commit object that points at the root tree and at the previous commit, and finally moves the current branch ref to the new commit. Four steps, all of them appending files or overwriting one small text file.

To explore this yourself, make a new repository, commit one file, and run `git cat-file -p HEAD`, then `git cat-file -p` on the tree hash it shows, then on the blob hash inside that. Following the chain from ref to commit to tree to blob makes the whole model clear.

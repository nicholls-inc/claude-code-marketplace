When you type an HTTPS address into a browser and press enter, the browser first has to work out what you actually asked for. It parses the address into a scheme, a hostname, an optional port and a path, and since the scheme is https it knows to use port 443 and to encrypt the connection. Before touching the network, it checks whether the site is on its built-in HTTPS-only or HSTS lists, which tell it never to attempt plain HTTP, and it looks for a cached copy of the resource that is still fresh enough to use without asking the server at all. If the cache cannot answer the request, the real work of reaching the server begins.

The browser cannot connect to a name, only to an IP address, so the next step is DNS resolution. The browser checks its own DNS cache first, then asks the operating system, which may consult a local hosts file and its own cache before forwarding the question to a recursive resolver, usually run by your internet provider or a public service. If the resolver does not already know the answer, it walks the hierarchy on your behalf, asking a root server which servers handle the top-level domain, then asking those which servers are authoritative for the domain, and finally asking the authoritative server for the address records. The answer comes back with a time-to-live that tells every cache along the way how long it may be reused, which is why a DNS change can take a while to be seen everywhere. Modern browsers may also encrypt this lookup with DNS over HTTPS, and they usually ask for both IPv4 and IPv6 addresses so they can pick whichever works best.

With an IP address in hand, the browser opens a TCP connection to port 443 on that machine. TCP provides a reliable, ordered stream of bytes on top of unreliable packets, and it begins with a three-step handshake in which the client sends a SYN, the server replies with a SYN-ACK, and the client acknowledges. This costs one full round trip, so the distance between you and the server matters a great deal here. Large sites reduce that distance by using content delivery networks, which publish an address that routes you to a nearby edge server, often through anycast routing, rather than to the origin machine that holds the original content. If the browser and server support HTTP/3, this step looks different, because that version runs over QUIC on top of UDP and folds the transport and encryption handshakes together, but the underlying goals are the same.

Once the connection exists, the browser and server perform a TLS handshake to establish an encrypted and authenticated channel. The browser sends a ClientHello that lists the TLS versions and cipher suites it supports, includes a key share for the key exchange, and carries the server name indication, which is the hostname in plain form so that a server hosting many sites knows which certificate to present. It also lists the application protocols it speaks, such as HTTP/2 and HTTP/1.1, so the two sides can agree on one without spending an extra round trip. The server answers with its chosen parameters, its own key share, and its certificate chain. Both sides can now derive the same session keys from the key exchange, using ephemeral values so that stealing the server's long-term key later would not reveal past traffic. In TLS 1.3 this takes a single round trip, and a returning visitor may be able to resume a previous session and send data even sooner.

Encryption alone would be pointless if you might be talking to an impostor, so the browser also validates the certificate. It checks that the certificate was issued for the hostname you requested, that its dates are valid, and that it chains up through intermediate certificates to a root authority the browser or operating system already trusts. It verifies the signatures along that chain, and it may check whether any certificate has been revoked, often through stapled responses supplied by the server itself. The server then proves it holds the private key matching the certificate by signing part of the handshake. If any of these checks fail, the browser stops and shows a warning page rather than continuing, which is the error you see when a certificate has expired or the name does not match.

Only now, with a secure channel in place, does the browser send the HTTP request itself. In HTTP/1.1 this is plain text, with a request line such as GET followed by the path, then headers like Host, Accept, User-Agent and Accept-Encoding, and any cookies that belong to that site. In HTTP/2 and HTTP/3 the same information is carried in compressed binary frames, which allows many requests to share one connection at once. All of this is encrypted by TLS, so anyone watching the network sees only the server's address, the approximate size and timing of the traffic, and possibly the hostname, but not the path, headers or body.

The request then travels across the internet to the server, possibly passing through a load balancer, a reverse proxy or a CDN cache along the way. Any of these may answer immediately from a stored copy, or pass the request on to an application server that runs your code, queries a database and builds a response. That processing time is the part the web developer controls most directly. When the server finally begins sending its reply, the first bytes to arrive are the status line and headers, and the moment that first byte reaches the browser is known as the time to first byte. Everything described above, from the cache check and DNS lookup to the TCP and TLS handshakes and the server's own work, adds up to that single measurement, which is why it is such a useful number to watch when a page feels slow.

Underneath the commands you type every day, Git is a simple key-value store that lives in the .git directory. Every piece of data it keeps is called an object. Each object is stored under a name that is the hash of its own contents, traditionally a SHA-1 digest written as forty hexadecimal characters, though newer repositories can use SHA-256. This is what "content-addressable" means: you cannot choose an object's name, because the name is computed from what the object holds. Two objects with identical content get the same name and are stored once. Change a single byte and you get a different name, and therefore a different object. Nothing in the object store is ever edited in place.

The first kind of object is the blob, which holds the contents of a file and nothing else. It does not record the file's name, its location in the project, its permissions or its modification time. When Git creates a blob, it prepends a small header consisting of the word blob, a space, the length of the content in bytes and a null byte. It hashes the header and content together to get the object's name. It then compresses the whole thing with zlib and writes it to disk. The first two characters of the hash become a subdirectory of .git/objects and the remaining characters become the filename, so an object might live at .git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391. Because the name depends only on content, if you have the same license file in ten directories, or the same file in a thousand commits, Git stores one blob.

Since blobs carry no names, something else must say which blob belongs at which path. That is the job of the tree object. A tree represents one directory. It is a list of entries, and each entry has a file mode, a name and the hash of another object. For an ordinary file the mode is 100644, for an executable file it is 100755 and for a symbolic link it is 120000. For a subdirectory the mode is 040000 and the hash points to another tree. A submodule is recorded with mode 160000 and points at a commit in a different repository. Trees nest, so the root tree of your project points to blobs for the files at the top level and to further trees for each folder, and so on down. The hash of a tree is computed from its entries, which means it depends on the names and contents of everything beneath it. If you change one line in a deeply nested file, the blob changes, so the tree containing it changes, so its parent tree changes, all the way up to the root. Files and directories that did not change keep their existing hashes and are shared with the earlier snapshot at no cost. This is why Git is described as storing snapshots rather than differences: each root tree describes the complete state of the project, but most of it is reused by reference.

The commit object is what gives a snapshot a place in history. A commit is a short text object with a few header lines followed by your message. The first line names the root tree for this snapshot. Next come zero or more parent lines, each holding the hash of a previous commit. The first commit in a repository has none, a normal commit has one and a merge commit has two or more. Then come an author line and a committer line, each with a name, an email address, a timestamp and a time zone offset. Author and committer are usually the same person, but they differ when a commit is cherry-picked or rebased or applied from a patch. A blank line follows, and then the commit message. Since the commit's hash is computed from all of this, including the parent hashes, every commit effectively vouches for the entire history behind it. You cannot change an old commit without changing its hash and the hashes of every commit that descends from it. That is what happens when you amend or rebase: Git builds new commit objects and leaves the old ones in place, unreferenced, until garbage collection eventually removes them.

None of the objects above is a name you would want to type, and none of them says where your work currently stands. That is the purpose of refs. A ref is a human-readable name that holds a commit hash. Branches are files under .git/refs/heads, and a file named main there contains nothing but the forty-character hash of the newest commit on that branch. Tags live under .git/refs/tags, and remote-tracking branches under .git/refs/remotes. Making a commit writes the new objects, then updates the current branch's file to point at the new commit, whose parent is the previous value. That one small write is all it means for a branch to advance. Creating a branch is just writing a new forty-byte file, which is why it is so cheap. The special file .git/HEAD usually holds a symbolic reference such as ref: refs/heads/main, saying which branch you are on. When you check out a commit directly, it holds a raw hash instead, which is the detached HEAD state. For efficiency, Git may also gather many refs into a single .git/packed-refs file, and it may pack loose objects into compressed packfiles that store similar objects as deltas. Those are storage optimizations and do not change the model.

Put together, a commit is a chain of references. A branch name points to a commit, the commit points to a root tree and to its parents, trees point to subtrees and blobs, and blobs hold the bytes. Everything except the refs is immutable and named by its own content. That is why Git can be so fast and why it can detect corruption.

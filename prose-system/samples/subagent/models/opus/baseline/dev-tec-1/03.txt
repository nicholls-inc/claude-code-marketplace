How Git Stores a Commit

Every time you run `git commit`, Git writes a few small files into `.git/objects` and updates one line of text in `.git/refs`. There are only four object types (blob, tree, commit and annotated tag), plus refs, which are named pointers into those objects. Once you know how these fit together, most of Git's behaviour follows from them.

Content addressing

Git's object store is a key-value database where the key is a hash of the value. To store an object, Git builds a short header (the object type, a space, the content length in bytes and a NUL byte), puts it in front of the content and hashes the result with SHA-1. Newer repositories can opt into SHA-256 instead. The 40-character hex digest is the object's name. Git compresses the header and content with zlib and writes them to `.git/objects/`, using the first two hex characters as a directory name and the remaining 38 as the file name. An object with hash `e69de29bb2d1d6434b8b29ae775ad8c2e48c5391` lives at `.git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391`.

Content addressing has three consequences. First, identical content always gets the same hash, so Git stores it only once, however many files or commits contain it. Second, objects can never change: different bytes give a different hash and therefore a different object. Third, a hash checks the integrity of everything it points to, directly or indirectly. You can see this for yourself: `echo hello | git hash-object --stdin` prints the same hash on any machine, and `git cat-file -p <hash>` prints any object in readable form.

Files written one per object like this are called loose objects. During `git gc` or a push or fetch, Git later packs many of them into packfiles (`.git/objects/pack/*.pack` with a matching `.idx` index) and stores similar objects as deltas against each other. Packing changes how objects are stored on disk but leaves their contents unchanged. An object's hash stays the same whether it is loose or packed.

Blobs: file contents only

A blob holds the bytes of one file. It has no file name, no permissions and no timestamp. If two files in different directories have the same contents, they share a single blob. If you rename a file without editing it, the blob stays the same. Git does not track renames anywhere. Commands like `git log --follow` work them out afterwards by comparing content.

Trees: directories

A tree object represents one directory. It is a sorted list of entries, and each entry has three parts:

- a mode: `100644` for a normal file, `100755` for an executable, `120000` for a symlink, `040000` for a subdirectory, or `160000` for a submodule commit
- a name
- the hash of the object the entry refers to (stored as raw 20 bytes, not hex)

File entries point to blobs and subdirectory entries point to other trees. The top-level tree therefore describes a full snapshot of the project. Because each tree is identified by the hash of its entries, a change to one file changes that file's blob hash, then the hash of its parent tree, and so on up to the root. Directories you did not touch keep their old tree hashes, so the new commit reuses them unchanged. This is why a commit in a large repository usually writes only a few new objects.

Run `git cat-file -p HEAD^{tree}` to see the root tree of your current commit.

Commit objects: snapshot plus history

A commit is a short text object. `git cat-file -p HEAD` shows something like this:

```
tree 9c1f0e...
parent 4b825d...
author Ada Lovelace <ada@example.com> 1731312000 +0000
committer Ada Lovelace <ada@example.com> 1731312000 +0000

Fix off-by-one in pagination
```

The `tree` line points to the root tree, which is the full snapshot. A commit stores a snapshot, not a diff. Git computes diffs when you ask for them by comparing two trees. The `parent` lines connect commits into a history. A root commit has no parent line, a normal commit has one and a merge commit has two or more. Author and committer are recorded separately because one person can write a change and another can apply it, for example with a rebase or cherry-pick. Each records a Unix timestamp and a timezone offset. A signed commit has an extra `gpgsig` header. The message comes after a blank line.

Since the parent hashes are part of the commit's content, each commit hash covers the whole history behind it. Changing anything in an old commit, even one character of its message, changes its hash and therefore the hash of every commit after it. That is why rebasing or amending creates new commits instead of editing the old ones, and why you have to force-push afterwards.

Refs: names for hashes

Hashes are hard for people to work with, so Git uses refs. A branch is a file such as `.git/refs/heads/main` whose entire content is a commit hash followed by a newline. A new commit on `main` is written in three steps:

1. Write the new blobs and trees.
2. Write a commit object whose parent is the current tip of `main`.
3. Overwrite `refs/heads/main` with the new commit's hash.

Creating a branch only writes another one-line file, which is why branches are cheap. Remote-tracking branches live under `refs/remotes/origin/`. Tags live under `refs/tags/`. A lightweight tag points directly at a commit. An annotated tag points at a tag object, which records the tagger, a date, a message and the target commit. To keep the directory small, Git may move many refs into a single `.git/packed-refs` file, so a ref can exist without its own file.

`HEAD` is usually a symbolic ref. The file `.git/HEAD` contains `ref: refs/heads/main`, meaning "the current branch is main". When you check out a commit directly, HEAD contains a raw hash instead, and Git calls that state "detached HEAD". Every change to a ref is also recorded in `.git/logs/` (the reflog). The reflog is how you can recover commits that no branch points to any more.

Putting it together

A commit is a chain of hashes: a ref names a commit, the commit names a tree and its parents, trees name subtrees and blobs, and blobs hold your file contents. Any object that cannot be reached from some ref or reflog entry is garbage, and `git gc` eventually deletes it.

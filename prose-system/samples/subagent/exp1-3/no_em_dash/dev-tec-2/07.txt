From HTTPS Address to First Byte: What the Browser Does

When you type https://www.example.com/products into a browser and press Enter, a surprising amount of work happens before any response data arrives. This description follows that journey step by step, from the moment the address is entered to the arrival of the first byte of the server's reply. That interval is often called Time to First Byte (TTFB), and understanding its parts helps you diagnose slow pages.

1. Parsing the URL

The browser first breaks the address into components. In https://www.example.com/products, the scheme is https, the host is www.example.com, the port is implied (443 for HTTPS), and the path is /products. If you typed something that is not a valid URL, such as plain words, the browser would treat it as a search query instead.

Before touching the network, the browser also checks a few local things. It consults its HSTS list, a record of sites that must only be loaded over HTTPS, and it checks the HTTP cache. If a fresh cached copy of the resource exists, the browser can use it immediately and skip the network entirely. Service workers, if registered for the site, get a chance to intercept the request too. Assuming none of these supply an answer, the request goes out to the network.

2. DNS Resolution

Networks route traffic using IP addresses, not hostnames, so the browser must translate www.example.com into an address such as 93.184.216.34. This is the job of the Domain Name System (DNS).

The lookup checks several caches in order: the browser's own DNS cache, the operating system's cache, and then the router. If none has the answer, the request goes to a recursive resolver, usually run by your ISP or a public provider. The resolver may already have the answer cached. If not, it works down the hierarchy: it asks a root server which servers handle .com, asks those which servers are authoritative for example.com, and finally asks the authoritative server for the address of www.example.com. Each record carries a time-to-live (TTL) that tells caches how long they may keep it.

A cold DNS lookup can take tens of milliseconds or more. A cached one is nearly instant. Modern browsers may also query for both IPv4 (A) and IPv6 (AAAA) records and pick whichever connects first.

3. Opening a TCP Connection

With an IP address in hand, the browser opens a connection to port 443. For HTTP/1.1 and HTTP/2, this uses TCP, which provides reliable, ordered delivery. TCP begins with a three-step handshake:

1. The client sends a SYN packet.
2. The server replies with SYN-ACK.
3. The client sends ACK.

This costs one full round trip between you and the server before any application data can flow. The farther away the server is, the longer this takes, which is why content delivery networks (CDNs) place servers close to users.

HTTP/3 is different. It runs over QUIC, which uses UDP and combines the transport and encryption handshakes, saving round trips. A browser typically learns a site supports HTTP/3 from an earlier visit (via an Alt-Svc header) and may race it against TCP.

4. The TLS Handshake

The "S" in HTTPS means the connection is encrypted using Transport Layer Security (TLS). Before any HTTP is sent, the browser and server negotiate a secure channel.

In TLS 1.3, the common modern version, this happens in one round trip:

1. The client sends a ClientHello listing supported cipher suites, its key-exchange share, and the hostname it wants (via the Server Name Indication, or SNI, extension). SNI matters because many sites share one IP address.
2. The server responds with a ServerHello, its chosen cipher suite, its own key share, and its certificate.
3. Both sides now derive the same session keys from the exchanged key shares, without ever sending the keys themselves. Everything after this point is encrypted.

The browser validates the certificate during this process. It checks that the certificate was issued by a certificate authority (CA) the browser trusts, usually through an intermediate chain leading to a root in the operating system or browser trust store. It checks that the certificate has not expired, and that the hostname matches one of the names the certificate covers. If any check fails, you see a certificate warning page instead of the site. Browsers may also check revocation status, though many rely on compact mechanisms like OCSP stapling, where the server attaches a recent signed status itself.

TLS 1.2, still seen in the wild, needs two round trips. If the browser has connected before, TLS 1.3 session resumption can shorten the handshake further, and 0-RTT can even send data with the first flight, with some replay-attack trade-offs.

5. Sending the HTTP Request

Now the secure channel exists, and the browser sends the actual request, encrypted. In HTTP/1.1 text form, it looks like this:

GET /products HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 ...
Accept: text/html,...
Accept-Encoding: gzip, br
Cookie: session=abc123

The request line names the method and path. Headers add context: which host is wanted, what content types and compression the browser accepts, and any cookies previously stored for this site. HTTP/2 and HTTP/3 carry the same information in a binary, compressed format rather than plain text, but the meaning is identical.

6. Server-Side Processing

The request travels across the network, often passing first through a load balancer, reverse proxy, or CDN edge. A CDN may answer directly from its cache, which is the fastest case. Otherwise the request reaches an application server.

There, your code runs. A framework routes /products to a handler, which may authenticate the user from the cookie, query a database, call other services, and render HTML or JSON. This work is frequently the largest controllable part of TTFB. Slow database queries, cold caches, and blocking calls to third-party APIs all show up here as waiting time.

7. The First Byte Arrives

As soon as the server begins sending its reply, the first bytes travel back through the encrypted connection. They typically contain the status line and headers, such as HTTP/1.1 200 OK, a Content-Type, caching directives, and any Set-Cookie headers. The browser decrypts them and, at that moment, the first byte of the response has arrived. TTFB is measured at this point.

The browser can then begin processing the response, parsing HTML as it streams in, which triggers further requests for CSS, JavaScript, and images. Those reuse the existing connection where possible, avoiding repeated DNS, TCP, and TLS costs.

Why This Matters in Practice

Roughly, TTFB is the sum of redirect time, DNS lookup, TCP connect, TLS handshake, request travel time, server processing time, and the return trip of the first byte. Browser developer tools make this visible. In the Network panel, the Timing tab breaks a request into stalled, DNS lookup, initial connection, SSL, waiting (TTFB), and content download.

Common levers for improvement follow directly from the steps above:

- Reduce redirects, since each one repeats much of this process (for example, http to https, or non-www to www).
- Use a CDN to shorten round-trip distance and serve cached responses.
- Enable HTTP/2 or HTTP/3 and TLS 1.3 to cut handshake overhead.
- Use connection hints such as preconnect and dns-prefetch for third-party origins you know you will need.
- Optimize server work with caching, efficient queries, and avoiding blocking calls.

Keeping this sequence in mind turns a vague "the site is slow" into a specific question: which stage is taking the time?

From HTTPS Address to First Byte: What the Browser Actually Does

When you type https://example.com/products into the address bar and press Enter, it feels instant. In the gap before the server sends anything back, though, the browser runs several separate protocols in order, and any of them can be slow. Knowing this sequence helps you read the Timing tab in DevTools and work out why a page is slow before it has even started to load.

1. Parsing the URL and checking for shortcuts

First, the browser decides whether the input is a URL or a search query. If it is a URL, the browser splits it into a scheme (https), a host (example.com), an optional port (443 by default for HTTPS), a path (/products) and an optional query string and fragment. The fragment, the part after #, is never sent to the server.

Before touching the network, the browser looks for ways to skip work:

- HSTS. If the site has sent a Strict-Transport-Security header before, or appears on the browser's built-in HSTS preload list, the browser will only use HTTPS for it. A typed http:// address is upgraded internally, with no insecure round trip.
- Service worker. If a service worker is registered for this origin, the request goes to it first. It may answer from its own cache, and then the network is never used.
- HTTP cache. If a fresh cached copy exists (for example, Cache-Control: max-age has not expired), the browser can use it straight away. The "first byte" then comes from disk, not from a server.
- An existing connection. If the browser already has an open connection to this origin (it is "kept alive"), it can skip steps 2 to 4 entirely. This is a big reason why the second request to a site is so much faster than the first.

If none of these apply, the browser has to build a connection from scratch.

2. DNS resolution: turning a name into an address

Computers connect to IP addresses, not hostnames, so the browser has to resolve example.com. It checks a series of caches, nearest first:

1. The browser's own DNS cache.
2. The operating system's resolver cache, plus the hosts file.
3. A recursive resolver, usually run by your ISP or a public service such as 1.1.1.1 or 8.8.8.8. Modern browsers may send this query over HTTPS (DNS-over-HTTPS) so other people on the network cannot read it.

If the recursive resolver does not have the answer cached, it works down the DNS hierarchy. It asks a root server where to find .com, asks the .com servers where to find example.com's authoritative nameservers, then asks those for the records. The answer comes back with a TTL (time to live) that controls how long each cache may keep it.

The browser typically asks for A records (IPv4), AAAA records (IPv6) and, increasingly, HTTPS records. An HTTPS record can tell the browser in advance that the server supports HTTP/3, which saves a later negotiation step. If both IPv4 and IPv6 addresses come back, the browser uses a technique called "Happy Eyeballs": it tries both in quick succession and keeps whichever connects first.

A cold DNS lookup can take anything from a few milliseconds to a few hundred. This is why <link rel="dns-prefetch"> and <link rel="preconnect"> exist: they let you start this work early for third-party origins you know you will need.

3. Opening a transport connection

With an IP address in hand, the browser opens a connection to port 443.

In the traditional path, this is TCP. TCP uses a three-way handshake: the client sends SYN, the server replies SYN-ACK, and the client sends ACK. This costs one full round trip (RTT) before any application data can flow. If the server is 100 ms away, you have spent 100 ms just agreeing to talk.

If the browser knows the server supports HTTP/3, it uses QUIC instead, which runs over UDP. QUIC combines the transport and encryption handshakes into one, which saves a round trip. The concepts below still apply, but some steps happen at the same time.

4. The TLS handshake: proving identity and agreeing on keys

HTTPS is HTTP sent inside TLS (Transport Layer Security). Before any HTTP is exchanged, client and server must agree on encryption keys, and the browser must confirm it is really talking to example.com. With TLS 1.3, the current standard, this goes as follows:

- ClientHello. The browser sends the TLS versions and cipher suites it supports, a random value and a key share (its half of a Diffie-Hellman key exchange). It also sends two important extensions. SNI (Server Name Indication) tells the server which hostname is wanted, because one IP address often hosts many sites. ALPN (Application-Layer Protocol Negotiation) lists the HTTP versions the browser can speak, such as h2 and http/1.1.
- ServerHello and friends. The server picks a cipher suite, sends its own key share and chooses an ALPN protocol. Both sides can now derive the same shared secret, and everything after this point is encrypted. The server then sends its certificate chain and a signature proving it holds the private key for that certificate, followed by a Finished message.
- Certificate validation. The browser checks that the certificate covers the hostname, has not expired and chains up to a root certificate authority it trusts. It may also check whether the certificate has been revoked, often using a "stapled" OCSP response that the server includes. If any check fails, you see the full-page certificate warning.
- Client Finished. The browser sends its own Finished message. The secure channel is ready.

TLS 1.3 needs one round trip for this, compared with two for TLS 1.2. When resuming a recent session, it can even send request data in the very first flight ("0-RTT"), with some replay-safety caveats.

On a cold connection over TCP, you have now spent roughly three round trips: one for DNS (often more), one for TCP and one for TLS.

5. Sending the HTTP request

Now the browser finally sends the request, using whichever protocol ALPN chose. With HTTP/2 or HTTP/3, the request is a set of binary frames on a stream. Several requests can share one connection at the same time. The request contains:

- The method and path: GET /products.
- Headers such as :authority (the host), User-Agent, Accept, Accept-Encoding (for example gzip, br, zstd) and Accept-Language.
- Cookies for this origin, filtered by their Domain, Path, Secure and SameSite attributes.
- Conditional headers such as If-None-Match or If-Modified-Since, if a stale cached copy exists. These let the server reply 304 Not Modified instead of resending the body.

6. Server processing and the first byte

The request may pass through a CDN edge, a load balancer or a reverse proxy before it reaches your application. Any of these may answer from its own cache. Otherwise, your code runs: routing, authentication, database queries, template rendering. Only when the server starts writing the response does the first byte travel back. That first byte is usually the start of the status line and headers, such as 200 OK.

The time from sending the request to receiving that byte, plus everything before it, is what people call Time to First Byte (TTFB).

Reading this in DevTools

Open the Network panel, click a request and choose the Timing tab. You will see these phases split out as Queueing, DNS Lookup, Initial connection, SSL, Request sent and "Waiting for server response". A large DNS or SSL value points to connection setup, which preconnect, CDNs and connection reuse can improve. A large waiting value points to slow server-side work, which is your back end. Knowing which phase is slow tells you where to start fixing it.

When you type an HTTPS address into a browser and press enter, the browser first has to work out what you actually asked for. It parses the address into a scheme, a host name, an optional port, a path, and any query string or fragment. Because the scheme is https, the browser knows it must use an encrypted connection, and it assumes port 443 unless the address says otherwise. Before touching the network, it also checks a few local places that might let it skip work: an HSTS list that says a site must only be reached over HTTPS, the HTTP cache that may already hold a fresh copy of the page, and any service worker registered for that site that could answer the request by itself.

If none of those shortcuts settles the matter, the browser needs an IP address for the host name, so it performs a DNS lookup. It first looks in its own cache, then asks the operating system's resolver, which may have its own cache or may forward the question to a recursive resolver run by your internet provider or a public service. If that resolver does not already know the answer, it works its way down the hierarchy, asking a root server which servers handle the top-level domain, asking those which servers are responsible for the domain, and finally asking the domain's authoritative server for the record. The answer comes back with a time-to-live value that tells every cache along the way how long it may be reused. Modern browsers may also ask for IPv4 and IPv6 addresses at once and may use encrypted DNS, but the goal is always the same, which is to turn a name into a number that routers understand.

With an address in hand, the browser opens a connection. Traditionally this means TCP, which begins with a three-step handshake in which the client sends a SYN packet, the server replies with SYN-ACK, and the client confirms with an ACK. That exchange costs one full round trip between you and the server, so physical distance matters here more than most developers expect. Newer HTTP/3 connections use QUIC, which runs over UDP and folds the transport and encryption setup together, but a browser typically only learns that a server supports it from an earlier visit or from an Alt-Svc header, so many first visits still begin with TCP. If the browser has several candidate addresses, it may race them and keep whichever connects first.

Next comes the TLS handshake, which is what makes the connection secure. In TLS 1.3 the client sends a hello message listing the cipher suites it supports, a key share for the key exchange, and the server name it wants, along with the application protocols it can speak, such as HTTP/2 or HTTP/1.1. The server replies with its own key share, which lets both sides derive the same session keys without ever sending those keys over the wire. The server then sends its certificate and proof that it holds the matching private key, and everything after the server hello is already encrypted. The browser checks that the certificate chains up to an authority it trusts, that it has not expired, that it has not been revoked, and that it actually covers the host name you typed. If any check fails, the browser shows a warning instead of continuing. TLS 1.3 needs only one extra round trip, and a client that has talked to the server before can sometimes resume a session and send data even sooner.

Once the encrypted channel exists, the browser can finally send the request itself. If the negotiation chose HTTP/2, the request is encoded as binary frames with compressed headers, whereas HTTP/1.1 sends plain text lines. Either way, the content is the same: a method such as GET, the path, the host, and headers describing what the browser accepts, which languages you prefer, what compression it understands, and what its user agent is. The browser also attaches any cookies that belong to that site, which is why a logged-in session carries through without you doing anything. Because the data travels through the TLS layer, anyone watching the network sees only encrypted bytes and the destination address.

The request then crosses a number of intermediaries before it reaches the application that will answer it. In practice, it often lands first at a content delivery network edge or a load balancer, which terminates the TLS connection, checks whether it has a cached copy, and otherwise forwards the request to an origin server. That origin might run a web server such as nginx, which hands the request to your application code, which in turn may query a database, call other services, and build a response. All of this work happens while the browser waits, and the time between sending the request and receiving the first byte of the reply is what performance tools call time to first byte. It therefore includes not only the server's processing time but also every earlier step, including DNS, connection setup, and the TLS handshake, depending on how the measurement is defined.

The moment the first byte of the response arrives, usually the start of the status line and headers, such as a 200 status or a 301 redirect, this stage ends. If the response is a redirect, the browser begins again with the new address, often reusing the existing connection if the host is the same. If it is a normal response, the body begins streaming in behind the headers, and the browser can start parsing HTML while the rest is still downloading. For a junior developer, the practical lesson is that each step is a separate place where delay can hide, and that caching, keeping connections open, using a nearby edge server, and keeping server-side work fast all exist to remove one of these waits.

Open the .git directory of any repository and the first thing you find is that Git is, at bottom, a key-value store: you hand it some content, it computes a SHA-1 hash of that content (newer repositories can be configured for SHA-256), and it files the content away under that hash. Everything you do with branches, merges and history is built on four kinds of object kept this way in .git/objects, plus a small set of text files called refs that give the hashes human-readable names. The hash is both the name and the integrity check, since changing a single byte of an object produces a different hash and therefore a different object, which is why nothing in Git's database is ever edited in place.

The simplest object is the blob, which holds the contents of one file and nothing else. Git builds it by prepending a header consisting of the word "blob", a space, the content's length in bytes and a null byte, hashes the header and content together, compresses the result with zlib and writes it to a path derived from the hash, where the first two hex characters become a subdirectory and the remaining thirty-eight become the filename. A blob does not record its filename, its permissions or where it lives in your project, so two files with identical contents anywhere in your history, however many times they were copied or renamed, share a single blob. You can see this for yourself by running git hash-object on a file and then git cat-file -p on the resulting hash, which decompresses and prints the original bytes.

Names and directory structure live in tree objects, each of which represents one directory as a sorted list of entries. An entry holds a file mode, a name and the hash of whatever it points to, so a tree entry for a regular file carries mode 100644 and points to a blob, an executable gets 100755, a symlink gets 120000 with the link target stored as blob content, and a subdirectory gets 040000 and points to another tree. A submodule appears as an entry with mode 160000 that points to a commit in a different repository altogether. Because a tree's hash is computed from the hashes of everything beneath it, the hash of the root tree identifies an entire snapshot of the project, and if you change one deeply nested file, only the blob, the trees along the path up to the root, and nothing else need to be created anew, while every untouched subtree is reused by hash. This is why Git stores full snapshots rather than diffs, yet stays compact in practice.

A commit object is a short piece of text that ties a root tree to a point in history. It contains a line naming the tree, a parent line for each preceding commit (none for the very first commit, one for ordinary commits, two or more for merges), an author line and a committer line each holding a name, an email address, a Unix timestamp and a timezone offset, then a blank line and the commit message. The author and committer can differ, which is what happens when someone applies a patch written by another person or when a commit is rebased, and the rebased copy is a brand new commit with a new hash because its parent line, and usually its timestamp, changed. Since each commit's hash covers its parent's hash, which covers that parent's parent, the whole chain is tamper-evident, and the history you see in git log is just a walk backward through parent pointers, with no separate log file recording it. Annotated tags are a fourth object type that wraps a target object with a tagger, a date and a message, while lightweight tags skip this and are only refs.

None of those objects knows what a branch is, and this is where refs come in. A branch is a file under .git/refs/heads whose name is the branch name and whose entire content is the forty-character hash of the commit at its tip, so creating a branch writes a file of about forty-one bytes, and making a commit means writing the new commit object and then updating that one file to point at it. Tags live under .git/refs/tags and remote-tracking branches such as origin/main under .git/refs/remotes, and all of them work the same way. The file .git/HEAD says where you currently are, and it usually contains not a hash but a line such as "ref: refs/heads/main", a symbolic reference that indirectly points at the commit through the branch, which is why committing moves the branch forward and why a detached HEAD, where the file holds a raw hash instead, leaves no branch behind to keep your new commits reachable. In large repositories many refs are gathered into a single .git/packed-refs file to avoid thousands of tiny files, and Git consults the loose file first when both exist.

Writing each object as its own file would eventually waste a great deal of disk space and slow everything down, so Git periodically packs loose objects into packfiles under .git/objects/pack, where similar objects are stored as deltas against one another, and this happens automatically during git gc and when you push or fetch. The reflog under .git/logs records where each ref used to point, which is how you can recover a branch after a bad reset, and objects that no ref or reflog entry can reach are eventually deleted as garbage. Seen this way, a commit is never a diff or a changeset but a pointer to a complete tree, a branch is a movable sticky note stuck to one commit, and the whole database is a graph of immutable, hash-named objects that you can inspect with git cat-file at any time.

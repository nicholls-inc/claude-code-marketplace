# How Git stores a commit

Every commit you make is stored as a handful of small files under `.git/objects`, plus one pointer under `.git/refs`. Git has only three object types involved in a commit (blob, tree and commit), and the same rule applies to all of them: the object's name is the hash of its content.

## The object store

Git is a key-value store. To save an object, Git takes its content, prepends a short header (the type and the size in bytes), and computes a SHA-1 hash of the result. That 40-character hex hash becomes the object's ID. The content is then compressed with zlib and written to a path derived from the hash: the first two characters name a directory, and the remaining 38 name the file.

```
.git/objects/8a/b686eafeb1f44702738c8b0f24f2567c36da6d
```

Two consequences follow from naming objects by their content:

- **Objects are immutable.** Changing one byte would change the hash, which makes it a different object.
- **Identical content is stored once.** If the same file appears in a thousand commits, or at two paths in one commit, there is one object.

You can inspect any object with `git cat-file -p <hash>`, and ask its type with `git cat-file -t <hash>`.

## Blobs: file contents

A blob holds the bytes of one file and nothing else. It has no filename, no permissions and no timestamp. Two files with identical contents share one blob, whatever they are called.

Blobs are created when you run `git add`, not when you commit. Staging a file writes its blob into the object store and records the blob's hash in the index (`.git/index`), which is the list of paths and blob IDs that will make up the next commit.

## Trees: directories

A tree represents one directory. It is a list of entries, each with a mode, a type, an object ID and a name:

```
$ git cat-file -p main^{tree}
100644 blob a906cb2a4a904a152e80877d4088654daad0c859    README.md
100755 blob 8f94139338f9404f26296befa88755fc2598c289    build.sh
040000 tree 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0    src
```

An entry pointing at a blob is a file; an entry pointing at another tree is a subdirectory. This is where filenames and the executable bit live.

Since a tree's hash depends on the hashes of everything it lists, the hash of the root tree identifies the exact contents of the whole project. Change one file deep in `src/` and you get a new blob, a new tree for each directory on the path up to the root, and a new root tree. Every directory you did not touch keeps its hash, and its tree is reused as it stands.

## Commit objects

A commit object is a short piece of text:

```
$ git cat-file -p HEAD
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 1f7ec5eaa8f37c2770c56e3a9f7d7e7c8a1e3b52
author Ada Smith <ada@example.com> 1762850000 +0000
committer Ada Smith <ada@example.com> 1762850000 +0000

Fix off-by-one in pagination
```

It contains:

- **One `tree` line**, the root tree of the project at that commit.
- **Zero or more `parent` lines.** The first commit in a repository has none, an ordinary commit has one, and a merge has two or more.
- **Author and committer**, each with a name, email and timestamp.
- **The message.**

A commit stores a complete snapshot, not a diff. What `git show` displays is computed on demand by comparing the commit's tree with its parent's tree. Snapshots stay cheap because unchanged blobs and trees are shared between commits.

The commit's hash covers its tree, its parents and its metadata. Each parent hash in turn covers that commit's parents, so a commit ID pins down the entire history behind it. This is why amending or rebasing produces commits with new IDs: the old ones cannot be edited, only replaced.

## Refs: names for commits

A ref is a file containing a commit hash. A branch is nothing more than this:

```
$ cat .git/refs/heads/main
3c4e9cd789d88d8d89c1073707c3585e41b0e614
```

Tags live in `.git/refs/tags`, and remote-tracking branches in `.git/refs/remotes`. Creating a branch writes one 41-byte file, which is why it is instant.

`HEAD` (the file `.git/HEAD`) records what you have checked out. Normally it points at a branch rather than a commit:

```
ref: refs/heads/main
```

When it holds a raw commit hash instead, you are in "detached HEAD" state.

## Putting it together

When you run `git commit`, Git:

1. Builds tree objects from the index, reusing any that already exist.
2. Writes a commit object pointing at the root tree, with the current `HEAD` commit as its parent.
3. Updates the branch that `HEAD` points to so it contains the new commit's hash.

Nothing existing is modified except that one ref file.

## What you may see instead

Two optimisations change the layout on disk without changing the model.

- **Packfiles.** Git periodically gathers loose objects into `.git/objects/pack/*.pack`, where similar objects are stored as deltas against each other. This is purely a storage detail; `git cat-file` still returns whole objects.
- **Packed refs.** Refs may be collected into the single file `.git/packed-refs`, so a branch may have no file of its own under `refs/heads`.

Newer repositories can also use SHA-256 instead of SHA-1, which gives longer IDs and the same structure.

When you type an HTTPS address and press Enter, the browser has no idea where the server is, whether it is reachable, or whether it can be trusted. Everything that happens before the first byte of the response arrives is the browser answering those three questions. Most of that time is spent on network round trips, so it helps to count them as you read.

1. Parsing the address

The browser first splits the URL into parts. Take https://www.example.com/products?id=7. The scheme is https, the host is www.example.com, the port is implied as 443, the path is /products, and the query is id=7. The scheme tells the browser to use TLS encryption, and the port tells it which door to knock on.

If you typed something that is not a valid URL, the browser treats it as a search query instead. That decision happens here, before any network activity.

2. Checks that avoid the network

Before going online, the browser consults local knowledge in this order.

First, the HSTS list. If the site has previously told the browser to use only HTTPS, or is on a preloaded list shipped with the browser, any plain http address is silently upgraded to https. No insecure request is ever sent.

Second, caches. The browser may already hold a fresh copy of the page, in which case it can skip the network entirely. It may also hold a recent DNS answer, a reusable open connection to this host, or a saved TLS session. Each of these removes one of the steps below. A warm visit can be dramatically faster than a cold one for exactly this reason.

3. DNS resolution

Networks route by IP address, not by name, so the browser must turn www.example.com into an address such as 93.184.216.34 or an IPv6 equivalent. It asks the operating system, which checks its own cache and the hosts file, then forwards the question to a recursive resolver. That resolver is usually run by your ISP, your company, or a public provider.

If the resolver does not know the answer, it works down the hierarchy. It asks a root server which servers handle .com, asks those which servers are authoritative for example.com, and finally asks the authoritative server for the record of www.example.com. The answer comes back with a time to live, which says how long it may be cached. A name may also resolve through a CNAME, which is an alias that points to another name and adds one more lookup.

A cached lookup takes under a millisecond. An uncached one can cost tens or hundreds of milliseconds. Modern browsers may also receive HTTPS records through DNS that advertise HTTP/3 support, which affects the next step.

4. Opening a connection

5. The TLS handshake

On a TCP connection, TLS comes next. TLS provides three guarantees. The connection is encrypted, the data cannot be altered unnoticed, and the server is who it claims to be.

The browser then validates the certificate. Host: www.example.com

Accept-Encoding: gzip, br
Cookie: session=abc123

Under HTTP/2 and HTTP/3 the same information is sent as compressed binary frames, but the meaning is identical. The method and path say what is wanted. The Host header says which site, since a server may host several. The Accept headers state what formats the browser can handle. Cookies for this domain are attached automatically, and these are why a logged-in user gets a personalised page.

Add up the costs for a cold visit to a distant server. DNS takes one or more lookups, TCP takes one round trip, TLS 1.3 takes one more, and the request itself takes one more plus server think time. That is roughly four round trips before the first byte, none of which is your code except the last piece.

This explains common performance advice. Use a CDN so round trips are short. Reuse connections with keep-alive so later requests skip steps 3 to 5. Enable HTTP/2 or HTTP/3. Keep TLS current.

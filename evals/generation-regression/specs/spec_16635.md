The ocpp_kafka service runs two Kafka consumer groups in a single process: the OCPP message consumer group (ocpp-group-id, handling live charger CALL/CALLRESULT traffic across ~100 pod replicas) and a smaller configuration-sync consumer group. Both currently rely on aiokafka's default partition assignment behavior.

Implement sticky partition assignment for these consumer groups so that partition-to-consumer mappings are preserved as much as possible across group membership changes (pods joining or leaving during deploys or autoscaling). Today, membership changes can reshuffle partition ownership broadly across the fleet, which is undesirable given the per-partition state each pod builds for the chargers it owns.

Requirements:
1. In ocpp_kafka/ocpp_kafka_consumer.py, configure the OCPPKafkaConsumer (and any other consumer classes in this module) to use a partition assignment strategy that favors stickiness — minimizing partitions that move when membership changes — while remaining compatible with consumers still running the previous (non-sticky) assignor during a rolling deploy. The assignor list/order should allow a safe transition without a coordinated simultaneous deploy.
2. In shared/kafka/base_kafka_consumer.py, add the general configuration point for specifying partition assignment strategy on the base consumer class, defaulting other subclasses to current behavior so this change is scoped to the OCPP consumer group(s) only.
3. Add a readiness signal to OCPPKafkaConsumer: when the group rebalance completes and this consumer has an assignment (including a legitimate zero-partition assignment), touch a readiness marker file (path configurable via a setting, e.g. OCPPConsumerReadinessFile) so external tooling (Kubernetes readiness probes) can detect the pod has finished (re)joining.
4. Add settings entries in inventev/settings/base.py and inventev/settings/test.py for new configuration values.
5. Unit tests in ocpp_kafka/tests/test_ocpp_kafka_consumer.py and shared/tests/kafka/test_base_kafka_consumer.py verifying assignor configuration and readiness marker behavior (including empty assignments).

Out of scope: ocpp_adaptor changes are handled separately — focus only on the Kafka consumer partition-assignment and readiness-marker work.

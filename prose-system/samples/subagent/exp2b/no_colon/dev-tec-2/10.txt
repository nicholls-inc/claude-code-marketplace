From Address to First Byte, What a Browser Does Over HTTPS

When you type an HTTPS address into a browser and press Enter, a surprising amount of work happens before any response data arrives. This description follows that journey in order, from the moment the address is accepted to the moment the first byte of the response comes back. Understanding it helps you debug slow pages, certificate errors and caching surprises.

1. Parsing the address

The browser first splits the address into parts. The scheme is https, the host is something like www.example.com, the port is 443 unless the address says otherwise, and the rest is a path, query string and fragment. The fragment (the part after the hash sign) never leaves the browser, so the server never sees it.

Before going to the network, the browser checks a few local things. It may have an HSTS record for the host, which is a stored instruction saying this site must only ever be reached over HTTPS. It also checks whether a service worker controls the page and whether the HTTP cache already holds a fresh copy of the resource. If the cache has a response that is still valid, the browser can skip the network entirely and the "first byte" arrives from local storage almost instantly. Assume for the rest of this description that the cache has nothing useful.

2. DNS lookup

Networks route traffic by IP address, not by name, so the browser must turn www.example.com into an address. It checks its own DNS cache first, then asks the operating system, which checks its cache and may consult a local hosts file. If nobody knows the answer, the request goes to a recursive resolver, usually run by your ISP or a public provider.

The resolver does the hard work. If it has no cached answer, it asks a root server where to find the servers for the top-level domain, then asks those servers where to find the authoritative servers for the domain, then asks the authoritative server for the final record. The answer comes back with a time to live, which tells every cache along the way how long it may reuse the result. Modern browsers may also request HTTPS or SVCB records, which can advertise that a site supports HTTP/3 or provide extra connection hints.

A cold lookup can take tens of milliseconds or more, while a cached one costs almost nothing. This is one reason repeat visits feel faster.

3. Opening a TCP connection

With an IP address in hand, the browser opens a connection to port 443. For HTTP/1.1 and HTTP/2 this uses TCP, which begins with a three-step handshake. The client sends a SYN packet, the server replies with SYN-ACK, and the client sends an ACK. Only then can data flow reliably and in order.

This costs one full round trip between you and the server. If the server is on another continent, a round trip may be 100 milliseconds or more, and physics sets that floor no matter how fast the hardware is. This is why content delivery networks place servers near users.

HTTP/3 works differently. It runs over QUIC, which sits on UDP and combines the transport handshake and the encryption handshake into one. A browser usually learns that a site supports HTTP/3 from an earlier visit or from DNS, and otherwise starts with TCP and upgrades later.

4. The TLS handshake

The S in HTTPS means the conversation is encrypted using TLS. Before any request is sent, the browser and server must agree on how to protect it and prove the server is who it claims to be.

In TLS 1.3, which most modern sites use, the client sends a ClientHello. It lists the encryption options it supports, includes a random value, and sends its half of a key exchange. It also includes the Server Name Indication, which tells the server which hostname the client wants. This matters because one IP address often hosts many sites, and the server needs the name to choose the right certificate. The ClientHello may also list the protocols the client can speak, such as h2 and http/1.1, using an extension called ALPN.

The server answers with its choices, its half of the key exchange and its certificate. Both sides now combine their key halves to derive the same secret session keys without ever sending those keys across the network. The rest of the handshake is already encrypted. The server proves it owns the certificate by signing the handshake with its private key, and sends a finished message. The client verifies and sends its own.

TLS 1.3 needs one round trip. Older TLS 1.2 needed two. If the browser has talked to the server recently, session resumption can shorten this further, and in some cases allows early data to be sent with the first flight, though that carries replay risks and is limited to safe requests.

5. Verifying the certificate

While the handshake happens, the browser validates the certificate. It checks that the certificate names the host you asked for, that it has not expired, and that it chains up through intermediate certificates to a root authority that your operating system or browser already trusts. It may also check revocation status, often through stapled responses the server includes, and it may consult certificate transparency logs evidence embedded in the certificate.

If any check fails, you get the full-page warning. As a developer, the common causes are an expired certificate, a missing intermediate certificate on the server, or a hostname mismatch.

6. Sending the request

Now the connection is encrypted and the protocol is agreed. The browser sends the HTTP request. At minimum it contains a method such as GET, the path, and headers. The headers include the host, the browser's accepted content types and languages, compression support, and any cookies stored for this site. If the site was visited before, the browser may add conditional headers carrying an ETag or last-modified date, so the server can answer with a tiny 304 Not Modified instead of resending the page.

With HTTP/2 and HTTP/3 these headers are compressed and sent as binary frames, and many requests can share one connection at the same time. With HTTP/1.1 the request is plain text inside the encrypted channel.

7. The server works and the first byte arrives

The request crosses the network and reaches the server, often first hitting a load balancer or CDN edge. The edge may answer from its own cache. Otherwise it forwards the request to an application server, which may run routing code, check authentication, query a database and render a page. All of this time is what developers measure as server think time.

When the server starts writing the response, the first bytes travel back through the encrypted connection. The time from sending the request to receiving that first byte is called Time to First Byte. It is the sum of everything above, namely DNS, connection setup, TLS, one request round trip and the server's processing time.

Why this matters

Each stage is a place to optimize. Reuse connections so you skip steps 3 and 4. Use a CDN to shorten round trips. Enable HTTP/3 and TLS 1.3. Cache aggressively. Keep server work fast. And when something fails, knowing which stage broke tells you where to look first.

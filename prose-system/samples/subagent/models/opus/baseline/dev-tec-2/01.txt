# From URL to First Byte: What Your Browser Does Before the Response Arrives

When you type `https://example.com/products` and press Enter, the page seems to start loading right away. Before the server can send even one byte of the response, though, the browser has to finish a series of steps, and each one costs time. Knowing these steps explains what the "Waiting (TTFB)" bar in DevTools is measuring. It also explains why some performance advice works.

## 1. Parsing the URL and checking local shortcuts

First the browser parses the URL into its parts: the scheme (`https`), the host (`example.com`), an optional port (443 if none is given for HTTPS), the path (`/products`) and any query string. If what you typed is not a valid URL, the browser treats it as a search instead.

Next it looks for ways to avoid using the network at all:

- **HSTS.** If `example.com` has sent a `Strict-Transport-Security` header before, or is on the browser's built-in preload list, the browser will only connect over HTTPS. Any `http://` link to the site gets upgraded internally, so no insecure request is ever sent.
- **Service worker.** If the site has registered a service worker for this scope, the request goes to it first. The worker can answer from its own cache and skip everything below.
- **HTTP cache.** If a fresh copy of the resource is stored and its `Cache-Control` rules still allow it to be used, the browser takes it straight from disk or memory.
- **Existing connection.** If the browser already has an open, healthy connection to this origin, for example from an earlier request, it reuses it and goes straight to step 5. Reusing connections is one of the biggest real-world performance gains.

Assume none of these apply and the browser has to start from nothing.

## 2. DNS resolution: finding the server

Computers connect to IP addresses, not names, so the browser has to turn `example.com` into an address such as `93.184.215.14` (IPv4) or `2606:2800:21f:cb07:6820:80da:af6b:8b2c` (IPv6). It checks several places in order:

1. The browser's own DNS cache.
2. The operating system's resolver cache, plus the `hosts` file.
3. A **recursive resolver**, usually run by your ISP or a public service like 1.1.1.1 or 8.8.8.8. Many browsers now send this query over DNS-over-HTTPS (DoH), which encrypts it.

If the recursive resolver doesn't have the answer cached, it asks the hierarchy itself. It asks a root server where `.com` is, asks the `.com` servers where `example.com`'s authoritative nameservers are, then asks those nameservers for the record. Each answer comes with a TTL (time to live) that controls how long it can be cached.

Modern browsers often request several record types at once: `A` for IPv4, `AAAA` for IPv6, and sometimes `HTTPS` (SVCB) records. An HTTPS record can tell the browser in advance that the server supports HTTP/3, which saves a round trip later. When both IPv4 and IPv6 addresses come back, the browser uses "Happy Eyeballs": it tries both and keeps whichever connects first.

A cached lookup takes almost no time. An uncached one can take tens to hundreds of milliseconds.

## 3. Opening a transport connection

With an IP address in hand, the browser opens a connection. There are two possibilities.

**TCP (used by HTTP/1.1 and HTTP/2).** TCP starts with a three-way handshake:

- The client sends `SYN`.
- The server replies `SYN-ACK`.
- The client sends `ACK`.

This costs one full **round trip time (RTT)** before any application data can be sent. If the server is 80 ms away, you have already spent 80 ms.

**QUIC (used by HTTP/3).** QUIC runs over UDP and combines the transport and encryption handshakes into one, so the next step happens in the same round trip. A browser usually uses QUIC only when it knows the server supports it, either from an `Alt-Svc` header on an earlier response or from that DNS HTTPS record.

## 4. The TLS handshake: encryption and identity

The "S" in HTTPS is TLS (Transport Layer Security). TLS has two jobs. It encrypts traffic so nobody on the path can read or change it, and it proves the server really is `example.com`. With TLS 1.3, the current standard, the handshake looks like this:

1. **ClientHello.** The browser sends the TLS versions and cipher suites it supports, a random value and a **key share** (its half of a Diffie-Hellman key exchange). It also includes two important extensions:
   - **SNI (Server Name Indication):** the hostname it wants. One IP address can host many sites, so the server needs this to pick the right certificate.
   - **ALPN (Application-Layer Protocol Negotiation):** the HTTP versions it speaks, such as `h2` and `http/1.1`.
2. **ServerHello and the rest of the server's flight.** The server picks a cipher suite, sends its own key share and agrees on a protocol through ALPN. At this point both sides can derive the same shared secret, so everything after this is encrypted. The server sends its **certificate chain**, a `CertificateVerify` signature proving it holds the certificate's private key, and a `Finished` message.
3. **Certificate validation.** The browser checks four things: the certificate covers `example.com`, it hasn't expired, it chains up to a root Certificate Authority the browser trusts, and it hasn't been revoked. If any check fails, you get the full-page security warning.
4. **Client Finished.** The browser sends its own `Finished` message, and the secure channel is up.

Over TCP, TLS 1.3 adds **one more RTT** on top of the TCP handshake, for two round trips in total before the request can go out. Older TLS 1.2 needed two RTTs just for TLS. When a client reconnects to a server it has visited recently, **session resumption** and optional **0-RTT** let it skip some or all of this work.

## 5. Sending the HTTP request

Now the browser finally sends the request, using whichever protocol ALPN chose:

```
GET /products HTTP/1.1
Host: example.com
User-Agent: ...
Accept: text/html,...
Accept-Encoding: gzip, br
Cookie: session=abc123
```

That is the HTTP/1.1 text form. HTTP/2 and HTTP/3 carry the same meaning in a binary format, with compressed headers sent as frames on a **stream**. Many streams can share one connection, so later requests for CSS, JavaScript and images don't each need their own handshake.

The request is encrypted with the TLS session keys, split into packets and sent across the network.

## 6. Server-side work

The request usually passes through several layers before your application code runs: a CDN edge node, a load balancer, a reverse proxy such as nginx, and then the application server. Any of these can answer straight from a cache. Otherwise the application routes the request, runs middleware such as authentication, queries databases or other services, and starts building the response.

This server "think time" is often the largest part of TTFB, and it is the part you control most directly as a developer. Slow database queries, calls to other services one after another, and rendering an entire page before sending any of it all add to it.

## 7. The first byte arrives

Once the server writes the start of the response (the status line and headers, such as `HTTP/1.1 200 OK`), those bytes are encrypted, cross the network and are decrypted by the browser. That moment is the **Time To First Byte**. The browser then starts reading headers and parsing HTML while the rest of the body is still arriving, but that is the next chapter.

## Putting the numbers together

For a fresh HTTPS connection over TCP with TLS 1.3, a rough budget is:

| Step | Cost |
|---|---|
| DNS | 0 to 1+ RTT to the resolver |
| TCP handshake | 1 RTT |
| TLS handshake | 1 RTT |
| Request plus first byte back | 1 RTT + server processing time |

On a mobile connection with a 100 ms RTT, that comes to 300 to 400 ms **before your server does any work at all**. This explains common advice: use a CDN (it shortens the RTT), keep connections alive and reuse them, enable HTTP/2 or HTTP/3, add `<link rel="preconnect">` for important third-party origins, and keep server response times low. Each of these removes either a round trip or server time from the path to the first byte.

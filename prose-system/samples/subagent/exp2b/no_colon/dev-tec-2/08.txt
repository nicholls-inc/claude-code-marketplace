# From HTTPS Address to First Byte

When you type an address such as https://example.com/products into a browser and press Enter, a lot happens before any of the page arrives. Most of it takes only milliseconds, but each step can fail or slow down, so knowing the order helps you debug real problems. The span from the request starting to the first byte of the response arriving is often called time to first byte, or TTFB.

## 1. The browser parses the address

The browser splits the address into parts. The scheme is https, the host is example.com, the port is implied (443 for HTTPS), and the path is /products. Any query string or fragment is separated out too. The fragment never leaves the browser, because it is only used after the page loads to scroll to an element.

If you typed only a word or a partial address, the browser decides whether to treat it as a URL or hand it to a search engine. Here we assume it is a valid URL.

## 2. Local shortcuts

Before touching the network, the browser checks whether it can skip work.

- **HSTS.** If the site previously sent a Strict-Transport-Security header, or is on a built-in preload list, the browser will refuse plain HTTP and goes straight to HTTPS.
- **HTTP cache.** If a fresh copy of the resource is stored, the browser may use it with no network request. The first byte then arrives almost instantly, from disk.
- **Service worker.** If the site registered one, it can intercept the request and answer from its own logic or cache.

If none of these satisfy the request, the browser goes to the network.

## 3. DNS lookup

Computers connect using IP addresses, not names, so the browser must translate example.com into an address such as 93.184.216.34 or an IPv6 equivalent. This is the Domain Name System.

The browser checks its own DNS cache first, then asks the operating system, which checks its cache and its hosts file. If neither knows the answer, the OS asks a recursive resolver, usually run by your ISP or a public provider. The resolver may already have the answer cached. If not, it walks the hierarchy by asking a root server, then the server for the .com top-level domain, then the authoritative name server for example.com, which gives the final answer.

Every record has a time to live (TTL) that tells caches how long to keep it. A cold lookup might cost tens of milliseconds or more, while a cached one costs almost nothing. Modern browsers can also query the newer HTTPS DNS record type, which can advertise HTTP/3 support and other hints.

## 4. Opening a connection

With an IP address in hand, the browser needs a reliable channel to the server. For HTTP/1.1 and HTTP/2 this is TCP, and it begins with a three-step handshake.

1. The client sends a SYN packet saying it wants to connect.
2. The server replies with SYN-ACK to acknowledge and agree.
3. The client sends ACK, and the connection is established.

This costs one network round trip. If you are in London and the server is in Sydney, a round trip may take 250 milliseconds, which shows why server location matters.

HTTP/3 works differently. It runs over QUIC, which uses UDP and merges the transport and encryption handshakes into one. Browsers usually learn about HTTP/3 support from a previous visit, from DNS hints, or from an Alt-Svc header, and they may race QUIC against TCP.

The browser also reuses connections. If it already has an open connection to this host, it skips this step and the next one.

## 5. The TLS handshake

The S in HTTPS means the traffic is encrypted using Transport Layer Security. Before any HTTP data is sent, the client and server negotiate how to protect it.

With TLS 1.3, the common modern version, the process goes roughly like this.

- **ClientHello.** The browser lists the cipher suites it supports and sends a key share, which is its half of a key exchange. It also sends the server name via an extension called SNI, so a server hosting many sites knows which certificate to present.
- **ServerHello.** The server picks a cipher suite and sends its own key share. Both sides can now compute the same shared secret without ever sending it. The rest of the handshake is encrypted.
- **Certificate.** The server sends its certificate chain and proves it holds the matching private key by signing the handshake.
- **Finished.** Both sides confirm the handshake was not tampered with.

The browser validates the certificate. It checks that the name matches example.com, that the dates are valid, that the chain leads to a certificate authority the operating system or browser trusts, and that the certificate has not been revoked. If any check fails, you see the full-page security warning and the request stops.

TLS 1.3 needs one round trip. Older TLS 1.2 needed two. A resumed session, using a ticket from an earlier visit, can be faster still, and TLS 1.3 even allows sending request data in the first flight, called 0-RTT, with some replay-safety caveats.

## 6. Sending the HTTP request

The connection is now encrypted, so the browser sends the request. In HTTP/1.1 it is plain text that looks like this.

```
GET /products HTTP/1.1
Host example.com
Accept text/html
Accept-Encoding gzip, br
Cookie session=abc123
```

In HTTP/2 and HTTP/3 the same information is sent as compressed binary frames rather than text, but the meaning is identical. The method, path, and headers still carry the same details. The browser attaches any cookies it holds for that site, tells the server which compression formats it understands, and may add conditional headers such as If-None-Match when it has a stale cached copy to revalidate.

## 7. The server does its work

The request travels across the internet and reaches the server, though in practice it often hits a CDN edge node or load balancer first. These can answer from their own cache or forward the request to an origin server. A reverse proxy such as Nginx may then pass it to your application.

Your application now does the real work. It routes /products to a handler, checks authentication from the cookie, queries a database, perhaps calls other services, and renders HTML or JSON. This is frequently the largest portion of TTFB, and it is the part you control most directly as a developer. Slow database queries, missing indexes, and cold starts in serverless functions all show up here.

## 8. The first byte arrives

The server writes the response, beginning with a status line and headers such as the status code 200, the Content-Type, and caching directives, followed by the body. The first bytes travel back through the same encrypted connection, and when the browser receives them, the wait is over. That moment is the TTFB.

The browser reads the status code first. A 200 means success. A 301 or 302 sends it back to step 1 with a new address, and a 404 or 500 tells it something went wrong. Only after this does it start parsing HTML and requesting scripts, styles, and images.

## Why this matters

You can see these phases yourself in the browser's DevTools Network tab. Open the timing breakdown for a request and you will find DNS lookup, initial connection, SSL, waiting (which is largely your server's thinking time), and content download.

Common ways to reduce the delay include these.

- Use a CDN to shorten the physical distance.
- Enable HTTP/2 or HTTP/3 and keep connections alive.
- Use modern TLS and keep certificate chains short.
- Add preconnect hints for third-party origins you know you will need.
- Cache aggressively, and optimize server-side queries.

Every request pays for DNS, connection setup, and encryption before your code runs a single line, so reusing connections and caching are the biggest wins.

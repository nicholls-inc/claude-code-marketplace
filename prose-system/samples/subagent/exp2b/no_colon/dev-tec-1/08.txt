Inside the .git directory, Git is a content-addressed database with a few small files layered on top. Once you see the four ideas below, every everyday command stops being magic.

**The object store**

Git keeps its data as objects. Each object is hashed with SHA-1 (newer repositories can use SHA-256), and the hash becomes its name. Hashing is done over a short header plus the content. The header holds the object type and the byte length. The content is then compressed with zlib and written to .git/objects, in a folder named after the first two hex characters of the hash. A file named by the remaining characters sits inside that folder. Because the name comes from the content, identical content always yields the same object, and nothing is stored twice. Changing a single byte produces a completely different name. There are four object types, and three of them describe your commit.

**Blobs**

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no path. If you commit two files with identical text, Git stores one blob and points to it twice. If you rename a file without editing it, the blob is unchanged, which is why renames are cheap. You can inspect one with `git cat-file -p <hash>`, which prints the file as it was. Staging a file with `git add` is the moment the blob is created, so the object exists before you ever commit.

**Trees**

A tree is a directory listing. Each entry holds a file mode, a type, a hash and a name. The mode records whether the entry is a regular file, an executable, a symlink or a subdirectory. The hash points to a blob for a file, or to another tree for a subdirectory. Names live here and not in blobs, so the tree is where "README.md" is tied to a particular piece of content. A repository with nested folders becomes a tree of trees, and the topmost one is the root tree, which describes your whole project at one instant.

Trees give you cheap change detection. If nothing under src/ changed, the hash of the src tree is identical between two commits, and Git reuses it without looking inside. Only the trees on the path to a changed file get new hashes, all the way up to the root. This is why Git can store full snapshots yet stay compact. It does not save diffs between versions. Each commit points to a complete tree, and unchanged parts are shared by reference.

**Commit objects**

A commit is a small text object with a handful of fields. It names the root tree, then lists zero or more parent commits, then records the author and committer with timestamps, and finally carries your message. The first commit in a repository has no parent. An ordinary commit has one. A merge commit has two or more. Run `git cat-file -p HEAD` and you will see exactly that layout.

The commit hash covers all of those fields, including the parent hash. That makes history a chain in which every link vouches for the one before it. If anyone altered an old commit, its hash would change, so the next commit's parent pointer would no longer match, and the difference would ripple forward. This is also why amending, rebasing and cherry-picking never modify a commit. They create new commits with new hashes, and the old ones remain in the object store until garbage collection removes them. A commit does not contain a diff. When Git shows you one, it compares the commit's tree with its parent's tree on the fly.

**Refs**

Hashes are hard to remember, so refs give them names. A ref is a plain text file whose only content is a commit hash. Branches live under .git/refs/heads, tags under .git/refs/tags, and remote-tracking branches under .git/refs/remotes. A branch is therefore nothing more than a 41-byte file. Creating a branch writes one small file, which explains why it is instant. Making a commit writes the new objects, then moves the current branch file to the new hash. That single update is what "advancing a branch" means. Over time Git may pack many refs into a single .git/packed-refs file, and objects into packfiles that store similar content as deltas, but this is an optimisation and the model stays the same.

**HEAD**

The file .git/HEAD tells Git where you are. Normally it contains a line such as `ref: refs/heads/main`, a symbolic reference to the current branch. When you commit, Git follows HEAD to the branch, then updates that branch. If HEAD instead contains a raw commit hash, you are in the "detached HEAD" state. Commits you make there are not held by any branch, so they can become unreachable once you switch away. The reflog, kept under .git/logs, records every movement of HEAD and of each branch, which is why you can usually recover work you thought was lost.

**Putting it together**

Suppose you edit one file and run `git commit`. Git writes a blob for the new file content. It writes new trees for each directory on the path from that file up to the root, reusing every unchanged tree. It writes a commit object that names the new root tree and your previous commit as its parent. Finally it moves the branch ref, which HEAD points at, to the new commit hash. That is the whole operation, and it is why Git feels fast. Most of the work is writing a handful of tiny, immutable objects and rewriting one small file.

Reachability ties it together. Git considers an object alive if you can reach it by starting from a ref and following commit parents, trees and blobs. Anything unreachable is eligible for cleanup. Seen this way, branches are labels, history is a graph of commits, and nothing in the store is ever edited in place, only added to.

You can verify all of this yourself in any repository. Run `git cat-file -p HEAD`, follow the tree hash with another `git cat-file -p`, then open .git/refs/heads in your file manager. Five minutes of looking will make the model stick.

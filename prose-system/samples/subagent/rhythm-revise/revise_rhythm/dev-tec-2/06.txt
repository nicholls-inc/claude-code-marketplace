When you type an HTTPS address into a browser and press enter, the browser first has to decide what you meant, so it parses the string into a scheme (https), a host (say, www.example.com), an optional port (443 by default for HTTPS), a path and a query. Before touching the network it checks a few local things: if the host is on the browser's HSTS preload list, or the browser has previously seen a Strict-Transport-Security header for that site, it will insist on HTTPS even if you typed http, and it also checks whether it already holds a fresh cached copy of the resource, in which case it may skip the network entirely, and whether a service worker registered for that origin wants to intercept the request. Assuming none of these short-circuits the request, the browser needs an IP address to connect to.

Turning the hostname into an address is the job of DNS, and the browser starts by looking in its own DNS cache, then asks the operating system's resolver, which has its own cache and may consult the hosts file. If neither knows, the request goes to a recursive resolver, usually run by your ISP or a public provider, which does the real work on your behalf. If the resolver does not have the answer cached, it walks the hierarchy: it asks a root server which servers handle the .com zone, asks those which servers are authoritative for example.com, and finally asks the authoritative server for the A record (IPv4) or AAAA record (IPv6) of www.example.com. The answer comes back with a time-to-live, which tells every cache along the way how long it may reuse it, and because sites often sit behind a CNAME, an alias to another name, the resolver follows that chain too. Modern browsers may also query for HTTPS or SVCB records, which can advertise that a server supports HTTP/3 and hint at its address, and they may use encrypted DNS (DNS over HTTPS) so that the lookup itself is private. If both IPv4 and IPv6 addresses come back, the browser typically races connections to them in a technique called Happy Eyeballs, favouring whichever completes first.

With an IP address in hand, the browser opens a connection. Classic HTTP/1.1 and HTTP/2 run over TCP, which begins with a three-way handshake in which the client sends a SYN, the server answers with a SYN-ACK and the client replies with an ACK, costing one full round trip before any application data can flow. HTTP/3 instead runs over QUIC, which sits on UDP and folds the transport and encryption handshakes together, saving a round trip. Browsers learn that a site supports HTTP/3 from an Alt-Svc header or the DNS records mentioned above, so a first visit usually starts with TCP and later visits may upgrade. Either way, packets travel through your router, your ISP and a series of intermediate networks, and the physical distance to the server sets a floor on latency, which is why content delivery networks place servers close to users.

Next comes the part that makes the address HTTPS: the TLS handshake. In TLS 1.3, the client sends a ClientHello naming the protocol versions and cipher suites it supports, a random value, a key share for an elliptic-curve Diffie-Hellman exchange, and the Server Name Indication extension containing the hostname, which matters because one IP address often hosts many sites and the server needs to know which certificate to present. It also carries the ALPN extension, in which the client lists the application protocols it speaks, such as h2 and http/1.1, so the two sides can agree on one without an extra round trip. The server replies with its own key share, which lets both sides derive the same shared secret without ever sending it over the wire, and everything after that point is encrypted. The server then sends its certificate chain and a signature proving it holds the private key matching the certificate, followed by a Finished message, after which the client finishes the handshake and can send its HTTP request immediately. TLS 1.3 needs one round trip for this, where TLS 1.2 needed two, and resumption with a session ticket can shorten repeat visits further, even allowing early data in some cases.

The certificate check is what stops someone in the middle from impersonating the site. The browser verifies that the certificate chain leads up to a certificate authority it trusts, which is a root certificate shipped in the operating system or browser trust store, and it checks that each certificate is within its validity dates, that the signatures are valid, and that the hostname you asked for appears in the certificate's Subject Alternative Name list. It may also check revocation status through mechanisms such as OCSP stapling, where the server attaches a recent signed statement that the certificate has not been revoked, or through compact revocation lists that the browser maintains, and many browsers also look for Certificate Transparency proof, which shows the certificate was logged publicly. If any of these checks fail, the browser stops and shows a full-page warning instead of continuing, because continuing would defeat the purpose of encryption.

Now the browser can finally send the actual request, through the encrypted channel. Under HTTP/1.1 this is plain text framed as a request line, such as GET /path HTTP/1.1, followed by headers, while under HTTP/2 and HTTP/3 the same information is carried in binary frames with compressed headers, but the meaning is identical. The headers include Host or the :authority pseudo-header, the User-Agent, the Accept headers describing which content types and compression schemes the browser handles, and any cookies previously set by this site that match the host and path. If the browser has a stale cached copy, it may add conditional headers such as If-None-Match so the server can answer with a cheap 304 Not Modified.

The request then travels to the server, which often is not the machine that does the real work: it may reach a CDN edge node, a load balancer or a reverse proxy that terminates TLS, picks a backend, and forwards the request inward. The application server routes the path to a handler, which may check authentication, query a database, render a template or read a file. When it has an answer, it writes a status line and response headers, such as the status code, Content-Type and Content-Length, and begins sending the body. The moment the first byte of that response reaches the browser is what performance tools call Time To First Byte, and it is therefore the sum of everything above: DNS lookup, connection setup, the TLS handshake, the request's journey, and the server's own processing time. This is why developers often measure and optimise each of those steps separately, using caching, CDNs, connection reuse, preconnect hints and fast server code to push it down.

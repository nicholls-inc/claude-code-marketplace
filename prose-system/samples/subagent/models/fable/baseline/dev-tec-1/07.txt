# How Git stores a commit

Every commit you make is stored as a handful of small files under `.git`. There are three kinds of object (blobs, trees and commits) plus refs, which are the names that point at them. Once you know how these four fit together, most of Git's behaviour stops being surprising.

## The object store

Git keeps its data in `.git/objects`, a key-value store in which the key is a hash of the value. To store something, Git prepends a short header (the object type and its size in bytes), hashes the result with SHA-1, compresses it with zlib, and writes it to a file named after the hash. The first two hex characters become a directory and the remaining 38 the filename, so object `8ab686ea...` lives at `.git/objects/8a/b686ea...`.

Two consequences follow from addressing content by its hash:

- **Objects are immutable.** Changing a byte changes the hash, which makes it a different object. Nothing in the store is ever edited in place.
- **Identical content is stored once.** Two files with the same bytes, in any directory or any commit, share one object.

You can inspect any object with `git cat-file -p <hash>`, and ask its type with `git cat-file -t <hash>`.

## Blobs: file contents

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no timestamp. If you rename a file without editing it, Git creates no new blob, because the bytes have not changed.

Blobs are written earlier than most people expect: `git add` creates the blob and records its hash in the index (`.git/index`), the staging area. By the time you run `git commit`, the file contents are already in the object store.

## Trees: directories

A tree represents one directory. It is a list of entries, each with a mode, an object type, a hash and a name:

```
100644 blob a906cb2a4a904a152e80877d4088654daad0c859    README.md
100755 blob 8f94139338f9404f26296befa88755fc2598c289    build.sh
040000 tree 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0    src
```

This is where filenames and the executable bit live. An entry points either to a blob (a file) or to another tree (a subdirectory), so a root tree, followed recursively, describes the complete state of the project at one moment.

Trees are content-addressed too, which makes snapshots cheap. If a commit changes one file in `src/`, Git writes a new blob for that file, a new tree for `src/` and a new root tree. Every other directory keeps its existing hash and is reused as is.

## Commit objects: a snapshot plus context

A commit object is a short piece of text:

```
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 1a410efbd13591db07496601ebc7a059dd55cfe9
author Ada Lovelace <ada@example.com> 1731312000 +0000
committer Ada Lovelace <ada@example.com> 1731312000 +0000

Fix off-by-one in pagination
```

It contains:

- **One `tree` line**, the hash of the root tree. This is the snapshot.
- **Zero or more `parent` lines.** The first commit in a repository has none, an ordinary commit has one, and a merge has two or more.
- **Author and committer**, each with a timestamp. They differ when, for example, someone else's commit is rebased or cherry-picked.
- **The message.**

A commit stores a full snapshot, not a diff. When `git show` or `git log -p` displays a diff, Git computes it on demand by comparing the commit's tree with its parent's.

The commit's hash covers its tree hash and its parent hashes, so it depends on the entire project contents and all the history before it. That is why amending or rebasing a commit produces a new hash for it and for every commit after it: they are new objects, and the old ones remain in the store until they are garbage collected.

## Refs: names for hashes

Nothing so far involves branch names. A ref is a file containing a 40-character commit hash:

- `.git/refs/heads/main` is the branch `main`.
- `.git/refs/remotes/origin/main` is your last-fetched copy of the remote's `main`.
- `.git/refs/tags/v1.0` is a tag.

A branch is therefore a 41-byte file, which is why creating one is instant and deleting one removes no commits.

`.git/HEAD` records what you have checked out. It normally holds a symbolic reference such as `ref: refs/heads/main`. When you check out a commit directly, it holds a bare hash instead, which is the "detached HEAD" state.

## What `git commit` does

1. Git builds tree objects from the index, reusing any tree whose contents have not changed.
2. It writes a commit object that points to the new root tree, with the commit `HEAD` currently resolves to as its parent.
3. It writes the new commit's hash into the branch file that `HEAD` names.

The third step is the only one that modifies an existing file; everything else adds new objects.

## Packfiles

A mature repository's `.git/objects` holds few loose object files. Git periodically bundles objects into packfiles under `.git/objects/pack`, where similar objects are stored as deltas against one another to save space, and it may collect refs into a single `.git/packed-refs` file. Both are storage optimisations. The model of blobs, trees, commits and refs is unchanged, and `git cat-file` works the same either way.

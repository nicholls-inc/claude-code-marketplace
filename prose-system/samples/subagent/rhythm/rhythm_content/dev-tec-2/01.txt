When you type an HTTPS address into a browser, or follow a link to one, the browser first parses the string into its parts: the scheme (https), the host (for example www.example.com), an optional port that defaults to 443 for HTTPS, a path, a query string, and a fragment, which never leaves the browser while the rest is eventually used to build the request. Before any network traffic happens, the browser consults local sources that might let it skip work entirely, including its HTTP cache, which can serve a stored response without contacting the server if the copy is still fresh according to its Cache-Control or Expires headers, a list of sites that must only be reached over HTTPS (HSTS, preloaded in the browser or learned from earlier visits), and any service worker registered for the origin, which can intercept the request and answer it from its own logic. If none of these produces an answer, the browser has to find a machine to talk to.

Name resolution comes next, because the network routes by IP address and not by hostname. The browser checks its own DNS cache, then asks the operating system, which checks its cache and the hosts file, and then sends a query to the configured recursive resolver, usually run by your ISP, your company, or a public provider, possibly over an encrypted transport such as DNS over HTTPS. If the resolver does not already have the answer cached, it walks the hierarchy on your behalf: it asks a root server which servers handle the .com zone, asks those which servers are authoritative for example.com, and asks one of those for the address records of the host. The answer carries a time-to-live that tells every cache along the way how long it may be reused, which is why a DNS change you make can appear to propagate slowly. Browsers typically request both A (IPv4) and AAAA (IPv6) records, and when several addresses come back they try them in a staggered fashion, favouring IPv6 but falling back quickly if it stalls, a strategy known as Happy Eyeballs. The address often belongs not to your origin server but to a CDN edge node chosen by DNS or anycast routing to be geographically close to the visitor.

With an IP address in hand, the browser opens a TCP connection, unless it already has an idle one to the same origin that it can reuse, or the server has advertised HTTP/3, in which case it uses QUIC over UDP and folds the transport and encryption handshakes together. TCP uses a three-way handshake in which the client sends a SYN, the server answers with SYN-ACK, and the client confirms with ACK, which costs one full round trip before any application data can flow, so latency to the server sets a floor on everything that follows, and each round trip to a server 100 milliseconds away costs 100 milliseconds no matter how much bandwidth your connection has.

Then comes the TLS handshake, which is what makes the address HTTPS rather than HTTP. In TLS 1.3 the client's first message names the server it wants (the SNI extension, which lets one IP address host many sites), lists the cipher suites and application protocols it supports through ALPN, such as h2 and http/1.1, and includes a key share, which is its half of an ephemeral Diffie-Hellman exchange. The server replies with its own key share, which lets both sides compute the same secret without ever transmitting it, and from that point the rest of the handshake is encrypted. The server then sends its certificate chain along with a signature proving it holds the matching private key, and the client verifies that the chain leads to a certificate authority in its trust store, that every certificate is within its validity dates, that the requested hostname appears in the certificate's subject alternative names, and, depending on the browser, that the certificate has not been revoked. Any failure produces the full-page warning you have probably seen, and it is a real signal that the server is misconfigured or that something is intercepting the connection. Once both sides send their Finished messages, application data can flow encrypted, and TLS 1.3 needs just one round trip on top of TCP for this, with session resumption and sometimes 0-RTT data trimming it further for a returning client. ALPN settles which HTTP version will be used, so by the end of the handshake the browser knows whether it will speak HTTP/1.1 text or HTTP/2 binary frames.

Only now does the browser send the request itself, which in HTTP/1.1 is a plain-text request line such as GET /path?query HTTP/1.1 followed by headers including Host, User-Agent, Accept, Accept-Encoding, Accept-Language, and any cookies stored for that domain and path, and which in HTTP/2 or HTTP/3 carries the same information as compressed header fields on a numbered stream. A session cookie attached at this stage is what lets the server decide that you are logged in. Because everything is encrypted by TLS, networks in between can see the IP address and, through SNI, usually the hostname, but not the path, headers, or body.

The request then travels across the internet and often through several layers on the server side before it reaches your application: a CDN or reverse proxy may answer from its own cache, a load balancer picks one of several backend instances, a web server such as nginx hands the request to an application process, and that process may query a database or call other services before it has anything to return. The time the server spends on this is what developers measure as time to first byte, and it is frequently the part you control most directly, whereas the DNS, TCP and TLS costs depend largely on geography and connection reuse, which is why CDNs, keep-alive connections and preconnect hints are such common optimizations. When the first byte of the response, the start of the status line and headers such as HTTP/1.1 200 OK or the equivalent HTTP/2 frame, arrives back at the browser and is decrypted, the wait is over and the browser can begin parsing the HTML while the rest of the body is still streaming in.

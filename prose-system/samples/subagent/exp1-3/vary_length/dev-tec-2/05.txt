From HTTPS address to first byte

You type https://www.example.com/products into the address bar and press Enter. A moment later, the first byte of the response arrives. In between, your browser does a surprising amount of work. Here is the sequence.

1. Parsing the URL

The browser first breaks the address into parts. The scheme is https, the host is www.example.com, and the path is /products. No port is given, so it assumes 443, the default for HTTPS.

Before touching the network, it checks a few local things. Is this host on the browser's HSTS list, meaning it must only be reached over HTTPS? Is there a cached copy of the page that is still fresh? If a fresh copy exists, the browser can skip the network entirely. Usually it does not, so we continue.

2. DNS lookup

Computers connect to IP addresses, not names. The browser must turn www.example.com into something like 93.184.216.34.

It checks several caches in order: its own, then the operating system's, then the router's. If none has the answer, the request goes to a recursive resolver, typically run by your ISP or a public provider. That resolver may already have the answer cached. If not, it works down the hierarchy. It asks a root server where to find .com, asks the .com servers where to find example.com, and finally asks example.com's authoritative name server for the address of www.example.com.

Each answer carries a time-to-live (TTL) value that says how long it may be cached. This is why DNS changes take time to spread. A cached lookup costs under a millisecond, but a cold one can cost tens or hundreds.

Modern browsers may also ask for HTTPS or SVCB records during this step. These can advertise that the server supports HTTP/3, saving a later round trip.

3. The TCP handshake

With an IP address in hand, the browser opens a connection. For HTTP/1.1 and HTTP/2, that means TCP. The two sides exchange three packets. The client sends a SYN, the server answers with SYN-ACK, and the client replies with ACK.

This costs one full round trip before any useful data moves. If you are in London and the server is in Sydney, a round trip is roughly 250 milliseconds. Distance matters, and this is why content delivery networks (CDNs) place servers near users.

Browsers also keep connections open and reuse them. If you already visited this site a few seconds ago, steps 3 and 4 may be skipped entirely.

4. The TLS handshake

TCP gives a reliable pipe, but anyone along the route can read it. TLS adds encryption and proves the server is who it claims to be.

In TLS 1.3, the client opens with a ClientHello. It lists the cipher suites it supports, sends a random value, and includes a key share, which is its half of a key exchange. It also includes the Server Name Indication (SNI) extension, which names the host it wants. This lets one IP address serve many sites. The client may also use ALPN to say which application protocols it speaks, such as h2 or http/1.1.

The server replies with its own key share, its certificate, and a signature proving it holds the matching private key. Both sides now compute the same shared secret without ever sending it. That is the point of the key exchange. Every byte after this is encrypted.

The browser then validates the certificate. Does the name match www.example.com? Has the certificate expired? Does it chain up to a certificate authority the browser trusts? Has it been revoked? If any check fails, you see a full-page warning and the process stops.

TLS 1.3 needs one round trip. Older TLS 1.2 needed two. A returning visitor can use session resumption to shorten this further, and in some cases send data in the very first flight, known as 0-RTT. That mode comes with replay risks, so servers restrict what it may do.

5. Sending the HTTP request

Now the browser finally speaks HTTP. Over an encrypted connection, it sends something like this:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

Under HTTP/2, the same information is sent as compressed binary frames rather than plain text, but the content is equivalent. Under HTTP/3, it travels over QUIC instead of TCP.

The request includes any cookies stored for that domain, a User-Agent string, and headers describing which formats and languages the browser accepts. If the browser holds a stale cached copy, it may add a conditional header such as If-None-Match. The server can then answer 304 Not Modified with no body.

6. What the server does

The request arrives at the server's network edge. Often that is not your application at all. It is a CDN node, a load balancer, or a reverse proxy such as nginx. A CDN may answer directly from its cache. If not, it forwards the request to the origin.

At the origin, the web server hands the request to application code. The code might check your session, query a database, call other services, and render a template. This is usually the slowest part of the whole journey, and it is the part you control as a developer. A slow database query shows up here as a long wait.

7. The first byte

The server writes the response status line and headers, such as HTTP/1.1 200 OK, and begins sending the body. The moment the first byte of that response reaches the browser, the clock stops. This measurement is called Time to First Byte, or TTFB.

Add up the pieces and you get TTFB: DNS lookup, TCP connect, TLS handshake, the request's trip to the server, the server's processing time, and the first byte's trip back. You can see each of these in your browser's developer tools. Open the Network tab, click a request, and look at the Timing breakdown.

Why this matters for you

Each step is a chance to lose time, and each has a standard fix. Slow DNS can be helped with a good provider and sensible TTLs. Connection setup costs shrink with keep-alive, HTTP/2 or HTTP/3, and CDNs placed near users. Handshake overhead drops with TLS 1.3 and session resumption. Server processing improves with caching, efficient queries, and less work per request.

When someone says a page feels slow, do not guess. Measure TTFB first. If it is high, the problem lies somewhere in the steps above, not in your JavaScript or images. Knowing the sequence tells you where to look.

When you give a browser an HTTPS address such as https://www.example.com/products?id=7, the first thing it does is split the string into a scheme (https), a host (www.example.com), an optional port (443 is implied by https), a path and a query, and decide whether this is a navigation at all or something it can answer without touching the network. It checks whether it already holds a fresh cached copy of the resource, whether the host is on an HSTS list that forces HTTPS, and whether a service worker registered for that origin wants to intercept the request, because any of those can short-circuit everything that follows, and a service worker in particular can fabricate a response without the network ever being involved. Assuming none of them does, the browser needs an IP address, and so it looks for one in layers: its own DNS cache, then the operating system's resolver and the hosts file, and finally a recursive resolver, usually run by your ISP or a public provider, which either answers from its own cache or walks the hierarchy itself, asking a root server who handles com, asking the com servers who handles example.com, and asking that domain's authoritative server for the address of www. Each answer carries a time-to-live that says how long it may be reused, which is why DNS changes you make as a developer take a while to be seen by everyone. Modern browsers may also query for IPv6 (AAAA) and IPv4 (A) records together and prefer whichever connects first, and some use DNS over HTTPS so the lookup itself is encrypted, but the outcome is the same: one or more IP addresses for the host.

With an address in hand the browser opens a connection. Classic HTTP/1.1 and HTTP/2 run over TCP, which begins with a three-way handshake in which the client sends a SYN, the server replies with SYN-ACK, and the client acknowledges, costing one full round trip before any application data can move. If the server instead speaks HTTP/3, which the browser may know from a previous visit through an Alt-Svc header or from an HTTPS DNS record, the transport is QUIC over UDP, which folds the transport and encryption handshakes together and saves a round trip. Because the connection is to a distant machine, the round-trip time between you and the server sets a floor under everything that follows, and this is the main reason content delivery networks place servers near users: the address your DNS lookup returned is often an edge node in a nearby city rather than the origin where your application actually runs. The browser also keeps idle connections to recently used hosts open, so if you have visited this origin moments ago it may skip DNS, TCP and TLS entirely and reuse a warm connection.

Over a fresh TCP connection the browser then performs the TLS handshake, which is what makes the address https rather than http. In TLS 1.3 the client's first message names the versions and cipher suites it supports, includes a key share for a Diffie-Hellman exchange, and carries the Server Name Indication extension containing the hostname, so that a server hosting many sites on one IP address knows which certificate to present. The server answers with its own key share, which lets both sides derive the same session keys without ever sending them, followed by its certificate chain and a signature proving it holds the private key matching that certificate, and from this point everything is encrypted. The browser validates the chain by checking that each certificate was signed by the next, that the chain ends in a root authority already trusted by the operating system or browser, that the certificate covers www.example.com in its subject alternative names, that the current date falls inside its validity period, and that it has not been revoked, which it may learn from a stapled OCSP response or from a compressed revocation list shipped with the browser. If any check fails you see the full-page certificate warning rather than your site. TLS 1.3 completes this in one round trip, and a client that has talked to the server before can sometimes resume the session with a pre-shared key and even send its request in the first flight as 0-RTT early data, although that data can be replayed by an attacker and so is only safe for requests that do not change anything. TLS 1.2, still common, needs two round trips.

Only now does the browser send the actual request, and by this stage the network has already cost several round trips before a single byte of your application has been involved. In HTTP/1.1 this is plain text inside the encrypted channel, a request line such as GET /products?id=7 HTTP/1.1 followed by headers like Host, Accept, Accept-Encoding, User-Agent and any cookies the browser holds for that domain, which is how the server recognises a logged-in user. In HTTP/2 and HTTP/3 the same information travels as compressed binary frames on a numbered stream, which lets many requests share one connection without blocking each other at the HTTP layer. If the request must pass through a corporate proxy, it first asks the proxy to open a tunnel with CONNECT, and the TLS handshake then happens end to end through that tunnel. Most of the time, though, the request lands at a load balancer or reverse proxy that terminates TLS, picks a healthy backend, and may consult its own cache before forwarding the request to your application server, where the router, middleware, database queries and template rendering you wrote actually run.

The time between sending the request and receiving the first byte of the response is what performance tools call time to first byte, and it is the sum of everything described above, namely DNS, TCP, TLS and the server's own thinking time, plus the return trip of the first packet. That first byte is typically the start of the status line in HTTP/1.1, for instance HTTP/1.1 200 OK, or the first headers frame in HTTP/2 and 3, and it tells the browser the status, content type, caching rules and any cookies to set before the body begins to stream in. Understanding this sequence is practical, because it explains why a slow TTFB can come from a slow DNS provider, a distant server, a missing keep-alive connection, an oversized certificate chain or a slow database query, and why the right fix differs for each, from adding a CDN and enabling HTTP/2 or HTTP/3 to caching responses and optimising the backend.

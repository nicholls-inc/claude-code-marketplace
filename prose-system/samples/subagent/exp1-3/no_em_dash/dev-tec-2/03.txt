From HTTPS Address to First Byte: What the Browser Does

When you type https://example.com/products into a browser and press Enter, a surprising amount of work happens before a single byte of the page arrives. Understanding this sequence helps you reason about slow page loads, certificate errors, and caching bugs. Here is the path, in order.

1. Parsing the address

The browser first splits the URL into parts. The scheme is https, the host is example.com, the port is implied (443 for HTTPS), and the path is /products. The scheme matters immediately: it tells the browser to use an encrypted connection and to refuse to fall back to plain HTTP.

Before touching the network, the browser checks a few local lists. If the site is on its HSTS list (a record of sites that must only be reached over HTTPS), the browser will never attempt an insecure request. It also checks its caches. If it holds a fresh, cached copy of the resource, the whole network journey below is skipped and the response comes from disk or memory.

2. Looking up the IP address (DNS)

Networks route traffic by IP address, not by name, so the browser must translate example.com into something like 93.184.216.34. This is DNS resolution, and it proceeds through layers of caches:

- The browser's own DNS cache.
- The operating system's cache, plus the local hosts file.
- A recursive resolver, usually run by your ISP, your company, or a public provider.

If the resolver does not already know the answer, it asks on your behalf. It queries a root server, which points to the servers for the .com top-level domain, which in turn point to the authoritative name server for example.com. That server returns the answer, along with a TTL (time to live) saying how long it may be cached. Most lookups finish in a few milliseconds because some layer already has the answer, but a cold lookup can take tens or hundreds of milliseconds. The result may contain several addresses, including IPv6 ones, and modern browsers often try more than one in parallel.

3. Opening a TCP connection

With an IP address, the browser opens a connection to port 443. Traditional HTTP runs over TCP, which guarantees ordered, reliable delivery. TCP begins with a three-step handshake:

1. The client sends a SYN packet ("I would like to connect").
2. The server replies with SYN-ACK ("Acknowledged, and I am ready").
3. The client sends ACK ("Great, connected").

This costs one full round trip, meaning the time for a message to reach the server and a reply to return. Round trips are the main currency of latency. If the server is far away, each one is expensive, which is why so much of web performance work is about reducing how many you need.

A note on HTTP/3: it runs over QUIC, which uses UDP and combines the transport and encryption handshakes into one. The browser typically learns that a server supports it from an earlier response header or a DNS record, and otherwise starts with TCP. The ideas below still apply; the steps are simply merged.

4. The TLS handshake

HTTPS means HTTP carried inside TLS (Transport Layer Security). Before any request is sent, the two sides must agree how to encrypt traffic and the browser must verify it is talking to the real example.com. In TLS 1.3, which most sites now use, this takes one round trip:

- The client sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, and a key share (its half of a key exchange). It also includes the hostname in an extension called SNI (Server Name Indication), so a server hosting many sites knows which certificate to present.
- The server answers with a ServerHello choosing the parameters and sending its own key share. At this point both sides can compute the same shared secret without ever transmitting it. Everything after this is encrypted.
- The server sends its certificate, a proof that it holds the matching private key, and a "finished" message.
- The client validates the certificate and sends its own finished message.

Certificate validation is where many developer-visible errors come from. The browser checks that the certificate covers the hostname, has not expired, and chains up to a certificate authority (CA) the browser trusts, through zero or more intermediate certificates. It may also check whether the certificate has been revoked. If any check fails, you see a full-page warning and the connection stops. A common mistake is forgetting to serve the intermediate certificate, which works in some browsers and fails in others.

If the browser has talked to this server recently, it may resume the session using a saved ticket, trimming the handshake further. With TLS 1.3 it can even send the first request alongside the handshake (0-RTT), at some cost to replay safety, so servers restrict it to safe requests.

5. Sending the HTTP request

The channel is now encrypted, so the browser finally sends the request. In HTTP/1.1 it is plain text before encryption:

GET /products HTTP/1.1
Host: example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

Besides the method and path, the browser attaches headers: the Host, what content types and compressions it accepts, and any cookies stored for that domain. HTTP/2 and HTTP/3 carry the same information in a compact binary form and let many requests share one connection, but the meaning is identical.

Note that DNS, TCP, and TLS all happen per origin and are reused afterward. Keep-alive connections mean later requests to the same host skip steps 2 to 4 entirely, which is why the first request to a site is always the slowest.

6. The server does its work

The request crosses the network, often reaching a CDN or load balancer first. These may answer directly from a cache, or they forward the request to an application server. That server routes /products to your code, which might check authentication, query a database, render a template, and build a response. Any slow step here, such as an unindexed database query, directly delays the first byte.

7. The first byte arrives

The server sends back a status line and headers, for example HTTP/1.1 200 OK with Content-Type, Cache-Control, and Content-Length or chunked encoding, followed by the start of the body. The moment the first byte of that response reaches the browser is called Time To First Byte (TTFB). You can see it in your browser's developer tools Network panel as "Waiting for server response."

Putting it together

TTFB is the sum of: DNS lookup, TCP handshake, TLS handshake, request transit, server processing, and the response's first leg back. On a cold connection that is roughly three round trips plus server time, which is why a distant server feels slow even if your code is fast.

Practical takeaways for you as a developer: use a CDN to shorten distances, enable HTTP/2 or HTTP/3, serve complete certificate chains, set sensible Cache-Control headers so the whole sequence can be skipped, and measure TTFB separately from total load time so you know whether the slowness is in the network or in your application.

Inside the .git directory, Git is a content-addressed database with a few small files layered on top. Once you see how a commit is stored, most Git commands stop being mysterious.

The object database

Everything Git remembers about your project lives in .git/objects. Each item there is an object, and each object is stored under a name derived from its content. The name is a hash, SHA-1 in most repositories and SHA-256 in newer ones, computed over a short header plus the content itself. The first two hex characters become a directory name and the rest become the file name, so an object with the hash 3b18e512dba79e4c8300dd08aeb37f8e728b8dad lives at .git/objects/3b/18e512.... The file is compressed with zlib, which is why you cannot simply read it in a text editor. You can inspect any object with the command git cat-file -p followed by its hash.

Because the name comes from the content, two identical pieces of content always produce the same object. Git stores that content once, no matter how many files or commits refer to it. It also means an object can never change. If the content changes, the hash changes, and you get a new object.

There are four object types. Three of them, blobs, trees and commits, are what a normal commit is built from. The fourth, the annotated tag, is a named pointer with a message attached.

Blobs

A blob holds the contents of a single file and nothing else. It has no file name, no permissions and no timestamp. If you have two files with the same text in different directories, both point at the same blob. Renaming a file creates no new blob, because the content did not change. This is a good first correction to a common mental model. Git does not store files. It stores contents, and names live somewhere else.

Trees

Names live in trees. A tree represents one directory. It is a list of entries, and each entry has a mode, a name and a hash. The mode says whether the entry is a regular file, an executable file, a symbolic link or a subdirectory. The hash points either at a blob, for a file, or at another tree, for a subdirectory.

So a project with a src folder has a root tree. That tree contains entries for the top-level files, which point at blobs, and an entry named src, which points at a second tree. That second tree lists the files in src. Following these pointers from the root tree reconstructs the entire working directory as it was at one moment. A tree is a snapshot of directory structure.

Since a tree's hash is computed from its entries, changing one file changes that file's blob hash, which changes the hash of the tree containing it, which changes every parent tree up to the root. Directories that did not change keep the same hash and are reused as they are. This is why Git snapshots are cheap. A commit that touches one file creates a handful of new objects and points at everything else that already exists.

Commit objects

A commit object ties a snapshot to its history. It is a small text object with a few fields. The tree field holds the hash of the root tree, which is the complete project snapshot. One or more parent fields hold the hashes of the previous commits. The first commit in a repository has no parent, an ordinary commit has one, and a merge commit has two or more. Then come the author and committer lines, each with a name, an email address and a timestamp, followed by a blank line and your commit message.

Notice what is missing. A commit does not store a diff. The patch you see in git show is computed on demand by comparing the commit's tree with its parent's tree. What Git actually records is the full state of the project each time, and it relies on structural sharing to keep that affordable.

Because the commit hash covers the tree hash, the parent hashes, the author and the message, the history forms a chain in which each link vouches for everything before it. Changing an old commit changes its hash, which changes the hash of every descendant. This is what people mean when they say a rebase rewrites history. The old commits still exist, and new ones are created beside them.

Refs

Hashes are poor names for humans, so Git adds refs, which are named pointers to commits. A branch is nothing more than a file under .git/refs/heads whose content is a single commit hash. The file .git/refs/heads/main contains forty hex characters and a newline. Tags live under .git/refs/tags and remote-tracking branches under .git/refs/remotes. Over time Git may pack many refs into a single file called .git/packed-refs for speed, but the idea is unchanged.

When you make a commit on a branch, Git creates the new blobs, trees and commit object, then overwrites the branch file with the new commit's hash. That one small write is the entire act of moving a branch forward. Creating a branch is just creating a new file with an existing hash in it, which explains why branches are so cheap.

HEAD

The file .git/HEAD tells Git where you are. Normally it holds a line such as ref: refs/heads/main, meaning you are on the main branch and the next commit should advance it. If it contains a raw commit hash instead, you are in the detached HEAD state, and new commits will not move any branch.

Putting it together

When you run git commit, Git turns the staged contents, which are recorded in the index file at .git/index, into trees and blobs. It writes a commit object that points at the root tree and at the current commit as its parent. Finally it moves the current branch ref to the new commit. Three kinds of immutable object, plus one mutable pointer, are all there is to it.

Try it yourself in a scratch repository. Run git log -1 to get a hash, then git cat-file -p on that hash to see the commit, then again on its tree line to see the directory, and once more on a blob to see file contents. Walking those links once is the fastest way to make the model stick.

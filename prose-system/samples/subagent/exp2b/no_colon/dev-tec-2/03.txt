From Address to First Byte

When you type an HTTPS address into a browser and press Enter, a surprising amount of work happens before a single byte of the page arrives. Understanding this sequence helps you reason about slow page loads, certificate errors, and caching bugs. The stages below happen in order, though browsers overlap and shortcut many of them.

1. Parsing the address

The browser first splits the address into parts. The scheme is https, the host is something like www.example.com, and there may be a port and a path. If you typed no port, HTTPS implies 443. The browser also checks whether the host is on its HSTS list, which is a record of sites that must only be reached securely, and it checks its own caches. If a fresh cached copy of the resource exists, the browser can skip the network entirely, and the "first byte" arrives from disk almost instantly. Service workers can also intercept the request at this point and answer it themselves.

2. Resolving the name with DNS

Computers connect to IP addresses, not names, so the browser must translate www.example.com into an address. It looks in several places in turn. First is its own DNS cache, then the operating system cache, then the hosts file. If none has an answer, the OS asks a recursive resolver, usually run by your internet provider or a public service. That resolver may already have the answer cached. If not, it walks the hierarchy by asking a root server where to find the .com servers, asking those where example.com's authoritative servers live, and finally asking the authoritative server for the record. Each answer carries a time to live (TTL) that says how long it may be cached.

The result is one or more IP addresses, possibly both IPv4 and IPv6. Modern browsers try both and use whichever connects first, a technique often called Happy Eyeballs. DNS lookups commonly take from a few milliseconds to a few hundred, and they are a frequent hidden cost for sites that pull resources from many different hostnames.

3. Opening a TCP connection

With an IP address in hand, the browser needs a reliable channel to the server. Traditionally this is TCP, which begins with a three-step handshake. The browser sends a SYN packet, the server replies with SYN-ACK, and the browser answers with ACK. This costs one full round trip, meaning the time for a message to travel to the server and back. If the server is far away, that round trip alone can be 100 milliseconds or more, which is why physical distance matters and why content delivery networks (CDNs) place servers close to users.

Newer browsers may instead use HTTP/3, which runs over QUIC on top of UDP. QUIC combines the connection and encryption setup into fewer round trips. The browser learns that a server supports it from an earlier response header or from DNS records, so a first visit usually still starts with TCP.

4. The TLS handshake

The "S" in HTTPS means the connection is encrypted using TLS. Before any request is sent, the browser and server must agree on how to protect it. In TLS 1.3, the browser sends a ClientHello message listing the encryption methods it supports, along with its half of a key exchange. It also includes the Server Name Indication (SNI), which is the hostname it wants. This matters because one IP address may host many sites, and the server needs to know which certificate to present.

The server replies with its own half of the key exchange and its certificate. Both sides can now compute the same shared secret without ever sending it over the network. Everything after this point is encrypted with keys derived from that secret. TLS 1.3 completes in one round trip. Older TLS 1.2 needed two. If the browser has connected before, session resumption can shorten this further.

5. Verifying the certificate

The certificate is how the browser knows it is talking to the real example.com and not an impostor. The browser checks several things. The certificate must list the requested hostname. It must not be expired. It must be signed by a certificate authority that chains up to a root the operating system or browser already trusts. The browser may also check that the certificate has not been revoked, through mechanisms such as OCSP stapling, where the server attaches a recent signed status to the handshake.

If any check fails, you see the full-page warning about an unsafe connection. As a developer, the most common causes you will meet are an expired certificate, a missing intermediate certificate on the server, and a hostname mismatch.

6. Sending the HTTP request

Only now does the browser send the actual request, through the encrypted channel. A simple one looks like a method (GET), a path, and a set of headers. These headers include Host, Accept, Accept-Encoding to say which compression it understands, User-Agent, and any cookies stored for that site. If the browser holds an expired cached copy, it adds validators such as If-None-Match so the server can reply that nothing changed.

With HTTP/2 and HTTP/3, the same information is sent in a compact binary form and many requests can share one connection at once. The meaning is unchanged.

7. The server does its work

The request may not reach your application directly. It often passes through a CDN edge, a load balancer, or a reverse proxy such as nginx. Any of these may answer from cache. If not, the request is routed to an application server. There the framework matches the path to a handler, which may check authentication, query a database, call other services, and render HTML or JSON. This is frequently the largest single delay, and it is the part you control most directly as a developer.

8. The first byte arrives

When the server starts sending its response, beginning with the status line and headers, the browser receives the first byte. The time from sending the request to this moment is called Time to First Byte (TTFB). Strictly, tools like browser developer panels often count TTFB from the start of navigation, so it includes DNS, connection, and TLS time as well as server processing.

Why this matters in practice

Each stage has a typical fix when it is slow. DNS cost drops with fewer distinct hostnames and sensible TTLs. Connection and TLS costs drop with CDNs, HTTP/2 or HTTP/3, TLS 1.3, and connection reuse through keep-alive. Server time drops with caching, efficient queries, and avoiding needless redirects, since each redirect repeats much of this process. You can see every stage for yourself in your browser's developer tools. Open the Network panel, select the main document request, and look at the Timing breakdown, which separates DNS lookup, initial connection, SSL, waiting for the first byte, and content download.

When you type an HTTPS address into a browser and press Enter, the browser first parses the URL into its parts: the scheme (https), the host name, an optional port (443 by default for HTTPS), the path, the query string and the fragment. The fragment never leaves the browser, so it plays no part in what follows. Before touching the network, the browser checks a few local things. It may consult its HSTS list, which records sites that must only ever be reached over HTTPS, and it looks in its HTTP cache to see whether a fresh copy of the resource is already stored. If a valid cached response exists, the browser can use it immediately and the network journey never starts. Assuming it does not, the browser needs to turn the host name into an IP address.

Name resolution begins close to home. The browser checks its own DNS cache, then asks the operating system, which checks its cache and the hosts file. If neither knows the answer, the operating system sends a query to a recursive resolver, usually run by your ISP, your employer or a public provider. The resolver does the heavy lifting if it has no cached answer. It asks a root server which servers handle the top-level domain such as .com, asks those servers which authoritative name servers handle the domain, and finally asks the authoritative server for the actual A record (IPv4) or AAAA record (IPv6). Each answer carries a time-to-live value, so every layer can cache it for a while. This is why the first visit to a site is often slower than later ones. Many modern browsers also support encrypted DNS and may ask for HTTPS or SVCB records, which can advertise things like HTTP/3 support before any connection is made.

With an IP address in hand, the browser must reach the server. For HTTP/1.1 and HTTP/2, this means opening a TCP connection using a three-way handshake. The client sends a SYN packet, the server replies with SYN-ACK, and the client answers with ACK. That costs one full round trip, meaning the time for a packet to travel to the server and back. Your packets do not travel directly. They pass through your router and a series of other routers operated by different networks, each forwarding the packet toward the destination based on IP routing tables. If the page is served through a content delivery network, the IP address returned by DNS usually points to an edge server geographically near you, which shortens every round trip. Some sites also use anycast, where the same IP address is announced from many locations and the network delivers your packets to the nearest one.

Next comes the TLS handshake, which is what makes the connection secure rather than merely reachable. Over TCP this happens on top of the connection just established. In TLS 1.3, the client sends a ClientHello listing the protocol versions and cipher suites it supports, the server name it wants through the Server Name Indication extension, the application protocols it can speak (such as h2 and http/1.1) through ALPN, and a key share for a key exchange, typically elliptic-curve Diffie-Hellman. The server responds with its chosen parameters, its own key share and its certificate. At that point both sides can compute the same shared secret without ever sending it across the wire, and everything after that is encrypted. The server also proves it holds the private key matching its certificate by signing part of the handshake. TLS 1.3 completes this in a single round trip, whereas TLS 1.2 needed two. If the client has connected before, session resumption or 0-RTT data can reduce this further, with some security trade-offs for replayable requests.

Certificate validation is the part developers most often meet when something goes wrong. The certificate presented by the server must name the host you asked for, usually in its Subject Alternative Name field. It must be within its validity dates, and it must chain back through one or more intermediate certificates to a root certificate authority already trusted by your operating system or browser. The browser may also check revocation information, through stapled OCSP responses or compressed revocation lists, and often checks Certificate Transparency records that prove the certificate was publicly logged. If any check fails, the browser shows a full-page warning instead of continuing. This is why an expired certificate, a missing intermediate or a mismatched domain breaks a site entirely rather than degrading it gracefully.

If the browser and server agree on HTTP/3, the story changes shape. HTTP/3 runs over QUIC, which uses UDP and folds the transport and TLS handshakes into one. A fresh connection needs roughly one round trip in total instead of one for TCP plus one for TLS. Because browsers cannot know in advance whether a server supports QUIC, they typically learn it from an Alt-Svc header on an earlier response or from DNS records, and may race a QUIC attempt against a TCP one.

Only now can the browser send the actual HTTP request. It builds a message containing the method (usually GET), the path and query, the Host or :authority header, and a set of headers such as Accept, Accept-Language, User-Agent and Accept-Encoding, which announces which compression formats it understands. It also attaches any cookies the browser holds for that site that match the request, and may include cache validators such as If-None-Match if it has a stale cached copy it would like to revalidate. In HTTP/2 and HTTP/3 these headers are compressed and sent as binary frames on a stream, which is what allows many requests to share one connection. In HTTP/1.1 they are plain text lines, sent in a form you could read if the traffic were not encrypted. All of it travels inside the encrypted TLS or QUIC channel, so intermediaries along the path see only the destination address and, depending on configuration, the server name.

The request reaches the server side, which is often more complicated than a single machine. It may first hit a load balancer or reverse proxy that terminates TLS, picks a backend, and perhaps serves the response from its own cache. The application then routes the path to a handler, which may query a database, call other services and render HTML. Once it has something to say, it writes a status line and headers, then begins sending the body. The moment the first byte of that response arrives back at the browser is what performance tools call time to first byte. Everything described above, the DNS lookup, the TCP or QUIC connection, the TLS handshake, the request transit and the server's processing time, is included in that single number, which is why it is a useful first place to look when a page feels slow.

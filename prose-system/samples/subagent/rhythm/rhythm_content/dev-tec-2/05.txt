When you type or click an HTTPS address, the browser first parses it into a scheme, a host, an optional port and a path, and then consults a series of local shortcuts before it touches the network. If the host appears on the browser's built-in HSTS preload list, or the browser has previously seen a Strict-Transport-Security header from that host, an http:// address is silently rewritten to https:// so that no unencrypted request is ever sent. The browser then checks whether a service worker registered for that origin wants to intercept the request, and whether the HTTP cache holds a response that is still fresh according to its Cache-Control or Expires headers, in which case the response can be served from disk or memory and the network is never involved at all. If the cache holds a stale entry, the browser keeps it around so it can later ask the server whether it has changed using an ETag or Last-Modified validator, which can turn a full download into a tiny 304 response.

Assuming the request has to go out, the browser needs an IP address for the hostname, and it looks in its own DNS cache first, then asks the operating system's resolver, which has its own cache and also consults the local hosts file. When nobody has the answer, the query goes to a recursive resolver, usually run by your ISP, your company or a public provider, and that resolver walks the hierarchy on your behalf: it asks a root server which servers handle the top-level domain, asks those which servers are authoritative for the domain, and finally asks an authoritative server for the A record (IPv4) and AAAA record (IPv6) of the name. Along the way it may follow CNAME records that alias one name to another, which is very common when a site sits behind a CDN, and every answer carries a time-to-live that tells each cache how long it may be reused, which is why a lookup that takes tens of milliseconds the first time costs almost nothing on the next visit. Modern browsers also ask for HTTPS or SVCB records in the same breath, since these can announce that the server speaks HTTP/3 and can hand over connection parameters before any connection exists. If the name resolves to both IPv4 and IPv6 addresses, the browser uses an approach called Happy Eyeballs, starting an attempt on one family and then a moment later on the other, and keeping whichever completes first so that a broken IPv6 path does not stall the page.

If a proxy is configured, the browser connects to the proxy and asks it to tunnel to the destination with a CONNECT request, and otherwise it opens a connection straight to the server, but before doing either it checks its connection pool, because an already-open HTTP/2 or HTTP/3 connection to the same origin, or to another name covered by the same certificate and resolving to the same address, can carry the new request with no setup cost. When there is no reusable connection, a TCP handshake begins: the client sends a SYN, the server answers with a SYN-ACK, and the client replies with an ACK, which costs one round trip and therefore depends heavily on the physical distance between you and the server. This is a major reason CDNs exist, since they place servers close to users, so the round trip that dominates this phase becomes short.

Over that TCP connection the TLS handshake follows, and in TLS 1.3 it fits into a single round trip. The client sends a ClientHello containing the protocol versions and cipher suites it supports, a key share that is the client's half of an ephemeral Diffie-Hellman exchange, the Server Name Indication extension naming the host it wants (so that a server hosting many sites on one IP address can pick the right certificate), and an ALPN extension listing the application protocols it can speak, typically h2 and http/1.1. The server replies with its own key share, which lets both sides derive the same session keys without those keys ever crossing the wire, and everything after the ServerHello is already encrypted, including the server's certificate chain and a signature proving it holds the private key matching that certificate. The browser validates the chain up to a root certificate in its trust store, checks that the leaf certificate covers the hostname, has not expired and has not been revoked, and typically verifies that it was logged in Certificate Transparency logs, and if any of these checks fails the user sees a certificate warning instead of the page. Both sides then exchange Finished messages that confirm they computed the same keys, and from that point the browser can send application data. If the browser has talked to this server recently, it may resume the session using a ticket and even send its first request as 0-RTT early data in the very first flight, accepting that such data can be replayed and is therefore only safe for idempotent requests.

When the server advertised HTTP/3 through an Alt-Svc header or an HTTPS DNS record, the browser may instead use QUIC, which runs over UDP and folds the transport handshake and the TLS 1.3 handshake into one exchange, so the separate TCP round trip disappears, and because each stream is independent, a lost packet delays only the stream it belongs to rather than every request on the connection.

With the encrypted channel established, the browser sends the request itself: a method and path, a Host (or :authority) header, the Accept and Accept-Encoding headers that tell the server which content types and compressions it can handle, the User-Agent, and any cookies stored for that domain. With HTTP/2 and HTTP/3 these headers are compressed with HPACK or QPACK and sent as binary frames on a numbered stream, which lets many requests share one connection. The request typically lands first on an edge server or load balancer, which may terminate TLS, consult its own cache and, on a miss, forward the request to an origin server, where the web server routes it to application code that may query a database, call other services and render a response. The moment the first bytes of that response, beginning with the status line and headers, travel back through the same encrypted connection and reach the browser, the interval that developers call Time to First Byte comes to an end, and its length is the sum of everything described above: redirects, DNS, connection setup, the TLS handshake, the network latency of the request, and the time the server spent producing an answer.

Git stores everything inside the .git directory, and the heart of it is a simple key-value database. Each value is a piece of content, and each key is a SHA-1 or SHA-256 hash of that content. This database lives in .git/objects. Once you understand the four things it holds, which are blobs, trees, commits and refs, nothing about everyday Git feels mysterious any more.

**Blobs: file contents**

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no timestamp. When you run git add on a file, Git reads the bytes, prepends a small header giving the object type and the byte length, hashes the result, compresses it with zlib and writes it to .git/objects. The first two hex characters of the hash become a directory name and the remaining characters become the filename. A blob with hash e69de29b... therefore lands at .git/objects/e6/9de29b....

Because the key is derived from the content, identical files always produce the same blob. If you copy a file ten times in your project, Git stores one blob. If you change one line in a large file, Git stores a brand new blob for the whole new version. Git does not store diffs at this level. You can inspect any object with git cat-file -p followed by its hash, and git cat-file -t tells you its type.

**Trees: directories**

Since a blob has no name, something must map names to blobs. That job belongs to the tree object. A tree is a directory listing. Each entry holds a file mode, a type, a hash and a name. The mode records whether the entry is a regular file, an executable, a symlink or a subdirectory. The hash points either to a blob for a file or to another tree for a subdirectory.

Trees nest, so a project with folders becomes a tree of trees. The top level tree is called the root tree, and it describes your whole working directory at one moment in time. Renaming a file changes only the tree that lists it, because the blob itself is unchanged. This is how Git detects renames cheaply, since the same blob hash appears under a new name.

Trees are also hashed from their content, and that content includes the hashes of their children. Change one byte in one deeply nested file and the blob hash changes, which changes its parent tree hash, which changes every tree above it up to the root. Two snapshots with the same root tree hash are guaranteed to be identical in every file.

**Commits: snapshots with history**

A commit object is small. It contains the hash of a root tree, zero or more parent commit hashes, an author with a timestamp, a committer with a timestamp and your commit message. That is the entire record. A commit does not contain a diff. When a tool shows you what changed, it computes the difference between the commit's tree and its parent's tree on demand.

The parent field is what creates history. An ordinary commit has one parent, a merge commit has two or more, and the very first commit has none. Following parent links backwards gives you the log. Because each commit hash covers its parent hashes, you cannot alter an old commit without changing the hash of every commit after it. That chain of hashes is what makes history tamper evident, and it is why rewriting history with rebase produces new commits instead of editing the old ones.

**Refs: human-friendly names**

Hashes are hard to remember, so Git adds refs, which are named pointers to commits. A ref is just a small text file containing a hash. Branches live in .git/refs/heads, so the file .git/refs/heads/main holds the hash of the latest commit on main. Tags live in .git/refs/tags, and remote tracking branches live in .git/refs/remotes. For efficiency, Git may pack many refs into a single file called .git/packed-refs, but the idea is the same.

When you make a commit on a branch, Git writes the new commit object and then overwrites the branch file with the new hash. That is all a branch is. Creating a branch means writing a forty character file, which is why it is instant. Deleting a branch deletes that file, and the commits remain in the database until garbage collection removes any that nothing reaches.

**HEAD and the index**

HEAD is a special ref stored at .git/HEAD. Normally it contains the text ref: refs/heads/main, meaning it points at a branch, which in turn points at a commit. When you check out a specific commit directly, HEAD contains a raw hash and you are in the detached HEAD state.

Between your working files and the commit sits the index, stored at .git/index. It is the staging area. When you run git add, Git writes blobs and records their names and hashes in the index. When you run git commit, Git turns the index into a tree, wraps that tree in a commit object and moves the current branch ref forward.

**Putting it together**

Run a commit and the sequence is concrete. Git writes a blob for each changed file, builds new trees for each affected directory, writes a commit pointing at the new root tree and at the previous commit, and updates the branch ref. Everything else you do in Git, including merging, rebasing, cherry-picking and resetting, is a manipulation of these four ingredients. Over time Git also packs loose objects into compressed pack files that store similar objects as deltas, but the model you work with never changes.

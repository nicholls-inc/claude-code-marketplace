## Act on these

1. **Latent crash in solar-only scheduling once household load is non-zero — MEDIUM (HIGH after follow-up PR).**
   `dc/scheduler/solar_only_schedules.py:96` — `max(i for i in power_steps_watts if i <= price.household_export_watts)`. `power_steps_watts` is all ≥ 0; the old `calculate_power_produced_watts` could never return negative (efficiency ≥ 0). Now the value is `generation - household_load`, and this PR adds no clamp.
   *Failure:* household load 3 kW, generation 1 kW → `household_export_watts = -2000` → empty generator → `ValueError: max() arg is an empty sequence` → solar-only scheduling raises for every affected user on every cloudy evening. Fix: clamp to 0 in `get_household_export_prices`, not at each consumer.

2. **`get_household_export_prices` silently returns `[]` instead of failing — MEDIUM.**
   `dc/scheduler/schedule_queries.py:670` — the new `or solar is None` early return. The signature still advertises `solar_forecast_id`-only use (`charging_session=None` default), and `fill_percentage_import` now re-derives solar from `energy_usages[0].charging_session` rather than the `solar` object `fill_energy_usage` already validated.
   *Failure:* any caller passing only `solar_forecast_id` (or a session whose `solar_enabled()` flipped off between the caller's guard and this call) gets zero forecast data → `percentage_import = 1` for every period → 100% of that session's energy billed and carbon-attributed as grid import, with no exception and no log line. Fix: thread the already-validated `solar` down as a parameter.

3. **`SmartPrice.household_export_watts: int` holds three different runtime types, none of them `int` — MEDIUM.**
   `dc/scheduler/schedule_queries.py:414` — `Decimal(0) if np.isnan(solar_mean) else round(solar_mean, 5)` yields `Decimal` on the nan branch and `np.float64` otherwise; `get_household_export_prices` produces `Decimal`. The removed `Decimal(...)` wrap (present for every sibling field) is what lost this. Dataclasses don't validate, so mypy won't catch it.
   *Failure:* an `== 0`/`isinstance` check or a numpy-scalar JSON/log serialisation breaks depending on which branch produced the slot. Secondary behaviour change: the value is no longer int-rounded, so export 5289.6 W no longer selects the 5290 W power step it used to (`int(round(...))` → 5290).

4. **The semantic core of the PR is untested — MEDIUM (violates CLAUDE.md "ALL new code must have tests").**
   `get_household_export_prices` has no direct test before or after — the new watts conversion (`forecast_efficiency * capacity_watts`) and the new `solar is None` return path are covered only incidentally. `Solar.forecasted_household_load_at_time` replaced `household_load_watts` and its test (`test_household_load`) was **deleted, not ported**.
   *Failure:* someone drops `* solar.capacity_watts` in a refactor; the only signal is whichever scheduler test happens to be magnitude-sensitive.

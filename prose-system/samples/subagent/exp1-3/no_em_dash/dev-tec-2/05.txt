From HTTPS Address to First Byte: What the Browser Does

When you type https://www.example.com/products into a browser and press Enter, a surprising amount of work happens before a single byte of the response arrives. Most of it takes place in a few tens of milliseconds, but each step can fail or slow down, which is why understanding the sequence helps when you debug performance.

1. Parsing the URL

The browser first splits the address into parts. The scheme is https, the host is www.example.com, the port is implied (443 for HTTPS), the path is /products, and there may also be a query string and a fragment. The fragment (the part after #) is never sent to the server. If you typed something that is not a valid URL, the browser treats it as a search query instead.

Before going to the network, the browser applies a few shortcuts. It checks whether the host is on its HSTS (HTTP Strict Transport Security) list, which forces HTTPS even if you typed http://. It also checks service workers and the HTTP cache. If a fresh cached copy of the resource exists, the browser can answer immediately and never touch the network. Only when these checks fail does the real network work begin.

2. DNS Resolution

Computers route traffic by IP address, not by name, so the browser must turn www.example.com into an address such as 93.184.216.34 (IPv4) or a longer IPv6 address. This is DNS resolution, and it runs through several layers of cache:

- The browser's own DNS cache.
- The operating system's resolver cache and the local hosts file.
- A recursive resolver, usually run by your ISP or a public provider.

If none of those has the answer, the recursive resolver walks the DNS hierarchy. It asks a root server which servers handle .com, asks those TLD servers which servers are authoritative for example.com, and finally asks the authoritative server for the record. Each answer carries a TTL (time to live) that says how long it may be cached. Modern browsers may also request HTTPS or SVCB records, which can announce that a site supports HTTP/3 and avoid extra round trips later.

A cold DNS lookup can cost tens of milliseconds or more. A warm one costs almost nothing.

3. Opening a TCP Connection

With an IP address, the browser needs a reliable channel to the server. For HTTP/1.1 and HTTP/2, that channel is TCP, established with a three-way handshake:

1. The client sends SYN.
2. The server replies SYN-ACK.
3. The client sends ACK.

That costs one full round trip (the time for a packet to travel to the server and back) before any application data can flow. If the server is on another continent, a round trip can easily be 100 milliseconds or more, so this step matters.

Browsers keep connections open and reuse them. If you already have a connection to this host from an earlier request, steps 2 and 3 are skipped entirely.

HTTP/3 is different. It runs over QUIC, which uses UDP and combines the transport and encryption handshakes into one. A browser typically learns that a site supports HTTP/3 from a previous visit (through the Alt-Svc header) or from DNS records, and may race a QUIC connection against TCP.

4. The TLS Handshake

The "S" in HTTPS means the connection is encrypted with TLS. Before sending your request, the browser and server must agree on how to secure the channel and prove the server is who it claims to be. With TLS 1.3, the common modern version, this takes one round trip:

- ClientHello: the browser lists the TLS versions and cipher suites it supports, sends a random value, and includes a key share (its half of a key exchange). It also sends the server name in an extension called SNI (Server Name Indication), so a server hosting many sites knows which certificate to present. It may advertise supported application protocols (ALPN), such as h2 and http/1.1.
- ServerHello: the server picks a cipher suite, sends its own key share, and from this point on the rest of its handshake is encrypted. It sends its certificate chain and a signature proving it holds the private key.

Both sides now compute the same shared secret from the exchanged key shares, without ever sending that secret over the wire. They derive session keys from it and exchange Finished messages to confirm nothing was tampered with.

The certificate check is the browser's job and has several parts. The browser verifies that the certificate chains up to a certificate authority it trusts, that it has not expired, that it covers the hostname you asked for, and, depending on the browser, that it has not been revoked. If any check fails, you see the familiar full-page certificate warning and the request stops.

TLS 1.2 needs two round trips instead of one. TLS 1.3 also supports session resumption, where a returning client reuses earlier secrets to shorten the handshake, and an optional 0-RTT mode that can send data in the first flight (with some replay-attack caveats, so it is limited to safe requests).

5. Sending the HTTP Request

Now the browser can finally send the request, encrypted with the session keys. Over HTTP/1.1 it looks like plain text before encryption:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The browser adds headers it knows are relevant, including cookies previously stored for this domain, language preferences, and a cache validator such as If-None-Match if it holds a stale cached copy. With HTTP/2 and HTTP/3 the same information is sent in a compressed binary format, and many requests can share one connection at the same time.

6. Waiting for the Server

The request crosses the network, possibly passing through a CDN edge server, a load balancer, or a reverse proxy before reaching the application. The application may route the request, check authentication, query a database, render a template, or call other services. All of that is server think time.

The moment the first byte of the response comes back is called Time to First Byte (TTFB). Everything we have described so far, plus the server's processing time and one-way network travel for the reply, is included in that number. In browser DevTools, the Network tab breaks a request into phases (DNS lookup, initial connection, SSL, waiting, content download), and the "Waiting" phase is essentially server time.

Where the Time Goes

Adding up a cold visit to a distant server using TCP and TLS 1.3, you pay roughly: one DNS lookup, one round trip for TCP, one for TLS, and one more for the request and first response byte, plus server processing. That is about three round trips before the first byte, which is why geographic distance hurts so much.

Practical Takeaways

- Use a CDN so the server is physically closer to users, which shrinks every round trip.
- Enable HTTP/2 or HTTP/3 and keep connections alive so handshakes are paid once.
- Use TLS 1.3 and make sure your certificate chain is complete and not oversized.
- Set sensible cache headers so repeat visits skip the network altogether.
- Keep server work fast; caching rendered output or database results lowers TTFB directly.
- Use preconnect and dns-prefetch hints for third-party origins you know the page will need.

Next time a page feels slow, open DevTools and look at the timing breakdown. Knowing the sequence above tells you which phase to blame and what to fix.

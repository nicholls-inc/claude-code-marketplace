Every object Git keeps in the .git directory is named by a hash of its own contents, and the whole system is built on that one idea. When you commit, Git does not record a diff against the previous version. It writes a handful of small immutable objects into .git/objects, each one stored as a zlib-compressed file whose name is the SHA-1 hash of its contents (newer repositories can use SHA-256, but the structure is identical), split so that the first two hex characters become a subdirectory and the remaining thirty-eight become the filename. Each object begins with a short header giving its type, a space, its size in bytes and a null byte, followed by the payload, and the hash is computed over the header and payload together, which is why the same content always lands at the same address and why you can inspect any object with `git cat-file -p` followed by enough of its hash to be unambiguous.

The simplest of these objects is the blob, which holds the contents of one file and nothing else. A blob has no filename, no permissions and no timestamp, so two files in entirely different directories that contain identical bytes share a single blob, and a file that is unchanged between two commits costs nothing extra to keep, because its hash has not changed and the existing object is simply referenced again. You can see this for yourself by running `git hash-object` on a file, which prints the hash Git would give it without storing anything, and adding `-w` writes the blob into the object database. The names and modes that blobs lack live one level up, in tree objects, and a tree represents a single directory as a list of entries, each consisting of a file mode, a name and the hash of whatever that name points to. When the entry is a regular file the hash refers to a blob and the mode is typically 100644, or 100755 if the file is executable, while a subdirectory is an entry with mode 040000 whose hash refers to another tree, so that the whole project becomes a nested structure of trees with blobs at the leaves, and the hash of the top-level tree depends on every name, mode and byte beneath it. Change one character in a deeply nested file and its blob gets a new hash, which changes the hash of its containing tree, which changes the tree above that, and so on up to the root, while every sibling subtree that was not touched keeps its old hash and is reused as it is. This is why a snapshot of a large repository can be recorded cheaply, since only the chain of objects along the path to a changed file needs to be written anew.

A commit object ties one of these root trees to a point in history. It is a short text payload that names the hash of the root tree, then one `parent` line for each preceding commit (none for the very first commit, two for a merge), then an author line and a committer line, each with a name, an email address, a Unix timestamp and a timezone offset, and finally a blank line followed by your commit message. Because the parent hashes are part of what gets hashed, a commit's identity depends on the entire history behind it, so altering any ancestor, even by amending only its message, produces a different hash for it and for every descendant. That is the reason rebasing is described as rewriting history rather than editing it, since the old commits are left untouched and new ones with new hashes are created alongside them, and the old ones linger until garbage collection discards the unreachable ones. The diffs you see in `git show` and `git log -p` are computed on demand by comparing the trees of a commit and its parent, and renames are likewise inferred by noticing that a blob has appeared under a new name, because nothing in the stored data says that a rename occurred.

What the objects do not provide is any way to find the latest commit, because a hash is an address and carries no meaning about which commit you care about, and that is the job of refs. A ref is just a named pointer, and a branch is the plainest example: the file .git/refs/heads/main contains the forty hex characters of a commit hash and a trailing newline. Making a new branch writes one tiny file, and committing on a branch writes the new commit object and then replaces the contents of that file with the new hash, which is how the branch appears to move forward. Tags live under .git/refs/tags and work the same way, with annotated tags adding a fourth object type that carries a message and a signature and points at a commit, and remote-tracking branches such as origin/main sit under .git/refs/remotes and record where the remote's branches were at your last fetch. When a repository has many refs Git may consolidate them into a single .git/packed-refs file, and the lookup rules treat a loose file as more recent than the packed entry. HEAD, in .git/HEAD, is normally a symbolic ref, a file containing `ref: refs/heads/main` that says which branch you are on, so that a commit follows HEAD to the branch and the branch to the commit, and in a detached HEAD state the file holds a raw commit hash instead, which is why commits made there are easy to lose, as nothing named points at them once you switch away.

Two further details complete the picture of what you would find on disk. Between your working files and the next commit sits the index, the binary file .git/index, which records the path, mode and blob hash of everything staged, and `git commit` essentially turns the index into a tree object, wraps it in a commit and advances the current branch. And because thousands of small loose files would be wasteful, Git periodically gathers objects into packfiles under .git/objects/pack, where similar objects are stored as deltas against one another, an optimisation that changes how the bytes are laid out on disk and nothing about the model of blobs, trees, commits and refs described above.

When you type an HTTPS address into a browser, the first thing it does is read the address and split it into a scheme, a host name, an optional port and a path. For https://www.example.com/shop?item=4 the scheme is https, the host is www.example.com, the port defaults to 443 because none is given, and the rest is the path and query. Before any network traffic, the browser checks a few local things. It looks for the host in an HSTS list, which records sites that must only be reached over HTTPS, and it looks in its HTTP cache for a stored copy of the page that is still fresh. If a fresh copy exists, the request ends here and no network traffic occurs.

If not, the browser needs an IP address for the host name. It checks its own DNS cache first, then asks the operating system, which checks its cache and the local hosts file. If neither has an answer, the request goes to a recursive resolver, usually run by your internet provider or a public service such as 1.1.1.1 or 8.8.8.8. The resolver may already hold the answer. If it does not, it asks a root server which servers handle .com, asks one of those which servers handle example.com, and then asks that domain's authoritative server for the address of www.example.com. The answer comes back with a time to live, often between 60 and 3,600 seconds, which tells every cache along the way how long it may keep the result. Many sites return both an IPv4 address such as 93.184.216.34 and an IPv6 address, and the browser usually tries both and uses whichever connects first. Modern browsers can also fetch an HTTPS record from DNS, which can say in advance that the server supports HTTP/3 and so save a step later.

With an address in hand, the browser opens a connection. For HTTP/1.1 and HTTP/2 this uses TCP, which begins with a three-step exchange. The client sends a SYN packet, the server replies with SYN-ACK, and the client sends an ACK. This costs one round trip, which is the time for a message to travel to the server and for the reply to come back. On a connection between London and a server in Virginia a round trip is roughly 75 milliseconds, so the handshake alone takes about that long. If the server supports HTTP/3, the browser uses QUIC instead, which runs over UDP and combines the transport and encryption setup into a single exchange. The browser learns that a server offers HTTP/3 either from the DNS record mentioned above or from an Alt-Svc header seen on an earlier visit, so a first visit to a site usually goes over TCP.

Next comes the TLS handshake, which sets up encryption and checks who the server is. In TLS 1.3 the client sends a ClientHello that lists the cipher suites it supports, includes a key share for key agreement, and contains the host name in a field called Server Name Indication. The host name is there because one IP address often serves many sites, and the server needs to know which certificate to present. The server answers with its own key share and its certificate chain, then sends a signature over the handshake to show that it holds the private key for the certificate. Both sides now compute the same session keys from the exchanged key shares, and the rest of the traffic is encrypted with them. TLS 1.3 needs one round trip for this. The older TLS 1.2 needs two. If the client has connected to the server before, it can sometimes resume the session with a ticket and skip parts of the handshake.

The browser checks the certificate before it trusts the connection. It confirms that the certificate names www.example.com, that today's date falls within its validity period, and that it chains up through one or more intermediate certificates to a root authority that the browser or operating system already trusts. Public certificates are currently valid for at most 398 days, and the limit is being reduced in stages. The browser may also check whether the certificate has been revoked, and many servers include a stapled OCSP response in the handshake so that the browser does not have to ask the issuer itself. If any check fails, the browser shows a full-page warning and does not send the request.

Only now does the browser send the HTTP request. Over HTTP/2 or HTTP/3 it is a set of headers carried in a binary frame, and over HTTP/1.1 it is plain text. A typical request has the method GET, the path /shop?item=4, and headers including Host, User-Agent, Accept, Accept-Encoding and any cookies stored for that site. The Accept-Encoding header lists compression formats the browser can decode, such as gzip and br, so the server can send a smaller body. Because the request travels inside the encrypted connection, anyone watching the network can see which IP address you contacted but not the path, the cookies or the content.

The request may not reach the application directly. Large sites usually put a content delivery network or load balancer in front of their servers. The DNS answer from earlier often points to one of its edge machines near the user, and that machine ends the TLS connection. It may answer from its own cache, or it may forward the request over a separate, already open connection to an origin server. The origin server then runs the application code, which might query a database or call other services, and builds a response.

The server sends back a status line or status code, such as 200 for success, followed by response headers and then the body. The first byte of that response to arrive at the browser is the moment this description ends. The time from sending the request to that byte is called time to first byte, and it is the sum of everything above that happens after the request leaves, which includes the network travel in each direction, any edge processing and the work the server does to produce the response. Time spent on DNS, the connection and TLS before the request is sent is normally measured separately in browser developer tools, where the Network panel shows each stage as a separate coloured segment on the timing bar for a request.

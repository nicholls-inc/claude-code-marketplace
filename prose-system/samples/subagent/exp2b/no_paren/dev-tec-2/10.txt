When you type an address such as https://example.com/products into a browser and press Enter, a lot of work happens before the first byte of the response arrives. Most of it is network negotiation, and each step adds latency you can measure and sometimes reduce.

**1. Parsing the address**

The browser first splits the URL into parts. The scheme is https, the host is example.com, the port is implied as 443 because HTTPS was requested, and the path is /products. If you typed something that is not a valid URL, the browser treats it as a search query instead.

Before touching the network, the browser checks several local sources. It consults its HSTS list, which records sites that must only be reached over HTTPS. It checks the HTTP cache for a fresh copy of the resource, and if one exists the request may finish without any network traffic. It also checks whether a service worker controls the page's scope, because a service worker can answer the request itself. If none of these produce a response, the browser goes to the network.

**2. DNS resolution**

Networks route traffic by IP address, not by hostname, so the browser must translate example.com into an address. It looks in layers. First comes the browser's own DNS cache, then the operating system's cache and the hosts file. If both miss, the OS asks a recursive resolver, usually run by your ISP, your company, or a public provider.

The recursive resolver does the heavy lifting if it does not already have the answer cached. It asks a root server which servers handle the .com zone, asks a .com server which servers are authoritative for example.com, and finally asks one of those authoritative servers for the address records. It returns the answer to your machine. Each record carries a time to live, which tells every cache how long the answer may be reused.

Modern browsers often request both A records, which hold IPv4 addresses, and AAAA records, which hold IPv6 addresses, and may also query HTTPS records that advertise protocol support. A warm DNS cache makes this step nearly free. A cold lookup can cost tens or hundreds of milliseconds.

**3. Opening a connection**

With an IP address in hand, the browser needs a transport connection. For HTTP/1.1 and HTTP/2 that is TCP. The browser sends a SYN packet, the server replies with SYN-ACK, and the browser sends an ACK. This three-way handshake costs one full round trip before any application data can flow. Browsers also reuse existing connections to the same origin when possible, which skips this cost entirely.

If the browser and server support HTTP/3, the transport is QUIC running over UDP instead. QUIC combines the transport and encryption handshakes, so it saves round trips. The browser learns about HTTP/3 support from a previous visit through the Alt-Svc header, or from an HTTPS DNS record.

**4. The TLS handshake**

Because the scheme is https, the connection must be encrypted and authenticated before any HTTP is sent. With TLS 1.3 this takes one round trip.

The browser sends a ClientHello. It lists the TLS versions and cipher suites it supports, a random value, and a key share, which is its half of a key exchange. It also includes the Server Name Indication extension containing example.com, so a server hosting many sites knows which certificate to present. It includes an ALPN extension too, listing protocols it can speak, such as h2 and http/1.1.

The server answers with a ServerHello that picks the cipher suite and supplies its own key share. Both sides now derive the same session keys without ever sending the key itself. Everything after the ServerHello is encrypted. The server then sends its certificate chain and a signature proving it holds the matching private key. It also selects the application protocol through ALPN, which is how HTTP/2 gets negotiated without an extra round trip.

The browser validates the certificate. It checks that the chain leads to a certificate authority it trusts, that every certificate is within its validity period, that the hostname matches the certificate's subject alternative names, and that the certificate has not been revoked. Revocation checks vary by browser and often rely on pre-distributed lists rather than live lookups. If any check fails, the browser shows a security warning and stops.

Once the handshake finishes, the browser sends a Finished message and can immediately send its HTTP request. If the browser has connected before, TLS session resumption can shorten the handshake, and with 0-RTT it can even send data in its first flight, with some replay risk that servers must handle.

**5. Sending the HTTP request**

Now the browser sends the request over the encrypted channel. In HTTP/1.1 it is plain text, beginning with a request line such as GET /products HTTP/1.1, followed by headers. Important headers include Host, which names the site; User-Agent; Accept, which says what content types are welcome; Accept-Encoding, which lists compression formats like gzip and br; and Cookie, which carries any stored cookies for that site. In HTTP/2 and HTTP/3 the same information travels as compressed binary frames, but the meaning is identical.

**6. Server-side processing**

The request travels to the server, often hitting a CDN edge node or a load balancer first. A CDN may answer directly from its cache, which is the fastest outcome. Otherwise, the request is forwarded to an origin server, perhaps through a reverse proxy such as nginx.

The application then does its work. It routes /products to a handler, checks authentication from the cookie, queries a database, perhaps calls other services, and renders HTML or JSON. This time is called server think time and is frequently the largest controllable part of the wait.

**7. The first byte arrives**

The server writes the response status line and headers, such as 200 OK and Content-Type, followed by the start of the body. The moment the browser receives the first byte of that response is called Time to First Byte, or TTFB. It is the sum of everything above: redirect time, DNS lookup, TCP connection, TLS negotiation, request transit, server processing, and the response's trip back.

**Why this matters**

You can see these phases in the browser's developer tools. The Network panel's timing breakdown labels them as DNS Lookup, Initial Connection, SSL, Waiting for server response, and Content Download. Knowing the sequence tells you where to optimise: use a CDN to shorten distance, keep connections alive to avoid repeated handshakes, enable HTTP/2 or HTTP/3, cache aggressively, set sensible DNS TTLs, and make server code and queries fast. Each step is small, but they happen in series, so delays add up.

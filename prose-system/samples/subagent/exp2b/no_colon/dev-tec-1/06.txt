Git stores everything inside the .git directory, and at its heart is a simple key-value database. Every piece of content is saved as an object, and the key is a SHA hash of that content. There are four kinds of object, which are blobs, trees, commits and annotated tags. On top of these sit refs, which are human-friendly names pointing at objects. Once you see how these pieces fit together, most Git behavior stops feeling like magic.

**Objects and the object store**

When you look in .git/objects you will find directories with two-character names, each holding files with long hexadecimal names. Together, the directory name and file name form the object ID. Git computes this ID by hashing a short header (the object type and size) followed by the content. Git compresses the result with zlib and writes it to disk. Because the ID derives from the content, identical content always gets the same ID, and changing even one byte produces a completely different one. This is why Git can detect corruption and why it never stores the same data twice.

Over time Git packs many loose objects into packfiles under .git/objects/pack, using delta compression to save space. This changes the storage format but not the model. Conceptually, every object is still addressed by its hash.

**Blobs hold file contents**

A blob is the simplest object. It contains the raw bytes of a file and nothing else. It has no filename, no permissions and no timestamp. If two files in your repository have identical contents, they share one blob. If you rename a file without editing it, the blob stays the same.

You can see this yourself by running git hash-object on a file, which prints the ID Git would assign. Add the -w flag and Git writes the blob into the object store. To read a blob back, run git cat-file -p followed by its ID.

**Trees hold directory structure**

Since blobs carry no names, something must map names to contents. That job belongs to trees. A tree object represents a single directory. It is a list of entries, and each entry records a file mode, a type, an object ID and a name. For a regular file the entry points at a blob. For a subdirectory the entry points at another tree. The mode tells Git whether the entry is a regular file, an executable, a symbolic link or a directory.

A tree for a project with a README and a src folder would therefore contain one entry pointing to a blob named README and another pointing to a tree named src. That nested tree would in turn list the files inside src. Following these pointers from the top, which is called the root tree, reconstructs the full snapshot of your project at one moment.

Trees also give Git a cheap way to compare snapshots. If a directory is unchanged between two commits, its tree has the same ID in both, so Git can skip the whole subtree without looking inside.

**Commits tie a snapshot to history**

A commit object is small. It holds a pointer to a root tree, zero or more parent commit IDs, an author with a timestamp, a committer with a timestamp, and the commit message. That is all. Run git cat-file -p HEAD and you will see these fields in plain text.

The tree pointer is what makes a commit a snapshot rather than a diff. Git does not store the changes you made. It stores the complete state of the project, and it relies on shared blobs and trees to avoid duplicating unchanged data. When you ask for a diff, Git computes it on demand by comparing two trees.

The parent pointers create the history. An ordinary commit has one parent, the commit it was built on. The first commit in a repository has none. A merge commit has two or more. Because each commit's ID depends on its parent's ID, the whole chain is cryptographically linked. Changing an old commit changes its ID, which changes every descendant. This is exactly why rebasing creates new commits instead of editing the old ones.

**Refs are names for commits**

Remembering forty-character hashes would be miserable, so Git uses refs. A ref is a file whose content is an object ID. Branches live in .git/refs/heads, so the file .git/refs/heads/main contains the ID of the commit at the tip of main. Tags live in .git/refs/tags, and remote-tracking branches live in .git/refs/remotes. Git may also pack refs into a single file called .git/packed-refs for efficiency.

This explains why branches are so cheap. Creating a branch writes a tiny file containing one hash. Making a commit on that branch creates the new commit object, then updates the branch file to point to it. Nothing else moves.

A special file called HEAD records where you currently are. Usually it holds a symbolic reference such as ref: refs/heads/main, meaning you are on the main branch. When you commit, Git follows HEAD to the branch and advances that branch. If HEAD instead contains a raw commit ID, you are in the detached HEAD state, and new commits are not attached to any branch name.

**Putting it together**

When you run git commit, Git takes your staged contents, which live in the index file at .git/index, and writes a blob for every new or changed file. It then builds trees from the bottom up, writes a commit object that points at the root tree and at the previous commit, and finally moves the current branch ref forward.

Every common operation reduces to manipulating these four ideas. Checking out a branch reads a ref, finds a commit, and unpacks its tree into your working directory. Merging creates a commit with two parents. Resetting moves a ref. Once you can picture blobs, trees, commits and refs, you can reason about almost any Git behavior from first principles, and commands like git cat-file and git ls-tree let you verify your understanding directly.

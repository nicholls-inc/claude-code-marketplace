Inside the .git directory, Git is a key-value store where every value is an immutable object and every key is the hash of that object's contents. The objects directory holds these values, and when you run `git add` or `git commit`, Git computes a SHA-1 hash (SHA-256 in repositories created in that mode) over a short header plus the raw content, compresses the content with zlib, and writes it to a file named after the hash. The first two hex characters become a subdirectory and the remaining thirty-eight the filename, so an object whose hash begins `3b18e5` lives at `.git/objects/3b/18e5...`. Because the name is derived from the content, two identical files anywhere in your history, on any branch or in any clone, resolve to the same object and are stored once, and a changed byte produces a completely different name, which is why Git can detect corruption simply by rehashing.

The simplest object is the blob, which holds the bytes of one file and nothing else. It records no filename, no permissions, no timestamp and no path, because those belong to the directory that contains the file. If you rename a file without changing its contents, the blob is untouched and only the surrounding structure changes. The header Git hashes is the word "blob", a space, the byte length and a null byte, followed by the content, which you can reproduce with `git hash-object`, and you can read any object back with `git cat-file -p <hash>`, which is the quickest way to see all of this for yourself.

Names and permissions live in tree objects, which play the role of directories. A tree is a list of entries, each with a mode, a name and the hash of the thing it points to, stored in a compact binary format with the hash as raw bytes rather than hex. The mode says what kind of thing the entry is: 100644 for an ordinary file, 100755 for an executable, 120000 for a symlink, 160000 for a submodule pointer and 040000 for a subdirectory, which is just another tree. A tree for a project with a `src` folder therefore contains blob entries for the top-level files and one tree entry for `src`, whose own tree lists the files inside it, so the whole directory hierarchy is a nested chain of hashes that bottoms out in blobs. Since each tree's hash covers the hashes of everything beneath it, the hash of the top-level tree acts as a fingerprint of the entire project at one moment, and if you edit a single file deep in the hierarchy, only the blob, the trees along the path to the root, and nothing else need to be new, while every untouched subtree is reused as is.

A commit object is small by comparison, a text record made of a few header lines and a message. The first line names the root tree for the snapshot being committed, followed by one `parent` line for each previous commit (none for the first commit, two for a merge), then an author line and a committer line, each with a name, email, Unix timestamp and timezone offset, then a blank line and your commit message. Nothing in it describes a diff, because Git stores snapshots and computes differences on demand by comparing the trees of two commits. The parent hash is part of what gets hashed, so each commit's identity depends on its whole ancestry, and changing anything about an old commit, even its message, yields a new hash and forces every descendant to be rewritten, which is exactly what happens when you rebase or amend and the reason those operations produce new commit hashes instead of editing history in place. History is therefore a directed acyclic graph of commits pointing backward, each commit pointing at one tree, and each tree pointing at blobs and subtrees.

All of that is immutable and addressed by hash, so something mutable is needed to give the graph human-friendly entry points, and that is the job of refs. A branch is a file under `.git/refs/heads` whose entire content is the forty-character hash of the commit at its tip; creating a branch writes one tiny file, and committing on that branch overwrites the file with the new commit's hash, which is why branches are cheap and why moving one is nearly instantaneous. Tags live under `refs/tags` in the same way, and remote-tracking branches under `refs/remotes`. HEAD, the file at `.git/HEAD`, normally holds a symbolic reference such as `ref: refs/heads/main`, meaning that your current branch is main and that a new commit should advance it, whereas in a detached HEAD state the file contains a raw commit hash and new commits advance nothing that a branch name will find, which is why they can become unreachable once you switch away. Annotated tags add one more object type, a tag object carrying a tagger, date and message that points at a commit.

Two practical details complete the picture. The staging area is a binary file named `index` that holds a sorted list of paths with the blob hashes and modes you have staged, and `git commit` builds its tree objects from that list, which is why `git add` has already written blobs into the object store before you commit anything. To keep thousands of loose files from bloating the repository, Git periodically packs objects into packfiles that store similar objects as deltas against one another, and it folds many refs into a single `packed-refs` file, so the layout you find after a `git gc` or a clone looks different from the one described here while following exactly the same model.

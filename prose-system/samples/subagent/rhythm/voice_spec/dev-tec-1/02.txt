Git keeps everything it knows about a project in the .git directory, and most of that is a store of objects. Each object is saved under a name that is the SHA-1 hash of its contents, written as 40 hexadecimal characters. The first two characters become a directory name inside .git/objects and the remaining 38 become the file name, so an object with the hash 3b18e512dba79e4c8300dd08aeb37f8e728b8dad sits at .git/objects/3b/18e512dba79e4c8300dd08aeb37f8e728b8dad. The file holds the object's content compressed with zlib, preceded by a short header giving its type and size. Because the name is derived from the content, two objects with identical content have the same name and are stored once. Git does not store a commit as a diff against the previous one. Each commit refers to a full snapshot of the project, and the compactness comes from sharing unchanged objects between snapshots. There are four object types, and three of them make up a commit.

The first is the blob. A blob holds the bytes of one file and nothing else. It has no file name, no permissions and no timestamp. If you add a file called notes.txt containing the word hello, Git hashes the header "blob 5" followed by a null byte and the five characters of content, and it writes the result as a blob object. If you later copy that file to another directory under a different name, the copy points at the same blob, because the content is the same. Renaming a file therefore costs almost nothing to store, since the content object already exists.

The second is the tree, which stands for a directory. A tree is a list of entries, and each entry has a file mode, a name and the hash of another object. The mode is 100644 for an ordinary file, 100755 for an executable file, 120000 for a symbolic link and 040000 for a subdirectory. An entry for a file points at a blob and an entry for a subdirectory points at another tree. This is where file names live. The tree for the top level of a project might hold a README.md entry pointing at a blob and a src entry pointing at a second tree, and that second tree lists the files inside src. Since a tree is hashed like any other object, its name depends on everything beneath it. Changing one line in src/main.c produces a new blob for that file, a new tree for src because one of its entries now has a different hash, and a new top-level tree because the src entry has changed. Every other blob and tree in the project is untouched and is reused as it is.

The third is the commit object. A commit is a small text record with a handful of fields. The first is the line "tree" followed by the hash of the top-level tree, which identifies the complete state of the project at that moment. Next comes one "parent" line for each earlier commit, giving the hash of the commit it follows. An ordinary commit has one parent, the first commit in a repository has none, and a merge commit has two or more. After the parents come the author and committer lines, each with a name, an email address, a Unix timestamp and a time zone offset, and then a blank line and the commit message. The commit's own hash is computed from all of this text, so it depends on the tree, the parents, the people, the times and the message. Because each commit contains the hash of its parent, the history forms a chain in which altering any earlier commit would change every hash after it. That is why amending or rebasing a commit produces new commits with new names rather than modifying the old ones. The old objects stay in the store until Git's garbage collection removes those that nothing refers to.

Hashes are hard for people to use, and this is the reason for refs. A ref is a file that holds the hash of one commit. Branches are refs stored under .git/refs/heads, so a branch called main is the file .git/refs/heads/main, and it contains one line with 40 characters. Tags are kept in .git/refs/tags in the same way, and remote-tracking branches such as origin/main are kept under .git/refs/remotes. Making a commit writes the new objects and then changes the current branch's file to contain the new commit's hash. That one small write is all that moving a branch forward involves. Creating a branch means writing a new file with the same hash in it. The file called .git/HEAD says which branch is checked out, and it normally holds text such as "ref: refs/heads/main". When you check out a commit directly rather than a branch, HEAD holds a bare hash instead, which is what Git calls a detached HEAD. In larger repositories Git may pack refs into a single file named packed-refs, and it also packs objects into compressed pack files, but the model is the same as before.

You can see all of this with Git's own plumbing commands. Running git cat-file -p HEAD prints the current commit, including its tree line. Running git cat-file -p on that tree hash lists the entries, and running it on a blob hash prints the file's content. Following a commit to its tree, then to the blobs and to its parent, is how Git reads every version of your project.

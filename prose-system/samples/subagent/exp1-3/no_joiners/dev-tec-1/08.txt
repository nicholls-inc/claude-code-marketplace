Inside the .git directory

Every day you run commit, branch and checkout without thinking about what lives on disk. Open the .git directory and you find something surprisingly simple. Git is a content addressed key value store with a handful of object types layered on top. A commit is just a few of those objects pointing at one another, plus a small text file that names the current tip of a branch.

The object database

Inside .git sits a folder called objects. Every piece of data Git stores goes in here as a file. The filename is derived from the SHA hash of the content, so the same content always gets the same name. A hash such as 3b18e512dba79e4c8300dd08aeb37f8e728b8dad is split so that the first two characters become a subdirectory and the remaining thirty eight become the filename. Objects are compressed with zlib, and each one begins with a short header giving its type and its size in bytes. The hash covers that header and the content together.

Because the name comes from the content, objects are immutable. Change one byte and you get a different hash, and therefore a different object. Nothing is ever edited in place. There are four object types, and three of them matter for a commit.

Blobs

A blob holds the raw contents of one file and nothing else. It does not know its filename, its permissions or where it lives in the project. If two files in your repository have identical contents, Git stores a single blob for both. If you copy a large file into a new directory, no extra storage is used. You can see this with the plumbing command git hash-object, which prints the hash Git would assign to a file, and git cat-file with the p flag, which prints an object's content in readable form.

Trees

A tree represents a directory. It is a list of entries, and each entry has a mode, a type, a hash and a name. The mode records whether the entry is a regular file, an executable, a symlink or a subdirectory. The type says blob or tree, and the hash points at the object holding that content. A subdirectory is simply an entry that points at another tree. So the root directory of your project is one tree, which points at blobs for its files and at further trees for its folders, all the way down.

This is where names finally appear. A filename belongs to the tree that contains it, not to the blob. Renaming a file therefore creates a new tree with the same blob hash under a different name. Editing one file in a deep folder creates a new blob, a new tree for that folder, and new trees for every ancestor up to the root, because each parent's content now includes a changed hash. Everything untouched is reused as is. This is why committing is cheap even in a huge repository.

Commit objects

A commit is a small text object with a handful of fields. The first is the hash of the root tree, which is a complete snapshot of the project at that moment. Next come one or more parent lines holding the hashes of the previous commits. A normal commit has one parent, a merge commit has two, and the very first commit has none. Then come author and committer lines, each with a name, an email, a Unix timestamp and a timezone offset. After a blank line comes the message.

Notice what is missing. A commit stores no diff. Git keeps snapshots and calculates differences on demand by comparing two trees. The parent hashes are what turn separate commits into history. Because each commit's hash covers its parents' hashes, the whole chain is tamper evident. Alter an old commit and every descendant gets a new hash.

Run git cat-file with the p flag on HEAD and you will see exactly this layout. It is a dozen lines of plain text.

Refs

If objects are immutable and named by hash, you need a human friendly way to find the latest one. That is the job of refs. A ref is a file whose entire content is a single commit hash. Branches live under .git/refs/heads, so a branch called main is a file at .git/refs/heads/main. Tags live under .git/refs/tags. Remote tracking branches live under .git/refs/remotes. A branch is nothing more than a forty character pointer, which explains why creating one is instant.

When you commit, Git writes the new blob and tree objects, writes the commit object with the current branch tip as its parent, and then overwrites the branch file with the new commit hash. That last step is the only mutation. Everything else is appending new objects.

HEAD

The file .git/HEAD tells Git where you are. Usually it holds a line such as ref followed by refs/heads/main, meaning HEAD points at a branch, and the branch points at a commit. If you check out a specific commit, HEAD instead holds a raw hash, which is the detached state that Git warns you about. It is not an error, only HEAD pointing straight at a commit rather than through a branch, so new commits will not be tracked by any branch name.

The staging area

One more file completes the picture. .git/index is the staging area. When you run git add, Git writes the file as a blob immediately and records its path, mode and blob hash in the index. Running git commit then builds the tree objects from the index, not from your working directory. That is why staged and unstaged changes can differ.

Putting it together

A commit is a chain of references. A branch file names a commit, the commit names a root tree and its parents, the tree names blobs and subtrees, and the blobs hold your bytes. Once you hold that model, rebasing, resetting and cherry picking stop being mysterious. They are just new objects and moved pointers.

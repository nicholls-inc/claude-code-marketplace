Every Git repository keeps its data in a directory called .git, and most of that data sits in a folder inside it called .git/objects. Git works as a key-value store. You give it some content, it computes a SHA-1 hash of that content, and it saves the content under that hash. Three kinds of object stored this way make up a commit: blobs, trees and commit objects. A set of small files called refs then gives the hashes names that a person can remember. Newer repositories can be set up to use SHA-256, which gives longer hashes, but the structure is the same.

A blob holds the contents of one file and nothing else. Git builds it by taking the bytes of the file and putting a short header in front, made of the word blob, a space, the length in bytes and a null byte. It hashes the result, compresses it with zlib and writes it to disk. The hash is 40 hexadecimal characters. The first two become a directory name and the other 38 become the file name, so an object whose hash begins ab12 is stored in a directory called ab. A blob has no file name, no permissions and no timestamp. Two files with identical contents therefore produce the same hash and are stored once, however many places or commits they appear in. If you change one byte of a file, the hash changes completely and Git writes a new blob. The old blob stays where it was.

File names come from trees. A tree object represents one directory and is a list of entries. Each entry has a mode, a name and the hash of the object it points to. The mode is 100644 for an ordinary file, 100755 for an executable, 120000 for a symbolic link and 040000 for a subdirectory. A file entry points to a blob and a subdirectory entry points to another tree, so a snapshot of a whole project is a tree of trees with blobs at the leaves. A tree is hashed in the same way as a blob, so its hash depends on every name, mode and child hash it lists. Changing a file deep in the project changes its blob, which changes the tree of its directory, which changes each tree above it up to the root. Directories that did not change keep their old hashes and are reused as they are. A commit that edits one file therefore adds a handful of small objects to the repository and not a second copy of the project.

A commit object ties a root tree to a point in history. It is a short text record. The first line is the word tree followed by the hash of the root tree. Next come zero or more parent lines, each holding the hash of an earlier commit. The first commit in a repository has none, an ordinary commit has one and a merge has two. An author line and a committer line follow, each with a name, an email address, a Unix timestamp and a time zone offset such as +0100. A blank line comes next, and after it the commit message as you wrote it. The commit is hashed and stored like the other objects. You can read any of them with git cat-file -p and a hash, and git cat-file -t reports whether it is a blob, a tree or a commit.

Because a commit contains the hashes of its parents, and each parent contains the hashes of its own, the hash of a commit depends on all the history behind it. If you alter an old commit, even to fix a typo in the message, it gets a new hash, and every commit after it has to be rewritten with a new hash as well. This is what amend and rebase do. They do not edit objects. They create new ones and then move a name so that it points at them.

Those names are refs. A ref is a plain text file whose content is one commit hash and a newline. A branch called main is the file .git/refs/heads/main, a tag called v1.0 is .git/refs/tags/v1.0, and a remote-tracking branch such as origin/main lives under .git/refs/remotes/origin. When you make a commit, Git writes the new objects and then replaces the hash in the current branch's file with the hash of the new commit. Creating a branch writes a new file of 41 bytes, which is why it is instant. Git also has to know which branch you have checked out, and it records that in .git/HEAD. Usually that file contains the text ref: refs/heads/main, which points at a branch. In a detached HEAD state it holds a commit hash directly. Repositories with many refs may collect them into one file, .git/packed-refs, and Git reads that file when it cannot find a loose ref file.

Two more details complete the picture. The staging area is a binary file, .git/index, that lists the paths, modes and blob hashes planned for the next commit. Git writes the blob for a file when you run git add, and git commit builds the trees from the index. Loose objects also do not stay loose for ever. When there are enough of them, git gc packs them into files under .git/objects/pack and stores similar objects as differences from one another. This is why a repository with years of history is often not much larger than a single checkout of its current files.

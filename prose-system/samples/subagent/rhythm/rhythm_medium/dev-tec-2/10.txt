When you type an HTTPS address into a browser and press enter, the browser first has to work out what you actually asked for. It parses the address into a scheme, a hostname, an optional port, a path and a query string, and it checks whether the hostname appears on its built-in HSTS preload list or in its cache of earlier Strict-Transport-Security headers. If so, the browser will refuse to use plain HTTP for that site at all. It also checks its own caches in case a fresh copy of the resource is already stored, in which case the network may not be needed and the response can come back almost instantly.

If the browser needs the network, it must turn the hostname into an IP address, and this is the job of the Domain Name System. The browser looks in its own DNS cache, then asks the operating system, which may have its own cache or a hosts file entry. If neither knows the answer, the request goes to a recursive resolver, usually run by your internet provider or a public service. That resolver either answers from its cache or walks the hierarchy of the DNS. It asks a root server which servers handle the top-level domain, asks those which servers are authoritative for the domain, and finally asks an authoritative server for the address records. Each answer carries a time-to-live value that says how long it may be cached, which is why changes to DNS records can take a while to spread. Modern browsers may also use encrypted DNS and may ask for IPv6 and IPv4 addresses at the same time.

With an IP address in hand, the browser opens a connection. For traditional HTTPS over HTTP/1.1 or HTTP/2, that means a TCP connection, which begins with the three-way handshake. The client sends a SYN packet, the server replies with SYN-ACK, and the client answers with an ACK. This costs one full round trip before any useful data can flow, so physical distance to the server matters here. If several addresses are available, the browser often races them and keeps whichever connects first, a technique usually called Happy Eyeballs. Browsers also reuse existing connections to the same origin where they can, which skips most of this work on later requests.

Next comes the TLS handshake, which is what makes the connection secure. The client sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, a key share for key exchange, and the server name it wants through the Server Name Indication extension. That extension lets one IP address host many different sites. The server replies with its chosen parameters, its own key share and its certificate chain. In TLS 1.3, both sides can derive shared session keys after this single exchange, and everything after the server's first reply is encrypted. Older TLS 1.2 needed an extra round trip. The key exchange uses ephemeral Diffie-Hellman, which gives forward secrecy, meaning a stolen server key cannot be used to decrypt traffic recorded earlier.

During this handshake the browser verifies the server's identity, and this step is easy to overlook. It checks that the certificate chain leads up to a certificate authority the browser or operating system trusts, that each certificate is within its validity dates, and that the hostname you asked for matches a name listed in the certificate. It also checks that the certificate has not been revoked, using mechanisms such as stapled OCSP responses or compressed revocation lists, and it may verify that the certificate appears in public Certificate Transparency logs. The server proves it holds the matching private key by signing part of the handshake. If any check fails, the browser stops and shows the familiar certificate warning instead of continuing. When a client has connected to the server before, TLS session resumption can shorten the handshake, and in some configurations the client can even send request data in the very first flight, although that early data carries some replay risks.

Once the secure channel exists, the browser builds the HTTP request. At minimum it contains a method such as GET, the path and query, and headers including Host, User-Agent, Accept, Accept-Encoding and Accept-Language. It also attaches any cookies that match the domain and path, and it may add cache validators like If-None-Match so the server can answer with a short 304 response if nothing has changed. Under HTTP/2 the request is converted into compressed binary frames sent on a numbered stream, which allows many requests to share one connection. Under HTTP/3, the browser instead speaks QUIC over UDP, which folds the transport and encryption handshakes together and avoids some head-of-line blocking. A browser typically learns that a site supports HTTP/3 from an Alt-Svc header on an earlier visit or from DNS records, so a first visit usually still uses TCP.

The encrypted request then travels across the internet, often passing through a CDN edge server or a load balancer before it reaches the machine that actually runs your application. These intermediaries may terminate TLS themselves, serve a cached copy, or route the request onward to an origin server. The origin may run a web server that passes the request to application code, which can query a database, call other services and render a page or a JSON payload. All of that work happens before any response exists, and it is often the largest part of the wait you see in developer tools.

Finally the server writes its response, starting with a status line and headers, and the first byte of that reply travelling back to the browser is the moment measured as Time To First Byte. You can see most of the stages above in the Network panel's timing breakdown, which separates DNS lookup, initial connection, SSL, request sent and waiting for the server. Knowing where the time goes tells you whether to fix slow DNS, add a CDN closer to users, enable keep-alive and HTTP/2, or speed up your own backend code.

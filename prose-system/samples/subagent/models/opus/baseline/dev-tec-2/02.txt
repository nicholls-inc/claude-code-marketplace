From Address Bar to First Byte: What Happens When You Load an HTTPS URL

When you type https://example.com/products into a browser and press Enter, a lot happens before the server sends even one byte back. Most of it takes milliseconds, and most of it is invisible in your code. It still decides how fast your pages feel, and knowing the steps makes the Network panel in DevTools much easier to read. Here is the sequence in order.

1. Parsing the input

First, the browser decides whether you typed a URL or a search query. If it is a URL, the browser splits it into parts: the scheme (https), the host (example.com), the port (443 by default for HTTPS), the path (/products), and any query string or fragment. The fragment (the part after #) is never sent to the server. It stays in the browser.

Before going to the network, the browser checks its HSTS (HTTP Strict Transport Security) list. If the site has told the browser before, or is on the preloaded list that ships with the browser, that it must only be reached over HTTPS, any http:// address is upgraded to https:// in the browser itself. No insecure request is ever sent.

2. Checking caches before the network

A network request is the slowest option, so the browser looks for a shortcut first. If a service worker is registered for the origin, it gets the request first and can answer from its own cache without using the network. If not, the browser checks its HTTP cache. A stored response that is still fresh under its Cache-Control or Expires headers can be used at once, and the rest of this process is skipped. A stale entry may still lead to a conditional request (If-None-Match or If-Modified-Since). That request still goes through the steps below, but the server can answer with a small 304 Not Modified instead of the full body.

The browser also checks whether it already has an open connection to this origin. If it does, steps 3 to 5 are skipped, which is why the second request to a site is usually much faster than the first.

3. DNS resolution: finding the server's address

Computers connect to IP addresses, not names, so the browser has to turn example.com into an address such as 93.184.215.14 (IPv4) or an IPv6 address. It tries the fastest sources first:

- The browser's own DNS cache.
- The operating system's resolver cache, which also reads the hosts file.
- A recursive resolver, usually run by your ISP, your company, or a public service such as 1.1.1.1 or 8.8.8.8. Many browsers can send this query over HTTPS (DNS-over-HTTPS) so others on the network cannot read it.

If the recursive resolver does not have the answer cached, it works through the DNS hierarchy. It asks a root server, which points to the servers for .com. Those point to the authoritative name servers for example.com, which return the actual records. Each answer has a TTL (time to live) that says how long it can be cached.

Modern browsers often also request an HTTPS-type DNS record. It can tell the browser in advance that the server supports HTTP/3, which can save a round trip later.

4. Opening a transport connection

With an IP address, the browser opens a connection to port 443. With classic HTTP/1.1 or HTTP/2, this is a TCP connection, set up with the three-way handshake:

1. The client sends SYN ("I want to connect").
2. The server replies SYN-ACK ("OK, I acknowledge").
3. The client sends ACK, and the connection is open.

This costs one full round trip between you and the server. If the server is 100 ms away, that is 100 ms before anything useful happens. This is a big reason why CDNs, which place servers close to users, make sites faster.

If the browser knows the server supports HTTP/3, it uses QUIC instead. QUIC runs over UDP and combines the transport and encryption handshakes, so it needs fewer round trips. Browsers also often race IPv6 and IPv4 connection attempts against each other ("Happy Eyeballs") and keep whichever succeeds first.

5. The TLS handshake: making the connection secure

The "S" in HTTPS is TLS (Transport Layer Security). Before any HTTP data is sent, client and server must agree on encryption keys, and the browser must check that it is really talking to example.com. With TLS 1.3, the current version, it goes like this:

- ClientHello: the browser sends the TLS versions and cipher suites it supports, a key share for the key exchange, the hostname it wants (SNI, Server Name Indication, so one IP address can host many sites), and the application protocols it supports (ALPN, for example h2 for HTTP/2 or http/1.1).
- ServerHello and the rest: the server picks the parameters, sends its own key share, and sends its certificate, a signature that proves it holds the certificate's private key, and a Finished message. From the key shares, both sides now derive the same secret keys without ever sending those keys over the network.
- Certificate validation: the browser checks that the certificate covers example.com, that it has not expired, and that it chains back to a certificate authority the browser or operating system trusts. If any check fails, you see a full-page security warning and the request stops.
- The browser sends its own Finished message, and the encrypted channel is ready.

TLS 1.3 needs one round trip on top of the TCP handshake (TLS 1.2 needed two). When resuming a recent session, it can sometimes send data in the very first flight ("0-RTT"). ALPN has also settled which HTTP version will be used.

6. Sending the HTTP request

Now the browser sends the actual request over the encrypted connection:

GET /products HTTP/2
Host: example.com (sent as the :authority pseudo-header in HTTP/2 and HTTP/3)
User-Agent, Accept, Accept-Encoding, Accept-Language
Cookie: any cookies stored for this origin
Plus conditional headers (If-None-Match and similar) if revalidating a cached copy

In HTTP/2 and HTTP/3, headers are compressed, and many requests can share one connection as separate streams, so later requests for CSS, JS and images do not need their own handshakes.

7. Server-side processing

The request may pass through several systems before your application code sees it: a CDN edge, a load balancer, and a reverse proxy such as Nginx. TLS is often terminated at one of these, and the request travels on to your backend over an internal network. A CDN may answer straight from its cache. Otherwise your application runs: routing, authentication, database queries, template rendering. Only when the server has the status line and headers ready does it start sending the response.

8. The first byte arrives

The response goes back over the same connection, encrypted, and the browser decrypts it. The moment the first byte arrives marks Time to First Byte (TTFB). In DevTools, the Timing tab for a request breaks this time into the steps above: Queueing, DNS Lookup, Initial connection, SSL, and Waiting for server response.

What this means for you

For a first visit to a distant server, DNS, TCP and TLS together can easily cost several hundred milliseconds before your server does any work. You can reduce this with:

- Connection reuse and HTTP/2 or HTTP/3, so one handshake serves many requests.
- A CDN, so the round trips are short.
- Resource hints: <link rel="preconnect" href="https://api.example.com"> tells the browser to do DNS, TCP and TLS ahead of time for an origin you know you will need. <link rel="dns-prefetch"> does just the DNS step.
- Good caching headers, so many requests never reach the network at all.
- Fast backend responses. After the network setup, "Waiting for server response" is the part your own code controls most directly.

Once you know these steps, a slow request in the Network panel stops being one unexplained number. You can see which step is slow and what to change.

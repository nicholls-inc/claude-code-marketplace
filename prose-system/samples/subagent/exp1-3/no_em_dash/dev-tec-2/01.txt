From HTTPS Address to First Byte: What the Browser Does

When you type https://www.example.com/products into a browser and press Enter, a lot happens before the first byte of the response arrives. Most of it takes only tens of milliseconds, but each step can fail or slow down, so knowing the sequence helps you debug real problems. The steps are: parsing the URL, checking caches, resolving the name, opening a TCP connection, negotiating TLS, sending the request, and waiting for the server.

1. Parsing the URL

The browser first splits the address into parts. The scheme is https, the host is www.example.com, the port is implied (443 for HTTPS), and the path is /products. Any query string or fragment is separated too. The fragment (the part after #) never leaves the browser. It is only used locally after the page loads.

The browser also checks its HSTS list. HSTS (HTTP Strict Transport Security) is a header a site sends to say "only ever talk to me over HTTPS." If you typed http://example.com and the site is on that list, the browser upgrades the request to HTTPS itself, skipping an insecure round trip.

2. Checking caches

Before touching the network, the browser looks in its HTTP cache. If it holds a fresh copy of the resource, as allowed by headers like Cache-Control: max-age, it can answer immediately and no network request is made. If the copy is stale, the browser may still use it as the basis for a conditional request later, sending validators such as an ETag. The rest of this description assumes a cache miss.

Service workers, if the site registered one, can also intercept the request at this point and answer from their own storage.

3. DNS resolution

Networks route by IP address, not by name, so the browser must turn www.example.com into an address like 93.184.216.34. This is DNS (Domain Name System) resolution. Several caches are checked in order: the browser's own DNS cache, then the operating system's cache and hosts file, then a configured recursive resolver, usually run by your ISP, your company, or a public provider.

If the resolver does not know the answer, it works through the hierarchy. It asks a root server which servers handle .com, asks those which servers are authoritative for example.com, and asks the authoritative server for the record of www.example.com. The answer comes with a TTL (time to live) that tells every cache how long it may reuse the result. The browser may receive A records (IPv4), AAAA records (IPv6), or a CNAME that points to another name and needs further lookups.

A cold lookup can cost tens of milliseconds or more; a cached one costs almost nothing. Modern browsers can also use encrypted DNS (DNS over HTTPS), which hides the lookup from the local network but follows the same logic.

4. Opening a TCP connection

With an IP address, the browser needs a reliable channel to the server. If it already has an open connection to this host, for example from an earlier request, it reuses it and skips to step 6. Otherwise it opens a TCP connection using the three-way handshake. The client sends a SYN, the server replies with SYN-ACK, and the client answers with ACK. This costs one full round trip, and the round trip time (RTT) between you and the server sets how long it takes. A server 100 ms away costs you at least 100 ms here, regardless of how fast either machine is.

When several IP addresses are available, browsers often try IPv6 and IPv4 nearly in parallel and use whichever connects first (called "Happy Eyeballs").

Note that HTTP/3 does not use TCP. It runs over QUIC, which uses UDP and combines the transport and encryption handshakes. A browser learns that a server supports HTTP/3 from an Alt-Svc header or an HTTPS DNS record, so the first visit usually uses TCP and later visits can use QUIC.

5. The TLS handshake

HTTPS means HTTP carried inside TLS (Transport Layer Security). Before any request is sent, the browser and server must agree on how to encrypt traffic and the browser must confirm it is talking to the real example.com.

In TLS 1.3, the common modern version, this takes one round trip:

- The client sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, a key share (its half of a key exchange), and the Server Name Indication (SNI). SNI is the hostname, sent so a server hosting many sites on one IP knows which certificate to present. It may also include ALPN, a list of protocols it can speak, such as h2 and http/1.1.
- The server replies with its choice of cipher suite, its own key share, and its certificate. From the two key shares, both sides independently compute the same shared secret without ever sending it. Everything after this point is encrypted.
- The server proves it holds the certificate's private key by signing the handshake. Both sides send Finished messages, and application data can flow.

The certificate check is the important security step. The browser verifies that the certificate covers the requested hostname, has not expired, and chains up through intermediate certificates to a certification authority (CA) that the browser or operating system already trusts. It may also check revocation status. If any check fails, you see the full-page certificate warning, and no request is sent.

TLS 1.2 needs two round trips instead of one. If the browser has connected before, TLS session resumption can shorten this further, and TLS 1.3 can even send early data in the first flight, though that has replay risks and is limited to safe requests.

6. Sending the HTTP request

Now the browser sends the request through the encrypted connection. ALPN has already chosen the protocol, typically HTTP/2 or HTTP/3. In HTTP/1.1 terms, the request looks like this:

GET /products HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

HTTP/2 and HTTP/3 carry the same information in a binary format with header compression, and the host appears as the :authority pseudo-header. The browser attaches cookies it holds for this site, so a request often carries login state automatically. It also adds headers for compression support, language, and a user agent string.

7. Waiting for the server

The request reaches the server, though often not the "real" application server first. It commonly hits a CDN edge or load balancer, which may terminate TLS, answer from its own cache, or forward the request to an origin. The origin application then routes the path, runs your code, queries databases, and builds the response. All of this time counts toward the wait.

The measurement of interest is TTFB (time to first byte): the time from starting the request until the first byte of the response arrives. It is the sum of everything above, which is why it varies so much. In rough terms:

TTFB = DNS + TCP + TLS + request transit + server processing + response transit

The first byte is usually the beginning of the status line and headers, for example HTTP/2 200. Redirects restart much of this process. A 301 response to a different host means another DNS lookup, connection, and handshake before you see the content you wanted.

Where to look when it is slow

The browser's developer tools make this visible. In the Network panel, select a request and open the Timing tab. You will see stalled or queued time, DNS lookup, initial connection, SSL (the TLS handshake), request sent, waiting for server response (this is the server's share of TTFB), and content download. Reading these phases tells you where to act:

- Long DNS time: use a faster DNS provider or longer TTLs.
- Long connection or TLS time: serve from locations closer to users with a CDN, enable keep-alive and connection reuse, and use TLS 1.3 or HTTP/3.
- Long waiting time: the problem is on the server, such as slow queries, missing caching, or cold starts.

A useful habit for a developer is to remember that these costs are paid per new connection, not per request. Reusing connections, caching aggressively, and avoiding needless redirects remove whole steps from the path before the first byte even has a chance to be late.

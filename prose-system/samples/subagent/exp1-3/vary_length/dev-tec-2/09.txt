From HTTPS address to first byte

You type https://shop.example.com/cart into the address bar and press Enter. A fraction of a second later, the first byte of the response shows up. In between, the browser does a surprising amount of work, and most of it happens before your server even hears about the request. Here is the sequence.

1. Parsing the address

The browser first splits the URL into parts. The scheme is https, the host is shop.example.com, the path is /cart, and the port is implied: 443 for HTTPS. It also checks a built-in list called the HSTS preload list. If the site is on it, the browser will never try plain HTTP, even if you typed http://. It silently upgrades the request.

2. Checking caches

Before touching the network, the browser asks whether it already has what it needs. It looks in its HTTP cache for a fresh copy of the page. It may also have a saved DNS answer, an open connection to the same host, or a stored TLS session. Any hit skips whole steps below. This is why a second visit to a site feels faster than the first.

3. DNS lookup

Computers talk to each other with IP addresses, not names. So the browser must translate shop.example.com into something like 203.0.113.42. This is DNS.

The browser checks its own cache, then asks the operating system, which checks its cache and its hosts file. If neither knows, the OS sends a query to a recursive resolver, usually run by your ISP or a public provider. The resolver may already have the answer. If not, it walks the hierarchy: a root server points to the .com servers, which point to example.com's authoritative name server, which finally returns the address. Each answer carries a time-to-live (TTL) that says how long it may be cached.

Queries normally travel over UDP port 53, because the exchange is small and speed matters. Modern browsers may use DNS over HTTPS instead, which hides the lookup from onlookers. Either way, this step can cost anywhere from zero to a few dozen milliseconds. Cached? Zero. A cold lookup across several servers? Noticeable.

Note too that a name can return several addresses, including IPv6 ones. Browsers often try them in parallel and keep whichever connects first.

4. Opening a TCP connection

With an IP address in hand, the browser opens a connection to port 443. TCP does this with a three-step handshake. The client sends a SYN. The server replies with SYN-ACK. The client answers with ACK. Only then can data flow reliably and in order.

This costs one round trip: the time for a packet to reach the server and for the reply to return. If the server is 50 ms away, that is about 50 ms of pure waiting. Nothing you write in your application code can shorten the speed of light, which is why round trips are the currency of web performance.

HTTP/3 changes this picture. It runs over QUIC, which uses UDP and folds the transport and encryption handshakes together. The browser learns that a site supports it from an earlier response header (Alt-Svc) or from DNS records, so the very first visit usually still uses TCP.

5. The TLS handshake

The connection is open, but it is not private yet. The "S" in HTTPS means the browser now negotiates encryption using TLS.

In TLS 1.3, the client sends a ClientHello listing the cipher suites it supports, a random value, a key share for the key exchange, and the server name it wants (the SNI field, so a server hosting many sites knows which certificate to present). The server answers with its choice of cipher, its own key share, and its certificate. Both sides can now compute the same shared secret without ever sending it across the wire. That is the magic of the key exchange. Everything after this point is encrypted.

The certificate matters for trust. The browser checks several things:

- The certificate names shop.example.com.
- It has not expired.
- It was signed by a certificate authority the browser trusts, directly or through a chain of intermediates.
- It has not been revoked.

If any check fails, you see the full-page warning. Do not tell users to click through it.

TLS 1.3 needs one round trip. Older TLS 1.2 needed two. If the browser has talked to this server recently, session resumption can shorten the handshake further, and 0-RTT lets some data ride along with the very first message, though with replay risks that make it unsuitable for requests that change state.

6. Sending the HTTP request

Now, finally, the browser speaks HTTP. A request looks roughly like this:

GET /cart HTTP/1.1
Host: shop.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The method (GET) and path say what you want. The Host header says which site. Accept-Encoding advertises compression the browser understands. Cookies for that domain are attached automatically. With HTTP/2 or HTTP/3, the same information is sent in a compact binary form instead of text, and many requests can share one connection at once.

7. The server works

The request arrives at the server, often first at a load balancer or CDN edge. A CDN may answer straight from its cache, which is the fastest outcome. Otherwise the request is forwarded to your application. A web server hands it to your code, your code may query a database, render a template, and build a response.

All of this time is called server think time. When the response begins, the first byte leaves the server and travels back. The browser's clock for this stretch is called Time to First Byte, or TTFB.

Putting numbers on it

Suppose the server is 50 ms away and nothing is cached. DNS might take 30 ms. TCP takes one round trip, 50 ms. TLS 1.3 takes another 50 ms. The request and the first byte of the reply take a further 50 ms plus whatever the server spends thinking, say 80 ms. That is roughly 260 ms before anything appears. Cut any step and the total drops.

What you can influence

As a developer you rarely control DNS or the speed of light, but you do control a few things:

- Serve from a nearby edge with a CDN, which shrinks every round trip.
- Reuse connections with keep-alive, HTTP/2 and HTTP/3 so later requests skip steps 3 to 5.
- Cache responses with sensible Cache-Control headers.
- Keep your server fast. Slow database queries show up directly in TTFB.
- Use preconnect and dns-prefetch hints for origins you know you will need.

Next time a page feels slow, open the Network panel in your browser's developer tools and expand a request's timing breakdown. It shows these exact stages: DNS lookup, initial connection, SSL, request sent, and waiting for the first byte. Once you can read that chart, you know where to look.

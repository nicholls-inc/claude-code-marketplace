## How Git Stores a Commit

Every day you run `git add` and `git commit`. Underneath, Git is a content-addressable key-value store: you give it content, it hands back a key derived from that content, and everything else is built from that idea. Open `.git/objects` and you will find the whole mechanism. There are four things to understand: blobs, trees, commits and refs.

### Objects and hashes

Git stores data as objects. Each object is identified by a hash (SHA-1 by default, SHA-256 in newer repositories) of its type, size and content. The identifier is computed from the content, so identical content always produces the same ID, and changing a single byte produces a different one. Objects are compressed with zlib and written to `.git/objects/ab/cdef...`, where the first two hex characters become a directory name. Over time Git also packs many objects into `.git/objects/pack/` files and stores similar objects as deltas, but the logical model is unchanged.

Objects are immutable. Git never edits one. It only adds new ones.

### Blobs: file contents

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no timestamp. If two files in your repository have identical contents, they share a single blob. If you rename a file without changing it, no new blob is created.

You can create one by hand:

```
$ echo "hello" | git hash-object -w --stdin
ce013625030ba8dba906f756967f9e9ca394464a
$ git cat-file -p ce01362
hello
```

`git add` does essentially this for each file you stage, and it records the result in the index (`.git/index`), the staging area.

### Trees: directories

A tree object is a directory listing. Each entry holds a file mode, a type, a hash and a name:

```
$ git cat-file -p HEAD^{tree}
100644 blob 8f94139...  README.md
040000 tree a1b2c3d...  src
100755 blob 5e6f7a8...  build.sh
```

Filenames and permissions live here, not in blobs. A subdirectory is another tree, referenced by hash, so the structure is recursive: the root tree points to blobs and to other trees, forming a complete snapshot of your project at one moment.

Because hashes cover content, trees give Git cheap change detection. If you edit one file deep in `src/lib/`, that blob gets a new hash, so its parent tree gets a new hash, and so on up to the root tree. Every subtree that did not change keeps the same hash and is reused. A commit therefore costs roughly one blob plus one tree per directory level on the changed path, not a copy of the repository.

### Commits: snapshots with history

A commit object ties a root tree to history:

```
$ git cat-file -p HEAD
tree 9c2e4b1f...
parent 3d5a7e90...
author Ada <ada@example.com> 1730000000 +0000
committer Ada <ada@example.com> 1730000000 +0000

Fix off-by-one in pagination
```

It contains:

- the hash of the root tree (the snapshot),
- zero or more parent commit hashes (none for the first commit, two or more for merges),
- author and committer identity with timestamps,
- the message.

Git stores snapshots, not diffs. When `git show` displays a patch, it computes the difference between the commit's tree and its parent's tree on the fly.

Since a commit's hash covers its parent hash, each commit cryptographically commits to the entire history before it. That is why rewriting history (`rebase`, `commit --amend`) produces new commits with new hashes: the old ones are not modified, they are simply abandoned. Amending gives you a different commit that nothing yet points to the old one from.

### Refs: human-readable names

Hashes are hard to remember, so Git uses refs, which are named pointers to objects. They are plain files under `.git/refs/`:

```
$ cat .git/refs/heads/main
9f3c1a2e8b7d...
```

A branch is only a file containing a 40-character commit hash. Creating a branch writes one small file. Committing on a branch writes a new commit object whose parent is the current tip, then updates that file to the new hash. That is all "advancing a branch" means. Tags work the same way under `refs/tags/`. Remote-tracking branches such as `origin/main` live under `refs/remotes/`. (Git may later consolidate refs into `.git/packed-refs` for efficiency.)

`HEAD`, at `.git/HEAD`, says where you are. Normally it is a symbolic ref:

```
$ cat .git/HEAD
ref: refs/heads/main
```

So HEAD points at a branch, and the branch points at a commit. In "detached HEAD" state, the file contains a commit hash directly.

### Putting it together

When you run `git commit`, Git:

1. Builds tree objects from the index, reusing existing ones where nothing changed (blobs were already written at `git add` time).
2. Writes a commit object referencing the root tree and the current HEAD commit as parent.
3. Moves the branch ref that HEAD points to so it names the new commit.

The result is a graph. Refs point to commits, commits point to parents and to a root tree, trees point to subtrees and blobs. Reachability from a ref is what keeps objects alive. Commits that no ref reaches (after a reset or rebase) are unreachable and are eventually removed by garbage collection, though `git reflog` can usually recover them for a while.

### Try it

`git cat-file -p <hash>` prints any object, and `git cat-file -t <hash>` prints its type. Start with `git cat-file -p HEAD`, follow the `tree` line, then follow a blob. Once you have walked that chain yourself, commands like `reset`, `rebase` and `cherry-pick` stop being magic: each one just builds new objects and moves refs.

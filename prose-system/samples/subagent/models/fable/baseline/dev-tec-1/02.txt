# How Git stores a commit

Every `git commit` you run writes a handful of small files into `.git/objects` and then updates one more file to point at them. Git has three object types that matter here (blobs, trees and commits), plus refs, which are the names you use to find them.

## The object store

Git's database is a key-value store in `.git/objects`. The value is an object's content. The key is a hash of that content: SHA-1 by default, written as 40 hex characters. To store an object, Git prepends a short header (the type and the size in bytes), hashes the result, compresses it with zlib, and writes it to a file named after the hash. The first two characters become a directory and the remaining 38 the filename, so object `8ab686ea...` lives at `.git/objects/8a/b686ea...`.

Because the key is derived from the content, two properties follow:

- **Objects are immutable.** Changing one byte gives a different hash, which is a different object. Nothing is ever edited in place.
- **Identical content is stored once.** If the same file appears in a thousand commits, or at two paths in one commit, there is one object.

You can inspect any object with `git cat-file -p <hash>`, and ask its type with `git cat-file -t <hash>`.

## Blobs: file contents

A blob holds the bytes of one file and nothing else. It has no filename, no permissions and no timestamp. Two files with the same contents, anywhere in the repository's history, share a blob.

Blobs are created by `git add`, not by `git commit`. Staging a file writes its blob to the object store and records the blob's hash against the path in the index (`.git/index`). By the time you commit, the file contents are already stored.

## Trees: directories

A tree represents one directory. It is a list of entries, each with a mode, a type, a hash and a name:

```
100644 blob a906cb2a4a904a152e80877d4088654daad0c859    README.md
100755 blob 8f94139338f9404f26296befa88755fc2598c289    build.sh
040000 tree 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0    src
```

This is where filenames live. An entry pointing to a blob is a file; an entry pointing to another tree is a subdirectory. The mode records the little that Git tracks about permissions: regular file (`100644`), executable (`100755`) or symlink (`120000`).

The tree for the repository's root directory therefore describes the whole project at one moment, recursively. Since a tree's hash depends on the hashes of everything beneath it, the root tree's hash identifies the exact contents of every file in the project.

It also makes snapshots cheap. If a commit changes one file in `src/`, Git writes a new blob, a new tree for `src` and a new root tree. Every unchanged file and directory is referenced by its existing hash.

## Commit objects: a snapshot plus context

A commit object is a few lines of text:

```
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 1a410efbd13591db07496601ebc7a059dd55cfe9
author Ada Lovelace <ada@example.com> 1762850000 +0000
committer Ada Lovelace <ada@example.com> 1762850000 +0000

Fix off-by-one in pagination
```

It contains:

- **One tree hash**: the root tree, which is the full snapshot of the project.
- **Zero or more parent hashes**: none for the first commit, one for an ordinary commit, two or more for a merge.
- **Author and committer**, each with a timestamp. They differ after operations such as a rebase or cherry-pick.
- **The commit message.**

A commit does not store a diff. It stores a pointer to a complete snapshot, and the diff you see in `git show` is computed on demand by comparing the commit's tree with its parent's tree.

The parent pointers are what form history. Because a commit's hash covers its parent hashes, it covers the whole chain behind it. That is why you cannot change an old commit without changing the hash of every commit after it, and why `git commit --amend` and `git rebase` produce new commits instead of modifying existing ones.

## Refs: names for hashes

Nothing so far involves a branch name. A ref supplies one: it is a file containing a commit hash. The branch `main` is the file `.git/refs/heads/main`, and its entire content is 40 hex characters and a newline. Tags live in `.git/refs/tags`, and remote-tracking branches in `.git/refs/remotes`.

`HEAD` is the file `.git/HEAD`, and it usually points at a ref instead of a hash:

```
ref: refs/heads/main
```

That line is what "being on main" means. If you check out a commit directly, `HEAD` contains a raw hash, which is the detached HEAD state.

This is why creating a branch is instant: Git writes one small file. A branch is a movable pointer to a commit, not a copy of anything.

## What `git commit` does

1. Git builds tree objects from the index, one per directory, and writes any that do not already exist.
2. It writes a commit object pointing at the root tree, with the commit `HEAD` currently resolves to as its parent.
3. It writes the new commit's hash into the ref that `HEAD` points to, moving the branch forward.

## Two caveats when you go looking

Git periodically packs objects: `git gc` combines loose objects into packfiles under `.git/objects/pack`, where they are delta-compressed against each other. Refs can likewise be collected into a single `.git/packed-refs` file. If the file you expect is not there, the object or ref still exists, and `git cat-file` and `git rev-parse` will find it either way.

From HTTPS address to first byte

You type https://www.example.com/products into the address bar and press Enter. Perhaps a second later, the page starts to appear. In that time, the browser and several other systems have exchanged a surprising number of messages. Here is what happens, in order.

1. Parsing the URL

The browser first splits the address into parts. The scheme is https. The host is www.example.com. The port is not written, so it defaults to 443, the standard HTTPS port. The path is /products. Nothing leaves your machine yet. The browser is only working out what it is being asked to fetch.

It then makes a few quick local decisions. If the site is on the browser's HSTS list, which records sites that must only be reached over HTTPS, the browser will refuse to fall back to plain HTTP. It also checks whether it already holds a fresh cached copy of the resource. If it does, the network may not be needed at all. Assume it is not cached.

2. Finding the IP address (DNS)

Networks route traffic by IP address, not by name, so www.example.com must be translated into a number such as 93.184.216.34. This is the job of the Domain Name System, DNS.

The browser looks in its own DNS cache first. If that fails, it asks the operating system, which checks its cache and its hosts file. If that also fails, the OS sends a query to a recursive resolver. This is usually run by your ISP, your company, or a public provider. The resolver does the hard work. If it does not already know the answer, it asks a root server, then the server for .com, then the authoritative server for example.com. Each step narrows the search. The answer comes back with a time-to-live (TTL), which tells every cache along the way how long it may reuse the result.

DNS is often the first slow step on a cold visit. It is also invisible, so developers forget about it. A DNS lookup can take a few milliseconds if cached nearby, or well over a hundred if it is not.

Modern browsers may also receive HTTPS or SVCB records, which can announce that the server supports HTTP/3 and other details. For now, treat DNS as returning one or more IP addresses.

3. Opening a TCP connection

Now the browser knows where to go. It picks an address and opens a TCP connection to port 443. TCP provides reliable, ordered delivery on top of an unreliable network, and it begins with a three-step handshake. The browser sends a SYN. The server replies with SYN-ACK. The browser answers with ACK. Only then can data flow.

This costs one full round trip: a message to the server and a reply back. Round trips are the currency of network performance. If the server is 80 ms away, each round trip costs roughly 80 ms, no matter how fast your connection is. Bandwidth does not help here. Only distance, and fewer round trips, do.

(If the browser and server use HTTP/3, this step changes. HTTP/3 runs over QUIC, which uses UDP and folds the transport and encryption handshakes together. The goals are the same, but it saves a round trip.)

4. The TLS handshake

The connection exists, but it is not yet secure. HTTPS means HTTP carried inside TLS, and TLS must be set up before any request is sent. Three things need to happen: the two sides agree on how to encrypt, the browser verifies who it is talking to, and both derive a shared secret key.

In TLS 1.3, the current version, this takes one round trip. The browser sends a ClientHello. It lists the cipher suites it supports, the TLS versions it accepts, and a key share, which is its half of a key exchange. It also includes the server name, www.example.com, in an extension called SNI. SNI matters because one IP address often hosts many sites, and the server needs to know which certificate to present.

The server replies with a ServerHello containing its own key share. At this point both sides can compute the same secret key without ever having sent it over the wire. This is the idea behind Diffie-Hellman key exchange. The rest of the server's reply is already encrypted. It includes the server's certificate and a signature that proves it holds the matching private key.

The browser then checks the certificate. Is it signed by a certificate authority the browser trusts, directly or through a chain? Has it expired? Does the name on it match www.example.com? Has it been revoked? If any check fails, the browser stops and shows a warning page. This is the step that stops someone on the same Wi-Fi network from pretending to be your bank.

Finally the browser sends a Finished message, and both sides switch to encrypted traffic. If you have connected to this server recently, session resumption can shorten the process further. TLS 1.3 even allows 0-RTT data, where a returning client sends its request alongside the handshake. That feature has trade-offs, because such early data can be replayed by an attacker, so servers restrict it to safe requests.

5. Sending the HTTP request

The secure channel is ready. The browser now writes out the request. In HTTP/1.1 it is plain text and looks like this:

GET /products HTTP/1.1
Host: www.example.com
User-Agent: ...
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=abc123

The method says what to do. The path says to what. Headers add context, including any cookies the browser has stored for this site. With HTTP/2 and HTTP/3 the same information is sent in a compact binary form, and many requests can share a single connection. The meaning is identical.

All of this is encrypted by TLS before it leaves your machine. Anyone watching the network sees only that you are talking to this IP address, roughly how much data moves, and, thanks to SNI in most cases, the hostname. They do not see the path, the headers or the cookies.

6. Travelling to the server, and what happens there

Your request crosses many routers on its way. It may not reach the origin server directly. Large sites put a CDN or a load balancer in front. A nearby edge server may answer from its own cache, which is far faster than a long trip to the origin. Or it may forward the request to an application server.

If it reaches the application, work begins. The server decodes the request and routes /products to a handler. The handler might check the session cookie, query a database, call other services and render HTML. Any of these can be slow, and this is the part you, as a developer, control the most.

7. The first byte

Eventually the server starts to write its response, beginning with a status line such as HTTP/1.1 200 OK, then headers, then the body. The moment the first byte of that response reaches the browser is called Time to First Byte, or TTFB. It is a useful number because it captures everything above in one measurement.

Roughly, TTFB is the sum of DNS lookup, TCP connect, TLS handshake, request travel time and server processing time, plus the trip back. On a cold connection with a distant server, the network setup can easily cost more than the server's own work. On a reused connection, DNS, TCP and TLS are all skipped, which is why keep-alive and HTTP/2 connection reuse help so much.

What to take away

Before a single byte of your page arrives, the browser has resolved a name, opened a connection, verified an identity and agreed on a secret key. Each step has a cost measured mostly in round trips. When a page feels slow to start, you can now ask a precise question: which of these steps is taking the time? The Network panel in your browser's developer tools breaks a request down into exactly these phases. Open it, load a page, and look at the timing tab. You will recognise every bar.

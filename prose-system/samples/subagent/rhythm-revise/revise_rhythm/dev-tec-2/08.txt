When you type an HTTPS address into a browser and press enter, the browser first has to work out what you actually asked for, so it parses the string into a scheme (https), a host (say, www.example.com), an optional port, a path, a query string and a fragment. If the scheme is missing or the text does not look like a URL, the browser may treat it as a search query instead. Before touching the network, it checks three local things: its HSTS list, which records sites that must only ever be reached over HTTPS; whether it already holds a fresh cached copy of the resource that can be used without asking the server; and whether it already has an open connection to this host that it can reuse. Only if none of those shortcuts apply does it go to the network.

The first network step is DNS resolution, because computers route traffic by IP address, not by name. The browser checks its own DNS cache, then asks the operating system, which checks its own cache and the hosts file. If neither knows the answer, the request goes to a recursive resolver, usually run by your internet provider or a public service, and that resolver, if it also lacks a cached answer, walks the hierarchy: it asks a root server which servers handle the top-level domain, asks those which servers are authoritative for the domain, and finally asks the authoritative server for the address records. Modern lookups often ask for both IPv4 (A) and IPv6 (AAAA) records, and the browser may race connections to both and keep whichever answers first, an approach called Happy Eyeballs. Each answer carries a time-to-live that tells caches how long they may keep it, which is why a freshly changed record can take a while to be seen everywhere. Many sites also publish HTTPS or SVCB records that advertise supported protocols, such as HTTP/3, so the browser can skip some guesswork.

With an IP address in hand, the browser needs a transport connection. Classic HTTPS runs over TCP, which begins with a three-way handshake: the client sends a SYN packet, the server replies with SYN-ACK, and the client answers with an ACK. This costs one full round trip before any application data can flow, so the distance to the server matters directly. TCP gives the two sides a reliable, ordered byte stream, retransmitting lost packets and slowing down when it detects congestion. Newer deployments use HTTP/3, which runs over QUIC on top of UDP; QUIC folds the transport and encryption handshakes together, so it saves a round trip, and it avoids head-of-line blocking at the transport layer. A browser usually learns that a site supports HTTP/3 from an earlier visit (via an Alt-Svc header) or from a DNS record, and otherwise starts with TCP.

Next comes the TLS handshake, which is what makes the connection secure and not merely HTTP. The client sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, a key share for key agreement, and the Server Name Indication extension, which names the host it wants; SNI matters because one IP address may serve many sites, and the server needs to know which certificate to present. It also offers ALPN, a list of application protocols such as h2 and http/1.1, so the two sides can agree on the HTTP version during the handshake without an extra exchange. In TLS 1.3, the server replies with its own key share, chooses the parameters, and sends its certificate chain along with a signature proving it holds the private key matching that certificate. Both sides then derive the same symmetric session keys from the key exchange, using ephemeral Diffie-Hellman, which gives forward secrecy: recording the traffic and later stealing the server's long-term key would not let anyone decrypt it. TLS 1.3 completes this in one round trip, where TLS 1.2 needed two. If the client has talked to the server before, session resumption or 0-RTT can shave off more, though 0-RTT data has replay risks and is limited to safe requests.

The browser does not simply trust the certificate the server presents. It checks that the chain leads to a certificate authority in its trust store, that every certificate in the chain is within its validity dates, that the signatures verify, and that the host name you typed appears in the certificate's Subject Alternative Names. It may also check revocation, through OCSP responses that the server staples to the handshake or through compressed revocation lists the browser distributes itself, and browsers also look for Certificate Transparency evidence, which shows the certificate was publicly logged. If any check fails, you see a full-page warning and the request does not proceed, which is the step that stops an attacker on the same network from impersonating the site.

Once the handshake finishes, everything sent on the connection is encrypted and authenticated, and the browser can finally send the HTTP request. With HTTP/1.1 this is plain text inside the encrypted channel, starting with a request line such as GET /path HTTP/1.1 followed by headers: Host, User-Agent, Accept, Accept-Encoding, Accept-Language, and any cookies that match the site. With HTTP/2 and HTTP/3 the same information travels in a compressed binary form and many requests can share one connection as interleaved streams. The browser also attaches things it holds for that origin, such as cookies and cached validators like an ETag or Last-Modified date, so the server can answer with a cheap 304 Not Modified when the cached copy is still good.

The request crosses the network to the server's edge, which is often a CDN node or a load balancer, not the machine that built the page. That edge may terminate TLS, answer straight from its cache, or forward the request to an origin server, which in turn may run application code, query a database, and assemble a response. The server starts writing the response with a status line and headers, such as 200 OK, content type, cache directives and any Set-Cookie headers, followed by the body. The moment the first byte of that response reaches the browser is what performance tools call time to first byte, and it is the sum of everything above: DNS lookup, TCP or QUIC setup, TLS negotiation, the request travelling to the server, the server's processing time, and the first byte travelling back. For a junior developer, the practical lesson is that most of this time is waiting on round trips, so reducing distance with a CDN, reusing connections, enabling HTTP/2 or HTTP/3, caching DNS and responses, and keeping server work fast all attack the same total.

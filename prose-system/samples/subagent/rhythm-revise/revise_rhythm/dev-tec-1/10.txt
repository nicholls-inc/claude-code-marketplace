When you run git commit, you are asking Git to record a snapshot of your project, and the place it does this is the .git directory, specifically a folder called objects. Git is, at its core, a content-addressable store: a simple key-value database where the key is a hash of the value. Everything it saves is one of four kinds of object, and three of them, blobs, trees and commits, are what make up a snapshot, while the fourth, the annotated tag, is a variation on the same idea and refs, which are not objects at all, are what make the whole thing navigable.

Start with the blob, which is created when you stage a file: Git takes its contents, prepends a small header giving the type and size in bytes, and computes a SHA-1 hash of the result (newer repositories can use SHA-256, but the principle is identical). That hash becomes the object's name, and the header plus contents are compressed with zlib and written to a file under .git/objects, where the first two hex characters of the hash form a subdirectory and the remaining characters form the filename. A blob holds only the raw bytes of a file and does not know its filename, its permissions, or where it lives in your project. Because the name is derived from the content, two files with identical contents, in any directory and at any point in history, share a single blob. Change one character and you get a completely different hash and therefore a new blob, which is why Git never has to ask whether a file changed; it simply compares names.

Filenames and structure live in the tree, an object that represents one directory as a list of entries, each containing a file mode, a name, and the hash of whatever that name points to. A regular file has mode 100644, an executable 100755, a symlink 120000, and a subdirectory 040000. For a file the hash points to a blob, and for a subdirectory it points to another tree, so a project of any size becomes a nested structure of trees ending in blobs. The tree for your repository root is therefore a complete description of every file and directory at one moment, and its own hash is computed from its entries, so it identifies that exact state. This produces a useful property: if you edit one file deep in the hierarchy, only the blob for that file and the trees on the path from it to the root need to be rewritten, and every untouched sibling file and directory keeps its existing hash and is reused as is, which is how Git stores full snapshots without wasting space on copies. You can see this yourself with git cat-file -p followed by a hash, which pretty-prints any object.

The commit object ties a tree to history. It is a small text object containing the hash of the root tree, zero or more parent commit hashes, an author line with a name, email, timestamp and timezone, a committer line in the same format, and finally the commit message. A normal commit has one parent, the commit you were on when you made it; the first commit in a repository has none, and a merge commit has two or more. Because a commit's hash is computed from all of this, including the parent hashes, each commit's identity depends on its entire ancestry. Altering an old commit changes its hash, which changes the hash of every descendant, and that is why amending or rebasing produces new commits rather than editing old ones, and why history in Git is tamper-evident. Note too that a commit does not store a diff but points to a full snapshot, and the diffs you see in git show or git log -p are computed on demand by comparing two trees.

So far every object is named by a hash that is unreadable and changes with each commit, which is no way to find your work, and that is the job of refs. A ref is a file containing a single commit hash, nothing more. Branches are refs stored under .git/refs/heads, so the file .git/refs/heads/main holds the hash of the latest commit on main. Tags live under .git/refs/tags, and remote-tracking branches under .git/refs/remotes. Creating a branch is therefore almost free: Git writes a forty-character line into a new file. When you commit, Git writes the new commit object, then updates the current branch file to contain its hash, which is what it means for a branch to move forward.

The last piece is HEAD, the file at .git/HEAD. Usually it does not contain a hash but a symbolic reference, a line such as ref: refs/heads/main, meaning that your current branch is main. Checking out another branch rewrites that line. In the detached HEAD state it contains a raw commit hash instead, which is why commits made there are easy to lose: nothing named points at them.

Taken together, the model is compact: blobs store file contents, trees assemble blobs and other trees into directories, commits wrap a root tree with authorship, a message and parents, and refs give human-friendly names to particular commits. Over time Git also packs loose objects into compressed packfiles that store similar objects as deltas, but that is purely a storage optimization beneath the same model. Everything else you do daily, branching, merging, rebasing, is manipulation of these few object types and the small files that point at them.

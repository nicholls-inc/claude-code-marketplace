Inside the .git directory, Git is a simple key-value store with a few conventions layered on top. Once you see the four kinds of thing it keeps, most of its behavior stops being mysterious.

The core is the object database, in .git/objects. Every object is stored under a name that is the SHA-1 hash (or SHA-256 in newer repositories) of its contents. The first two hex characters become a directory and the remaining characters become the filename, so an object named ab12cd... lives at .git/objects/ab/12cd... The file holds the content compressed with zlib, preceded by a short header giving the object type and size. Because the name is derived from the content, identical content always produces the identical name, and changing a single byte produces a completely different one. This is called content-addressable storage, and it explains why Git can detect corruption and why it never stores the same data twice.

There are four object types. The first is the blob.

A blob is the raw contents of a file and nothing else. It has no filename, no permissions and no timestamp. If two files in your project have identical contents, whether they sit in different directories or have different names, Git stores a single blob for both. If you edit one line of a large file, Git stores a whole new blob for the new version. It does not store a diff at this level. (Later, a process called packing compresses similar objects against each other into packfiles, but that is an optimization hidden beneath the model, not part of it.)

The second type is the tree. A tree represents a directory. It is a list of entries, and each entry holds a file mode, a name, and the hash of either a blob or another tree. The mode records whether the entry is a regular file, an executable, a symlink or a subdirectory. This is where filenames live. Renaming a file therefore creates a new tree but reuses the existing blob. A tree that contains subdirectories points at other trees, so the whole project snapshot forms a hierarchy with one root tree at the top. Because each tree's hash depends on the hashes of everything beneath it, a change to one deeply nested file changes every tree on the path up to the root, while all untouched subtrees keep their old hashes and are shared with the previous snapshot. This sharing is why a commit is cheap even in a large repository.

The third type is the commit object. A commit is a small text record with these parts. It names the root tree for the snapshot, it lists zero or more parent commits, it records an author and a committer, each with a name, email and timestamp, and it carries your message. A first commit has no parent, an ordinary commit has one, and a merge commit has two or more. Notice what a commit does not contain. It holds no files and no diff. It points to a complete snapshot through its tree, and the changes you see in git show or git log -p are computed on the fly by comparing the commit's tree with its parent's tree. The commit's own hash covers the tree hash, the parent hashes, the author and the message, so each commit effectively fingerprints the entire history behind it. Rewriting any old commit, whether by amend, rebase or filter, necessarily creates new commits with new hashes all the way forward. That is the real reason history rewrites change commit IDs.

The fourth type is the annotated tag, which wraps a commit with a name, a tagger and a message. It matters less day to day, so I will leave it there.

Objects are immutable and have unreadable names, so Git needs a way to give things human-friendly handles. That job belongs to refs, which live under .git/refs. A ref is just a text file containing a hash. A branch such as main is the file .git/refs/heads/main, and its entire content is the 40-character hash of the commit the branch currently points to. Remote-tracking branches live under refs/remotes, and lightweight tags live under refs/tags. When you make a commit on a branch, Git writes the new commit object, with the previous tip as its parent, and then overwrites the branch file with the new hash. That is all a branch is. Creating one is nearly free because it only writes a 41-byte file, and deleting one removes only the pointer, leaving the commits in place until garbage collection eventually reclaims any that nothing reaches.

One more piece completes the picture. The file .git/HEAD says where you currently are. Usually it holds a symbolic reference such as ref: refs/heads/main, meaning you are on the main branch. When you check out a specific commit directly, HEAD holds a raw hash instead, which is the detached HEAD state. A new commit advances whatever HEAD resolves to.

So what really happens when you run git commit? Earlier, git add hashed your file contents into blobs and recorded them in the index, a staging file at .git/index. On commit, Git turns the index into tree objects, writes a commit object pointing at the new root tree and at the current HEAD commit as its parent, and moves the branch ref forward. Four small writes, and your snapshot is permanent.

You can inspect all of this yourself. Run git cat-file -p HEAD to print the latest commit, then git cat-file -p on the tree hash it shows, then on a blob hash from that tree. Following those hashes by hand is the quickest way to make the model feel real.

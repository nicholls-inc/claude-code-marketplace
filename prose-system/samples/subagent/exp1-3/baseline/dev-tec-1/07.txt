## How Git Stores a Commit

Run `git init` and look inside `.git`. The directory you find is a database, and your commits are rows in it. Most of what Git does is built on one idea: a content-addressable object store with a handful of object types, plus small text files that name things.

### The object store

Everything Git remembers about your project lives in `.git/objects`. Each object is identified by the SHA-1 hash of its content (newer repositories can use SHA-256). The hash is also the object's filename: an object with hash `8f3a2c...` is stored at `.git/objects/8f/3a2c...`, with the first two hex characters used as a directory name to keep directories small. The file is zlib-compressed. Objects are immutable, because changing the content changes the hash, and that makes it a different object.

There are four object types. Three matter here: blob, tree and commit. (The fourth is the annotated tag.) You can inspect any of them with `git cat-file -p <hash>`, and `git cat-file -t <hash>` tells you the type.

### Blobs: file contents

A blob holds the contents of one file and nothing else. It has no filename, no permissions and no timestamp. If two files in your repository have identical contents, they share one blob. If you rename a file without editing it, no new blob is created.

You can create one directly:

```
echo "hello" | git hash-object -w --stdin
ce013625030ba8dba906f756967f9e9ca394464a
```

The `-w` flag writes it into `.git/objects/ce/013625...`. Now `git cat-file -p ce0136` prints `hello`.

### Trees: directories

A tree object records one directory. It is a list of entries, and each entry has a mode, a type, a hash and a name:

```
100644 blob ce013625...  README.md
100755 blob 4b825dc6...  build.sh
040000 tree a1b2c3d4...  src
```

The mode records whether a file is regular (`100644`), executable (`100755`), a symlink (`120000`) or a subdirectory (`040000`). A subdirectory entry points to another tree, so a whole project snapshot is a tree of trees with blobs at the leaves. The hash of the top-level tree depends on the hashes of everything below it. Change one byte in one file and that file's blob, every tree above it, and the root tree all get new hashes. Unchanged files and directories keep their hashes and are reused, which is why a commit is cheap even in a large repository.

Names live in trees, not in blobs. That is why the same blob can appear under different names in different places.

### Commits: snapshots with history

A commit object is small. Here is `git cat-file -p HEAD` on a typical commit:

```
tree 9c4e1f7a...
parent 5d2b8e03...
author Ada Lovelace <ada@example.com> 1731312000 +0000
committer Ada Lovelace <ada@example.com> 1731312000 +0000

Fix off-by-one in pagination
```

It contains:

- **tree**: the hash of the root tree, which is the complete snapshot of the project at that moment. A commit stores a snapshot, not a diff. Diffs are computed on demand by comparing two trees.
- **parent**: the hash of the previous commit. The first commit has none, and a merge commit has two or more.
- **author and committer**: a name, email and timestamp each. They differ after a rebase or a cherry-pick.
- **the message**.

Because the commit's hash is computed over all of this, including the parent hash, history is tamper-evident. Alter any ancestor and every descendant's hash changes. This is also why `git commit --amend` and `git rebase` make new commits rather than editing old ones: the old commits are untouched and simply become unreachable.

So a commit is a chain: commit points to its tree and its parent, the tree points to subtrees and blobs, and the parent points further back.

### Refs: names for hashes

Hashes are hard to remember, so Git keeps names in `.git/refs`. A ref is a text file containing one commit hash.

```
$ cat .git/refs/heads/main
9f1c7d2e4a...
```

That is all a branch is: a 40-character file. Creating a branch writes a new file. Committing on a branch writes the new commit object, then updates that file to point at it. This is why branches are cheap and why "moving" a branch is just overwriting a hash. Tags work the same way, under `.git/refs/tags`. Remote-tracking branches such as `origin/main` live under `.git/refs/remotes`.

`HEAD` is a special file at `.git/HEAD` that says where you are now. Normally it holds a symbolic reference:

```
$ cat .git/HEAD
ref: refs/heads/main
```

When you commit, Git follows HEAD to the branch, and moves the branch. If you check out a specific commit, HEAD holds a raw hash instead. That is the "detached HEAD" state: nothing is wrong, HEAD just points at a commit directly and no branch will follow your new commits.

For efficiency, Git sometimes consolidates many refs into `.git/packed-refs`, and it packs many loose objects into compressed packfiles under `.git/objects/pack`, storing similar objects as deltas. These are storage optimizations and do not change the model above.

### What `git commit` actually does

1. `git add` hashes each file you staged, writes blobs, and records the paths and blob hashes in the index (`.git/index`).
2. `git commit` turns the index into a set of tree objects, bottom-up, ending with a root tree.
3. It writes a commit object that points to that root tree and to the current HEAD commit as parent.
4. It updates the branch ref that HEAD points to, so the branch now names the new commit.

Everything you do day to day, such as branching, merging, rebasing and resetting, is manipulation of these three object types and the small files that name them.

Everything Git records is kept in the .git directory at the top of your working tree, and the core of it is a simple key-value store. The values are objects, each compressed with zlib, and the keys are the SHA-1 hashes of their contents. Git writes each object to a file under .git/objects, using the first two hex characters of the hash as a directory name and the remaining thirty-eight as the file name. A commit is built from three kinds of object, the blob, the tree and the commit itself, and a fourth thing, the ref, gives one of them a name you can type.

A blob holds the contents of one file and nothing else. It has no file name, no permissions and no timestamp. Before hashing, Git prepends a short header made of the word blob, a space, the length in bytes and a null byte. A file containing the word hello and a newline therefore becomes an object with the hash ce013625030ba8dba906f756967f9e9ca394464a. Because the hash depends only on the contents, two files with identical text, whether in different directories or in different commits, share one blob. If you change a single line in a large file, Git stores a new blob for the whole file.

Names and permissions live in trees. A tree object represents one directory and is a list of entries, each holding a mode, a name and the hash of the thing it refers to. The mode is 100644 for an ordinary file, 100755 for an executable, 120000 for a symbolic link and 40000 for a subdirectory. Entries for files point to blobs and entries for subdirectories point to other trees, so the root tree of a project leads down through nested trees to every blob in it. Hashes inside a tree are stored as 20 raw bytes rather than 40 hex characters, and entries are sorted by name so that the same directory always produces the same hash. Renaming a file changes the tree that contains it but leaves the blob alone. A change deep in the project alters every tree on the path from that file up to the root, because each tree's hash includes the hashes of its children. Subdirectories that were not touched keep their old trees.

A commit object is a short text file. It begins with a line naming the root tree, followed by one parent line for each earlier commit: none for the first commit in a repository, one for an ordinary commit and two for a merge. After those come an author line and a committer line, each with a name, an email address, a Unix timestamp and a timezone offset, then a blank line and the message. A commit does not contain a diff. What git show displays is worked out by comparing the commit's tree with its parent's tree. Since the parent hash is part of the commit's own contents, every commit's hash depends on all the history behind it. That is why amending or rebasing an old commit produces new hashes for every commit that follows it.

Hashes are hard to remember, so refs supply the names. A branch is a file under .git/refs/heads whose entire contents are the 40-character hash of the newest commit on that branch, followed by a newline. The file .git/refs/heads/main is the branch called main. Making a commit writes the new objects and then updates that file to point at the new commit, which is all it means for a branch to move forward. Tags are stored the same way under .git/refs/tags, and remote-tracking branches under .git/refs/remotes. The file HEAD, at the top of .git, usually holds not a hash but a line such as ref: refs/heads/main, which records which branch is checked out. If it holds a bare hash instead, you are in the detached HEAD state. Over time, git gc folds many separate ref files into a single .git/packed-refs file.

Loose objects are only the first storage format. When you run git gc, or when you push or fetch, Git gathers objects into packfiles under .git/objects/pack. Similar blobs are stored there as a base version plus deltas, which is where the space for a one-line edit to a large file is recovered. The remaining piece is the staging area, kept in .git/index. It is a sorted list of paths with blob hashes and file modes, and git commit builds the trees from it. You can see all of this for yourself with git cat-file -p. Given HEAD it prints the commit, given the tree hash from that commit it prints the directory listing, and given a blob hash it prints the file as it was committed.

Everything Git remembers about your project lives in the .git directory at the top of your working tree, and most of it is a simple key-value store in which the key is a hash of the value. When you commit, Git does not record a diff against the previous version; it records a complete snapshot built from a handful of object types, the first of which is the blob. A blob holds the raw bytes of one file and nothing else, so it knows nothing about the file's name, its location in the project or its permissions. To store one, Git prepends a small header consisting of the word blob, a space, the length in bytes and a null byte, computes the SHA-1 hash of the header plus contents (newer repositories can be configured to use SHA-256), compresses the result with zlib, and writes it under .git/objects at a path made from the hash, where the first two hex digits name a subdirectory and the remaining thirty-eight name the file. Because the hash is derived from the content, two files with identical bytes anywhere in your history resolve to a single blob whatever they are called, and changing one byte yields a completely different hash and therefore a new object while the old one stays untouched.

Names and structure come from trees, which are directory listings in which each entry carries a file mode, a name and the hash of either a blob or another tree. The mode tells Git whether the entry is a regular file (100644), an executable (100755), a symbolic link (120000), a subdirectory (040000) or a submodule pointer to a commit in another repository (160000). Entries are sorted by name and each hash is stored in raw binary rather than hex, which is why printing a tree straight to your terminal produces garbage that git cat-file -p will happily render as readable columns. A project with nested folders is therefore a tree of trees, and the hash of the top-level tree depends on everything beneath it, so a single changed line in a deeply nested file changes the hash of its blob and of every tree on the path up to the root and of nothing else, while all the untouched subdirectories are referenced by their existing hashes and shared with the previous snapshot at no cost.

A commit object ties a root tree to history and is plain text containing a tree line with the hash of the top-level directory snapshot, zero or more parent lines naming the commits that came directly before it, an author line and a committer line each with a name, email, Unix timestamp and timezone offset, a blank line, and then your message. The first commit in a repository has no parent, an ordinary commit has one, and a merge commit has two or more, which is all the history graph amounts to. Since the parent hash is part of the commit's own content and therefore part of its hash, you cannot alter an old commit without producing a new hash for it and for every descendant, which is why rebasing creates new commits instead of editing existing ones and why one hash can vouch for the entire history behind it. The separate author and committer lines explain why a cherry-picked or rebased commit keeps its original author while showing a new committer and date.

None of these objects can be changed, and none has a friendly name, so Git keeps names in refs, which are small files containing a commit hash. A branch called main is the file .git/refs/heads/main holding forty hex characters, and creating a branch means writing a new file with the same hash in it, which explains why branching is instantaneous. Tags live under .git/refs/tags, where a lightweight tag is merely another such pointer and an annotated tag is a further object type with its own tagger, date and message that in turn points at a commit, while remote-tracking branches such as origin/main are refs under .git/refs/remotes recording where the remote's branch stood at your last fetch. When you commit on the current branch, Git writes the new blobs, trees and commit object and then updates that one branch file to the new hash, so a branch is a movable label on the tip of a chain whose links never change. For efficiency, git pack-refs may fold many ref files into a single .git/packed-refs file and git gc compresses loose objects into packfiles that store similar objects as deltas against each other, so a long-lived repository often holds far fewer separate files than this model suggests even though the logical picture is unchanged.

HEAD, the ref that tells Git where you are, usually contains a line such as ref: refs/heads/main, a symbolic reference naming the checked-out branch, so the commit you build on is found by following HEAD to the branch and the branch to a hash. If you check out a specific commit, HEAD holds a raw hash instead, which is the detached state Git warns you about, and any commits you make there are reachable from nothing but HEAD until you give them a branch. Between your working files and the next commit sits the index, the binary file .git/index, which lists every tracked path with the blob hash that git add stored for it, and git commit builds its trees from that list rather than from the working directory, which is why staging behaves as it does.

You can watch all of this yourself by running git cat-file -p HEAD to print the latest commit, git cat-file -p on the tree hash it mentions to list the directory, and git cat-file -t on any hash to see which type it is. Objects that no ref can reach, directly or through parents, are eventually removed by garbage collection once they age past the reflog's retention window, which is why a commit that seems lost can often be recovered for a while and then is gone for good.

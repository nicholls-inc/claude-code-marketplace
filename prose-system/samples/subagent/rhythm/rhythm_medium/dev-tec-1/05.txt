When you run git commit, you create a small chain of objects inside the hidden .git directory, and understanding them explains most of how Git behaves. Git is at heart a content-addressable store: a simple key-value database in which every value is hashed and the hash becomes its key. Everything it saves lives under .git/objects, and every object comes in one of four kinds, of which three matter here: blobs, trees and commits. The fourth kind, the annotated tag, is a close relative of the commit.

The simplest object is the blob, which holds the raw contents of a single file and nothing else. It does not record the file's name, its location in the project, or its permissions. Git takes the bytes, prepends a short header giving the object type and size, computes a SHA-1 hash of the result (newer repositories may use SHA-256), and compresses the data with zlib. The hash becomes the object's identity. It is stored under .git/objects in a directory named after the first two hexadecimal characters, with the remaining characters as the file name. Because identity comes from content, two files with identical bytes share one blob, even if they sit in different directories or were committed years apart. You can see this with git hash-object, which computes the hash of a file, and git cat-file -p, which prints any object in readable form.

Since blobs carry no names, something else has to say which blob is which file, and that is the job of the tree object. A tree represents one directory. It is a sorted list of entries, each holding a file mode, a type, a name and the hash of the thing it points to. A file entry points to a blob, and a subdirectory entry points to another tree. A project with nested folders is therefore a hierarchy of trees, with a single root tree describing the top level of your repository. The mode records whether an entry is a regular file, an executable, a symbolic link or a directory. Because a tree's hash is computed from its contents, which include the hashes of its children, changing one line in one file changes that blob's hash, then the hash of every tree above it, all the way up to the root. This is a Merkle tree structure, and it means a single root hash summarizes the exact state of every file in the project.

A commit object ties a snapshot to a point in history. It is a short text record containing the hash of the root tree, the hash of each parent commit, an author line with name, email and timestamp, a committer line in the same format, and finally your commit message. Most commits have one parent, the first commit in a repository has none, and a merge commit has two or more. Those parent pointers form the chain of history you see in git log, and the hash of each commit depends on its parent's hash. Altering any earlier commit therefore changes every commit after it, which is why rewriting history produces new commits rather than editing old ones. This also clarifies a common misconception: Git does not store a commit as a diff. Each commit points at a complete snapshot of the project. Diffs are computed on demand by comparing two trees, and unchanged files cost almost nothing because their blobs and subtrees are simply reused by reference.

Objects begin life as loose files, but Git later gathers them into packfiles under .git/objects/pack, which store similar objects as compact deltas against one another. This is invisible in daily use, and the content-addressed model above still applies, since objects keep the same identities whether loose or packed.

The last piece is the ref, which solves a human problem: nobody wants to remember forty hexadecimal characters. A ref is simply a file containing a commit hash, and the files live under .git/refs. A branch such as main is the file .git/refs/heads/main, and a tag lives under .git/refs/tags. Remote-tracking branches live under .git/refs/remotes. Creating a branch just writes a new tiny file, which is why branching in Git is so cheap. When you make a commit on a branch, Git creates the new commit object with the current commit as its parent and then rewrites the branch file to hold the new hash. In a large repository, refs may be consolidated into a single packed-refs file, but the meaning is the same.

Finally, the file .git/HEAD records where you currently are. Normally it contains a symbolic reference such as ref: refs/heads/main, which means you are on that branch, and so the next commit will advance it. If HEAD contains a raw commit hash instead, you are in the detached HEAD state, and new commits are not attached to any branch. Between your working directory and the next commit sits the index, stored as .git/index, which holds the staged snapshot that git commit turns into trees.

Put together, a commit is a chain of pointers. A ref names a commit, the commit names a root tree and its parents, trees name blobs and further trees, and blobs hold the bytes, all identified by hashes of their own contents.

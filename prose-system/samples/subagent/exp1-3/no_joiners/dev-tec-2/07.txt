From Address to First Byte

When you type an HTTPS address into a browser and press Enter, nothing visible happens for a moment. Underneath, the browser works through a long chain of steps before the first byte of the response arrives. Each step exists for a reason, and each one can be slow or can fail. Knowing the chain helps you read the network tab in developer tools and understand why a page feels sluggish.

Parsing the address

The browser first breaks the address into parts. The scheme says https, which means the connection must be encrypted and will normally use port 443. The host, such as www.example.com, says which server to contact. The path and query string say what to ask that server for. If the text you typed is not a valid address, the browser treats it as a search term instead.

Checking what it already knows

Before touching the network, the browser looks for shortcuts. It checks whether a service worker controls this site, since that script can answer the request on its own. It checks the HTTP cache for a stored copy that is still fresh. If one exists, the request ends here and no first byte needs to travel anywhere.

The browser also consults its HSTS list. A site that sent a Strict Transport Security header earlier has told the browser to always use HTTPS, so the browser upgrades any plain HTTP request without asking the server.

Finding the server with DNS

Servers are reached by IP address, but people use names, so the browser must translate. This is the job of the Domain Name System. The browser checks its own DNS cache, then asks the operating system, which checks its cache too. If neither knows the answer, the operating system sends a query to a recursive resolver, usually run by your internet provider or a public service.

The resolver may also have the answer cached. If not, it works down the hierarchy. It asks a root server which servers handle the com zone, asks those which servers handle example.com, and finally asks the authoritative server for example.com, which returns the IP address. Every answer carries a time to live, which tells caches how long they may remember it. A cold lookup might take tens of milliseconds, while a cached one is nearly instant.

Many sites also publish several addresses, and large sites use DNS or anycast routing to hand you a server that is physically close to you.

Opening a TCP connection

With an IP address in hand, the browser opens a TCP connection to port 443. TCP provides an ordered and reliable stream of bytes, and it begins with a three step handshake. The client sends a SYN packet. The server replies with SYN and ACK. The client answers with an ACK. After one full round trip, both sides agree the connection exists.

This is why distance matters. Every round trip costs the time light and routers need to cross the network, so a server on another continent adds noticeable delay to every step that follows. Newer HTTP versions built on QUIC, which runs over UDP, merge the transport and encryption handshakes to save some of these trips, though the underlying ideas are the same.

Negotiating encryption with TLS

The connection is open but still unencrypted, so now the browser and server run a TLS handshake. The browser sends a ClientHello listing the TLS versions and cipher suites it supports, a random value, and the server name it wants through an extension called SNI. SNI matters because one IP address often hosts many sites.

The server replies with its chosen version and cipher suite, its own random value, and its certificate. In TLS 1.3 both sides also exchange key shares, and from those they independently compute the same secret session keys without ever sending the keys across the wire. A single round trip is usually enough.

The browser then validates the certificate. It checks that the certificate chains up to an authority the browser trusts, that it has not expired, that it has not been revoked, and that the host name in the certificate matches the host in the address. If any check fails, you see a full page warning and the request stops. If all checks pass, the browser and server finish the handshake, and from this point everything they send is encrypted and tamper evident.

Sending the HTTP request

Now the browser can finally ask for the page. It writes an HTTP request and sends it through the encrypted channel. The request has a method such as GET, a path, and a set of headers. Typical headers include Host, UserAgent, Accept, AcceptLanguage, and AcceptEncoding, which lists the compression formats the browser understands. Any cookies stored for this site travel in a Cookie header, which is how the server recognizes a logged in user.

With HTTP/2 and HTTP/3 the request is packed into compact binary frames, and headers are compressed, but the meaning is the same.

The server does its work

The request arrives at the server, but often not at the machine that holds your application. It may first hit a CDN edge node, which can answer from its own cache. If not, the request passes through a load balancer or reverse proxy, which picks a healthy application server.

The application then does the real work. It routes the path to a handler, checks the session, perhaps queries a database, renders a template or builds a JSON response, and prepares a status code and headers. A slow database query or a heavy render shows up in the browser as waiting time before the first byte.

The first byte arrives

As soon as the server writes the start of its response, the bytes cross the network and the browser reads the status line, such as 200 OK, followed by headers. The moment that first piece lands is called Time to First Byte, and developer tools show it as the waiting phase of a request.

Notice how many costs came before it. DNS, TCP, TLS, and the server's own work all add together. You can shorten them with fewer redirects, a nearby CDN, connection reuse, caching headers, and efficient server code. Everything after this point, such as downloading the body and parsing HTML, is a separate story that begins only once this chain is complete.

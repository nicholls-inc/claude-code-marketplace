When you commit a change in Git, nothing about your files is stored as a diff or as a named file. Everything lives in the .git directory as a collection of immutable objects, each identified by a hash of its own contents. Once you see that this is a content-addressed database sitting underneath the familiar commands, most of Git's behavior stops seeming mysterious. The objects are kept in .git/objects, and there are only four kinds: blobs, trees, commits and annotated tags. The first three are what make up an ordinary commit.

A blob is the simplest of these. It holds the raw bytes of one file and nothing else, with no filename, no permissions and no timestamp attached. Git computes the SHA-1 or SHA-256 hash of a short header, which names the type and the size, followed by the file contents, and uses the result as the object's identity. The first two hex characters become a subdirectory name under .git/objects, and the remaining characters become the filename inside it. The object is compressed with zlib before it is written, which is why you cannot simply open it in a text editor. Because the name is derived from the content, two files with identical bytes produce a single blob, even if they sit in different directories or have different names. This is also why renaming a file costs almost nothing in storage terms, since the blob is unchanged.

Since blobs carry no names, something else has to say which blob belongs at which path, and that job belongs to the tree. A tree object represents one directory and is essentially a sorted list of entries. Each entry records a file mode, a name, and the hash of either a blob, for a regular file, or another tree, for a subdirectory. The mode distinguishes ordinary files, executable files, symbolic links and directories. Trees are hashed in the same way as blobs, so a tree's identity depends on the names, modes and hashes of everything beneath it. If you change one line in a deeply nested file, that file gets a new blob, its parent directory gets a new tree, and so does every ancestor up to the root, while all the untouched siblings keep their existing hashes and are simply referenced again. This sharing is what keeps snapshots cheap, because each commit describes the whole project but only the changed paths require new objects.

The commit object ties a snapshot to its history. It is a small text record that contains the hash of the root tree, the hashes of zero or more parent commits, an author line and a committer line, each with a name, an email address and a timestamp, and finally the commit message. A first commit has no parent, an ordinary commit has one, and a merge commit has two or more. Because the parent hashes are part of the commit's own content, they are also part of its hash, which means that history forms a chain in which each link vouches for everything before it. Changing an old commit in any way produces a different hash, and that forces every descendant to be rewritten as well. This is precisely what happens during a rebase or an amend, and it explains why those operations create new commits and leave the originals behind rather than editing them.

Even though everything is addressed by hash, you never type forty hexadecimal characters in daily work, because refs provide human-friendly names. A ref is just a small file whose contents are a commit hash. Branches live under .git/refs/heads, tags live under .git/refs/tags, and remote-tracking branches live under .git/refs/remotes. If you open .git/refs/heads/main in a terminal, you will find a single line containing the hash of the tip of that branch. Making a commit on a branch amounts to writing the new commit object and then overwriting that one file with the new hash, which is why creating and moving branches is so fast. For efficiency, Git sometimes consolidates many refs into a single packed-refs file, but the meaning is the same.

The last piece is HEAD, a file at .git/HEAD that tells Git where you currently are. Most of the time it contains a symbolic reference such as ref: refs/heads/main, meaning that you are on the main branch and that new commits should advance it. When you check out a specific commit directly, HEAD instead holds a raw hash, which is the detached state that produces the well-known warning.

You can see all of this for yourself with a few plumbing commands. Running git cat-file -p HEAD prints the current commit, including its tree hash and parent, and running git cat-file -p on that tree hash lists its entries. Running git cat-file -p on a blob hash then shows the file contents. Following that chain once makes the model concrete: a ref points to a commit, a commit points to a tree and its parents, trees point to blobs and other trees, and every one of those pointers is a hash that also guarantees the integrity of what it points to.
